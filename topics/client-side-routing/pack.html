Client-side routing

A router is the two-way binding between the address bar and what is on screen — everything the browser did for free, switched off by not reloading the page, and rebuilt by hand.

Read this in order. Each node exists because the one before it left something specifically broken, and the broken thing is named at the bottom of every node. If you follow the chain you should be able to derive most of a router rather than memorise one.

Depth markers appear inline. [EXPLAIN] means you should be able to explain it out loud, from first principles, with no notes. [USE] means you must be able to use it correctly and debug it when it breaks, without needing the internals cold. [AWARE] means know it exists, know what problem it solves, and know roughly when to reach for it.

Node 0 — before client-side routing: the server owns every URL

For the first fifteen years of the web there was no such thing as client-side routing, because there was nothing for it to do. The browser had exactly one way to show you a different page, and it was this: you click a link, the browser reads its href, it sends an HTTP request to that URL, the server responds with a complete HTML document, and the browser throws away everything it currently has and builds the new document from scratch. Every variable your JavaScript held is gone. Every DOM node is destroyed. The stylesheet is re-parsed, the scripts are re-executed, images are re-decoded. This is called a full page navigation, and it is still the default behaviour of every browser on earth.

In that world, "routing" meant something that happened entirely on the server. A request arrives for /products/42. Some code on the server — a PHP file laid out on disk, an Express app.get("/products/:id"), a Django URL pattern — looks at that path string, decides which handler should run, that handler queries a database, fills a template, and returns HTML. The URL was a real address of a real document that the server produced on demand. The browser's job was to ask and to paint.

This model is enormously good at several things, and it is worth being honest about them, because a large part of the last decade of frontend work has been spent rediscovering them. The URL is always correct, because the URL is what caused the page to exist. The back button always works, because the browser is the one moving. Bookmarking, sharing, opening in a new tab, refreshing — all of it works with no effort from you, because the server can produce that page from that URL alone. Search engines see real content. The page works with JavaScript disabled or broken. Accessibility tooling gets a fresh document and announces it.

The problem is what it costs. Every navigation is a full round trip before anything changes on screen, so the interface freezes on the old page and then flashes white. Everything the user built up in memory is destroyed: the search filters they had set, the scroll position of the sidebar, the WebSocket they had open, the half-typed comment, the audio that was playing. If ninety-five percent of the page is identical between two URLs — the same header, the same navigation, the same sidebar — you re-download, re-parse and re-paint all of it to change the five percent that differs. And there is a whole category of interface that is simply impossible: a music player that keeps playing while you browse, a chat panel that stays connected, a multi-step form that survives moving between steps.

Around 2005–2008, once XMLHttpRequest made it possible to fetch data without navigating, developers started building pages that changed their own content in place. Gmail and Google Maps are the famous early examples. And the moment you do that, you have created the problem this entire topic exists to solve.

What's still broken: as soon as JavaScript starts changing the page without a navigation, the URL in the address bar stops describing what is on screen — and everything the browser gives you for free is built on the URL describing what is on screen.

Node 1 — the single-page application, and the six things it breaks

The limitation: updating the DOM with JavaScript is invisible to the browser's navigation machinery. Nothing about it touches the URL, the history stack, or the document.

A single-page application [EXPLAIN] is an application where the browser loads one HTML document, once, and from then on JavaScript swaps the contents of the page in response to what the user does. No further full navigations happen. The word "page" in the name is misleading — there are many screens; there is one document.

Do this naively and you get something that feels wonderful and is unusable. Consider the simplest possible version: a variable holds the current screen name, clicking a button sets it, and a render function reads it and draws the right thing. It is fast, nothing flashes, state survives. Now look at what you have destroyed.

The address bar is a lie. It still says /, no matter how deep into the app the user has gone. That single fact causes all of the following. The back button leaves your app entirely — the browser has no record of the user moving between screens, because they never did, so "back" goes to whatever site they were on before yours. This is the number one user complaint about badly built SPAs and it is a routing bug every time. Refresh loses everything, dumping the user back at the home screen, because the only thing the browser can do on refresh is re-request the URL, and the URL says home. Bookmarking and sharing are impossible — there is no way to send someone a link to the thing you are looking at, which for most applications is the single most-used sharing mechanism in existence. Deep links don't exist, so an email that says "your order shipped" can only link to the front door. Search engines and link previews see one page, whatever the initial HTML contained. And screen readers are never told anything changed: on a real navigation the browser announces the new document; here, the document never changed, so a blind user clicks a link and, as far as their software is concerned, absolutely nothing happens.

Notice the shape of this. The problem is not "I need a router library." The problem is that the browser's URL, history stack, and document lifecycle are a public API that you have opted out of, and you now have to opt back in manually. That, and only that, is what a router does. [EXPLAIN] A router is not a rendering technology and it is not a data-loading technology; it is a two-way binding between a string in the address bar and what your application is currently showing.

What you can do at this point: state precisely what a router is for, and name what breaks without one. [EXPLAIN]

What's still broken: you need a way to change the URL from JavaScript without the browser doing a full navigation to it. In 2008 no such thing existed.

Node 2 — the hash fragment: the first workaround, and why it still exists

The limitation: setting window.location to a new path makes the browser navigate. There was no way to change the path without leaving the page.

There was, however, one part of a URL the browser treated differently: the fragment [EXPLAIN], everything after the #. In https://example.com/app#/settings, the fragment is /settings. Fragments were invented for in-page anchors — #chapter-3 scrolls to the element with that id — and because of that, they have two properties that turned out to be extraordinarily useful.

First, the fragment is never sent to the server. The browser strips it before making the request. A server receiving a request for that URL sees only /app and has no idea the fragment exists. Second, and consequently, changing only the fragment does not cause a navigation. The browser updates the address bar, pushes an entry onto the history stack, tries to scroll to a matching element, and does nothing else. No request, no document teardown.

So: put the application's route in the fragment. Write window.location.hash = "/settings" and you have changed the URL and created a history entry without leaving the page. To detect it, listen for the hashchange event [USE], which fires whenever the fragment changes for any reason — your code setting it, the user clicking a #/... link, or the user pressing back. Read location.hash, match it against your screens, render. That is a complete, working router in about fifteen lines, and it is what every SPA used from roughly 2008 to 2012. hashchange was formalised in HTML5 and shipped in Internet Explorer 8 in 2009; before that, libraries polled location.hash on a timer, typically every fifty milliseconds, because there was no event at all.

The costs are real. The URL is ugly: example.com/app#/products/42 instead of example.com/products/42. Because the server never sees the fragment, it cannot server-render the page — a request for the settings screen and a request for the home screen are literally the same request, so the server cannot produce different HTML, which rules out SSR and hurts crawlers and link previews. And the fragment's original job collides with its new one: you cannot use #section-2 to scroll to a heading while # is also carrying your route, which is why hash routers grew the awkward #/products/42#reviews double-hash convention. Google published a #! "hashbang" crawling scheme in 2009 to work around the SEO problem and deprecated it in 2015, telling everyone to use real URLs instead.

Hash routing is not dead, and knowing exactly when to reach for it is a real interview answer. [USE] It is the correct choice when you do not control the server: static file hosts with no rewrite rules, GitHub Pages, an app served from inside a CMS, a page embedded in someone else's product, a Chrome extension, an Electron app loading from file://. In every one of those, a real path would 404 and a fragment will not. React Router still ships HashRouter [AWARE] for exactly this.

What you can do at this point: build a working router with no library and no server cooperation, and explain when a hash router is still the right answer. [USE]

What's still broken: the URL still isn't a real URL. The server can't see it, so it can't render it, and it looks wrong to users. You want /products/42 in the address bar, with no page load.

Node 3 — the History API: pushState, replaceState, popstate

The limitation: the fragment hack exists only because the path was untouchable. Give JavaScript the ability to change the path without navigating and the hack becomes unnecessary.

That is exactly what HTML5 added, in the specification work around 2010 and shipping across browsers through 2011–2012 (Chrome 5, Firefox 4, Safari 5, and — the reason it took so long to adopt — Internet Explorer 10). Three pieces, and they are the entire foundation every router in every framework is built on. Know these cold. [EXPLAIN]

history.pushState(state, "", "/products/42");
history.replaceState(state, "", "/products/42");
window.addEventListener("popstate", (event) => { /* event.state */ });

history.pushState(state, unused, url) adds a new entry to the browser's history stack and changes the address bar to url — and does nothing else. No request is made. The document is not touched. Nothing renders. It is purely a bookkeeping call that says "pretend the user navigated here." Three arguments, and the middle one is a historical joke: it was meant to be the page title, no browser ever implemented it, and the spec now says pass an empty string. The first argument, state, is an arbitrary serialisable object the browser stores with that history entry and hands back to you if the user ever returns to it — useful for stashing scroll position or a snapshot of the screen. It is serialised with the structured clone algorithm, so functions and DOM nodes are not allowed, and browsers cap it (Firefox at 16 MB per entry; treat anything over a few kilobytes as a mistake).

history.replaceState is identical except it overwrites the current history entry instead of adding one. The distinction between these two is the single most practically important thing in this node, and it comes back at Node 8 and Node 12.

popstate is the event the browser fires when the user moves within the history stack — back button, forward button, history.back(), history.go(-2). Its event.state is whatever you passed as state for the entry being restored. And here is the detail that trips up everyone building a router from scratch: popstate does not fire when you call pushState or replaceState. [EXPLAIN] The browser assumes that if your own code changed the URL, your own code knows it changed the URL. So a hand-rolled router needs two paths into its "the route changed, re-render" function: one it calls itself right after pushing, and one wired to popstate for the user's back button. This asymmetry is why routers wrap the History API in their own object with its own subscription model rather than exposing it directly.

There are two security-shaped constraints worth knowing. The URL you push must be same-origin [EXPLAIN] — you can change path, query and fragment, but not scheme, host or port, or the call throws a SecurityError. Obviously so: otherwise any page could make the address bar say bank.com while showing its own content. And browsers rate-limit these calls (Safari has historically thrown after around 100 calls in 30 seconds), which real apps hit by syncing a slider or a text input to the URL on every keystroke — the fix, always, is to debounce and use replaceState.

Finally, note what pushState deliberately does not do, because these become their own nodes later: it does not scroll, it does not move focus, it does not change document.title, and it does not announce anything to assistive technology. Everything the browser did for you during a real navigation, you now do by hand.

What you can do at this point: change the URL without a page load, react to the back button, and explain the primitive that every router in every framework wraps. [EXPLAIN]

What's still broken: the user does not call pushState. The user clicks links. Every <a href> in your app still triggers a full page navigation, which throws away the application you just spent all this effort keeping alive.

Node 4 — intercepting navigation: why <Link> renders a real <a>

The limitation: pushState is something your code calls. Users click anchors, and anchors navigate.

So the router has to get in front of the click. The mechanism is the one you already know from the DOM: listen for click, call event.preventDefault() [EXPLAIN] to cancel the browser's built-in navigation, then pushState the link's href and re-render yourself. That is the whole trick. But the conditions under which you are allowed to do it are a genuinely long list, and getting them wrong produces bugs that are maddening to diagnose because they only reproduce on some clicks.

You must not intercept if any of the following is true. The click was not the primary button — event.button !== 0 — because middle-click means "open in a new tab" and right-click opens a context menu. A modifier key was held: metaKey (Cmd on macOS), ctrlKey (new tab on Windows and Linux), shiftKey (new window), or altKey (download, in most browsers). The anchor has a target that is not _self. It has the download attribute. It has rel="external". The href points at a different origin, or a different scheme entirely such as mailto: or tel:. Or the event has already been default-prevented by something else. Miss the modifier-key checks and Cmd-clicking a link in your app opens nothing at all, which users experience as the app being broken and which never shows up in testing because nobody Cmd-clicks in testing.

This is the actual reason for a rule people repeat without knowing why: a router's <Link> component must render a genuine <a href="...">, not a <div onClick> or a <button>. [EXPLAIN] A real anchor with a real href gives you, for free: middle-click and Cmd-click opening a new tab, "Copy link address" in the context menu, the browser showing the destination in the status bar on hover, keyboard focusability and Enter activation with no tabIndex or key handler, the correct link role for screen readers so a user can list every link on the page, and crawlers being able to discover the URL. A div with a click handler gives you none of those and you will re-implement each one badly. The href is not decoration — it is the accessibility and platform contract; the onClick is the optimisation.

Alongside link clicks, a router exposes programmatic navigation [USE] — React Router's useNavigate() giving you navigate("/products/42") — for the cases where there is no link: after a successful form submit, after login, on a timer, in response to a socket message. The rule of thumb interviewers like: if the user is choosing to go somewhere, it is a link; if the application is sending them somewhere as a consequence of something, it is a programmatic navigate. Never wire a navigate() call to something that should have been an anchor.

Forms have the same problem in a second flavour. A <form> submit is also a real navigation — it serialises the fields and does a GET or POST to action. Routers that care about this (Remix and React Router's data APIs, discussed at Node 9) ship a <Form> component that intercepts submit the same way <Link> intercepts click.

What you can do at this point: build a complete working router by hand — intercept clicks, push state, listen for popstate, render from the path. Nodes 0 through 4 are a router. [EXPLAIN]

What's still broken: "render from the path" was doing a lot of work in that sentence. You have a string like /products/42/reviews. Turning that into "the reviews list, for product 42" is a real problem with real rules.

Node 5 — route matching: from a string to a component, with parameters

The limitation: a chain of if (path === "/about") comparisons cannot express /products/:id, cannot rank two patterns that both match, and becomes unmaintainable at about twelve routes.

A route [EXPLAIN] is a pairing of a pattern with something to render. Matching is the process of taking the current path, finding the pattern that best describes it, and extracting the variable parts.

Patterns are built from a small vocabulary. Static segments match themselves: /about. Dynamic segments, written with a colon, match exactly one segment and capture it: /products/:id matches /products/42 and gives you { id: "42" }. Note the string — params are always strings [USE], because a URL is text; id === 42 is false and this bug is extremely common. Splats or wildcards, written *, match the rest of the path including slashes, which is how you build file browsers and catch-all 404 routes. Optional segments exist in some routers — React Router v6.5+ writes them /users/:id? — and are the usual way to express an optional locale prefix.

Under the hood a pattern is compiled to a regular expression once, at startup, not on every navigation. /products/:id becomes roughly ^/products/([^/]+)$, with the capture group names remembered so the match array can be turned back into a named params object. The path-to-regexp library did this for Express and, for years, for React Router; React Router v6 replaced it with its own smaller matcher.

The subtle part is ranking [EXPLAIN]. Given /products/new, both /products/new and /products/:id match. If you resolve by declaration order, then moving a route in your file changes behaviour, and the classic bug is a "new product" page that renders the detail page for a product whose id is the literal string "new". React Router v6 fixed this by scoring every route independently of order: more segments beats fewer; within a segment, a static segment beats a dynamic one, and a dynamic one beats a splat. So /products/new always wins over /products/:id, regardless of the order you wrote them. This is a real interview question and the correct answer names the ranking, not "put the specific one first" — that was the v3-era answer, and it is what Express still requires, because Express genuinely is first-match-wins in declaration order.

Two more matching details that bite. Exact versus prefix matching: in React Router v3 and v4, /products matched /products/42 too unless you passed exact, which is why so much old code is littered with that prop; v6 made exact matching the default and expresses "also match children" through nesting instead (Node 6). Trailing slashes and encoding: /about and /about/ are different strings and most routers normalise them, and params arrive percent-decoded, so a product named a/b encoded as a%2Fb is a well-known source of broken links — always encodeURIComponent a value before putting it in a path.

Worth naming the historical shift, because it explains why old tutorials look so different. React Router v3 and earlier used static routing: you declared the whole route table up front, as configuration, before rendering. v4, released in March 2017, rewrote everything around dynamic routing — a <Route> was just a component that rendered its children when the URL matched, so routes could appear anywhere in the tree and be created conditionally. It was philosophically clean and it lost something important: nothing could know the route table without rendering, which made data preloading and code-splitting decisions impossible in advance. v6.4 (September 2022) brought back a declared route object tree for exactly that reason. That pendulum — config for analysability, components for flexibility — is the tension you will see again at Node 9 and Node 17.

What you can do at this point: design a route table, read params, and predict which of several overlapping routes wins. [EXPLAIN]

What's still broken: your route table is flat, but your UI is not. /settings/profile and /settings/billing share a settings shell with its own sidebar, and a flat table forces every route to re-declare and re-mount that shell.

Node 6 — nested routes: the URL is a tree, and so is the UI

The limitation: a flat list of routes cannot express "these three screens live inside that layout," so shared chrome is duplicated and remounts on every navigation, destroying its state.

The insight that defines modern routing: a URL path is already hierarchical, and the UI usually is too, in the same shape. [EXPLAIN] /settings/billing/invoices is three levels, and on screen that is the app shell, inside it the settings layout with its sidebar, inside that the billing section, inside that the invoice list. So describe routes as a tree whose nesting mirrors the path's segments, and let each level render its own layout with a hole in it for the level below.

<Route path="/settings" element={<SettingsLayout />}>
  <Route index element={<SettingsHome />} />
  <Route path="profile" element={<Profile />} />
  <Route path="billing" element={<Billing />} />
</Route>

The hole is <Outlet /> [EXPLAIN] — a component the parent renders wherever the matched child should appear. It is the same idea as props.children, except the router supplies the child based on the URL rather than the parent naming it. Vue Router calls it <router-view>, Angular calls it <router-outlet>, and Next.js's App Router passes it as the children prop to layout.tsx. Same concept, four names.

Three consequences follow, and they are the whole payoff. First, matching produces a chain, not a single route: navigating to /settings/billing matches the settings route and the billing route, and the router renders them nested. Second, the layout does not remount when you move between its children, because React reconciles it as the same element in the same position — so the sidebar's scroll position, an open accordion, and a form's local state survive. That is precisely the thing full page navigation could never do, recovered. Third, child paths are relative: path="profile" inside path="/settings" means /settings/profile, so a whole feature can be moved under a different prefix by changing one line — provided every link inside it is also relative (<Link to="profile">, not to="/settings/profile").

Two special kinds of child are worth naming precisely. An index route [USE] has no path and renders into the parent's outlet when the URL matches the parent exactly — it is the answer to "what fills the pane at /settings before you pick anything." A layout route (or pathless route) has an element but no path, contributing nothing to the URL while still wrapping its children — which is how you apply one shell to several unrelated top-level routes, or attach one error boundary to a group.

What you can do at this point: model a real application's screens as a route tree, keep layout state alive across navigation, and use index and layout routes deliberately. [EXPLAIN]

What's still broken: the path says which screen. It says nothing about the state within a screen — which filters are applied, which page of results, how the table is sorted. Put that in React state and you are back to Node 1: unshareable, lost on refresh, invisible to the back button.

Node 7 — the query string: the URL as application state

The limitation: paths identify resources. They are a bad place for a variable-length, unordered, optional set of modifiers, and every state you keep out of the URL is state the user cannot share, bookmark, or return to.

The query string [EXPLAIN] is everything after the ?: /products?category=shoes&sort=price&page=3. Unlike the path, it is unordered, every key is optional, and keys may repeat — ?tag=red&tag=blue is a legitimate way to express a multi-select. It is parsed with the built-in URLSearchParams [USE], which handles encoding correctly and offers get, getAll, set, append, delete and toString. Note the distinction it forces on you: get returns the first value or null, getAll returns the array. Like path params, every value is a string, so page arrives as "3" and comparing it to 3 fails.

React Router surfaces this as const [searchParams, setSearchParams] = useSearchParams() [USE], deliberately shaped like useState so the mental model is "this is state that happens to live in the address bar." The design rule this unlocks is worth stating as a principle: state that another person should be able to see by opening your link belongs in the URL; state that is private to this moment in this tab does not. [EXPLAIN] Filters, search text, sort order, pagination, the selected tab, an open detail panel — URL. Whether a dropdown is open, the current value of an uncommitted input, an animation's progress — not the URL. The payoff is enormous and mostly invisible: support can ask for a link and see the same broken table; a user can bookmark a filtered view; and the back button starts undoing filter changes, which is what users expect and which no amount of React state gives you.

Which brings the push-versus-replace decision from Node 3 into daily use. Every character typed into a search box, if pushed, is a history entry, and the user must press back forty times to escape. So: continuous or rapid changes use replace (and are debounced, roughly 300 ms, which also avoids the browser's rate limit), while discrete deliberate changes use push — changing the category, moving to page 2. Getting this wrong in either direction is one of the most common real routing bugs: push everything and the back button is useless; replace everything and the back button skips the user out of the app when they expected to undo a filter.

One more piece of the URL exists and is easy to forget now that it is no longer carrying routes: the fragment is free again, and is the right place for "which section of this document am I looking at" — and the browser's native scroll-to-id still works for it, which is why deep-linking to a heading needs no code at all.

What you can do at this point: decide, per piece of state, whether it belongs in the path, the query string, the fragment, or component state — and defend the choice. [EXPLAIN]

What's still broken: you now write to the history stack constantly, from many places, for many reasons. What the stack actually contains — and therefore what "back" does — has become something you have to reason about carefully.

Node 8 — the history stack: push, replace, scroll, and the redirect trap

The limitation: the browser gave you a stack and two ways to write to it, and every navigation in your app is now a decision about which.

Picture the stack literally: an ordered list of entries with a pointer at the current one. pushState inserts a new entry after the pointer, moves the pointer to it, and discards everything that was ahead — which is why the forward button greys out the moment you go back and then click something new. replaceState overwrites the entry at the pointer and changes nothing else. Back and forward move the pointer without creating or destroying anything, and fire popstate.

Two things about that stack are structural and constrain everything you can build. It belongs to the tab, not your app — the entries from the site the user visited before yours are in there, which is why a "go back" button in your UI that calls history.back() can eject the user from your application entirely, and why the safe version is to navigate to a known parent route instead, or to check whether you have any entries of your own to return to. And it is opaque: for privacy reasons you cannot read it. You can read history.length and that is all. You cannot ask what the previous URL was, whether the user came from inside your app, or how many of the entries are yours. Every "smart back button" is therefore built on breadcrumbs your own router left behind — typically a value stashed in the state object at push time.

The failure mode this node exists to name is the redirect trap [EXPLAIN]. Route /dashboard checks auth, finds none, and navigates to /login with a push. The user logs in, lands back on /dashboard, and presses back. The previous entry is /login. Being logged in now, /login immediately redirects forward to /dashboard. The user is stuck; back appears completely broken. The fix is one word: redirects always replace, never push, because a redirect means "you were never really here." The same rule covers a legacy URL forwarding to its new home, a bare / sending you to /dashboard, and any normalising navigation.

The second thing the browser used to do and now does not is scroll. On a real navigation the browser scrolls to the top for a new page and restores your exact position when you press back — that restoration is history.scrollRestoration, which defaults to "auto" and which SPAs frequently set to "manual" so they can take over. With pushState, nothing scrolls at all, so the classic symptom is clicking a result at the bottom of a long list and landing halfway down the detail page. Correct behaviour has three cases, and a good router or a hand-written ScrollRestoration component implements all three: push scrolls to top; pop restores the saved position for that entry, which means recording window.scrollY against the entry before leaving; and replace leaves the scroll alone. The hard case, which is genuinely unsolved in general, is restoring a position that only exists after data has loaded and the list has re-rendered — restore too early and the page is too short to scroll that far.

What you can do at this point: reason about what the back button will do at any point in your app, and fix a dead-back-button or scroll bug from first principles. [EXPLAIN]

What's still broken: navigation currently renders a component, which then discovers it needs data and starts fetching. The router knew the destination well before that. Routing and data fetching are still strangers.

Node 9 — routing meets data: the waterfall, and route-level loaders

The limitation: when data fetching lives inside components, nothing can start until that component renders — and a nested component cannot render until its parent has finished loading.

Trace the naive sequence for /projects/7/tasks, where each level fetches in its own useEffect. The layout renders and starts fetching the project. It shows a spinner, so the child never renders. Project arrives. The child renders and only now starts fetching tasks. Another spinner. Tasks arrive. If each request takes 300 ms, the screen is complete after 600 ms of strictly sequential waiting, and if there is a third level, 900 ms. This is the request waterfall [EXPLAIN], and it is the defining performance problem of component-fetched SPAs. Nothing about those two requests actually depends on the other — both are derivable from the URL alone — so the serialisation is pure accident of where the code was written.

The observation that fixes it: the router knows the full matched chain of routes the instant the URL changes, before rendering anything. If each route declares what data it needs, the router can start every request in the chain in parallel, immediately, and render once. This is fetch-as-you-route replacing render-then-fetch, and it is the single biggest architectural idea in modern routing. Remix shipped it in 2021 with a loader per route; React Router absorbed it in v6.4, September 2022; Next.js's App Router (2023) does the equivalent with async server components per segment; TanStack Router does it with a loader plus an integrated query cache.

{ path: "projects/:id",
  loader: ({ params, request }) => fetchProject(params.id, request.signal),
  element: <Project /> }

Several things fall out of that shape and each is worth being able to explain. The loader receives params, so data depends on the URL rather than on props, which is what makes it startable before render. It receives a request carrying an AbortController signal, so when the user navigates away mid-load the router cancels the in-flight fetch — the same AbortController from the fetch topic, now driven by navigation. A loader can throw a redirect or throw a Response with a 404 status, which the router turns into a navigation or routes to the nearest error boundary, letting an auth check live in the loader instead of in a component that must render first to redirect (Node 12). And because the router owns the whole transition, it can hold the old screen on-screen while the new one loads rather than flashing a spinner — which is Node 11.

The mirror image for writes is the action [USE]: a per-route function that handles a <Form> submission, and after which the router automatically re-runs the loaders for the currently matched routes. That last part quietly deletes an entire category of code — the manual cache invalidation you would otherwise write after every mutation — by reusing the browser's own model, where submitting a form results in a fresh page.

Loaders have a real cost, and it is that they are blocking by default: nothing renders until every loader in the chain resolves, so one slow endpoint holds the whole screen. The answer is to stream — return a promise rather than awaiting it (defer, and in React Router v7 just returning the raw promise), render the shell immediately, and let <Await> plus <Suspense> fill the slow part in when it arrives. And note honestly that loaders and a query cache like TanStack Query overlap: loaders are excellent at when to fetch and terrible at caching and background revalidation, which is why the mature pattern is a loader that calls queryClient.ensureQueryData — the router decides timing, the cache decides freshness. That connects directly to what you covered in client-data-fetching.

What you can do at this point: identify a waterfall in a real app and explain how route-level loading removes it. [EXPLAIN]

What's still broken: you have made the app fast at fetching, and every route's code is still in one JavaScript bundle that the user downloads in full before the first screen appears.

Node 10 — code splitting: routes as the natural bundle boundary

The limitation: one bundle means the admin panel, the checkout flow and the settings screens are all downloaded and parsed by a user who only opened the home page.

Routes are the best split point a bundler can be given, because a route is exactly a chunk of the application that a given user may never enter, and the router knows in advance whether they are entering it. The mechanism is the dynamic import() expression [EXPLAIN] — standardised in ES2020, and treated by every bundler as a hard instruction to emit a separate file. In React it is wrapped by React.lazy, and the boundary that shows something while the file downloads is <Suspense>.

const Settings = React.lazy(() => import("./routes/Settings"));

Route-object routers express the same thing as a per-route lazy field, which is strictly better, because the router can start the chunk download and the loader fetch at the same moment rather than discovering the loader only after the chunk lands — the waterfall from Node 9, in a different costume.

Three real problems come with splitting, and they are what separates someone who has shipped this from someone who has read about it. The fallback flash: a chunk that arrives in 80 ms still unmounts the current screen and shows a spinner for 80 ms, which looks worse than not splitting at all — the fix is to keep the old screen visible during the transition (useTransition, or a data router's pending state, Node 11), not to add a nicer spinner. Too many chunks: splitting every route separately can mean dozens of tiny requests and duplicated shared code; bundlers mitigate with shared chunks, and the practical rule is to split at meaningful boundaries — the admin area, the editor, the heavy chart library — rather than reflexively at every route. The stale-chunk error after deploy [USE]: a user has your app open, you deploy, the old chunk filenames no longer exist, they navigate, and the import rejects with a chunk-load error. This is one of the most common production errors in the entire SPA world. Handle it: catch the failure at the route's error boundary and reload the page, which is safe because reloading gets the new HTML with the new filenames.

Splitting also enables prefetching [USE], which is where routing starts to feel magical. The router knows every link's destination, so it can begin downloading a route's chunk and even its data on hover, on focus, or when the link scrolls into view — typically a hundred to three hundred milliseconds of head start, which is often the entire perceived latency of the navigation. Next.js's <Link> prefetches links in the viewport by default; TanStack Router prefetches on hover by default; React Router does it for lazy routes on hover through its <Link prefetch> options in v7 and framework mode.

What you can do at this point: split a real app by route, prefetch sensibly, and diagnose a chunk-load error in production. [USE]

What's still broken: both the last two nodes ended with the same problem — a navigation now takes real time, and the interface currently either freezes or blanks while it does.

Node 11 — pending navigation: the transition, and the moment nothing happens

The limitation: a navigation that needs data or code is asynchronous, but a click is instantaneous, and the gap between them is user-visible.

Two designs are available, and naming them clearly is the point of this node. In a non-blocking (optimistic) navigation, the URL changes immediately, the new screen mounts immediately, and it renders its own skeletons while its data arrives. In a blocking (pending) navigation — the browser's own model — the old screen stays, visibly marked as busy, until the new one is ready, and then it appears complete. Blocking is what makes a SPA feel like the web rather than like a slideshow of spinners, and it is only possible when something outside the components knows a navigation is in flight, which is exactly what a data router or a React transition provides.

React's primitive is useTransition [USE] (React 18, March 2022): a state update wrapped in startTransition is marked non-urgent, so React keeps the current UI on screen and hands you an isPending boolean while it prepares the next one in the background. React Router's data router exposes the routing-shaped version, useNavigation(), whose state is "idle", "loading" or "submitting", along with the destination being loaded — enough to grey out the page, run a top progress bar, or highlight the specific link being loaded.

The failure this addresses is the one users describe as "the button doesn't work": they click, nothing changes for 400 ms because the router is quietly loading, so they click again. The rule of thumb from decades of interface research still holds — under about 100 ms feels instant and needs no indicator; up to a second needs some acknowledgement; beyond that needs real progress. So the good pattern is to show nothing at all for a short delay, then a subtle indicator, and to keep the old content visible throughout. And there is a matching trap: a spinner that appears for 50 ms and vanishes is worse than none, which is why indicators want both a delay before showing and a minimum display time once shown.

The same machinery covers the write path. Optimistic UI [USE] — React Router's useFetcher, React 19's useOptimistic — renders the expected result of a submission immediately from the submitted form data, then reconciles when the action's revalidation returns. And useFetcher covers the important case of loading or submitting without navigating at all: a like button, an inline delete, a type-ahead that hits the server. Recognising that "this is a data operation, not a navigation" is a genuine design skill and a good interview signal.

What you can do at this point: choose blocking or optimistic per route deliberately, and build pending states that do not flash. [USE]

What's still broken: everything so far assumes the navigation is allowed to happen. Some are not — the user is not logged in, or has unsaved work.

Node 12 — guards and protected routes, and why they are not security

The limitation: matching a route says the URL is valid. It says nothing about whether this user may see it.

The component-era pattern, which you will still meet in most codebases, is a wrapper that checks and redirects:

function RequireAuth({ children }) {
  const user = useAuth();
  const location = useLocation();
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;
  return children;
}

Four details in five lines. It renders a <Navigate> element rather than calling navigate() inline, because navigating during render is a side effect and React forbids it — <Navigate> performs it in an effect. It passes replace, for the redirect-trap reason from Node 8. It stashes the attempted location in history state so that after login you can send the user where they were actually going — and note the choice: state keeps the URL clean but is lost if the login page is opened fresh, whereas ?redirectTo=/dashboard survives, at the cost of being user-editable and therefore requiring you to reject absolute URLs, or you have built an open redirect vulnerability. And it needs a third state: user is often undefined while the session is still being checked, and treating "not yet known" as "not logged in" bounces every authenticated user to the login screen on every refresh. That bug is extremely common.

With a data router the check moves into the loader, which is better on every axis: it runs before anything renders, so there is no flash of protected content, and it can throw redirect("/login") directly. A pathless layout route with a loader that authenticates is the idiomatic way to protect a whole subtree in one place.

The thing that must be said plainly, because it is asked in interviews specifically to see whether you understand the trust boundary: a client-side route guard is not security. [EXPLAIN] It is a user-experience feature. Every byte of your JavaScript is on the user's machine and they can edit it; the route table, the component, and the guard are all inspectable and removable. Someone can force-render your admin panel in about thirty seconds. That is harmless if and only if the panel is empty without data, which it is if and only if every endpoint independently authorises every request. The client guard prevents an honest user from landing on a broken screen; the server prevents a dishonest one from getting anything. Code-splitting an admin route also means the code is not even downloaded, but never describe that as the security measure.

What you can do at this point: protect routes correctly, preserve the intended destination, avoid the loading-state bounce, and state where the real boundary is. [EXPLAIN]

What's still broken: guards handle "this navigation is not allowed." Nothing yet handles "this navigation happened and then something went wrong" — a URL that matches nothing, a loader that throws, a component that crashes.

Node 13 — errors and not-found, per route

The limitation: an unhandled error anywhere in a React tree unmounts the entire tree, so one failing widget produces a blank white page and the user loses the whole application, including the navigation they would use to escape.

Routing gives errors a natural place to stop, because the route tree already describes containment: a failure inside the billing screen should replace the billing screen, not the settings sidebar and not the app shell. So the modern answer is an error boundary per route [USE] — React Router's errorElement or ErrorBoundary on a route object — which catches anything thrown by that route's loader, action, or rendering, and renders in the place of that route while every ancestor stays mounted and interactive. Errors bubble up the route tree to the nearest boundary, so one at the root is your safety net and one on a risky subtree is the containment. useRouteError() gives you the thrown value; isRouteErrorResponse() distinguishes a thrown HTTP Response (a deliberate 404 or 403) from a genuine JavaScript exception, which is what lets one boundary render both a "not found" page and a "something went wrong" page appropriately.

Not found deserves care because it exists in two different places [EXPLAIN]. Client-side, a catch-all route — path="*" — matches anything no other route did, and renders your 404 screen. But the HTTP response was still 200 OK, because the server sent your index.html for that URL (Node 14). That is a soft 404, and search engines dislike it, monitoring cannot see it, and a link checker will report the page as fine. Fixing it properly requires the server to know your routes, which is what a framework with server rendering gives you and a static SPA cannot. Know the limitation and be honest about it — that honesty is itself the good interview answer.

Two related cases: a route that matches but whose resource doesn't exist (/products/99999) should have its loader throw a 404 Response rather than render an empty product page; and the chunk-load error from Node 10 belongs here too, caught at a boundary and resolved with a reload.

What you can do at this point: stop a failure from taking the whole app down, and distinguish the four different "not found" situations. [USE]

What's still broken: all of this assumes the application loaded. Type a deep URL into a fresh tab and, on a default static host, you get a 404 from the server before any of your JavaScript exists.

Node 14 — the server: why deep links 404, and what SSR changes

The limitation: your router lives in JavaScript inside a document. To run at all, that document must be served — and the server has no file at /products/42.

This is the moment every developer meets, usually in production, usually on a Friday: the app works perfectly, links work perfectly, and pasting a URL into a new tab or pressing refresh gives a bare 404. The cause is simple once seen. Navigating inside the app never touches the server. Loading a URL fresh is a real HTTP request, and the server looks for something at that path, finds nothing, and returns a 404 — and your router, which would have handled it, is inside the HTML that never got sent.

The fix is a single rule, implemented once per platform: any request that isn't a real file should return index.html, with a 200. [USE] Then the app boots, the router reads location.pathname, and renders the right screen. This is the only reason the following exist, and knowing at least a couple by name is a practical DevOps-adjacent signal:

  • Vite dev server and webpack-dev-server: historyApiFallback (on by default in Vite).
  • Nginx: try_files $uri $uri/ /index.html;
  • Apache: a .htaccess rewrite of anything that isn't an existing file to /index.html.
  • Netlify: /* /index.html 200 in _redirects. Vercel and Cloudflare Pages: equivalent rewrite config, mostly automatic for detected SPA frameworks.
  • S3 static hosting: set the error document to index.html — which works, but returns a 404 status, so pair it with CloudFront if the status matters.
  • Express: app.get("*", (req, res) => res.sendFile(indexHtml)), declared after your API routes, or it swallows them.

Two things follow. Order matters: the fallback must not shadow /api/* or your asset paths. And this is the one problem hash routing never had (Node 2) — every hash URL is a request for the same real path — which is precisely why hash routing survives on hosts you cannot configure.

Serving the same empty shell for every URL also means the first response contains no content: bad first paint, and a crawler or link-preview bot sees nothing unless it executes JavaScript (Google generally does, on a delay; many social and messaging previewers do not, which is why an unfurled link shows a generic title). Server-side rendering [AWARE] answers that by running the router and the components on the server for the requested URL and sending real HTML, which the client then hydrates — attaching event listeners and taking over subsequent navigation client-side. So SSR does not replace client-side routing; it makes the first navigation server-rendered and every subsequent one client-side. Meta-frameworks (Next.js, Remix, SvelteKit, Nuxt) are, to a large degree, the pieces of this node built in: routing that both server and client understand, plus the fallback, plus hydration.

What you can do at this point: deploy a SPA that survives refresh on any host, and explain exactly why the 404 happens. [EXPLAIN]

What's still broken: the URL and the server are correct now. The user is still not being told anything has changed — particularly a user who cannot see the screen.

Node 15 — focus, announcements, titles: the part almost everyone skips

The limitation: a real navigation makes the browser reset focus, announce the new page, and change the title. pushState does none of it, and none of it is visible to a sighted developer testing with a mouse.

Work through what a screen reader user experiences on a default SPA. They tab to a link and press Enter. The router swaps the main content. Focus is still on the anchor — which may no longer exist, in which case focus falls back to document.body and their reading position is lost entirely. Nothing is announced, because no document loaded. The title in the tab and in the browser history still says whatever the first page said. From their perspective, they activated a link and the application did nothing. This is not an edge case; it is the majority of SPAs.

Four things to implement, and they are cheap. Move focus on navigation [USE]: after the new route renders, focus a target near the top of the new content — commonly the <h1> or the main landmark, given tabIndex={-1} so it can receive programmatic focus without entering the tab order. This also fixes keyboard users' next Tab starting from the top of the new page rather than from wherever they were. Announce the change: an ARIA live region — a visually hidden element with aria-live="polite" — whose text you set to the new page's name, causing assistive technology to read it without stealing focus. Focusing a heading often achieves this too; doing one or the other deliberately is the requirement. Update document.title, which is what the browser's history menu, the tab, and bookmarks all show. And restore scroll, which is Node 8, and is an accessibility matter as much as a cosmetic one.

Two more, quickly: a skip link is only useful if it still works after a client-side navigation, which requires the same focus handling; and route-level <title> and <meta> management — historically react-helmet, natively in React 19, and by convention in every meta-framework — is the same problem for crawlers and link previews.

This node is worth over-preparing for interviews specifically because so few candidates mention it. Naming focus management and live regions unprompted marks you as someone who has shipped an application to real users.

What you can do at this point: make a SPA navigation as perceivable as a real one. [USE]

What's still broken: you can now tell the user a navigation happened. You still cannot stop one — and the case where you need to is universal: a half-filled form.

Node 16 — blocking navigation, and the platform catching up

The limitation: the router changes the URL and the screen the instant a link is clicked. There is no hook that says "wait — ask first."

Two different kinds of leaving exist, and they have different answers because only one of them is yours to control. Leaving inside the app — clicking a <Link>, calling navigate() — is entirely your router's decision, so it can be intercepted cleanly and you can show a real modal. React Router exposes useBlocker [USE], which gives you a blocker object in state "blocked" with proceed() and reset() methods, and you render whatever dialog you like.

Leaving the site — closing the tab, refreshing, typing a new address — is the browser's decision, and your only lever is the beforeunload event [USE], where you call event.preventDefault() and the browser shows its own generic dialog. You cannot customise the text (browsers removed that around 2016–2017 because it was used for scams), you cannot make it prettier, and it only fires if the user has interacted with the page. Register it only while there are unsaved changes: a permanent beforeunload listener is user-hostile and also disqualifies the page from the browser's back/forward cache, making back navigation to your site measurably slower.

The genuinely hard case is the back button [EXPLAIN]. By the time popstate fires, the browser has already moved — the URL is the previous one and it cannot be vetoed. The historical workaround is ugly and worth knowing because you will see it: push a duplicate entry so there is something to consume, and on popstate, push it again to undo the move while you ask the question. Fragile, and it is why blocked navigation has always been the flakiest part of every router.

Two newer platform pieces close this out. The Navigation API [AWARE] (Chrome 102, May 2022; not in Safari or Firefox as of 2026) is the browser finally shipping what routers have been simulating for fifteen years: a single navigate event for link clicks, form submits, back, forward and programmatic navigation alike, with event.intercept({ handler }) to take it over, a real preventDefault() that works for back navigation, a readable list of your own history entries, and built-in scroll and focus handling. It makes most of Node 4 and much of Node 8 unnecessary where it is available. And View Transitions [AWARE] (Chrome 111, March 2023) give the browser-level crossfade and shared-element animation between two states, which routers expose as a viewTransition flag on a link — the reason SPA navigations are starting to look like native app transitions.

What you can do at this point: guard unsaved work, know why the back button is the hard case, and name what the platform is replacing. [USE]

What's still broken: you understand routing as a set of capabilities. You have not chosen a router — and the choices differ in ways that matter.

Node 17 — the landscape of routers: config, components, files, and types

The limitation: everything so far is mechanism. Real work starts by picking a library, and the differences are architectural, not cosmetic.

Routers differ along three axes worth naming. How routes are declared: as a config object tree (analysable before render, which enables preloading and type generation), as components in the tree (flexible and dynamic, the React Router v4–v6 model), or by the file system — app/routes/products/[id].tsx — where directory structure is the route tree, which removes an entire class of "I forgot to register the route" bugs and is why Next.js, Remix, SvelteKit and Nuxt all do it. Whether it owns data: a pure matcher, or a router with loaders and actions. Whether it is type-safe: whether navigate("/prodcts/42") is a compile error and whether params.id is typed, which is TanStack Router's central pitch and the direction the whole ecosystem is moving.

In React: React Router [USE] is the default answer and the one you will be asked about — it descends from 2014, is used by a very large share of React apps, and its history is worth knowing because the versions are genuinely different products (v3 static config; v4 in 2017 all-components; v6 in 2021 with ranking, nesting and <Outlet>; v6.4 in 2022 adding loaders and actions; v7 in late 2024 merging with Remix so one library covers a plain SPA and a full-stack framework). TanStack Router [AWARE] (1.0 in late 2023) is the type-safe, loader-first, search-param-schema alternative and is what people reach for when the URL carries a lot of typed state. Next.js App Router [AWARE] is file-based, server-first, and folds routing, data and rendering into one model. wouter [AWARE] is a ~2 kB minimal matcher for when you need nothing more.

Outside React, the same ideas wear different names, and recognising them is useful in interviews: Vue Router (config-based, <router-view>, per-route navigation guards as first-class API), Angular Router (config-based, <router-outlet>, resolvers — which are loaders, and predate them by years — and guard interfaces), SvelteKit and Nuxt (file-based, server-integrated). Angular in particular had guards and resolvers long before the React ecosystem arrived at them; the convergence is real and worth saying out loud.

A practical selection heuristic: if the app has a server or needs SEO, reach for a meta-framework rather than bolting SSR onto a SPA. If it is behind a login and purely client-rendered, React Router in data mode is the safe default. If the URL is carrying a lot of structured state, TanStack Router earns its cost. If you need three screens, use wouter or the twenty lines from Nodes 3 and 4.

What you can do at this point: choose a router for a described application and defend the choice against the alternatives. [USE]

What's still broken: nothing structural — the chain is complete. What remains is that every capability here has a default that is wrong for some app, and knowing which default to override is what the project stage exists to teach.

Where the chain gets misread

  • "A router is a React thing." (Node 3) It is the History API plus click interception. Every framework's router is a wrapper over the same three browser calls; you can write a working one in twenty lines with no library.
  • "pushState fires popstate." (Node 3) It does not. Only user- or script-driven history traversal does. Missing this is why hand-rolled routers fail to re-render.
  • "<Link> is just a styled button." (Node 4) It must render a real <a href>. The href is what gives you new-tab clicks, copy-link, the status bar, keyboard activation, the link role, and crawlability.
  • "Put the specific route before the dynamic one." (Node 5) True for Express and React Router v3–v5. React Router v6+ ranks by specificity, so order does not matter. Answering with the old rule dates you.
  • "Params are typed." (Node 5) Every path param and every query value is a string. params.id === 42 is false. Parse at the boundary.
  • "Nesting is about code organisation." (Node 6) It is about the layout not remounting, which is what preserves sidebar scroll, open panels and form state across navigation — the exact thing MPAs could never do.
  • "Filters and pagination are component state." (Node 7) If a link to it should show the same screen, it is URL state. This is the single highest-leverage design principle in the topic.
  • "A redirect is just a navigation." (Node 8) Redirects must replace. Pushing them creates the back-button trap where back re-enters the redirect and bounces forward again.
  • "Fetching in useEffect per component is fine." (Node 9) It serialises independent requests into a waterfall, because a child cannot start until its parent has finished. Route-level loading removes it because the URL alone determines every request.
  • "Code splitting always makes it faster." (Node 10) It moves cost. Without a pending state it trades bundle size for a blank flash on every navigation, and it introduces stale-chunk errors after deploy.
  • "The guard protects the admin page." (Node 12) It protects the experience. All the code is on the user's machine. Only server-side authorisation on every endpoint is security.
  • "A path="*" route gives me a 404." (Node 13) It gives a 404 screen with a 200 status — a soft 404 — because the server sent index.html. Only server-aware routing fixes the status.
  • "It works locally, so deployment is fine." (Node 14) The dev server has historyApiFallback on. Production hosts do not, until you configure the rewrite. This is the most common SPA deployment failure in existence.
  • "Accessibility is a separate concern from routing." (Node 15) Routing removed the browser's focus reset, page announcement and title update. Restoring them is the router's job and nobody else's.
  • "SSR replaces client-side routing." (Node 14, Node 17) It replaces only the first navigation. After hydration, every subsequent one is client-side, using everything in this chain.

The chain in one paragraph

Before routing, the server owned every URL and the browser threw away the whole document on each navigation, which was correct in every way except speed and continuity; the moment JavaScript started swapping content in place, the address bar stopped describing the screen and the back button, refresh, bookmarking, deep links, crawling and screen-reader announcements all broke at once, so a router is simply the two-way binding between the URL and what is rendered. The first version used the fragment, because # was the only part of a URL you could change without navigating and it is never sent to the server — still the right answer on a host you cannot configure. HTML5 replaced it with pushState, replaceState and popstate, which change the address bar and the history stack without a request and which every router since is a wrapper over — remembering that pushState fires no event, so you must notify yourself. Users click links rather than calling functions, so the router intercepts anchor clicks, carefully skipping modifier-clicks, new-tab targets and cross-origin hrefs, which is why <Link> must render a real <a href>. Matching turns the path into a component and a set of string params, ranked by specificity so declaration order stops mattering; nesting turns the flat table into a tree mirroring both the URL's segments and the UI's layout, so shells persist and never remount; and the query string carries everything within a screen that another person should see when they open your link — pushed for deliberate changes, replaced for continuous ones, since the history stack is a real stack you are writing to and redirects that push create the classic back-button trap. Once the router knows the whole matched chain before rendering, data can be fetched per route in parallel instead of waterfalling through useEffect, code can be split per route and prefetched on hover, and because navigation now takes real time it needs a pending state that keeps the old screen visible instead of flashing, guards that redirect with replace while preserving the intended destination, and per-route error boundaries that contain a failure instead of blanking the app. All of it still assumes the document was served, which is why every deep link 404s until the host is told to return index.html for anything that is not a file — the one problem hash routing never had — and why server rendering exists at all, being the first navigation done on the server before the client takes over. Finally, restore by hand what the browser used to do for free: move focus, announce the change, set the title, restore scroll, and ask before discarding unsaved work — until the Navigation API and View Transitions hand those back to the platform.
