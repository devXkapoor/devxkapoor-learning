Node 25 — users, permissions, and capabilities

The limitation: the kernel enforces permissions and nothing has said what a permission is or who a user is to the kernel.

A user is a number

To the kernel there are no usernames. There is a UID — an unsigned integer in the process's credentials (Node 5) — and a set of GIDs. Names exist only in /etc/passwd and /etc/group, which are ordinary text files read by ordinary library code in user space to render numbers as names.

This has a consequence that matters enormously for containers, and it is worth stating before anything else: UID 1000 inside a container and UID 1000 on the host are the same user as far as the kernel is concerned, unless a user namespace is in play (Node 26). The container's /etc/passwd may call it node and the host's may call it devansh, but a file written by one is owned by the other. That is why a bind-mounted volume shows up with confusing ownership and why files created by a container are sometimes not deletable by you.

UID 0 is root, and historically the kernel's check was literally if (uid == 0) allow; — root bypasses all permission checks.

The permission bits

Each inode carries an owner UID, a group GID, and nine bits: read, write and execute, for owner, group, and other. Written as three octal digits — rwx is 7, rw- is 6, r-x is 5. 644 is owner read-write, everyone else read-only; 755 adds execute for all, which is what a program or a directory needs.

The check picks one class and stops: if you are the owner, only the owner bits apply — even if the group bits would grant more. A file owned by you with mode 044 is one you cannot read and everyone else can, which is a counter-intuitive result that follows directly from "first match wins".

On directories the three bits mean something different and the difference is the source of much confusion:

  • r — you may list the names in it.
  • w — you may create, delete and rename entries in it. Deleting a file is governed by the directory's permissions, not the file's, because deletion is unlink, which edits the directory (Node 21). So you can delete a read-only file you do not own, if you can write its directory.
  • x — "search": you may traverse through it to reach something inside. A directory with x but not r lets you open a file whose exact name you know while preventing you from listing what is there.

Three extra bits sit above the nine. setuid makes a program run with the file owner's UID rather than the caller's — this is how passwd lets an ordinary user modify /etc/shadow, and it is a permanent source of privilege-escalation vulnerabilities, since any bug in a setuid-root program is a path to root. setgid does the same for groups, and on a directory makes new files inherit the directory's group. The sticky bit on a directory restricts deletion to the file's owner, which is why /tmp is 1777 — world-writable without letting anyone delete anyone else's files.

umask is the complement: a mask of bits removed from the mode of newly created files. The common 022 turns a requested 666 into 644. It is per-process state (Node 5), inherited by children, which is why it is set in a shell profile and why a daemon's umask can surprise you.

Capabilities: splitting root into pieces

All-or-nothing root is a poor design. A web server needs to bind port 80 — ports below 1024 are privileged — and nothing else, yet the traditional approach was to start as root, bind, and drop privileges, leaving a window in which a bug is total compromise.

Linux 2.2 (1999) split root's powers into distinct capabilities, each grantable independently. The ones worth knowing:

  • CAP_NET_BIND_SERVICE — bind ports below 1024.
  • CAP_NET_ADMIN — configure interfaces, routes, firewall rules.
  • CAP_NET_RAW — raw sockets. This is what ping needs, and why ping often fails in a container.
  • CAP_SYS_ADMIN — an enormous grab-bag including mount. Widely described as "the new root", and granting it is close to granting everything.
  • CAP_CHOWN, CAP_DAC_OVERRIDE (bypass all file permission checks), CAP_SETUID, CAP_KILL, CAP_SYS_PTRACE (attach a debugger to any process — and therefore read its memory), CAP_SYS_MODULE (load kernel modules, i.e. game over).

Capabilities can also be attached to a file, so a binary gains only what it needs — setcap cap_net_bind_service=+ep /usr/bin/node lets Node bind port 80 with no root anywhere. In practice, in containers, the interesting operation is the opposite: dropping everything and adding back the one thing needed.

Beyond the bits

ACLs (setfacl, getfacl) allow per-user and per-group entries beyond the three classes; a file with an ACL shows a + in ls -l. SELinux and AppArmor are mandatory access control: policies enforced regardless of the ordinary permissions, and not overridable by the file's owner. SELinux labels every file and process and checks every access against a policy — which is why on Red Hat systems a volume mount into a container needs the :z or :Z suffix to relabel it, and why the failure without it is a permission denied that the permission bits say should have worked.

Where this is in your stack

Containers run as root by default and this is the most common container security failure. Without a USER instruction, your image's process runs as UID 0. Combined with a bind mount, a container escape, or a kernel vulnerability, that is root on the host. It also means files the container writes into a mounted volume are owned by root, which is the annoyance most people notice first. The fix is three lines, and the reason it is three lines rather than one is this node:

RUN addgroup -g 1001 nodejs && adduser -u 1001 -G nodejs -s /bin/sh -D nodejs
USER nodejs
# and, if you need port 80, do not add a capability — listen on 3000
# and let the load balancer or Service map 80 to it.

In Kubernetes the equivalent is a securityContext, and the set worth knowing as a default is runAsNonRoot: true, runAsUser: 1001, allowPrivilegeEscalation: false (which sets the no_new_privs bit so setuid binaries cannot elevate), readOnlyRootFilesystem: true with an emptyDir mounted where the app genuinely needs to write, capabilities: {drop: [ALL]}, and seccompProfile: RuntimeDefault from Node 4. That list is not a checklist to memorise — every item is one mechanism from this part of the document, turned off.

The port-1024 rule explains a design decision you have seen everywhere. Node applications listen on 3000, 8000 or 8080 rather than 80, and the reason is that binding below 1024 historically required root. So the pattern is: application on a high port as a non-root user, with nginx, a cloud load balancer, or a Kubernetes Service handling 80 and 443. On modern Linux you can also lower net.ipv4.ip_unprivileged_port_start, and Kubernetes generally sidesteps the issue entirely.

The volume ownership problem, and its real fix. A container running as UID 1001 writing into a host bind mount owned by UID 1000 gets permission denied, because the kernel compares numbers and does not care what either side's /etc/passwd says. Common workarounds — chmod 777, running as root, an entrypoint that chowns on startup — are all bad. The correct answers are to match the UIDs deliberately (build the image with the host user's UID), to use a named Docker volume rather than a bind mount so the runtime handles ownership, or, in Kubernetes, to set fsGroup in the pod's security context so the volume is group-owned appropriately. The genuinely correct answer is user namespaces, which map container UID 0 to an unprivileged host UID, and that is the next node.

File permission bugs in Node. fs.writeFile's mode argument is subject to umask, so requesting 0o600 yields 0o600 only because umask does not usually clear owner bits — but requesting 0o666 gives you 0o644. Writing a secret or a private key requires an explicit fs.chmod after creation, or opening with the right mode and verifying, and an SSH private key with group-readable permissions is silently rejected by ssh, which is a good habit for other tools to copy.

What you can do at this point: explain that a user is a number and what that means across a container boundary, read and reason about permission bits including the directory meanings and the first-match rule, explain setuid and the sticky bit, name the capabilities that matter and explain why CAP_SYS_ADMIN is effectively root, and write a correct non-root container security context justifying every field.

What's still broken: permissions decide what a process may do to things it can see. Nothing yet limits what it can see. A process can list every other process, every mount, every network interface, and every user on the machine. Two customers' workloads on one machine can watch each other, and no permission bit changes that.
