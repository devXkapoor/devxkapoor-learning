Node 19 — readiness: select, poll, epoll, and why files are different

The limitation: the architecture requires one thread waiting on many connections, and no system call can wait on more than one descriptor.

First: non-blocking mode

Before there can be a "wait on many" call there must be a way to not wait. Setting O_NONBLOCK on a descriptor changes its semantics: read on an empty socket returns immediately with −1 and errno = EAGAIN (identically EWOULDBLOCK) instead of sleeping.

That alone is not a solution. A loop over ten thousand non-blocking descriptors, calling read on each, makes ten thousand system calls per pass and almost all of them return EAGAIN. At 50–100 nanoseconds each (Node 4), one pass costs a millisecond of pure overhead and finds, typically, nothing. This is polling, and Node 2 already established when polling loses.

So the requirement is precise: one call that takes a set of descriptors and returns when at least one is ready, or a timeout elapses. That call is where the entire event loop comes from.

select (1983) — the first attempt

From 4.2BSD. You pass three bitmaps — descriptors to watch for readability, writability, and errors — plus a timeout. It blocks until something is ready, then modifies your bitmaps in place to indicate which.

Three problems, all structural:

  • FD_SETSIZE is 1024, compiled into the bitmap type. Not a tunable — a hard ceiling. Ten thousand connections is not expressible.
  • You rebuild and re-pass the entire set on every call, because the call destroys it. The kernel then copies it in and scans all of it. O(n) per call in both directions, every iteration, forever.
  • The return tells you how many are ready, not which. You scan all n to find them. Another O(n).

At 10,000 descriptors with 10 ready, every loop iteration copies and scans 10,000 entries twice to find 10. The cost is proportional to the number of connections you have, not to the number of events that happened — which is the exact wrong scaling property, since real servers hold many mostly-idle connections. That sentence is the whole node.

poll (1986) — one problem fixed, two left

System V's version takes an array of struct pollfd instead of bitmaps, each holding a descriptor, the events wanted, and a field the kernel fills in with events that occurred. The array is not destroyed, so it need not be rebuilt, and there is no fixed limit.

But the array is still passed in full on every call, still copied into the kernel, still scanned entirely, and still scanned by you on return. The O(n) per call remains, which means poll was an ergonomic improvement rather than an architectural one. It is still the right choice for small descriptor counts and it is what libuv uses on platforms lacking anything better.

epoll (2002) — the fix, and why it is a fix

Linux 2.5.44, by Davide Libenzi. The insight is that the watch set changes rarely and is queried constantly, so it should live in the kernel rather than being re-uploaded every iteration. Three calls instead of one:

  • epoll_create1() — create a kernel-side set, returning a descriptor that refers to it.
  • epoll_ctl(epfd, ADD|MOD|DEL, fd, events) — register interest in one descriptor. Called once per connection, not once per loop.
  • epoll_wait(epfd, events, maxevents, timeout) — block until something is ready, and return only the ready ones.

The mechanism inside is what makes it O(1). When you register a descriptor, the kernel attaches a callback to that socket's wait queue — the same wait queue from Node 18 step 4. When data arrives and the network softirq (Node 2) appends it to the socket buffer, that callback runs and pushes the descriptor onto the epoll instance's ready list. So the ready list is maintained continuously by the events themselves. epoll_wait does not scan anything; it hands back the list.

The cost becomes proportional to the number of events, not the number of connections. [EXPLAIN] A hundred thousand idle connections cost nothing to wait on. That property — and only that property — is what makes a modern server possible, and it is the correct answer when an interviewer asks what makes epoll better than select.

Level-triggered versus edge-triggered is the one real subtlety. Level-triggered (the default) reports a descriptor as ready as long as data remains unread — so a partial read is safe, and the next epoll_wait reports it again. Edge-triggered (EPOLLET) reports only on a transition from not-ready to ready, so if you do not drain the socket completely you will never be told about the remainder and the connection hangs silently. Edge-triggered requires reading in a loop until EAGAIN, and it is faster because it avoids repeated notifications. libuv uses level-triggered, which is the safer choice; nginx uses edge-triggered.

Every platform has its own version — kqueue on BSD and macOS (Jonathan Lemon, FreeBSD 4.1, 2000, and in some respects a better design than epoll since it handles timers, signals and file events through one interface), IOCP on Windows (a completion-based rather than readiness-based model), and event ports on Solaris. libuv exists to hide these four behind one interface, which is most of its reason to exist and why "Node is built on libuv" is a meaningful statement rather than trivia.

The crucial exception: regular files

Here is the fact that explains the strangest thing about Node's architecture, and it is routinely omitted.

A regular file is always "ready". [EXPLAIN] Readiness notification answers "will this operation block?", and for a socket that is a meaningful question — the data either has arrived or has not. For a file on disk, the answer is always yes, you can read it; the question is how long the read will take, which readiness cannot express. epoll flatly refuses regular files: adding one returns EPERM.

Nor is O_NONBLOCK any help — on a regular file it is simply ignored. A read that must fetch from the disk will block for however long the disk takes, and there is no interface in the readiness model that avoids it.

So a single-threaded event loop cannot do file I/O without blocking. There are only three possible responses:

  1. Use threads. Hand the blocking call to a pool thread and post the result back to the loop. This is what libuv does, and it is the entire reason UV_THREADPOOL_SIZE exists.
  2. Use a genuine asynchronous file interface. Linux's aio (POSIX AIO) has existed for years and is widely regarded as broken — it silently falls back to blocking in many configurations and only works with O_DIRECT.
  3. io_uring (Jens Axboe, Linux 5.1, May 2019), which is a completion-based interface built on two shared-memory ring buffers between user space and the kernel: you write submission entries into one ring and read completions from the other, with zero or one system calls for thousands of operations. It works properly for files, sockets, and much else, and it is the first genuinely good asynchronous I/O interface Linux has had. libuv has used it for some file operations since 1.45 (2023), gated on kernel version.

The mixed model — sockets on epoll, files on threads — is therefore not an inconsistency in Node's design. It is a direct consequence of the kernel interfaces available. Knowing this makes several Node behaviours predictable rather than mysterious.

Where this is in your stack

An idle Node server is one thread in epoll_wait, and you can see it. strace -p $(pgrep -n node) on an idle server prints one line: a blocked epoll_wait. That is the entire runtime at rest. Under load, it becomes epoll_wait returning, a burst of read/write/futex, and back. Watching that once makes the event loop concrete in a way no diagram does. [USE]

Threadpool saturation is a specific, diagnosable failure and it comes straight from the exception above. Four threads by default. If four file reads are in flight, the fifth queues. Crucially, dns.lookup also uses the pool — because getaddrinfo is a blocking library call — and so do crypto.pbkdf2, scrypt, randomBytes for large sizes, and zlib. So a slow DNS server can stall your file reads, which is a genuinely surprising coupling until you know the pool is shared. Symptoms: rising latency on file or DNS operations while the main thread is idle and CPU is low. Fixes: raise UV_THREADPOOL_SIZE (bounded by cores for CPU-bound work, per Node 6), use dns.resolve instead of dns.lookup where possible since it uses sockets and epoll, and move heavy crypto and compression to worker threads or out of the process.

The ulimit -n ceiling. Each connection is a descriptor and each process has a limit — often 1024 by default, which is a fossil of select's FD_SETSIZE. Hitting it produces EMFILE: too many open files, and it is one of the classic production failures, usually caused by descriptors leaking rather than by real concurrency: HTTP responses never consumed, streams never closed, connections without keep-alive timeouts. Diagnose with ls /proc/<pid>/fd | wc -l and lsof -p. Raise with ulimit -n, LimitNOFILE= in a systemd unit, or a container's ulimit settings — but always check for a leak first, because a leak will exhaust any limit.

Backpressure is epoll's write side, and it is why streams have the API they do. A socket's send buffer is finite. When it is full, a non-blocking write returns EAGAIN having written fewer bytes than asked, and the correct response is to register for EPOLLOUT and resume when the socket becomes writable. libuv does that for you, and Node surfaces it as stream.write() returning false and later emitting 'drain'. Ignoring that return value means Node buffers the unwritten data in your heap, without limit — which is how a service streaming a large file to a slow client runs out of memory. pipeline() and pipe() handle it correctly, which is the actual reason to prefer them over manual write loops.

What you can do at this point: explain the progression select → poll → epoll in terms of what scales with what, explain edge versus level triggering, explain why regular files cannot be polled and what that forces on Node's architecture, diagnose threadpool saturation and descriptor exhaustion, and explain backpressure as the write side of readiness.

What's still broken: there is now one call that reports many ready descriptors. That is a mechanism, not a program. Something has to loop on it, decide the order in which the resulting work runs, interleave timers and completed threadpool tasks and promise callbacks, and decide what happens when a callback schedules more work. That something is a scheduler, in user space, and it is the last node of this part.
