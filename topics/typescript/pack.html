TypeScript

JavaScript plus a layer of claims about what your values are — checked before the program runs, then deleted. Everything hard about TypeScript lives in that gap.

Read this top to bottom, in order. Each node exists because the node before it left something specifically broken. Every node ends by naming what is still broken, and that broken thing is the entire reason the next node exists. Read this way, you should be able to derive most of TypeScript rather than memorize it — and when you forget a detail later, you'll know which link in the chain it hangs off.

Depth markers appear inline. [EXPLAIN] means you must be able to explain it out loud, from first principles, under interview pressure, with no notes. [USE] means you must use it correctly and debug it when it breaks, without needing the internals cold. [AWARE] means know it exists, know what problem it solves, know roughly when to reach for it.

Node 0 — the problem before TypeScript exists

You are writing JavaScript. You write a function called sendInvoice that takes a user and charges them. Somewhere else — a different file, written three weeks later, possibly by someone else — you call it with an object that has emailAddress instead of email. Nothing complains. The editor is happy. The tests pass, because the tests call it correctly. The code ships. At 2 a.m. a customer triggers that path and the program reads user.email, gets undefined, and sends an invoice to the string "undefined". You find out from a support ticket.

That is the shape of every problem TypeScript exists to solve, and it has four faces worth naming separately because they get asked about separately.

The first is errors found late. In plain JavaScript, a misspelled property, a function called with two arguments instead of three, a value that's a string where the code assumes a number — none of these are detected until the exact line executes with the exact bad value. Your coverage of the code is only as good as your coverage of the inputs, and in a real system the inputs are the part you control least.

The second is the editor knows nothing. When you type user. in a JavaScript file, the editor can only guess what comes next, usually by scanning for similar-looking objects. So you don't get a list of what a user actually has. You get either nothing or a pile of irrelevant suggestions. This sounds like a comfort issue. It isn't — it's the main reason people can't work in unfamiliar codebases quickly. Without the editor telling you what's on a value, the only way to know is to go read the code that produced it, and then the code that produced that.

The third is refactoring is guesswork. You want to rename a field, or change a function to take an options object instead of five positional arguments. In JavaScript your tool is text search. Search for email in a large codebase and you get hundreds of hits across unrelated concepts, and no way to know which ones refer to this email. So people don't refactor. The code calcifies. Bad names and bad shapes survive for years because changing them is a gamble nobody wants to take on a Friday.

The fourth is documentation that lies. A comment saying // opts: { retries: number, timeout: number } is correct on the day it's written and slowly becomes fiction. Nothing enforces it. The only fully trustworthy documentation of what a function accepts is the function's body, which means reading implementations to use interfaces — the exact thing an interface is supposed to prevent.

The obvious fix is to move to a language that checks types. Java, C#, Go. And that fix was available the whole time, and people did not take it, for a reason that shapes everything about TypeScript's design: the code already exists, it runs in browsers and in Node, and there are millions of lines of it plus an ecosystem of hundreds of thousands of JavaScript packages. You cannot switch languages. Any solution must run the existing JavaScript, interoperate with untyped packages, and be adoptable one file at a time by a team that cannot stop shipping.

TypeScript was Anders Hejlsberg's answer at Microsoft, announced October 2012. Hejlsberg had designed Turbo Pascal, Delphi, and C# — so the pedigree is a static-typing pedigree — but the constraint here was new: the type system had to be bolted onto a language it did not control, describing patterns JavaScript programmers had already invented, without being allowed to forbid any of them.

What's still broken: we have a reason to want types, but no way to state one. The smallest possible thing is to write down what a single value is, and have something check it.

Node 1 — annotations, inference, and the compiler as the only enforcement

The limitation: nothing in JavaScript records what a value is meant to be, so nothing can check it.

TypeScript's smallest unit is the type annotation [EXPLAIN]: a colon and a type after a name. let count: number = 0. You have now made a claim — this name holds numbers — and a program called tsc, the TypeScript compiler, will read your whole codebase and tell you every place the claim is violated. count = "five" is now an error reported before you run anything.

The claim is checked by static analysis, meaning by reading the code rather than by running it. This is the first thing to hold onto, and it is the thing most people never fully internalize: tsc never executes your program. It reads it, builds a model of what every expression's type must be, and compares that model against itself. Everything TypeScript knows, it knows from reading.

The second thing, immediately: you rarely write annotations, because TypeScript infers [EXPLAIN]. Write let count = 0 with no annotation and TypeScript concludes count is a number, because you initialized it with one. Write const name = "devansh" and it concludes something narrower and stranger — the type is not string but the literal type "devansh", meaning "this exact string and no other," because a const can never be reassigned so no other value is possible. That difference between let and const inference is small now and becomes load-bearing at Node 4.

Inference flows through expressions. const doubled = count 2 is a number because multiplying numbers yields a number. const parts = "a,b".split(",") is string[] because TypeScript ships descriptions of every built-in JavaScript function. So a well-written TypeScript file often has annotations only at the edges* — function parameters, and the shapes of external data — with everything in between inferred. Annotate where information enters; let inference carry it through [USE]. Over-annotating is a real smell; it means writing down things the compiler already knew, and those written-down things then rot the way comments do.

The practical arrangement: your file is app.ts, you run tsc, and out comes app.js — ordinary JavaScript, which is what actually runs. TypeScript is not a runtime. There is no TypeScript engine in the browser or in Node in the ordinary case (Node's newer type-stripping is a real but narrow exception, and it's Node 19). Everything TypeScript does happens before your program exists.

One consequence of that arrangement bites everyone once: by default, tsc still emits JavaScript even when it found type errors [USE]. Type errors are reported, not fatal. This is deliberate — it lets you adopt TypeScript on a codebase with thousands of errors and still ship — but it means "it ran" proves nothing about whether it type-checked. The flag that changes this is noEmitOnError, and the more common real-world arrangement is that a bundler builds the code without checking types at all while a separate tsc --noEmit runs in CI as the actual gate. That split is Node 14 and it explains a whole category of "but it worked locally."

What you can do at this point: state what a variable holds, have a compiler check it, and get an editor that knows what you meant.

What's still broken: you can annotate a variable, but you have no idea what "is a number" actually means to the checker — what makes two types compatible, and what happens to all of this when the program actually runs.

Node 2 — structural typing and erasure: the two rules everything else obeys

The limitation: annotations are checked against something, and until you know what that something is, every later behaviour looks arbitrary.

Two properties define TypeScript. Almost every surprise in the rest of this chain is one of them showing up somewhere you didn't expect.

The first: TypeScript is structurally typed [EXPLAIN]. A value is compatible with a type if it has the right shape — the right properties with the right types — regardless of what it was declared as, what class it came from, or what it's named. If a function wants { name: string }, then an object literal with a name string works, and so does an instance of a class you wrote that has a name string, and so does something from a library that happens to have a name string. Nobody has to declare an intention to be compatible.

This is the opposite of nominal typing, which is what Java and C# use, where compatibility requires the declared relationship: this class implements that interface, by name. Hejlsberg — who designed C# — chose structural here for a specific reason [EXPLAIN]: JavaScript code is written with object literals and duck typing everywhere, and a nominal system would have rejected virtually all existing JavaScript as untyped. Structural typing lets TypeScript describe code that was written years before TypeScript existed.

The consequence you will actually feel: two unrelated types with the same shape are interchangeable. If UserId and PostId are both just string, TypeScript cannot stop you passing one where the other belongs, and it will never warn you, because there is nothing structurally different about them. Teams that need that distinction fake nominality with branded types [AWARE] — intersecting a primitive with an impossible marker property — which is a Node 10 technique and a very common senior-level interview question precisely because it exposes whether you understand structural typing.

The other consequence, from the other direction: excess property checking [USE]. Structural typing says extra properties should be fine — an object with name and age still has the right shape for { name: string }. And they are fine, except in one case: when you pass an object literal directly, TypeScript flags unknown properties as errors. This is a deliberate special case, not a rule of the type system, added because passing a literal with a typo'd or misplaced property is nearly always a mistake rather than a deliberate superset. Assign the same literal to a variable first and pass the variable, and the error disappears — which looks insane until you know that the check is specifically about fresh literals.

The second: types are erased [EXPLAIN]. When TypeScript compiles, every type annotation, every interface, every generic parameter is deleted. The output is JavaScript with the types stripped out and nothing added. There is no type information at runtime — not in a variable, not on an object, nowhere. This too was a deliberate constraint: the output had to be clean, readable JavaScript with no runtime library and no performance cost, so that adopting TypeScript could never be blamed for slowing anything down.

Erasure is the single most consequential fact in this entire topic, and it is the source of the two biggest classes of confusion:

You cannot check a type at runtime. There is no if (x is User). typeof and instanceof exist, but they're JavaScript operators that predate TypeScript and only answer JavaScript's questions — typeof distinguishes the seven primitives plus function and object, and instanceof checks the prototype chain, which only works for things built with classes or constructors. Neither can tell you whether a plain object matches an interface. That gap is what Node 15 is entirely about.

And types cannot influence what the program does. Two functions can't behave differently based on a type parameter, because by the time the code runs, the type parameter is gone. Generics do not generate specialized code the way C++ templates do; there is exactly one function at runtime.

What you can do at this point: predict whether the checker will accept an assignment, and explain why a type "disappeared."

What's still broken: you can type single values, but real data is objects with many fields, reused in many places, and writing the shape out longhand at every use is untenable.

Node 3 — object types: interfaces, type aliases, and naming a shape

The limitation: function f(u: { name: string; email: string; age: number }) is fine once and unbearable at the twentieth use site.

You need to name a shape and refer to it by name. TypeScript gives you two ways, and the difference between them is a near-universal interview question with a mostly boring answer and one genuinely important asymmetry.

An interface [EXPLAIN] declares a named object shape: interface User { name: string; email: string }. A type alias [EXPLAIN] gives a name to any type whatsoever: type User = { name: string; email: string }, but equally type Id = string or type Status = "on" | "off". For describing an object, they are almost entirely interchangeable — both are structural, both are erased, both are checked identically, neither is faster in any way you'd notice at ordinary scale.

The real differences [USE]: interfaces merge — declare interface User twice in the same scope and you get one User with the union of the members. Type aliases collide and error. That merging is not a quirk to work around; it is a feature the whole ecosystem depends on for extending library types, and it is Node 17. Second, type aliases can express things interfaces cannot: unions, tuples, primitives, conditional and mapped types — everything from Node 4 and Node 10. Interfaces can only ever describe object-like things.

The working rule most teams land on: interfaces for object shapes that others may extend, type aliases for everything else [USE]. Consistency matters more than the choice.

Inside a shape you get three modifiers that carry more weight than they look. Optional properties with ? — email?: string — mean the property may be absent, and its type becomes string | undefined, which is why you cannot use it without checking first (Node 5). readonly [USE] means the compiler rejects assignment to that property, which is compile-time only — the property is perfectly writable at runtime, and Object.freeze is the runtime equivalent, entirely unrelated. And index signatures [USE] — { [key: string]: number } — describe an object with arbitrary keys of a known value type, which is how you type a dictionary; the cost is you lose all knowledge of which keys exist, so every lookup is a maybe.

Shapes compose. interface Admin extends User { permissions: string[] } adds to a shape. type Admin = User & { permissions: string[] } does nearly the same via intersection [USE], the & operator, which means "has all the members of both." Intersections do something slightly strange with conflicting members — an intersection of { a: string } and { a: number } gives a: never, a type no value can have, rather than an error at the declaration — and that quiet never is a classic source of a confusing error message three files away.

What you can do at this point: name and reuse the shapes your real data has, and compose them.

What's still broken: real values are frequently one of several shapes — a response is success or failure, a field is a string or a number — and a single fixed shape cannot say that.

Node 4 — unions, literal types, and narrowing: where TypeScript stops resembling Java

The limitation: a value that could be one of several different things has no expressible type yet, and that describes most real data.

A union type [EXPLAIN] is written with | and means "one of these": string | number. This is where TypeScript diverges hard from the type systems it superficially resembles, and it's the feature that makes it able to describe JavaScript at all, because JavaScript code returns a value or null, takes a string or a number, and branches on what it got — constantly.

The immediate problem with a union is that you can barely use it. If x: string | number, you cannot call x.toUpperCase(), because it might be a number. A union only lets you do what is valid for every member. So a union is useless until you can prove which member you're holding — and proving that is narrowing [EXPLAIN], the single most important mechanism in day-to-day TypeScript.

Narrowing is TypeScript's control flow analysis: it reads your if statements and follows the program's branches, and inside a branch it knows more than it did outside. Write if (typeof x === "string") and inside that block x is a string — not by magic, but because tsc understands what typeof means and applies that knowledge to the branch. The narrowing devices [USE] are: typeof for primitives; instanceof for class instances; the in operator for "does this object have this property"; truthiness checks; equality against literal values; Array.isArray; and — crucially — the fact that narrowing survives across return, throw, and else, so an early return narrows the entire rest of the function.

To make narrowing powerful, you need types narrow enough to distinguish. That is what literal types [EXPLAIN] are for: "pending" is a type inhabited only by that exact string. On their own they're a curiosity. Unioned, they become the thing you'll use constantly: type Status = "pending" | "active" | "cancelled" — a set of allowed values, checked at compile time, with autocomplete, and with zero runtime cost. This is the answer to "why don't I need enums," and it's the reason experienced TypeScript teams use string unions where a Java programmer reaches for an enum.

Put literals inside object shapes and you get the pattern that carries most real TypeScript architecture: the discriminated union [EXPLAIN], also called a tagged union.

type Result =
  | { ok: true; data: User }
  | { ok: false; error: string };

Every member has a common property whose type is a distinct literal. Now if (r.ok) narrows the whole object — inside the branch, r.data exists and r.error does not, and TypeScript enforces that. This is how you model a fetch result, a form state, a job status, a websocket message, an AST node. If you learn one design idea from this topic, it's this one, and the interview question that goes with it is "how do you model a request that can succeed or fail without using exceptions."

The companion trick is exhaustiveness checking [EXPLAIN]. Switch on the discriminant, handle every case, and in the default branch assign the value to a variable of type never (Node 9). If you later add a fourth case to the union and forget to handle it here, that assignment fails to compile — the compiler now tells you every place that needs updating when the union grows. That is the closest TypeScript comes to the "change one thing, get a list of what else must change" experience that made static typing worth having in the first place.

One sharp edge worth knowing now [USE]: narrowing is forgotten when the compiler can't prove it still holds. Call any function in between, and a narrowed property on a mutable object goes back to its declared type, because that function might have reassigned it. TypeScript is conservative here on purpose. The usual fix is to copy the narrowed value into a const first.

What you can do at this point: model data that has alternatives, and write code the compiler can follow through its branches.

What's still broken: the most common alternative of all — "or nothing at all" — is still invisible. By default null and undefined slip into every type unchallenged.

Node 5 — strictness, and null as a type

The limitation: you modelled unions carefully, and TypeScript is still letting undefined through everywhere, because by default it doesn't consider it an error.

In TypeScript's original default configuration, null and undefined are assignable to every type. A string can be null. This existed because early TypeScript had to accept mountains of existing JavaScript, and treating null as an error would have flagged all of it.

strictNullChecks [EXPLAIN], introduced in TypeScript 2.0 (2016), removes that hole. With it on, null and undefined have their own types and are only allowed where you said so. string means a string. If it might be missing, you write string | null or string | undefined, and then — because it's a union — you cannot use it until you narrow. The compiler now points directly at the exact places the 2 a.m. undefined could occur, which is the single highest-value type-checking feature in the language. Tony Hoare called the null reference his "billion-dollar mistake"; this flag is the correction, and the interview version of this question is exactly that story.

Turning it on is also the single most disruptive thing you can do to an existing codebase, which is why it lives behind a flag and why adoption is often the multi-week project a team keeps postponing.

The ergonomics that make it livable are JavaScript features, not TypeScript ones, but TypeScript understands them precisely [USE]: optional chaining a?.b?.c returns undefined instead of throwing if anything in the chain is nullish, and the resulting type includes undefined; nullish coalescing x ?? fallback supplies a default only for null and undefined — importantly not for 0 or "", which is the entire reason it exists alongside ||.

strictNullChecks is one of a family. strict [EXPLAIN] is a single flag that turns on the whole set, and it is the correct default for any new project. The members worth knowing by name: noImplicitAny (a parameter whose type can't be inferred is an error rather than silently any — this is the second most valuable flag after null checks); strictFunctionTypes (parameter checking becomes contravariant, Node 6); strictBindCallApply; strictPropertyInitialization (a class field must actually get assigned); noImplicitThis; useUnknownInCatchVariables (a caught error is unknown, not any, because a JavaScript throw can throw literally anything). Adjacent and separately toggled: noUncheckedIndexedAccess [USE], which makes arr[0] have type T | undefined — technically correct, because arrays have holes and indices can be out of range, and genuinely annoying, which is why it's outside strict.

The thing to understand about all of these is what it means that they're flags at all: TypeScript's strictness is a dial, and "is this valid TypeScript" is not a well-formed question without knowing the config [EXPLAIN]. The same file can compile cleanly in one repo and produce forty errors in another. That's Node 13.

What you can do at this point: eliminate the entire class of null-reference crashes at compile time.

What's still broken: you've typed data thoroughly. Functions — the things that transform data, and the main thing you actually write — have only been typed casually so far.

Node 6 — functions, and the direction compatibility runs

The limitation: functions are values with their own rules of compatibility, and getting those rules wrong is how unsound code passes the checker.

A function type states parameters and return: (a: number, b: number) => number. Annotate parameters always; let the return type be inferred usually [USE], since inference keeps it honest as the body changes — with the exception of exported public API functions, where writing the return type explicitly stops an accidental change from silently altering your published contract, and dramatically improves error messages and compile speed.

Two inference behaviours to know. Contextual typing [EXPLAIN]: when a function is written in a place where its type is already known — a callback passed to .map, a handler assigned to a typed field — parameters get their types from that context, and you don't annotate. This is why users.map(u => u.name) needs no annotation on u, and why the same arrow function extracted to a standalone const suddenly errors with "implicitly has an any type." Second, optional and default parameters [USE]: b?: number makes the parameter number | undefined, b = 0 gives it a default and makes it optional at the call site while remaining number inside the body. Rest parameters ...args: number[] type the variadic tail.

Now the part that matters and that most people never learn properly: function compatibility runs in two directions at once [EXPLAIN].

Return types are covariant, which is the intuitive direction. A function returning Dog is usable where one returning Animal is expected, because every caller expecting an animal gets one.

Parameters are contravariant, which is the direction nobody guesses. A function accepting Animal is usable where one accepting Dog is expected — the more general function is the substitutable one, because it can handle everything the specific one could and more. The reverse is unsafe: a handler that only accepts dogs cannot stand in where any animal may arrive.

Then the exception that makes it confusing: TypeScript checks method parameters bivariantly — accepting both directions — deliberately and unsoundly, because array and DOM types in the real world depend on it. strictFunctionTypes restores correct contravariance for function-property syntax but leaves method syntax bivariant. So handler: (e: Event) => void and handler(e: Event): void are checked by different rules in the same interface. This is a real, documented hole, it's a favourite senior interview question, and the honest answer includes "TypeScript accepted some unsoundness to stay usable."

Two more mechanisms round out functions. Overloads [USE] let one function have several call signatures — several declarations, then one implementation whose signature must be compatible with all of them and is not itself callable. Overloads are how you type a function that returns different things based on argument count or shape. In modern TypeScript, a union or a generic often expresses the same thing more cleanly, so overloads are a tool of last resort. And typing this [AWARE] — a fake first parameter, function f(this: HTMLElement, e: Event), erased at compile time — exists because JavaScript's this is determined by call site, and TypeScript needs a way to state what the call site must be.

What you can do at this point: write and pass functions with confidence about what is substitutable for what.

What's still broken: collections. Lists of things are everywhere and you haven't typed one yet, and the way JavaScript uses arrays for both "many of the same" and "a fixed sequence of different" needs two answers.

Node 7 — arrays, tuples, and as const

The limitation: number[] is easy; [string, number] and "this array's contents are exactly these literals" are not, and both are load-bearing in real code.

An array type [USE] is T[] or equivalently Array<T> — identical, pick one and be consistent. Arrays are homogeneous by declaration, though (string | number)[] gets you mixed. TypeScript ships full types for every array method, so .map, .filter, .reduce all infer correctly, with two rough patches worth knowing [USE]: .filter(Boolean) does not remove null from the element type, because TypeScript can't see that Boolean narrows — you need a type predicate (Node 9); and .reduce frequently needs its accumulator type annotated explicitly because inference picks the type of the initial value, which is often too narrow.

A tuple [EXPLAIN] is a fixed-length array where each position has its own type: [string, number]. It's how you type useState's return, coordinate pairs, and destructured returns generally. Tuples support optional elements, rest elements ([string, ...number[]]), and labels ([x: number, y: number]) which exist purely to make editor hints readable. The critical caveat: tuple-ness is a compile-time claim only. At runtime it's an ordinary array, and nothing stops .push from making it longer — declare it readonly if you want the compiler to stop that.

as const [EXPLAIN] is the highest-value small feature in this node. Applied to a literal, it makes everything about it maximally narrow and deeply readonly: ["a", "b"] as const has type readonly ["a", "b"] rather than string[], and { mode: "dark" } as const gives mode the literal type "dark" rather than string. This is what lets you define a list of allowed values once as data and derive the union type from it (typeof arr[number], Node 10), rather than writing the same list twice and letting the copies drift. Any time you find yourself maintaining a runtime array and a matching type by hand, as const plus a derived type is the fix.

What you can do at this point: type collections precisely and derive types from real data instead of duplicating it.

What's still broken: everything so far is concrete. A function that takes an array and returns its first element works identically for every element type, and you currently have no way to say that without either lying with any or writing the same function once per type.

Node 8 — generics: types with parameters

The limitation: reusable code is used with types you don't know when you write it, and every tool you have so far forces you to commit to a specific one.

Write a function that returns the first element of an array. Type it (arr: any[]) => any and you've thrown away the answer — the caller gets any back and every downstream check evaporates. Type it (arr: string[]) => string and it only works for strings.

Generics [EXPLAIN] solve this by making the type a parameter: function first<T>(arr: T[]): T | undefined. T is a placeholder filled in per call site. Call it with string[] and it returns string | undefined; with User[] and it returns User | undefined. The relationship between input and output is preserved, which is exactly what any destroys. The mental model that makes generics stop being scary: a generic is a function that takes types as arguments and returns a type [EXPLAIN]. Same idea as a normal function, one level up.

In practice you almost never pass the type explicitly — TypeScript infers type arguments from the values you pass [USE]. first([1,2,3]) figures out T = number on its own. You only write first<number>(...) when inference can't get there or gets it wrong.

Generics get useful, rather than merely clever, with constraints [EXPLAIN]. Unconstrained T means "literally anything," so you can't do anything with it — you can't even read .length, because T might be a number. <T extends { length: number }> says "any type that at least has a length," and now you can read it while still returning the caller's precise type. Note that extends here does not mean inheritance; it means "is assignable to," which is the structural relation from Node 2. The most common constrained pattern in real code, and one you should be able to write cold: function get<T, K extends keyof T>(obj: T, key: K): T[K] — a fully type-safe property getter, which needs keyof and indexed access from Node 10.

Also useful: default type parameters [USE] (<T = string>), and generics on interfaces, type aliases, and classes, not just functions — interface Box<T> { value: T }, Map<string, User>, Promise<Response>. Every one of those you've already used without noticing.

Two rules of thumb worth keeping [USE]. First, a type parameter used in only one place is usually not doing anything — if T appears once, in one parameter, it could probably be a union or unknown; the value of a generic is in linking two positions. Second, generics do not exist at runtime. There is one function. T is gone. You cannot write new T() or check what T was.

What you can do at this point: write reusable code that preserves the caller's types instead of erasing them.

What's still broken: sometimes you genuinely don't know a type, or the type system genuinely can't see what you know. You need a way out — and the ways out are the most dangerous part of the language.

Node 9 — the escape hatches: any, unknown, never, and assertions

The limitation: external data arrives untyped, libraries lie, and sometimes you know something the compiler can't derive. Without a pressure valve, people abandon the language.

any [EXPLAIN] means "turn checking off for this value." Anything is assignable to it, it's assignable to anything, and every property access on it succeeds and yields any. It exists for the migration story — it's what an untyped JavaScript value becomes when it crosses into TypeScript.

The essential thing about any is that it is contagious [EXPLAIN]. One any propagates through every expression it touches: pass it to a generic and the type parameter becomes any, spread it into an object and the object's properties go soft. A single any in a hot path can silently disable checking across a whole module, which is why one any in a code review is worth more attention than twenty other issues, and why noImplicitAny exists to at least stop the compiler from inserting them for you.

unknown [EXPLAIN], added in TypeScript 3.0, is the correct alternative and one of the best small ideas in the language. unknown also accepts any value — but you can do nothing with it until you narrow it. It's the type-safe top type: "I don't know what this is, and the compiler will force me to find out before I use it." Every place you're tempted to write any for incoming data, unknown is the right answer, and knowing that difference cold is a reliable signal in interviews. It's also why useUnknownInCatchVariables matters: a caught value really is unknown, and pretending otherwise (err.message on an any) is how error handlers throw their own errors.

never [EXPLAIN] is the empty type — no value has it. It shows up in four places, and recognizing them is most of what "never" means in practice: as the return type of a function that never returns normally (it always throws or loops forever); as the type of a variable in a branch the compiler has proven unreachable, which is what makes exhaustiveness checking work (Node 4); as the result of an impossible intersection; and as the identity element of unions — string | never is just string, which becomes structurally important when filtering unions in Node 10. never is assignable to everything, and nothing is assignable to never, which is exactly backwards from any/unknown and worth being able to state.

Type assertions [EXPLAIN] — value as User — are you telling the compiler "trust me." No check happens, at compile time or runtime; it's a pure claim, and if you're wrong, you get exactly the crash TypeScript was supposed to prevent. Note it is not a cast: nothing converts, no code is emitted. TypeScript will refuse assertions between wildly unrelated types unless you launder through as unknown as X, and that double assertion is a loud signal that something upstream is wrong. The older angle-bracket syntax <User>value exists and is unusable in .tsx files because it collides with JSX. Also in this family: the non-null assertion x! [USE], which says "this isn't null, promise" and is the single most common source of runtime null errors in strict codebases — every ! is a place you overrode the exact check you turned on in Node 5.

Two safer relatives are worth learning at the same time, because they cover most legitimate uses of assertions. Type predicates [EXPLAIN] — a function returning x is User — are user-defined narrowing: the compiler trusts your boolean function and narrows accordingly, so the unsafe claim is written once, in one auditable place, instead of scattered as as at every use. Assertion functions [AWARE] — function assertIsUser(x: unknown): asserts x is User — do the same but narrow for the rest of the enclosing scope by throwing instead of returning false.

And finally satisfies [EXPLAIN], TypeScript 4.9 (2022), which fixes a long-standing annoyance. const config: Config = {...} checks the object but widens it to Config, losing the literal detail. const config = {...} satisfies Config checks it against Config and keeps the precise inferred type. It's the "validate without widening" operator, and it's the modern answer to a lot of code that used to reach for as.

What you can do at this point: handle values of unknown type safely, and know exactly which constructs are you turning the checker off.

What's still broken: you keep writing types by hand that are mechanically derived from other types — a version of User with all fields optional, a version with only some keys. Duplicating those by hand means they drift.

Node 10 — type-level programming: computing types from types

The limitation: types now duplicate each other. Change User and five hand-written variants of User silently go stale — the exact rot problem from Node 0, reintroduced at the type level.

TypeScript's answer is that the type system is itself a programming language [EXPLAIN] — a pure, functional, lazily-evaluated one, in which you compute new types from existing types. This is the part that looks like wizardry and is actually five composable operators.

keyof gives the union of a type's keys: keyof User is "name" | "email". typeof (in type position — a different operator from the JavaScript one, despite the shared spelling) lifts a value's inferred type into type space: typeof config. Together they're how you derive types from real data rather than declaring both: define the object with as const, then typeof obj[keyof typeof obj] gives you the union of its values.

Indexed access reads a property's type: User["email"] is string. T[number] on an array or tuple gives the element type — that's the idiom behind deriving a union from an as const array.

Mapped types [EXPLAIN] transform every member of a shape: { [K in keyof T]: ... }, with modifiers to add or remove ? and readonly (-? removes optionality, -readonly removes immutability). This is the machinery behind the utility types you'll actually use daily [USE]: Partial<T> (all optional), Required<T>, Readonly<T>, Pick<T, K> (keep some keys), Omit<T, K> (drop some), Record<K, V> (build a dictionary type), plus ReturnType<F>, Parameters<F>, Awaited<T> (unwrap a promise), NonNullable<T>, Exclude/Extract. Every one of these is a few lines of TypeScript in the standard library, and being able to write Pick and Omit from scratch is a common senior screening exercise — the point being that they're not built-in magic.

Conditional types [EXPLAIN] are the if of type space: T extends U ? X : Y, where extends again means assignability. Two behaviours make them powerful and confusing. Distribution: a conditional over a naked type parameter applies to each union member separately and re-unions the results, which is how Exclude<T, U> filters a union — members that match become never, and never vanishes from unions (Node 9). Wrapping in a tuple ([T] extends [U]) suppresses distribution, which you'll need the first time it surprises you. And infer [EXPLAIN], which declares a type variable to be captured by pattern-matching: T extends Promise<infer U> ? U : T extracts what a promise resolves to. infer is how ReturnType, Parameters, and Awaited are written.

Template literal types [USE], from TypeScript 4.1, do string manipulation in type space: ` on${Capitalize<K & string>} turns "click" into "onClick". Combined with mapped-type key remapping (as` inside a mapped type), this is how libraries type things like event-handler props and route parameter objects derived from a path string.

Recursion [AWARE] is allowed, with a depth limit, which is how DeepPartial<T> and JSON-path types are written. It's also where compile times go to die (Node 18).

Two things to hold onto through all of this. First, it is all still erased — none of this produces runtime code; it's an elaborate way of arranging compile-time checks. Second, this is where a codebase gets unmaintainable if you let it. The correct default is: use the built-in utilities freely, write a simple mapped or conditional type when it removes real duplication, and treat anything requiring a comment to explain as a design smell. A clever type that nobody on the team can modify is a liability, and being able to say that in an interview is a better answer than showing off a recursive conditional.

What you can do at this point: derive types mechanically so that one source of truth stays the only source of truth.

What's still broken: none of this addresses classes — and you'll meet classes constantly in Node backends, in DI-style frameworks, in error hierarchies, and in older code.

Node 11 — classes, enums, and the runtime-shaped features

The limitation: everything so far is erased. Classes are real runtime objects, and TypeScript's class layer adds features that are not purely erasable — which makes them a different category and a source of controversy.

TypeScript's class syntax is JavaScript's class syntax plus type annotations, plus a handful of extras. Access modifiers [USE] — public, private, protected — are compile-time only; a private field is fully accessible at runtime and visible in JSON.stringify. JavaScript later grew its own #private fields, which are enforced at runtime, so the two coexist and mean genuinely different things. readonly on fields, implements (which checks structural compatibility without creating a nominal relationship), and abstract classes and members round out the shape.

Parameter properties [USE] — constructor(private name: string) — declare and assign a field in one stroke. Purely a TypeScript convenience; it emits an assignment. This is the syntax that makes NestJS-style dependency injection concise, and it's the first hint that some of this layer is not erasable.

Enums [EXPLAIN] are the clearest example. enum Status { Active, Cancelled } emits an object into your JavaScript — it exists at runtime, which no other type-level construct does. Numeric enums also have a genuinely unsafe hole: for historical reasons, any number is assignable to a numeric enum type in many positions, and reverse mappings mean Status[0] gives back "Active". The modern consensus is to prefer a union of string literals plus as const objects, and TypeScript 5.0 added const type parameters and 5.8's erasableSyntaxOnly explicitly targets this: enums, parameter properties, and namespaces are the constructs that can't be stripped, which makes them incompatible with the type-stripping runtimes of Node 19. Being able to explain why enums are discouraged — "they're the one type-level feature that emits runtime code, and the numeric ones are unsound" — is a strong interview answer.

Namespaces [AWARE] are TypeScript's pre-ES-modules module system. Legacy. You will meet them in old code and in .d.ts files; you should not write new ones. Decorators [AWARE] — @Injectable(), @Column() — are how Angular, NestJS, and TypeORM work; TypeScript had an experimental version behind experimentalDecorators for a decade, and TypeScript 5.0 shipped the standardized ECMAScript version, which is not fully compatible with the old one. If you touch a Nest or TypeORM codebase, know which flavour it's on.

What you can do at this point: read and write the class-based code you'll meet in real backends, and explain which parts of TypeScript are and aren't erasable.

What's still broken: every file so far has been alone. Real programs are many files plus hundreds of npm packages, most of which were written in JavaScript with no types at all.

Node 12 — modules, declaration files, and how JavaScript packages get types

The limitation: you can't type a codebase one file at a time and you can't type the ecosystem at all, unless types can cross file and package boundaries.

TypeScript uses ES modules — import/export — and adds one important distinction: types can be imported and exported like values, but they vanish at compile time [EXPLAIN]. import type { User } from "./types" states that this import is types only, so the emitted JavaScript drops it entirely. This matters more than it sounds: an ordinary import that only happened to be used for types still emits a require/import in some configurations, dragging a module into the bundle for nothing, and in others gets elided in a way that breaks decorators or side-effecting imports. verbatimModuleSyntax [USE] resolves the ambiguity by keeping exactly what you wrote and requiring import type where you mean types.

The mechanism that lets TypeScript describe code it didn't compile is the declaration file [EXPLAIN], .d.ts — types with no implementation. Declarations, no bodies. It's the header file idea: a description of an interface that some JavaScript elsewhere provides. tsc generates them from your source with declaration: true, which is how a published library ships types for consumers who don't see your source.

That gives three ways a package gets types [USE], and diagnosing "why doesn't my editor know about this library" is exactly the ability to check them in order. Bundled — the package ships its own .d.ts and points at it via types/typings in package.json, or via the modern exports map with a types condition; this is the norm for anything written in TypeScript. DefinitelyTyped — a colossal community repo of types for JavaScript-only packages, published as @types/<name>, which is why you npm i -D @types/node and @types/express; note that these are written by volunteers, are versioned separately from the library, and can be wrong or stale, which is a real and underappreciated source of "the types say this works and it doesn't." Nothing — you write your own .d.ts, or declare the module as any to silence the error.

declare [USE] is the keyword for "this exists, I'm not defining it": declare global, declare module, ambient declarations for globals injected by a script tag or a bundler. It's how you type process.env, window.myThing, or an import of a .css file.

Then the part that eats days: module resolution [EXPLAIN]. TypeScript has to find what a specifier like "./utils" or "zod" refers to, and the algorithm has evolved through several incompatible eras — node (classic CommonJS lookup), node16/nodenext (respects package.json type and exports, and requires file extensions in relative ESM imports), and bundler (added in TS 5.0, for the very common case where a bundler resolves, not Node). Mismatched settings here are the source of the whole family of "cannot find module or its type declarations," "the default export isn't callable," and esModuleInterop/allowSyntheticDefaultImports errors — all of which trace to the fundamental awkwardness that CommonJS and ES modules have genuinely different semantics and TypeScript has to describe both, plus the interop layer between them.

What you can do at this point: wire types across your own files and across the npm ecosystem, and debug the errors that arise when they don't line up.

What's still broken: you've been saying "with this flag on" for six nodes. The flags themselves are now the thing you don't understand.

Node 13 — tsconfig.json: the file that defines what your TypeScript even is

The limitation: TypeScript's behaviour is configuration-dependent to a degree that makes "does this compile" unanswerable without seeing the config.

tsconfig.json [EXPLAIN] does three jobs at once, and separating them makes it far less intimidating: it says which files are in the project, what checking rules apply, and what output to produce.

Which files: include, exclude, files, and the fact that anything imported by an included file is pulled in whether you listed it or not.

What checking: the strict family from Node 5, plus the linting-adjacent flags noUnusedLocals, noUnusedParameters, noImplicitReturns, noFallthroughCasesInSwitch, exactOptionalPropertyTypes, and noUncheckedIndexedAccess.

What output, and this is where the real confusion lives [USE]:

target — which JavaScript version to emit. ES2022 is a sane modern default. Setting it lower makes TypeScript downlevel newer syntax (async/await into state machines, for example), which produces bigger, slower, harder-to-debug output. It does not add missing runtime APIs — no polyfills, ever. lib — which built-in API declarations to include (DOM for browser globals, ES2023 for newer standard library methods). This is why Array.prototype.at errors in one project and works in another. module and moduleResolution — the emit format and the lookup algorithm from Node 12, which should agree with each other and with reality. outDir, rootDir, sourceMap (so stack traces and the debugger point at your .ts, not the emitted .js), declaration, declarationMap. paths and baseUrl for import aliases like @/lib/db — with the sharp edge that paths only teaches the type-checker, not the runtime, so a bundler alias or a runtime resolver must be configured to match or you get a module that type-checks and crashes on start. isolatedModules [USE], which forbids constructs that can't be understood one file at a time — required by every transpile-only tool, because esbuild and swc compile each file in isolation and never see your types.

Two structural features worth knowing [AWARE]: extends, for sharing a base config (the @tsconfig/* published bases are a good starting point), and project references with composite, which split a monorepo into separately-buildable units so you don't recheck everything on every change.

The mental model that makes this node stick: tsconfig.json is not settings, it's the definition of the language dialect this repo speaks. That's why the first thing to read in an unfamiliar TypeScript codebase is its tsconfig, and why "the same code, different config, different errors" is expected rather than surprising.

What you can do at this point: read a config and predict how the project behaves, and diagnose config-caused errors rather than fighting them.

What's still broken: tsc is slow, and nothing in production actually runs it the way you've been imagining.

Node 14 — the build story: why almost nobody compiles with tsc

The limitation: tsc does two jobs — checking and emitting — and type-checking is inherently slow, which makes it a bad fit for the edit-save-reload loop.

Type-checking a large project means building a graph of every type in your code and every type in your dependencies, and it takes seconds to minutes. Stripping types, by contrast, is nearly free — types are syntax, and deleting syntax is fast.

So the ecosystem split the two jobs [EXPLAIN], and this is the single most useful thing to understand about running TypeScript in practice. Fast tools — esbuild (Go), swc (Rust), and the wrappers around them (tsx, Vite, Bun, modern ts-node modes) — do transpile-only: they delete the types and emit JavaScript in milliseconds, and they do not check anything at all. Meanwhile tsc --noEmit runs separately, in your editor continuously and in CI as a gate.

The consequence, which trips up everyone at least once: your dev server will happily run code that has type errors. The errors show in the editor, not the terminal. If CI is missing the tsc --noEmit step, broken types reach main and nobody notices. So the correct project setup is: a fast transpiler for running, tsc --noEmit in CI and as a pre-commit or pre-push check, and — if you publish a library — a real tsc build with declaration: true for the .d.ts files, because only tsc can generate those.

Because transpilers see one file at a time, isolatedModules matters here [USE]: re-exporting a type without export type is fine for tsc and ambiguous for esbuild, which is why modern configs require the explicit form.

Also in this node: source maps [USE], which map emitted JavaScript back to your TypeScript so stack traces and breakpoints land on the lines you wrote — sourceMap plus, in Node, either --enable-source-maps or the source-map-support package, without which every production stack trace points at meaningless compiled line numbers. And watch/incremental builds (tsc --watch, incremental: true with its .tsbuildinfo cache) as the reason a second build is much faster than the first.

What you can do at this point: set up a project that runs fast and is actually checked, and know which tool is responsible when something goes wrong.

What's still broken: every guarantee you've built is a compile-time guarantee, and your program's most dangerous data arrives at runtime from outside it.

Node 15 — the runtime boundary: where types stop being true

The limitation: erasure (Node 2) means that at the exact moment data enters your program — from a network request, a database, a config file, a form — TypeScript has no way to check anything, and yet that's the moment you most need it checked.

This is the most important node in the chain for backend work, and it's where a lot of otherwise-competent TypeScript developers have a hole.

Consider const user: User = await res.json(). It compiles. res.json() returns Promise<any>, and any is assignable to User, so the annotation is accepted without a whisper. But nothing checked anything. If the API changed last Tuesday and now sends email_address, your user.email is undefined and you are back in Node 0 — with the added insult that the type annotation gave you false confidence and made the bug harder to suspect. A type annotation on external data is a lie until something validates it [EXPLAIN]. That sentence is worth memorizing verbatim; it's the answer to a very common interview question, and it's the reason zod exists.

There are three honest ways across the boundary [USE].

Hand-written type predicates (Node 9) — a function returning x is User that actually inspects the value. Correct, explicit, and tedious, and the tedium is why it silently degrades: nobody updates the predicate when the type changes, because nothing forces them to.

Schema validation libraries — Zod above all, and Valibot, ArkType, io-ts, and the older JSON Schema route (Ajv, and Fastify's built-in schema validation). The move that makes Zod feel inevitable is that you define the schema once as a runtime value, and derive the static type from it with z.infer<typeof schema>. One source of truth, validated at runtime, typed at compile time, and they cannot drift because one is computed from the other. That inversion — the runtime artifact is primary, the type is derived — is the whole idea, and it's the direct answer to why you can't just use an interface. It's also your own request-validation-zod topic, sitting one step downstream of this node.

Generated types — when the data source can describe itself, generate the types from it: OpenAPI specs, GraphQL schemas, Prisma or Drizzle schemas, protobuf. Generation gives you compile-time safety with no runtime cost, but only guarantees agreement at generation time, so a stale generated file is its own failure mode.

The rule that follows from all this: validate at the edges, trust in the interior [EXPLAIN]. Parse and validate everything at the boundary — HTTP handlers, queue consumers, process.env, file reads, third-party API responses, LLM tool-call arguments — and once past that boundary, work with typed values and no defensive checks. Both halves matter. Validating everywhere is noise; validating nowhere is Node 0.

Worth naming specifically because it's ubiquitous and universally done badly: process.env is typed Record<string, string | undefined>, so every environment variable is possibly undefined and always a string. Parsing the whole environment through a schema at startup — so the process refuses to boot with a bad config rather than failing at 3 a.m. on the one code path that reads it — is a small change with a large payoff, and it's a good thing to have an opinion about in an interview.

What you can do at this point: draw a defensible line between the untyped world and the typed one, and explain why annotations alone don't cross it.

What's still broken: you can validate one boundary by hand. A real application has many — database, HTTP, queue, client — and re-declaring the same shapes at each is exactly the duplication Node 10 tried to kill.

Node 16 — types across the whole system

The limitation: the same User now exists in a database schema, a query result, an API response type, and a frontend fetch. Four hand-written copies is four chances to drift.

The goal is one definition, with everything else derived — end-to-end type inference [EXPLAIN] — and this is where TypeScript stops being a language feature and starts being an architecture.

At the database, Drizzle (which you already use in qbank) defines tables as TypeScript values and derives row types from them, so typeof users.$inferSelect is the row type — change a column and every consumer of that type breaks at compile time. Prisma does the same via a code-generation step instead. Either way the schema is the single source of truth and the types are computed, which is Node 10's principle applied at system scale.

At the HTTP layer, Fastify's type providers [USE] connect a route's Zod or JSON schema to the types of request.body and the reply, so declaring the schema types the handler — validation and typing from one declaration, which is Node 15 and Node 10 meeting. Express, by contrast, types request bodies as any by default, which is why Express codebases so often have a validated-but-untyped middle layer.

Across the client/server boundary, tRPC [AWARE] shares types directly by importing the server's router type into the client — no code generation, no schema file, full autocomplete on the client for server procedures, at the cost of requiring one TypeScript codebase on both sides. OpenAPI generation is the equivalent for a system where the client isn't yours.

And in your applied-AI work, the same principle runs one step further: an LLM tool definition is a JSON Schema the model must produce arguments for, and the arguments arriving back are untrusted external data in exactly the Node 15 sense. Deriving the schema and the argument type from one Zod definition — and validating what comes back before using it — is the same pattern one more time. That's the direct line from this node to qbank's forced tool use and to your MCP server.

The thing to take from this node is the pattern rather than the libraries: pick one artifact as the source of truth and derive every other representation from it, mechanically. Everything else in a large TypeScript system's type story is an instance of that.

What you can do at this point: design a system where one change propagates to every place that must change, and the compiler produces the list.

What's still broken: deriving types from libraries works until you need to add to a library's types — a property you attach to a request object, a global you inject.

Node 17 — declaration merging and module augmentation

The limitation: you attach request.user in an authentication hook, and TypeScript says Property 'user' does not exist on type 'FastifyRequest' — a type you don't own and can't edit.

TypeScript's answer is that interfaces merge [EXPLAIN] — the property from Node 3 that looked like a quirk. Two declarations of the same interface in the same scope combine into one. Applied across module boundaries, this is module augmentation [USE]:

declare module "fastify" {
  interface FastifyRequest { user?: AuthUser }
}

You have added a member to a type inside someone else's package, from your own code, and every use site now knows about it. This is precisely how Fastify plugins, Express middleware (Express.Request), Next.js, and Vitest's expect extensions all work, and how you'd type a decorate call on a Fastify instance. declare global [USE] does the same for globals — extending Window, or typing process.env with your specific variable names.

Two rules that save real time [USE]: the augmentation must be inside a module (a file with at least one import or export), or declare module means "declare a whole new ambient module" instead of augmenting an existing one — a genuinely confusing failure where your augmentation silently becomes a stub declaration for a package that already exists. And the file has to actually be included in the project, which is why augmentations placed in files nothing imports appear to do nothing.

The other side of the coin: augmentation is global and unconditional. Adding user?: AuthUser to FastifyRequest adds it everywhere, including routes with no authentication, and the ? is doing real work — without it you'd be claiming every request has a user, which is exactly the kind of false confidence Node 15 warns about.

What you can do at this point: extend third-party types safely, which is a prerequisite for real plugin-based backend work.

What's still broken: the type system is now doing a lot of computation on your behalf, and computation costs time. Sooner or later the editor starts lagging and the build takes four minutes.

Node 18 — when the type system becomes the problem

The limitation: every mechanism from Node 8, 10, and 16 makes the compiler do more work, and the work compounds.

Type-checking is not free, and TypeScript's checker is essentially a lazy evaluator over a graph of types [AWARE]. Three things dominate real-world slowness. Large unions and their combinations — an intersection or a conditional over a 200-member union can produce enormous intermediate types. Deep recursive conditional types, which have a hard instantiation-depth limit and produce the famous Type instantiation is excessively deep and possibly infinite — usually a signal to stop, not to optimize. And inferred return types on exported functions, where the checker must reconstruct a possibly enormous type at every use site; explicitly annotating the return type of exported functions is the single highest-leverage compile-speed fix, and it's why library authors do it.

The tooling [AWARE]: tsc --diagnostics and --extendedDiagnostics for where time goes, --generateTrace for a profile you can open in a trace viewer, incremental and project references for avoiding repeat work, and skipLibCheck: true — which skips checking .d.ts files in node_modules and is on in nearly every real config, because checking other people's declarations is slow and their errors aren't yours to fix.

The judgment this node exists to install: a type is only worth what it prevents. A clever recursive type that catches a bug nobody was going to write, at the cost of a four-minute build and an unreadable error message, is a net loss. The senior version of TypeScript skill is not writing the most elaborate types; it's knowing which guarantees are worth their cost, keeping error messages legible, and being willing to write unknown plus a runtime check where the type-level version would be a monster. That's also the answer to "have you ever regretted a TypeScript decision," which is a question you will be asked.

What you can do at this point: diagnose a slow project and make a defensible call about how much type machinery is worth it.

What's still broken: everything above describes TypeScript as it is now, and the ground is moving under two of these nodes specifically.

Node 19 — where the language is going, and what that changes

The limitation: the build story (Node 14) and the erasability question (Node 11) are both actively changing, and answering an interview question with a 2021 model of them will date you.

Three shifts are live as of 2026, and it's worth being honest that some of it is still settling.

Runtimes are learning to strip types themselves. Node added --experimental-strip-types in Node 22, made type stripping on by default in Node 23, and it is unflagged in current versions; Deno and Bun run TypeScript directly. The consequence: for a growing class of projects there is no build step at all, and tsc --noEmit is purely a checker. The catch — and this is the part to actually understand — is that stripping only works on erasable syntax, so enums, parameter properties, and namespaces are excluded, which is why TypeScript 5.8 added erasableSyntaxOnly [USE] to enforce that. This is the practical reason to prefer literal unions over enums going forward: it's not style, it's compatibility with how code will be run.

The compiler is being rewritten in Go. Microsoft announced the native port in 2025, targeting roughly ten-times-faster type-checking and much better editor responsiveness, shipping as TypeScript 7 with the existing JavaScript compiler continuing as 6.x during the transition. If it lands as advertised, Node 18's whole cost calculus loosens — but treat it as in-progress rather than done.

The language keeps adding, in the same additive way JavaScript does. Worth knowing by name [AWARE]: satisfies (4.9), const type parameters (5.0), standard decorators (5.0), using and explicit resource management (5.2), NoInfer (5.4), and the ongoing steady improvement of narrowing and inference — TypeScript gets smarter between versions, meaning code that needed an assertion two years ago may not need one now.

And one structural fact to close on, because it explains the whole topic's texture: TypeScript's type system is deliberately unsound [EXPLAIN]. There are known holes — bivariant method parameters (Node 6), assertions (Node 9), any, unchecked index access, mutable array covariance. Every one is a conscious trade: the alternative was rejecting real JavaScript that works fine. TypeScript's design goal was never "prove the program correct"; it was catch the most bugs possible while staying usable on the code people actually write. Knowing that — and being able to name three holes and why they exist — is the difference between someone who uses TypeScript and someone who understands it.

Where the chain gets misread

"TypeScript is a different language from JavaScript." It's JavaScript plus a checked, erased annotation layer. Every valid JavaScript file is valid TypeScript (given loose enough settings). Node 1.

"Types exist at runtime — I can check if something is a User." They're deleted at compile time. No runtime type information exists, which is the whole reason for Zod, type predicates, and unknown. Node 2, Node 15.

"interface is for objects, type is for primitives, and they're deeply different." They're near-interchangeable for object shapes. The differences that matter are that interfaces merge (which enables augmentation) and type aliases can express unions and computed types. Node 3, Node 17.

"If it compiles, it's correct." Compiling proves the claims you wrote are internally consistent. It proves nothing about data from outside, and nothing about logic. Node 15.

"any and unknown are basically the same." Opposites in the way that matters: any disables checking and spreads; unknown preserves it and forces you to narrow. Node 9.

"A type annotation on res.json() validates the response." It's an unchecked claim over an any. Nothing was verified. Node 15.

"Generics make the code work for many types at runtime." Generics are entirely compile-time. There's one function at runtime and T is gone — no new T(), no runtime specialization. Node 8, Node 2.

"Compiling with tsc is how TypeScript projects run." Most run a transpile-only tool that never checks types, with tsc --noEmit as a separate gate. This is why your dev server runs code with type errors in it. Node 14.

"private protects the field." Compile-time only, fully readable at runtime. JavaScript's #private is the enforced one. Node 11.

"Enums are the TypeScript way to express a set of values." Enums emit runtime code, numeric ones are unsound, and they're not erasable — so they're incompatible with type-stripping runtimes. Prefer string literal unions. Node 11, Node 19.

"extends in a generic constraint means class inheritance." It means "is assignable to," the structural relation. Same keyword, unrelated meaning. Node 8, Node 2.

"The compiler forgot my narrowing — that's a bug." It's deliberate conservatism: a function call in between could have mutated the property, so the narrowing can no longer be proven. Copy to a const. Node 4.

"Setting target: ES5 makes my code run on old browsers." It downlevels syntax, not APIs. No polyfills are added, so Promise and Map are still missing. Node 13.

"More elaborate types are better types." A type is worth what it prevents, minus what it costs in build time and readability. Node 18.

The chain in one paragraph

JavaScript records nothing about what a value is, so mistakes surface at runtime, editors can't help, refactors are unsafe, and docs rot — so TypeScript adds annotations checked by tsc before the program runs, and infers most of them so you only annotate at the edges. Compatibility is decided structurally (shape, not name) and the annotations are erased at compile time, and those two facts explain everything downstream. Shapes get named with interfaces and type aliases; alternatives get expressed as unions, which are useless until narrowing proves which member you hold, and the pattern that makes this practical is the discriminated union with exhaustiveness checking. strictNullChecks — and the strict family generally — makes "or nothing" explicit and kills the null-crash class, at the price of TypeScript's behaviour becoming config-dependent. Functions add contravariant parameters, covariant returns, and a deliberately bivariant method hole; generics carry the caller's type through reusable code, with constraints making them usable; any, unknown, never, assertions and satisfies are the escape hatches, and knowing which of them keeps checking on is the real skill. Type-level programming — keyof, mapped, conditional, infer, template literals — lets you compute types from types so a single source of truth stays single. Classes and enums are the non-erasable corner. Modules and .d.ts files carry types across files and into the npm ecosystem via bundled types or DefinitelyTyped, and tsconfig.json defines the dialect the repo speaks — which is why real builds split a fast transpiler that checks nothing from a separate tsc --noEmit gate. All of it stops at the runtime boundary, where erasure means external data is unchecked and an annotation is a lie until something validates it — so you parse at the edges with Zod or generated types, and derive every representation across database, HTTP, and client from one artifact, augmenting third-party types where you must. Finally, all of this costs compile time, so a type is worth what it prevents; and the system is deliberately unsound, because TypeScript's goal was never proof — it was catching the most bugs possible on the code people actually write.
