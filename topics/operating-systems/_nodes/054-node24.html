Node 24 — filesystems, journaling, and the one a Docker image is made of

The limitation: a block device is a numbered array of blocks; files and directories are not.

What a filesystem has to lay out

Any filesystem divides the device into: a superblock holding global metadata (size, block size, where everything else is, and a clean/dirty flag); allocation structures recording which blocks and inodes are free; the inode table from Node 21; and the data blocks themselves.

The interesting design question is how an inode points at its data. The classic Unix scheme used direct pointers for the first few blocks plus single, double and triple indirect blocks — so a small file needs one lookup and a huge file needs four, with the cost paid only by files large enough to justify it. Modern filesystems use extents instead: a start block and a length, so a contiguous 1 GB file is described by a handful of records rather than 262,144 pointers. That change alone is a large part of why ext4 outperforms ext3 on big files.

Crash consistency: the actual hard problem

Creating a file requires several separate writes: allocate an inode, write the inode, allocate data blocks, write the data, add the directory entry, update the free maps. A crash between any two leaves the filesystem inconsistent — an inode marked in use with no directory entry pointing at it (a leaked file), or a directory entry pointing at an inode that was never initialised (which is worse, since it may contain another file's old data).

The old answer was fsck: on boot after an unclean shutdown, scan the entire filesystem and repair it. On a multi-terabyte filesystem that is hours, during which the machine is down. Unacceptable for a server.

Journaling is the answer, and it is Node 23's write-ahead log applied to filesystem metadata. Before performing a group of related updates, write a description of them to a dedicated journal area and flush it. Then perform the real updates. Then mark the journal entry complete. After a crash, replay any entries that were written but not marked complete — bounded work, seconds rather than hours. [EXPLAIN]

ext4 offers three modes, and the middle one being the default explains a behaviour people find surprising:

  • data=journal — data and metadata go through the journal. Safest, and everything is written twice.
  • data=ordered (the default) — only metadata is journaled, but data blocks are forced to disk before the metadata that references them. So you never see a file whose metadata points at blocks containing another file's old contents. You can still lose recent data.
  • data=writeback — metadata journaled, no ordering. Fastest, and after a crash a file can contain arbitrary stale bytes.

Because ext4 journals metadata rather than data, a crash can leave a file that exists, has the right size, and is full of zeros. That is not a bug; it is the documented consequence of data=ordered with delayed allocation, and it is why applications that care must fsync — and must fsync the directory too, after a rename, or the rename itself may not be durable. The rename idiom from Node 21 is atomic with respect to readers and is not automatically durable with respect to power loss; a correct safe-write is: write temp, fsync temp, rename, fsync the directory.

The filesystems you will meet

  • ext4 (2008) — the Linux default. Journaled, extent-based, dull and reliable. The correct choice unless you have a reason.
  • XFS (SGI, 1993; Linux since 2001) — excellent at large files and high parallelism; the default on Red Hat. Cannot be shrunk.
  • btrfs and ZFS — copy-on-write filesystems (Node 14's pattern at block level) with built-in snapshots, checksums on all data, and volume management. ZFS is the more mature and its licence keeps it out of the Linux kernel tree.
  • tmpfs — a filesystem in RAM, backed by the page cache and swap. This is what /dev/shm and much of /run are, what Docker's --tmpfs and Kubernetes' emptyDir: {medium: Memory} give you, and — importantly — its contents count against your cgroup memory limit (Node 13). A build that writes a few gigabytes into a memory-backed emptyDir will be OOMKilled, and the reason is not obvious from the error.
  • Network filesystems — NFS, SMB, and cloud file services. They break assumptions that local filesystems satisfy: locking is advisory and unreliable, fsync semantics vary, latency is milliseconds, and a server that stops responding puts your process into the D state from Node 5, unkillable. Never put a database on NFS, and be careful about putting anything latency-sensitive there.
  • FUSE — filesystems implemented in user space. s3fs, sshfs, and many container and cloud tools use it. Every operation is a round trip to a user process, so it is slow, and it is why "mount S3 as a filesystem" is always a worse idea than it sounds.

overlayfs, and therefore Docker

A union filesystem presents several directory trees merged into one. overlayfs, in the Linux kernel since 3.18 (2014), is the one Docker uses. It takes some read-only lower directories and one writable upper directory and presents a merged view:

  • Reading a path searches the upper layer first, then each lower layer in order, and returns the first hit.
  • Writing to a file that exists only in a lower layer triggers a copy-up: the entire file is copied into the upper layer, then modified. Copy-on-write at file granularity (Node 14).
  • Deleting a lower-layer file cannot actually delete it, so a whiteout marker is created in the upper layer to hide it.

This is what a Docker image is. [EXPLAIN] Each instruction in a Dockerfile that changes the filesystem produces one layer — a directory of the differences. A running container adds one writable upper layer. Every property of Docker images that you have learned as a rule falls out of this mechanism:

  • Layers are shared. Ten containers from one image share one set of lower directories, so ten containers cost one copy of the image plus ten small upper layers. This is also why the same base image across many services is a genuine and large saving.
  • The writable layer is ephemeral — it is a directory on the host that is deleted when the container is removed. Hence volumes.
  • Deleting a file does not shrink the image. RUN apt-get install ... && rm -rf /var/lib/apt/lists/* in one instruction removes the files before the layer is finalised. Split across two instructions, the first layer still contains them and the second only adds whiteouts — the image is larger, and the deleted secret is still extractable from the layer. This is the single most common way credentials leak from container images, and it is why multi-stage builds and --secret mounts exist.
  • Layer ordering is a caching decision. A layer's cache is invalidated when its instruction or its inputs change, and every layer after it is then rebuilt. So COPY package*.json ./ then RUN npm ci then COPY . . is not a style convention: it puts the slow, rarely-invalidated step above the fast, always-invalidated one. Reversing them means reinstalling dependencies on every source change.
  • Write-heavy workloads are slow on the overlay. The first write to any file pays a full copy-up, which for a large file is a full copy. This is the mechanical reason databases need volumes, and why heavy build work inside a container benefits from a mounted cache.
  • docker commit and image bloat. Because layers are additive, an image's size is the sum of its layers regardless of what the final view contains.

Where this is in your stack

Docker Desktop's bind-mount slowness on macOS and Windows is a filesystem boundary. Linux containers there run inside a virtual machine (Node 29), so a bind mount from the host crosses from the host's filesystem into the VM through a network-style protocol — originally osxfs, then gRPC-FUSE, now VirtioFS, each faster than the last but none free. Every stat crosses that boundary, and a tool that stats a hundred thousand files — which is exactly what a bundler or a test runner does on node_modules — becomes an order of magnitude slower. The standard fix is to keep node_modules inside the container as a named volume rather than bind-mounted from the host, which now has a mechanical explanation rather than being folklore. Running the whole workflow inside WSL2's own filesystem, rather than under /mnt/c, is the same fix on Windows and makes an enormous difference.

Case sensitivity is a filesystem property and it breaks CI. macOS's APFS is case-insensitive by default; ext4 is case-sensitive. import Button from './button' works on a Mac and fails in a Linux container with Cannot find module. This is one of the most common "works on my machine" failures in JavaScript projects and its cause is one line of this node.

Timestamps and reproducible builds. Filesystem mtime values end up in archives and image layers, so identical inputs produce different layer hashes and the cache misses. This is why reproducible-build tooling normalises timestamps and why SOURCE_DATE_EPOCH exists.
