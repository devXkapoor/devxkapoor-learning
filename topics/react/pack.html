React

From hand-writing every DOM transition to describing the screen as a function of data — reconciliation, hooks, effects, identity, concurrency, and server components, as one causal chain.

Read this top to bottom. Each node exists because the node before it left something specifically broken, and each node ends by naming what is still broken — which is the next node's entire reason for existing. Nothing here is introduced because "React has this feature." Everything is introduced because the previous step hurt.

Three depth markers appear inline, attached to specific capabilities. [EXPLAIN] — you should be able to explain this from first principles, out loud, with no notes, while someone interrupts you. [USE] — you should be able to use it correctly and debug it when it breaks; you do not need the internals cold. [AWARE] — you should know it exists, what problem it solves, and roughly when someone reaches for it.

Node 0 — The problem before React: keeping the screen in sync by hand

Before any framework, a web page is a document that the browser has already turned into a tree of objects. You can reach into that tree from JavaScript and change it: find an element, set its text, add a class, remove a node, attach a click handler. That is the DOM, and everything React does eventually turns back into exactly those operations. React is not an alternative to the DOM. It is a way of deciding which of those operations to run.

So imagine building a task list without a framework. You have an array of tasks in a JavaScript variable, and you have a <ul> on the page. When the page loads, you loop over the array and build one <li> per task and append them. Now the screen and the array agree.

Then someone adds a task. You now have two jobs, not one: push onto the array, and create an <li> and append it. Then someone marks a task complete. Three jobs: flip the boolean in the array, add a completed class to the right <li>, and update the "3 of 7 done" counter somewhere else on the page. Then someone deletes a task. Now you must find the correct <li> — which means you had to have stored a reference to it, or given it an id you can query by — remove it, splice the array, update the counter again, and if the list is now empty, show the "no tasks yet" message that was hidden. Then a filter gets added — "show only incomplete" — and now every one of those operations has to ask whether the changed task is even supposed to be visible under the current filter.

The number of things in the app grew by one each time. The number of update paths you had to write grew much faster, because every pair of (thing that can change, part of the screen that depends on it) is its own code path. Ten pieces of state and fifteen pieces of screen do not give you twenty-five lines of code; they give you a web of hand-written transitions, each of which you had to remember to write.

And there is a worse problem hiding underneath. Some of your application's truth ends up living only in the DOM. Whether a task is complete is in your array — but whether the "empty state" message is showing is only discoverable by asking the DOM if that element is hidden. Whether the modal is open is only knowable by checking for a class. The DOM stops being an output and becomes a second, unreliable database that you never designed, that has no schema, and that any stray line of code — or a browser extension, or a CSS transition — can mutate behind your back. Bugs in this style of code almost always have the same shape: two parts of the screen disagree, because one update path fired and its sibling did not.

jQuery, which dominated this era, made every individual operation shorter and cross-browser-safe. It did not reduce the number of operations. That is why apps written that way tended to be fine at a hundred lines and unmaintainable at ten thousand — the failure was not verbosity, it was that the programmer was personally responsible for every transition between every two states of the screen.

What's still broken: you are writing transitions — "when this changes, go find that and edit it" — when what you actually know is destinations: given the current data, here is what the screen should look like. Nobody has offered you a way to say the destination and have the transitions computed for you.

Node 1 — Describe the UI instead of mutating it

The limitation: you know the destination but are forced to write every transition to reach it.

React's founding move, open-sourced by Jordan Walke at Facebook on 29 May 2013, is to delete the transition-writing job. You never write "add this <li>." You write a function that, given the current data, returns a description of what the entire screen should be. React compares that description with the previous one and performs the DOM operations itself.

The thing your function returns is called a React element [EXPLAIN]. This is the single most misunderstood object in React, and getting it right early saves you months. A React element is not a DOM node. It is not on the page. It is an ordinary, immutable JavaScript object — roughly { type: 'li', props: { className: 'task', children: 'Buy milk' } } — that describes a DOM node that should exist. It is a plan, not a building. Creating one costs almost nothing, which is why React is happy to throw away and re-create the entire description on every update.

You create elements with React.createElement(type, props, ...children) [USE]. Nobody writes that by hand, because it is unreadable once nested three deep, so React ships JSX [EXPLAIN] — an extension to JavaScript's syntax where <li className="task">Buy milk</li> is compiled into that createElement call before the browser ever sees it. This is the fact to hold onto: JSX is not a template language and it is not HTML. It is syntax sugar over function calls, which is why the rules feel strange until you know that. class becomes className because class is a reserved word in JavaScript and props is a real object with real keys. Attributes are camelCase (onClick, tabIndex) because they are object keys, not HTML attributes. Braces inside JSX are not interpolation — they mean "stop parsing markup, start parsing a JavaScript expression, and use its value." That is why mapping over an array works, why an if does not (an if is a statement, not an expression), and why the ternary and the logical-and are the idioms instead. And a component must return one root element, because a function call returns one value — which is why fragments [USE], written <>...</>, exist: a wrapper that groups children without producing a DOM node.

Since React 17 (October 2020) there is a second, now-default compilation target called the new JSX transform [AWARE]: JSX compiles to _jsx(...) imported automatically from react/jsx-runtime, which is why modern files no longer need import React from 'react' at the top just to use JSX. If you read a codebase from 2018 and one from 2024, that missing import is often the first visible difference.

To get any of this onto a real page you need the other half of React, which is deliberately a separate package: react knows about elements and components; react-dom knows about the browser. You call createRoot(document.getElementById('root')).render(<App />) [USE] — createRoot is the React 18 API; before March 2022 it was ReactDOM.render(...), and seeing which one a codebase uses tells you immediately whether it has been migrated. The split exists because the same element-description machinery drives React Native and other renderers; the description of "what should be on screen" is renderer-agnostic.

The mental model to install now, and to keep for every later node: your job is to produce a description; React's job is to make the DOM match it. The old name for the intermediate description is the virtual DOM [EXPLAIN] — an unfortunate name, because it invites the belief that React keeps a full mirror copy of the page for speed reasons. It does not do it for speed. Building and comparing plain objects is not faster than a single well-chosen assignment written by a careful human. The trade is that you give up the theoretical best-case performance and get, in return, a program where the screen cannot disagree with the data, because the screen is derived from the data every single time.

What you can do at this point: render a fixed screen from fixed data, and re-render the whole thing from new data without writing a single DOM edit.

What's still broken: everything is one enormous function. There is no way to build a piece once — a task row, a button, an avatar — and reuse it in five places with different data. And nothing changes yet: you can render, but you have no way to make the screen respond to anything.

Node 2 — Components and props: reuse and one-way flow

The limitation: one giant render function with no reuse and no way to respond to input.

A component [EXPLAIN] is a function that takes one object argument and returns a React element. That is the entire definition. function TaskRow(props) { return <li>{props.title}</li>; }. Because it is a plain function, you compose UI the way you compose functions — a component's returned elements can include other components, arbitrarily deep.

The one non-obvious rule is capitalisation [USE]: <TaskRow /> compiles to createElement(TaskRow, ...), passing the function itself, while <taskRow /> compiles to createElement('taskRow', ...), passing the string. React decides "is this a DOM tag or one of your components?" purely on whether the type is a string or a function, and the compiler decides which one to emit purely on whether the first letter is uppercase. A lowercase component name fails in a confusing way — React tries to create an unknown HTML element — and this is the mechanism behind it.

The argument object is props [EXPLAIN]. Props are how a parent passes data down. They arrive as a single object, which is why destructuring in the parameter list is the universal style. Anything can be a prop, because it is just an object property: strings, numbers, arrays, objects, other React elements, and functions. children [USE] is not special magic; it is simply the prop React fills in with whatever you nested between the opening and closing tags, which is what lets you write a Card that wraps arbitrary content.

Two properties of props are load-bearing and both are conventions React relies on rather than enforces. First, props are read-only. A component must never assign to its own props. React does not deeply freeze them in production, so mutation "works" — and then breaks in ways that look like haunted behaviour, because React's entire update strategy assumes that rendering the same inputs produces the same output. This is the first appearance of a rule that will keep recurring under different names: rendering must be pure [EXPLAIN]. Given the same props and state, a component returns the same elements and changes nothing outside itself — no mutation of arguments, no writing to variables declared outside, no DOM edits, no network calls, during render.

Second, data flows one way: down. A parent can hand data to a child. A child cannot reach up. This feels restrictive for about a week and then becomes the reason you can debug the app at all: when something on screen is wrong, its value came from exactly one place — the component directly above it — and you walk up that chain until you find the lie. In the Node 0 world, a wrong value could have been written by any of forty places.

Communication upward is done by passing a function down [EXPLAIN]. The parent owns the data and owns the function that changes it; the child receives that function as a prop and calls it. The child does not know what happens; it only announces that something occurred. This inversion — data down, events up — is the shape of nearly every React app, and it is what makes a component reusable: TaskRow does not know whether clicking delete removes from an array, sends a request, or opens a confirmation dialog.

You will also see conditional rendering [USE] settle into two idioms, both of which are just JavaScript expressions: the ternary, and the logical-and. The second has one famous trap worth knowing now — if the left side is the number 0, the expression evaluates to 0, and React renders the character "0" on the page, because zero is a valid thing to render while false, null, and undefined render nothing. Checking items.length on an empty array puts a stray 0 on your screen; write items.length > 0 instead.

What you can do at this point: build a real component tree — an app made of small, reusable, testable functions with explicit inputs, where you can point at any value on screen and trace exactly where it came from.

What's still broken: the app is a photograph. Calling render again with new data would update the screen, but nothing inside the app can cause that to happen. A component has no memory: every call is fresh, local variables die when the function returns, and there is nowhere to put "the user typed this" or "this row is expanded."

Node 3 — State: giving a component memory, and what a render actually is

The limitation: components are pure functions with no memory, so nothing inside the app can cause an update.

const [count, setCount] = useState(0) [EXPLAIN]. This one line contains three ideas that must be separated.

First, state is memory that survives across calls of the function. A component function runs many times over the app's life. A normal let count = 0 inside it resets on every call, because that is what local variables do. useState asks React — which is the thing calling your function — to hold a value on your behalf, keyed to this component instance, and hand it back next time. The value does not live in your function. It lives in React's internal record for that component.

Second, the returned value is a snapshot, not a live binding. count is a plain constant holding the value that state had when this render began. It will never change during this render, no matter what you call. This is the source of the single most common piece of confusion in React: calling setCount(count + 1) twice in one handler increments by one, not two, and logging count immediately afterwards prints the pre-click number. Nothing is broken — count is a constant in this render's scope, so count + 1 is the same number both times. The fix is the updater form, setCount(c => c + 1) [EXPLAIN], where you hand React a function to apply to whatever the latest value is at the time it processes the queue. Reach for the updater form whenever the new value depends on the old one.

Third, calling the setter is a request, not an assignment. It does not write to a variable and does not synchronously re-run your component. It schedules a re-render. React then re-invokes your component function, useState returns the new value, you build a fresh element description, and React reconciles it with the old one. If you call the setter with a value React considers equal to the current one — using Object.is [USE] — it may skip the re-render entirely, which is exactly why setting state to the same object reference changes nothing on screen even though the object's contents were mutated.

That last point generalises into the rule that causes the most silent failures: treat state as immutable [EXPLAIN]. Pushing onto an array and setting it back renders nothing, because you handed back the same array reference. Spreading into a new array or a new object works. React compares by identity, not by contents, so a new value must be a new object. The immer library [AWARE] exists precisely to let you write mutating-looking code that produces new objects underneath.

Two more mechanics belong here. Batching [EXPLAIN]: multiple setter calls inside one event handler produce exactly one re-render, not one each. React collects them and processes them together before painting. In React 17 and earlier this only happened inside React's own event handlers — state updates inside a setTimeout, a promise callback, or a native listener each caused their own render. React 18 (29 March 2022) made batching automatic everywhere, which is one of the concrete behavioural differences when a codebase upgrades.

And render, commit, paint [EXPLAIN] — three distinct phases, and knowing the names lets you reason about everything later in this chain. Render is React calling your component functions to produce the new element description; it is pure, and React may do it more than once or throw the work away. Commit is React applying the computed DOM operations. Paint is the browser actually drawing pixels, which happens after the commit, in the next frame — a browser typically aims for one frame every 16.7 milliseconds, which is what "60 frames per second" means, and it is the budget everything in Node 14 is fighting for.

Finally: state is per component instance, not per component. Render a counter twice and there are two independent counters, because React keys state to the position of the component in the tree, not to the function.

What you can do at this point: build genuinely interactive components — counters, toggles, expandable rows — where changing data updates the screen with no DOM code anywhere.

What's still broken: you are trusting React to turn "here is the new description" into a small, correct set of DOM edits. You have no idea how it decides. And the moment you render a list that can reorder, that ignorance produces bugs that look like the framework is corrupting your data — text in the wrong row, input contents jumping between items, a checked checkbox following the wrong task.

Node 4 — Reconciliation and keys: how a description becomes DOM edits

The limitation: you cannot predict what React will reuse and what it will destroy, so list bugs look like framework corruption.

Comparing two arbitrary trees to find the minimum set of edits is a solved problem in computer science and the known algorithms are far too slow to run sixty times a second. React does not use them. It uses two assumptions that are not always true but are almost always true for user interfaces, and gets a fast, predictable algorithm in exchange. This is worth being able to state plainly, because it is a common interview probe [EXPLAIN].

Assumption one: different element types produce different trees. React compares old and new element at the same position. If the type differs — a div became a span, or a ProfileCard became an EmptyState — React does not attempt to reuse anything. It destroys the entire old subtree, including all of its DOM nodes and all of the state inside every component in it, and builds the new one from scratch. If the type is the same, React keeps the existing DOM node and only updates the attributes that actually changed, then recurses into the children.

The immediate consequence, and the classic bug it causes: state is tied to position in the tree, not to your component's name or its props [EXPLAIN]. If a conditional swaps one wrapper element for another around the same form, flipping the condition changes the type at that position, so the whole subtree is thrown away, and the form inside loses everything the user typed. Keep the same shape and the state survives. The inverse trap is just as common: changing which user a message panel shows is the same type at the same position, so React reuses the instance — and any state inside it, like a half-typed reply, silently carries over to the other user. The deliberate fix for that is to give it a key, which forces a fresh instance.

Assumption two: children can be given a stable identity by the developer. Without help, React matches children by index: first old child to first new child, second to second. Insert an item at the front of a list of a thousand, and every index shifts, so React sees every single row as "changed" and rewrites all of them, while any DOM state — focus, scroll position, uncontrolled input values, CSS animation progress — sits in the wrong place. The key prop [EXPLAIN] fixes this by giving React a name for each child. Matched by key instead of index, React knows the new item is genuinely new and the other thousand merely moved.

The rules around keys are precise. A key must be stable (same item, same key across renders), unique among siblings (not globally), and derived from the data, typically a database id. Using the array index [USE] is the trap: it is correct only if the list is never reordered, never filtered, and items are never inserted or deleted anywhere but the end. Otherwise it is worse than no key, because it actively tells React a lie — after deleting the first item, the item now at index 0 claims to be the same thing that was there before, so React keeps the old DOM node and its state and just changes the text. The symptom is a checkbox or an input value that stays behind while the text around it moves. Using a random value is the opposite failure: a new key every render means React destroys and recreates every row every time, losing focus and state, and it is slower than having no key at all. Keys are consumed by React and are not passed to your component as a prop — if you need the id inside, pass it twice. Keys also work on fragments, which is the reason the long React.Fragment form still exists alongside the short one.

There is a third mechanism sitting underneath all of this, added in React 16 (26 September 2017), called fiber [AWARE for now, and it returns in Node 14]. React 15 reconciled with plain recursion: once a render started it ran to completion, because you cannot pause a JavaScript call stack halfway. Fiber replaced the call stack with a linked data structure of work units that React walks itself, so it can stop partway, do something more urgent, and resume. Nothing about your code changed; the entire concurrent-rendering story in Node 14 became possible because of this rewrite.

What you can do at this point: render dynamic, reorderable lists correctly, and — more valuably — diagnose the "why did my component's state reset or not reset" class of bug from first principles instead of by guessing.

What's still broken: the screen updates when data changes, but the user has no way to change the data. You need input: clicks, typing, submits — and the browser's own event system does not fit a model where the DOM nodes are things React owns and may replace at any moment.

Node 5 — Events and controlled inputs

The limitation: no way for the user to change the data, and no place to put what they type.

You attach handlers as props, such as onClick. Two mistakes are worth naming immediately [USE]. You pass the function, you do not call it — writing onClick={handleClick()} runs it during render and passes the return value, which typically means a handler that fires once on page load and never again. And to pass arguments you wrap it in an arrow function.

What you receive is a SyntheticEvent [EXPLAIN], React's own object wrapping the browser's native event. Its reason for existing was originally cross-browser normalisation — in 2013, event objects genuinely differed between browsers — and it remains because React needs a consistent event system across its renderers. The real native event is always available at e.nativeEvent. One historical detail matters when reading old code or old blog posts: before React 17, synthetic events were pooled — the same object was reused across events and its fields were nulled out after the handler returned, so accessing e.target inside an async callback gave you null and people wrote e.persist(). React 17 removed pooling entirely. That advice is now obsolete, and knowing that is a small, real signal of currency.

React also does not attach a listener to each of your buttons. It attaches a small number of listeners at the root and uses event delegation [EXPLAIN], relying on the fact that browser events bubble up the tree; when one arrives, React works out which component it belongs to and runs the handlers along that path, simulating capture and bubble phases itself. Before React 17 those listeners were attached to document; React 17 moved them to the root container element, specifically so that two React versions, or React embedded inside a non-React page, could coexist without stealing each other's events. This is why e.stopPropagation() inside React stops React handlers but a native listener you added yourself on document may still fire — the two systems are stacked, not merged.

The bigger idea in this node is the controlled component [EXPLAIN]. A DOM input has its own internal value; the user types and it changes without asking anyone. That is exactly the Node 0 disease returning: application truth living in the DOM. React's answer is to take the value away from the DOM and put it in state — pass value from state and set state from onChange. Every keystroke fires the handler, which sets state, which re-renders, which sets the value back onto the input. The input renders the state; it never holds the truth. Now the value is available to everything else in the app for free — a character count, a disabled submit button, a debounced search, a clear button — because it is just data. The trade is one render per keystroke, which is the trigger for a great deal of Node 13's performance work.

The counterpart is the uncontrolled component [USE]: you let the DOM keep the value, provide defaultValue instead of value, and read it out when you need it — via a ref, Node 9, or from the form itself. Uncontrolled is legitimate; it is less code and fewer renders, and it is the right choice for a large form you only read on submit. The failure mode to recognise is the half-controlled input: passing value without onChange makes a permanently frozen field, and React logs a specific warning about it. Similarly, letting value be undefined on the first render and a string later flips an input from uncontrolled to controlled and produces another well-known warning; the fix is to initialise state to an empty string, never undefined.

Also here: onChange in React fires on every keystroke, unlike the native DOM change event which fires on blur. React deliberately renamed the semantics, which trips up people coming from vanilla JavaScript. And putting onSubmit on the form with preventDefault is still how you stop a full page navigation — React does not change that.

What you can do at this point: a fully interactive app — forms, filters, buttons, live-validating inputs — with every piece of user-visible truth in state.

What's still broken: components are islands. The filter input in the header and the list in the body both need the same query string, but state declared inside one component is invisible to the other. Duplicating it in both means they immediately disagree — Node 0's bug, rebuilt at a higher level.

Node 6 — Where state lives: lifting up, deriving, and the single source of truth

The limitation: sibling components cannot see each other's state, and duplicating it makes them disagree.

The mechanical answer is lifting state up [EXPLAIN]: move the state to the nearest common ancestor of every component that needs it, then pass the value down as a prop and pass a setter down as a prop. The search input becomes controlled by its parent; the list receives the same query. Neither owns it. They cannot disagree, because there is only one copy.

That is the easy half. The half that separates people who use React from people who can design with it is knowing what should not be state at all.

Do not store anything you can compute [EXPLAIN]. If you have tasks and filter in state, then the visible tasks are not state — they are a filter over the array, computed fresh during render. Storing them means writing an update path to keep them in sync every time either input changes, which is the Node 0 disease one more time. Same for counts, totals, emptiness flags, full names, error flags. The test is: can I derive this from other state or props? If yes, derive it. Recomputing on every render is cheap and always correct; a cached copy is fast and eventually wrong.

The two failure modes that follow from ignoring this are worth naming, because they have names in the community and appear in interviews. Duplicated state: storing the selected task as a whole object alongside the array of tasks — edit the task in the array and the selection still shows stale data; store the selected id and look the object up. Contradictory state: three booleans — loading, success, error — that can be true simultaneously, representing a state your UI has no rendering for; replace them with one variable holding 'idle', 'loading', 'success', or 'error'. This is a small idea with a large payoff, and it is the seed of Node 12.

There is a related question with a genuinely useful answer: props versus state. Props are what a component is told; state is what a component remembers. A component should not copy a prop into state — initialising state from a prop captures the value on the first render only and then silently ignores every later change, which produces "the parent updated but the child didn't" bugs. If you truly need to reset a child when something changes, the idiomatic tool is the one from Node 4: change its key, which throws away the instance and its state deliberately.

Finally, the structural pattern this node produces: state gets pushed up, and components get pushed down. Components with no state of their own — pure functions of props — are trivially testable, trivially reusable, and cheap to reason about. The historical name for that split is container and presentational components [AWARE]; the terminology has fallen away, but the instinct behind it has not.

What you can do at this point: design a component tree with a coherent state layout, where every value has exactly one home and everything else is derived.

What's still broken: the app is a closed world. It computes screens from data it already has. It cannot fetch anything from a server, read from browser storage, set the page title, subscribe to a websocket, start a timer, or measure an element — because every one of those is an effect on the outside world, and rendering was defined in Node 2 as pure and side-effect-free.

Node 7 — Effects: the door out of React, and the door back in

The limitation: rendering must stay pure, so there is nowhere to talk to the network, the browser, or any external system.

useEffect(fn, deps) [EXPLAIN] runs fn after React has committed to the DOM and the browser has painted. That timing is the whole point: your render stayed pure, the screen is already correct, and now you may touch the world.

The parts. The function is your side effect. The optional returned function is cleanup, run by React before the effect runs again and when the component unmounts — anything you started, you stop here: clear the interval, remove the listener, close the socket, abort the request. The dependency array [EXPLAIN] tells React when to re-run: omit it and the effect runs after every render; an empty array runs it after the first render only; a list re-runs it whenever one of those values changes between renders, compared with Object.is, item by item — which is why passing a freshly-created object or function makes it run every time (that thread continues in Node 13).

Now the correction that matters more than any other in this node, because most people learn React through the wrong frame and stay there for years. Effects are not lifecycle hooks. Before hooks, class components had componentDidMount, componentDidUpdate, and componentWillUnmount, and it is very natural to read an effect with an empty dependency array as "on mount." That framing produces a specific, endemic bug: two effects that need to run at slightly different moments get merged into one because they happen to share a lifecycle slot, and one effect ends up with the wrong dependencies because the developer was thinking about when it runs rather than what it depends on.

The correct frame [EXPLAIN] is synchronisation. An effect describes an ongoing relationship between some React state and some external system: "while this room id is X, this component should be connected to chat room X." You do not write connect-on-mount and disconnect-on-unmount. You write "connect to this room id," return "disconnect," and list the room id as the dependency. React then does the correct thing at every moment — including the case you would have forgotten, where the room id changes while the component stays mounted, and the connection must be torn down and rebuilt. When you think in synchronisation, the cleanup function stops being an afterthought and becomes the mandatory other half of the statement.

React 18 added a development-only behaviour that enforces this, and it confuses everyone the first time. Under StrictMode [EXPLAIN], in development only, React mounts each component, runs its effects, immediately runs the cleanups, and runs the effects again. If your effect is a correct synchronisation with a proper cleanup, this is invisible. If it is a fire-once "on mount" action with no cleanup, you get two network requests, two websockets, a doubled counter — and the thing to understand is that React is not being buggy; it is showing you a bug that would otherwise appear later, when a future feature causes a remount. It does not happen in production builds. Do not "fix" it with a ref guard; fix the effect.

The most valuable skill in this node is knowing when not to write an effect [EXPLAIN], because unnecessary effects are the most common cause of both bad performance and cascading-render bugs. Transforming data for display? Do it during render — an effect that watches the task list and sets a filtered-tasks state causes a second render every time and can never be right on the first. Responding to a user action? Put it in the event handler; buying a product belongs in the click handler, not in an effect watching a flag, because the effect also runs if the component remounts for an unrelated reason. Resetting state when a prop changes? Use key (Node 4), not an effect. Computing something expensive from props? That is useMemo (Node 13), not state plus an effect.

The honest summary is that effects are for external systems — the DOM outside React's tree, network, timers, browser APIs, subscriptions, third-party widgets, analytics — and for nothing else. React 19.2 (October 2025) added useEffectEvent [AWARE] for the recurring awkwardness where an effect needs to read the latest value of something without re-running when it changes; before that, the workaround was a ref, and you will see that pattern everywhere in existing code.

Related hooks that belong to this family: useLayoutEffect [USE], which runs after DOM mutation but before the browser paints — necessary when you must measure and adjust in the same frame to avoid a visible flicker, and to be avoided otherwise because it blocks painting. And useSyncExternalStore [AWARE], added in React 18, the correct way to subscribe to a store that lives outside React; it exists because with concurrent rendering (Node 14) a naive subscription can show two parts of one screen reading two different versions of the same store, a failure with the name tearing.

What you can do at this point: talk to the world. Fetch on mount, subscribe to events, sync with browser storage, integrate a non-React library.

What's still broken: the moment you actually fetch data in an effect, you discover that the naive version is wrong in at least four separate ways, and none of them show up on your fast laptop against a fast API.

Node 8 — Fetching data, and why nobody does it by hand for long

The limitation: the textbook fetch-in-an-effect is wrong in four ways that only appear under real network conditions.

Take the textbook version: an effect that sets loading true, fetches a user by id, and sets the result into state, with the id as its only dependency. Here is what is wrong with it [EXPLAIN], and this list is a genuinely common interview question.

Race conditions. Change the id from 1 to 2 quickly and two requests are now in flight. If request 1 resolves after request 2 — which is entirely normal, since network ordering is not guaranteed — you render user 1's data on a page that says user 2. The fix is cleanup: set an ignore flag or call abort on an AbortController in the returned cleanup function, so a response belonging to a stale render is discarded. This is the clearest possible demonstration that the cleanup function is not optional bookkeeping — omitting it is a correctness bug, not a leak.

No error handling. A rejected promise with no catch produces an unhandled rejection and a component stuck on a spinner forever.

Loading state that lies. With separate loading, error, and data state, there is always a render where two of them disagree. This is the contradictory-state problem from Node 6, and it is why every data library models a single status.

Network waterfalls [EXPLAIN]. If a parent fetches, then renders a child that fetches, the child's request cannot even begin until the parent's has returned, because the child does not exist until then. Three nested levels means three sequential round trips where one parallel batch would do. Waterfalls are the single largest cause of slow React screens and they are invisible in code review — you have to look at the network timeline to see them.

No caching, no deduplication, no revalidation. Navigate away and back, and you refetch. Two components need the same user, and you fetch it twice. The data goes stale and nothing knows.

Every one of these is solvable by hand, and solving all of them by hand produces a worse version of a library that already exists. This is the honest reason TanStack Query [USE] (formerly React Query) and SWR [AWARE] dominate: they treat server data as a cache of someone else's state, not as your state. They give you a status, deduplicate identical in-flight requests, cache by key, revalidate in the background, retry, and let multiple components share one request. The framing worth being able to say out loud is: useState is for state you own; server data is state you are borrowing, and it needs different rules.

React 19 (5 December 2024) also introduced the use() API [AWARE] — you can pass it a promise and it suspends the component until the promise resolves, which ties into Node 15 — and Actions with useActionState, useFormStatus, and useOptimistic [AWARE], which package the pending, error, and optimistic-update pattern for form submissions and mutations directly into the framework. These are recent enough that most codebases you interview against will not use them yet, but knowing they exist is a currency signal.

What you can do at this point: load and mutate real server data correctly, and explain why the naive effect version is not merely inelegant but wrong.

What's still broken: some things genuinely cannot be expressed as "render a description." You need to focus an input after it appears, measure an element's height, play a video, store a timer id that must not trigger a re-render, or hand a raw DOM node to a charting library. The declarative model has no vocabulary for any of that.

Node 9 — Refs: the deliberate escape hatch

The limitation: focus, measurement, media control, and third-party libraries have no declarative expression.

const ref = useRef(initial) [EXPLAIN] returns a plain mutable object, with a single current property, that React keeps for you across renders. Two properties define it, and they are exactly the inverse of state: mutating ref.current does not trigger a re-render, and reading it during render is not safe because React does not track it.

That gives it two distinct uses, which are easy to conflate. First, holding a value between renders that the screen does not depend on [USE]: an interval id you need in order to cancel it, the previous value of a prop, a "has this already run" flag, a mutable accumulator. If the UI does not display it, state is the wrong tool — state would cause pointless renders. Second, getting hold of a real DOM node [EXPLAIN]: put the ref on an element and React sets ref.current to the actual DOM element after commit, and back to null on unmount. Now you can call the imperative browser APIs React has no declarative equivalent for: focus, scroll into view, measure a bounding rectangle, play a video, select text. React's official framing is that refs are an escape hatch and reaching for one is a signal to first check whether the thing can be expressed as state — but focus, scroll, measurement, and integrating third-party libraries are legitimate and unavoidable.

The rules [USE]: do not read or write ref.current during rendering, since it makes render impure and the value is not guaranteed to be set yet; read it in effects and event handlers. Do not mutate DOM nodes React owns — adding and removing your own children under a React-managed node makes React's picture of the tree wrong, and it will eventually crash or clobber you.

Passing a ref through a component was, for years, its own small subject. Refs are not normal props: ref was consumed by React, so putting one on your own component did not reach the input inside. The answer was forwardRef [USE], wrapping a component so it receives the ref as a second argument. React 19 removed the need: ref is now an ordinary prop that you can destructure directly, and forwardRef is on the way out. Both forms are everywhere in real code, so you need to recognise both. useImperativeHandle [AWARE] lets a component expose a deliberately narrow API to its parent — a focus method and a scroll method rather than the raw node — which is how well-built component libraries avoid leaking their DOM structure. React 19 also added ref cleanup functions: return a function from a ref callback and React calls it on detach.

Paired with refs is useLayoutEffect, mentioned in Node 7 and properly at home here: measure the node, set state, and have it all happen before paint, so the user never sees the intermediate layout. The tooltip that needs to know whether it fits above the button is the canonical case.

What you can do at this point: everything the declarative model cannot express, without abandoning it — integrate imperative libraries, manage focus for accessibility, measure and position.

What's still broken: you now have five hooks, all of which behave strangely if you put them inside an if, and you have started copy-pasting the same three-hook combination into six components. Nobody has explained why the restriction exists, and there is no way to extract the repeated combination without a mechanism.

Node 10 — How hooks actually work, and custom hooks

The limitation: hook rules look arbitrary, and repeated stateful logic cannot be extracted.

Hooks arrived in React 16.8, on 6 February 2019, and they replaced class components as the default way to write React. The problem they solved was not verbosity. It was that in classes, stateful logic could not be extracted and reused. Lifecycle methods force you to split one concern across three places — subscribe on mount, resubscribe on update, unsubscribe on unmount — while a single method mixes three unrelated concerns together. The previous escape routes, higher-order components and render props [AWARE], worked but produced deeply nested "wrapper hell" in the component tree.

The mechanism is much simpler than it looks, and being able to explain it is a strong senior signal [EXPLAIN]. React keeps, for each component instance, an ordered list of hook records. When your function runs, React sets an internal pointer to that component and to position 0 in the list. Each hook call takes the record at the current position and advances the pointer by one. On the first render the records are created; on every later render they are read back in the same order. Hooks are matched by call order, not by name — useState has no idea it is called count.

Every rule follows from that one sentence, which is why you should never memorise the rules separately [EXPLAIN]. Only call hooks at the top level: a hook inside an if, a loop, or after an early return means the number and order of calls can differ between renders, so on the render where the condition flips, position 2 now holds a different hook's record and React hands your useState someone else's value. React detects the count change and throws "Rendered fewer hooks than expected," but the underlying failure is a silent misalignment. Only call hooks from React functions — components or other hooks — because outside a render there is no component whose list to point at.

The eslint-plugin-react-hooks package enforces both, plus the exhaustive-dependencies rule for effects, and it is not optional tooling in practice.

Now the payoff: a custom hook [EXPLAIN] is just a function whose name starts with use and which calls other hooks. There is no API, no registration, nothing special — the prefix exists so the linter knows to apply the rules. Extract your three-hook combination into a useChatRoom hook and you have reused logic without adding a single level to the component tree, which is exactly what higher-order components and render props could not do. The one thing to be clear about: custom hooks share logic, never state. Two components calling the same counter hook get two separate counters, because each call site gets its own hook records. Sharing actual state requires lifting up (Node 6) or context (Node 11), and this is a genuinely common misconception.

Class components [AWARE] still work, are not deprecated, and appear in every codebase older than 2019. You should be able to read this.state, this.setState, the render method, and the three main lifecycle methods, and to map them onto hooks — but write new code with hooks. There is exactly one thing classes can still do that hooks cannot: be an error boundary (Node 15).

What you can do at this point: read and write idiomatic modern React, extract reusable stateful logic, and explain the hook rules from mechanism rather than from memory.

What's still broken: lifting state up (Node 6) is correct but does not scale. The theme, the logged-in user, the locale — these are needed by components fifteen levels deep, and threading them through every intermediate component as props means dozens of components accept and forward props they do not use. That is prop drilling, and it makes refactoring miserable.

Node 11 — Context: values that skip the tree

The limitation: global-ish values have to be threaded through every intermediate component.

Context [EXPLAIN] lets a component provide a value to its entire subtree, and lets any descendant read it without it being passed through the components in between.

Three parts. createContext(defaultValue) creates the channel. Rendering the context as a provider with a value prop — in React 19 you can render the context directly, and in every earlier version you render its .Provider, and you will read both — makes the value available below it. useContext(TheContext) reads it. React walks up from the reading component and takes the value from the nearest matching provider above; if there is none, it uses the default from createContext, which is why that default is usually set to something that makes the "you forgot a provider" mistake loud rather than silent.

Two facts control everything you will do with it. First, context does not make data flow upward or sideways. It is still one-way flow — it just skips the intermediate steps. A component can only read what some ancestor provided. Second, every consumer re-renders when the provided value changes, compared by Object.is [EXPLAIN]. This is where context gets its bad reputation. If you provide an object literal built inline, that is a new object on every render of the provider, so every consumer in the app re-renders on every parent render regardless of whether anything meaningful changed. The mitigations are useMemo on the value (Node 13), or splitting one context into two — a rarely-changing one for the dispatch functions and a frequently-changing one for the data — so that components which only need to act do not re-render when the data changes.

The sentence to be able to say in an interview: context is a dependency-injection mechanism, not a state manager [EXPLAIN]. It solves transport. It does nothing about how state is updated, does not batch or select, and has no way for a consumer to say "only re-render me when this one field changes." That is precisely the gap Zustand, Redux Toolkit, and Jotai [AWARE] fill; the standard question "why would you use Redux instead of context?" is answered by selective subscription, predictable update patterns, devtools with time-travel, and middleware — not by "context is slow."

The honest guidance: use context for values that are genuinely global and change rarely — theme, current user, locale, feature flags, a router's state — and for a well-scoped subtree's shared state. Reach for a library when you have frequently-changing global state with many consumers.

What you can do at this point: eliminate prop drilling, and explain to an interviewer both what context is for and precisely why it is not Redux.

What's still broken: state has been about where it lives, never about how it changes. A component with eight useState calls and update logic scattered across a dozen handlers has no single place where you can read the rules of the thing. Invalid combinations from Node 6 keep sneaking back in.

Node 12 — useReducer: state as a set of legal transitions

The limitation: update logic is scattered across handlers with no single place that defines what the state can legally do.

const [state, dispatch] = useReducer(reducer, initialState) [EXPLAIN]. A reducer is a pure function taking the current state and an action and returning the new state. An action is a plain object describing what happened, conventionally with a type and a payload. Dispatching an action hands it to React, which calls your reducer and re-renders with the result.

The shift is one of framing, and it is the frontend version of an idea that recurs everywhere in software: instead of components setting values, they report events, and one function decides what each event means. The consequences are worth listing. All transition logic sits in one place you can read top to bottom, outside the component; it is a pure function, so it is testable with no rendering at all. Components get smaller and dumber — they dispatch "toggled with this id" rather than knowing how toggling works. You can make impossible states unrepresentable, closing Node 6's contradictory-state hole properly, because the reducer is the only writer. dispatch has a stable identity across renders, which React guarantees, so passing it down through context or props never causes the identity-based re-render problems of Node 13. And the action list becomes a readable log of everything your feature can do — which is also why the pattern pairs so well with devtools.

Choosing between useState and useReducer [USE]: use useState for independent, simple values. Move to useReducer when several state values change together, when the next state depends on the previous in non-trivial ways, when the same update logic is triggered from many places, or when you keep writing the same three setters in a row. The clean rule of thumb is number of related transitions, not number of variables.

The natural extension is useReducer plus context [USE]: hold the state at the top with a reducer, put the state in one context and dispatch in another, and any depth of component can read state or trigger transitions without prop drilling and without a library. That combination covers a surprisingly large fraction of what people install Redux for, and being able to say so — and say where it stops being enough — is a good interview answer.

Redux [AWARE] is the same idea, made global, with a single store, middleware, and devtools; modern Redux means Redux Toolkit, which uses immer so reducers look mutating while producing new state. Knowing that useReducer is the same shape makes Redux a small step rather than a new subject.

What you can do at this point: model complex features as explicit state machines, and keep the update rules in one auditable place.

What's still broken: correctness is now under control; cost is not. Every state change re-renders a subtree, controlled inputs render on every keystroke, and context re-renders every consumer. On a large tree with expensive components, the app becomes visibly sluggish, and you have no framework for reasoning about why.

Node 13 — Re-render cost, memoisation, and the identity problem

The limitation: the app is correct but slow, and you have no model of what makes it slow.

Start with the actual rule, because most performance confusion comes from a wrong belief about it [EXPLAIN]: when a component re-renders, React re-renders all of its descendants by default. Not because their props changed — it does not check. Because their parent rendered. A state change near the top of the tree re-runs every component function below it.

That is usually fine. Running a function that returns objects is cheap, and React only touches the DOM where the description actually differs. Rendering is not painting. The moments it stops being fine are specific: a component that does real work per render (a big list, heavy formatting, a chart), a very large subtree, and a state change that fires very often — a keystroke, a scroll, a drag, a mousemove.

Three tools, and the thing that makes them work or fail is the same in all three [EXPLAIN]. React.memo wraps a component so React skips re-rendering it when its props are shallowly equal to last time — each prop compared with Object.is, one level deep. useMemo caches the result of a computation between renders, recomputing only when a dependency changes; for genuinely expensive computation, and for keeping an object or array's identity stable. useCallback caches a function, so the same function identity is handed down across renders — it is exactly a useMemo returning the function, with nicer syntax.

Now the mechanism that ties them together, and which is the real content of this node — referential identity [EXPLAIN]. Every time a component renders, every object literal, array literal, and arrow function inside it is created anew. Two objects with identical contents are not equal. So a memoised child that receives a freshly filtered array and an inline arrow handler gains nothing at all: both props are new values every render, the shallow comparison always fails, and you have added a comparison cost for no benefit. Wrapping in memo without stabilising the props is one of the most common wasted optimisations in real codebases, and spotting it is a good code-review instinct. The same mechanism explains an effect that re-runs every render (an object in the dependency array), and Node 11's context problem (a fresh object as the provider value).

Two things worth saying honestly, because interviewers ask and because the ecosystem has moved. Do not memoise by default. useMemo and useCallback are not free — they allocate, they store, they compare dependencies, and they make code harder to read. Measure first, with the React DevTools Profiler [USE], which shows you which components rendered, why, and how long they took. Optimising a component that takes 0.2 milliseconds is worse than doing nothing. And the React Compiler [AWARE] changes this picture: announced in 2024 and reaching 1.0 in late 2025, it is a build-time compiler that analyses your components and inserts memoisation automatically, correctly, everywhere it is safe — which is most places, provided your code follows the Rules of React (pure render, no mutating props or state). Where it is adopted, hand-written useMemo and useCallback largely stop being necessary. It is not yet universal, so you still need to understand manual memoisation to read existing code and to work in codebases that have not adopted it, but "React Compiler makes most manual memoisation unnecessary" is a current, accurate thing to say.

Other levers at this node [AWARE]: move state down into the smallest component that needs it, so the frequently-changing state re-renders less; pass expensive subtrees as children so they are created by a parent that is not re-rendering; virtualise long lists with react-window or TanStack Virtual so only visible rows exist in the DOM; and remember that the fastest optimisation is usually structural, not a hook.

What you can do at this point: diagnose slow React with the profiler, explain re-render causes precisely, and apply memoisation where it actually helps.

What's still broken: all of this assumes rendering is fast enough to finish in one uninterrupted go. When it is not — a search box filtering fifty thousand rows — memoisation cannot save you, because the work genuinely must happen. Once React starts rendering, it will not stop, so the keystroke that started it cannot be shown until it finishes. The input freezes. There is no way to say "this update matters more than that one."

Node 14 — Concurrent rendering: priorities, not speed

The limitation: rendering cannot be interrupted, so an expensive update blocks an urgent one.

This is what the fiber rewrite of React 16 was for, and what React 18 finally exposed. React can now begin rendering, pause partway through, handle something more urgent, and either resume or throw the partial work away. Nothing is rendered to the screen until a render completes, so the user never sees a half-updated UI — React works on an in-progress tree and only commits when it is finished, which is why partial work can be discarded harmlessly.

The point is not that rendering became faster. The point is that not all updates are equally urgent [EXPLAIN]. Typing a character must appear immediately; the filtered list of fifty thousand results can lag by a few hundred milliseconds without anyone minding. Before React 18 there was no way to express that difference, so both updates were processed with equal urgency and the cheap one waited behind the expensive one.

useTransition [EXPLAIN] gives you the vocabulary. It returns a pending flag and a function; state updates made inside that function are marked non-urgent. React renders the urgent update first — the input showing the new character — and does the transition work in interruptible chunks, abandoning it if another keystroke arrives. The pending flag is true while it is in flight, so you can dim the stale results. The input never freezes because React yields control back to the browser between chunks, roughly every 5 milliseconds, so the browser gets a chance to process input and paint within its 16.7-millisecond frame.

useDeferredValue [USE] is the same idea from the other end: it gives you a copy of a value that "lags behind" during heavy work. You render the input from the live value and the expensive list from the deferred one. Use it when you do not control the state update — for instance the value arrives as a prop.

Both require the createRoot entry point from React 18; an app still on the legacy render API runs in a compatibility mode without concurrent features, which is one concrete reason the migration matters.

Underneath is the lane model [AWARE], React's internal priority system, where updates are tagged with a lane and lanes are processed in priority order, with starvation protection so a low-priority update cannot be postponed forever. You do not interact with it, but the name comes up.

Two honest caveats. Concurrent rendering only helps when the bottleneck is rendering — it does nothing for a slow network request or a slow API. And it is precisely because rendering can now be interrupted, restarted, and discarded that the purity rules from Node 2 became non-negotiable: a render function with a side effect in it may now run twice, or run and be thrown away, and an impure component that got away with it in React 17 can break under React 18. StrictMode's double-rendering in development exists to surface exactly this class of bug before it reaches production.

What you can do at this point: keep an interface responsive under genuinely expensive rendering, and explain the difference between "make it faster" and "make it interruptible."

What's still broken: the whole app is still one JavaScript bundle that must download and execute before anything appears, and a component that is waiting — for code, for data — has no standard way to say so. Every component invents its own loading boolean, and one component throwing an error still takes down the entire page with a blank screen.

Node 15 — Suspense, lazy loading, and error boundaries

The limitation: waiting and failing are handled ad hoc per component, and the whole bundle must load before anything renders.

React.lazy [USE], given a function that dynamically imports a module, turns a component into one that is only downloaded when it is first rendered. The dynamic import is a JavaScript feature the bundler recognises: it splits that module and everything it imports into a separate file fetched on demand. That is code splitting, and it is the standard answer to "how do you improve initial load time in a React app" — split by route first, since a user landing on the login page does not need the admin dashboard's charting library.

A lazily-loaded component is not there yet when React first tries to render it, which needs a way to express "not ready." That is Suspense [EXPLAIN], given a fallback. Wrap a boundary around part of your tree; if anything inside it suspends, React shows the fallback instead of that subtree — leaving the rest of the page alone — and swaps in the real content when it is ready. The important shift is that the parent declares the loading UI for a region, rather than every leaf component managing its own spinner. That is what makes coordinated loading states possible: one fallback for a group of things arriving together, instead of six spinners popping in at different moments.

Suspense started as code-splitting only. In React 18 it gained the ability to work with data on the server, and with React 19 and the use() API it works with promises on the client too, which is why data-fetching libraries and frameworks increasingly express loading through Suspense rather than through booleans.

The failure counterpart is the error boundary [EXPLAIN]. An uncaught error during render kills React's ability to reason about the tree, so since React 16 the deliberate behaviour is to unmount the whole tree — a blank white page — on the theory that a visibly broken app is safer than a silently corrupted one. An error boundary is a component that catches errors from its subtree and renders a fallback instead, containing the damage to one region. It is implemented with the class lifecycle methods getDerivedStateFromError and componentDidCatch — the one thing hooks still cannot do, which is why react-error-boundary [USE] is a near-universal dependency; almost nobody writes the class by hand any more. Note what boundaries do not catch: errors inside event handlers (use try/catch; they are not during render), errors in async code, and errors during server rendering. React 19 improved the reporting around all of this, adding root-level caught and uncaught error callbacks and much better hydration mismatch messages.

React 19.2 added Activity [AWARE], which lets you keep part of the tree mounted but hidden, preserving its state while deprioritising its rendering — the long-requested "keep the previous tab alive" capability.

What you can do at this point: ship an app that loads a fraction of its code up front, shows coordinated loading regions, and degrades a broken widget instead of the whole page.

What's still broken: the fundamental shape is still an empty HTML file plus a large JavaScript bundle. The user stares at nothing until the bundle downloads and executes; search engines and link previews see nothing; and every byte of data still requires a round trip after the app has already loaded, on top of every waterfall from Node 8.

Node 16 — Server rendering, hydration, and React Server Components

The limitation: an empty HTML shell plus a large bundle means slow first paint, no crawlability, and data fetched only after the app loads.

Server-side rendering [EXPLAIN]: run your components on the server, produce HTML as a string, send that. The user sees real content on the first response, before any JavaScript has run. Then the same JavaScript loads in the browser and hydration [EXPLAIN] happens — React renders your tree in the browser, walks the existing server HTML, and attaches event handlers and state to the DOM nodes that are already there rather than recreating them. The entry point is hydrateRoot rather than createRoot.

This buys real first-paint speed and real crawlability, and it introduces its own family of problems, which is what most SSR interview questions are actually about. Hydration mismatches [EXPLAIN]: the server's HTML and the client's first render must match, and current dates, random numbers, window dimensions, locale-dependent formatting, and anything read from browser storage all produce different output in the two places — React warns, and in React 19 shows a proper diff. The standard fixes are rendering the varying part only after mount, or suppressing the warning for a genuinely unavoidable case like a timestamp. The window and document objects do not exist on the server, so any module-level access crashes the render. Time to interactive lags first paint, which is worse in a specific way, because the page looks ready and does not respond until hydration finishes, and the user tries to click. And you still ship the whole component's code to the client, even for a component that is purely static.

React Server Components [EXPLAIN] attack that last point, and they are the most significant architectural change in React's history since hooks. A server component runs only on the server, once, and never ships its JavaScript to the browser at all. It can await directly in the component body — query a database, read a file, call an internal API with secrets — and what reaches the client is not HTML and not a bundle but a serialised description of the rendered output, which React merges into the tree. The consequences: no client-side JavaScript for static parts, no API layer needed for a component's own data (which kills a large class of waterfalls from Node 8), and a genuinely smaller bundle.

The cost is a new distinction you must hold in your head [EXPLAIN]. Server components cannot use state, effects, refs, context, or event handlers — none of it means anything without a browser. Components that need interactivity are marked with the 'use client' directive at the top of the file, which marks the boundary where server rendering stops and client code begins; everything imported below that boundary ships to the browser. 'use server' is a different thing entirely, marking a server function (previously "server action") — a function that runs on the server but can be called from client code, which React wires up as a request for you. Confusing the two directives is common and worth not doing.

Server components became stable in React 19 but require a framework with a bundler integration; you do not adopt them by installing React. In practice that means Next.js [AWARE] with the App Router, or React Router v7 / Remix. That is the honest reason "learn React then learn Next.js" is the standard path — and also why Next.js is its own topic in the catalog rather than a section of this one.

What you can do at this point: explain the whole rendering spectrum — client-only, SSR, static generation, streaming, server components — and say what each one costs and buys. This is one of the highest-value things you can say confidently in a 2026 frontend interview, because a large share of candidates only know client-side rendering.

What's still broken: React still does not do routing, forms, styling, or testing, and it never will. It renders a tree. Everything else is ecosystem — and choosing badly there is where real projects go wrong.

Node 17 — The ecosystem React deliberately does not include

The limitation: React renders a tree and decides nothing else, so an application is a stack of choices you must defend.

React's scope is a library for building user interfaces out of components. Assembling an application means choosing the rest, and knowing the current landscape is directly interview-relevant [AWARE unless marked].

Routing. React has no router. React Router [USE] is the long-standing default and, from version 7, has absorbed Remix and can operate as a full framework. TanStack Router is the type-safe challenger. Next.js brings its own file-system router. What an interviewer is checking is whether you understand client-side routing at all: the app intercepts navigation, updates the URL with the browser's History API without a page load, and renders a different component tree — which is why you must configure a server to serve the index HTML for every path, or deep links return 404.

Server state. TanStack Query or SWR, as argued in Node 8. Client state. Context plus reducer for many apps; Zustand (small, hook-based, no provider), Redux Toolkit (large apps, strong devtools, established conventions), Jotai or Recoil (atomic) beyond that. The mature answer to "which state manager do you use" separates server cache from client state and points out that most apps that reached for Redux only ever needed the former.

Forms. React Hook Form [USE] is dominant, and its selling point is exactly Node 5's cost: it keeps inputs uncontrolled and subscribes via refs, so typing does not re-render the form. Paired with Zod for schema validation, which is the same validation library on both ends of the stack.

Styling. Tailwind is the current default; CSS Modules, vanilla-extract, and CSS-in-JS libraries all still appear, with the runtime CSS-in-JS approach declining specifically because it does not work well with server components. Components. shadcn/ui — not a dependency but a generator that copies accessible Radix primitives into your repo — is the current mainstream, which is its own catalog topic.

Build tooling. Vite [USE] has replaced Create React App, which was formally deprecated in February 2025. If you scaffold a React app in 2026 you use Vite or a framework; knowing CRA is dead is a currency signal.

Testing. React Testing Library [USE] with Vitest or Jest, and its philosophy is a genuine principle worth being able to state: test what the user experiences, query by accessible role and visible text, never by class name or component internals — so that a refactor that changes structure but not behaviour does not break the suite. Playwright for end-to-end.

TypeScript. In practice not optional in 2026. Typed props are the single largest quality win available to a React codebase.

What you can do at this point: assemble and defend a full stack of choices, which is precisely what "tell me how you'd structure a React app" is asking.

Where the chain gets misread

"The virtual DOM is fast." (Node 1) It is not a speed technique. Diffing objects is overhead compared to a perfect hand-written DOM edit. What it buys is that the screen is derived from data every time, so it cannot drift out of sync — you trade peak performance for guaranteed correctness.

"JSX is HTML" or "JSX is a template language." (Node 1) It is syntax compiled into createElement calls. Every rule that feels arbitrary — className, camelCase props, one root element, expressions but not statements in braces — falls straight out of that.

"setState changes the variable." (Node 3) It queues a re-render. The variable in the current render is a frozen snapshot and will never change. This is the reason two increments in one handler add one, and why the updater form exists.

"useEffect with an empty array means componentDidMount." (Node 7) That framing is the root of most bad effect code. Effects synchronise with an external system for as long as their dependencies hold; the cleanup is half the statement, not cleanup in the janitorial sense.

"StrictMode double-rendering is a React bug." (Node 7) It is a development-only detector for effects that are not idempotent and for impure renders. It does not happen in production, and suppressing it with a ref guard hides a real defect.

"Index keys are fine, the warning just wants something." (Node 4) With reordering or deletion, index keys are worse than none — they tell React that a different item is the same item, so DOM state stays behind while text moves.

"A component re-renders because its props changed." (Node 13) It re-renders because its parent did. React does not check props unless you asked it to with memo. Almost all performance confusion starts here.

"useMemo and useCallback make things faster, so use them everywhere." (Node 13) They cost allocation and comparison, and they do nothing at all if the props or dependencies are new objects each render — which is the usual case people miss. Profile first; and where the React Compiler is adopted, most of this is handled for you.

"Context is a state management library" or "context is slow." (Node 11) It is transport with no selective subscription. The re-render pain people attribute to context is almost always an unstable object as the provider value.

"Custom hooks share state between components." (Node 10) They share logic. Each call site gets its own hook records and therefore its own state. Sharing state needs lifting up, context, or a store.

"Refs are a hack you should avoid." (Node 9) They are the intended escape hatch. Focus management, measurement, media control, and third-party integration have no declarative form, and pretending otherwise produces worse code than using a ref.

"SSR makes the app faster." (Node 16) It makes first paint faster and content crawlable. It usually makes time-to-interactive worse relative to what the user sees, adds hydration mismatch as a whole new bug class, and does not reduce the bundle — that is what server components do.

"React is a framework." (Node 17) It renders a tree. Routing, data, forms, styling, and testing are all your choices, which is a strength when you know the landscape and a liability when you do not.

The chain in one paragraph

Without React you hand-write every transition between data and screen, and application truth leaks into the DOM until two parts of the page disagree; React deletes that job by having you describe the screen as a function of data, returning immutable element objects — created by JSX, which is just compiled createElement calls — and letting it compute the DOM edits. Those descriptions are made reusable as components taking read-only props with data flowing strictly down and events reported upward as callbacks; memory across renders comes from useState, whose value is a per-render snapshot and whose setter queues a batched re-render rather than assigning, which is why immutable updates and the updater form are mandatory. React turns the new description into edits by reconciling position-by-position — same type means reuse the node and its state, different type means destroy the subtree — with key supplying stable identity for lists, which is why index keys corrupt row state and why changing a key is the deliberate way to reset a component. Input arrives through delegated synthetic events and is captured as state via controlled inputs, and shared values are lifted to a common ancestor while anything derivable is computed during render rather than stored, avoiding duplicated and contradictory state. Because render must stay pure, contact with the outside world happens in effects, which are not lifecycle hooks but declarations of ongoing synchronisation whose cleanup is half the statement — a fact made unavoidable the moment you fetch data, where missing cleanup is a race condition and where waterfalls, caching, and status modelling push you toward a data library. Refs supply the escape hatch for focus, measurement, and imperative libraries; all hooks work because React keeps a per-instance ordered list matched by call order, which is the entire reason for the rules and the entire reason custom hooks can share logic but never state. Context transports values past prop drilling without becoming a state manager, useReducer turns scattered setters into one auditable set of transitions, and once correctness is handled, cost is governed by the fact that a re-render cascades to all descendants — so memo, useMemo, and useCallback work only when referential identity is stable, and increasingly the React Compiler does that for you. When work is genuinely expensive, concurrency lets React interrupt and prioritise rendering with transitions and deferred values, Suspense and error boundaries turn waiting and failing into declarative regions rather than per-component booleans, and pushing rendering to the server adds first-paint speed and hydration's bug class, culminating in server components that never ship their JavaScript at all — beyond which routing, data, forms, styling, and testing are choices React deliberately leaves to you.
