Node 44 — the six forces, seen from the end

The forces named at the start were a promise that the chain would not be forty-five unrelated mechanisms. Here they are again, with the instances filled in. If you remember one thing from this document, make it this node, because it is what lets you understand a mechanism you have never seen before by asking which force it is answering.

Sharing — one resource, many claimants

Every part of a machine that exists once needs a story for how many things use it. The processor is shared by the context switch and the scheduler (6, 7); memory by paging (10); the disk by the filesystem and the block layer (23, 24); the network by ports and the four-tuple (32); a database connection by a pool; a cache line by the coherence protocol (16). Sharing always begins with the same question — time-slice it, space-partition it, or queue for it? — and the three answers are the scheduler, virtual memory, and every queue in your stack.

Protection — sharing means one party can destroy another

Every sharing mechanism drags a protection mechanism behind it, and the protection is always enforced below the level the protected party can reach. The mode bit (3), page table permissions (10), file permissions and capabilities (25), namespaces (26), cgroups (27), seccomp (4), the hypervisor (29). The recurring lesson is Node 3's: a guard the guarded party can remove is not a guard. It is why WebAssembly bounds-checks in the runtime rather than trusting the module, why eBPF has a verifier, and why Site Isolation moved from software separation to process separation the moment hardware made software separation insufficient.

Indirection — the universal move

Do not let anyone touch the real thing; give them a name the system translates. Virtual addresses instead of physical (10). File descriptors instead of files (22). Inodes instead of names (21). PIDs instead of task structures (5). Namespaces instead of global tables (26). The VFS instead of a filesystem (21). Sonames and the GOT instead of addresses (34). A Service IP instead of a pod IP (32). Every one buys the same three things — relocation, substitution, and protection — at the same cost of a translation step, which is then cached (the TLB, the descriptor table, DNS, the module cache). When you meet a new indirection, ask what it lets the system change without telling anyone, and where its cache is.

Latency — the parts differ in speed by a hundred million

One nanosecond to one hundred milliseconds. Everything in between is a layer hiding the slowness beneath it, and there are only three techniques. Cache: L1/L2/L3, the TLB, the page cache, shared_buffers, the module cache, a CDN, your Redis. Buffer: the store buffer, socket buffers, the page cache again, stream highWaterMark, spooling. Overlap: DMA, interrupts, the event loop, readahead, pipelining, speculative execution, Promise.all. Every one of them introduces the same two problems — staleness (what if the cached copy is wrong?) and durability (what if we crash before the buffer drains?) — which is why cache invalidation and fsync are hard in the same way.

The boundary — crossing costs, so cross less

A syscall is ~100 ns (4, 40); a database round trip ~200 µs; a cross-region call ~100 ms. Every layer's optimisation is the same optimisation: buffered I/O, writev, sendfile, epoll, io_uring, the vDSO, HTTP keep-alive, connection pooling, DataLoader batching, HTTP/2 multiplexing, and the difference between a monolith's function call and a microservice's request (41). Batch, or move the work to the other side of the boundary. Those are the only two moves, and they are the same two moves at every scale.

Compatibility — nothing here was designed cleanly

The 8-bit byte because System/360 won (0). 4 KB pages because the VAX chose it in 1977 (10). 1024 descriptors because of select's bitmap (19). Port 1024 as the privilege line (25). The Unix epoch and the 2038 problem (8). SIGSEGV named for a scheme no longer used (3). x86 real mode at every boot (36). Rings 1 and 2, unused for thirty years (3). Linux's syscall numbers, permanent by policy (4). Interfaces outlive their reasons, because the cost of changing them is borne by everyone and the benefit by no one. This is also why your own public API is the hardest thing in your system to change, and why it is worth more design attention than the code behind it.

The one force that is not in the list

Node 42 made it visible and it deserves naming: licensing, litigation and economics decided as much as engineering did. The AT&T consent decree spread Unix. The GPL made Linux safe to contribute to. The BSD lawsuit cost BSD the exact window in which Linux gathered momentum. The CDDL keeps ZFS out of the kernel. EC2's pricing model, not any technical property, is why containers matter. None of that is in the mechanisms, and all of it determined which mechanisms you use.

What to do with this

When you meet a mechanism you have never seen — a new kernel interface, a database's isolation implementation, a framework's scheduler, a cloud service's consistency model — ask, in order: which resource is being shared, and how? what stops one user harming another, and is the enforcement below their reach? what is the name and what is the real thing behind it, and where is that translation cached? which slow thing is being hidden, and what goes stale or gets lost as a result? which boundary is being crossed, and what is the batching story? and what in it is the way it is only because something in 1977 was?

Six questions. They will not tell you the answer, but they will tell you what the answer must be about, and in this material that is most of the work.
