Node 36 — boot: from no electricity to PID 1

The limitation: every process has a parent, the chain ends at PID 1, and PID 1 was started by the kernel — which is itself a program in a file that something had to load, on a machine where nothing is running.

The bootstrap problem, stated exactly: to load a program you need a program. The resolution is that the first program is not loaded at all — it is physically present in non-volatile memory, at an address the processor is wired to start from.

Power-on

When power is applied, the processor's registers are set to hardware-defined values. On x86 the instruction pointer starts at 0xFFFFFFF0, sixteen bytes below the top of the address space, and the chipset arranges for the firmware flash chip on the motherboard to be visible there. So the first instruction executed by any x86 machine is a jump into firmware, and that fact is fixed in silicon. Before even that, on any modern machine, other processors have already run: Intel's Management Engine or AMD's Platform Security Processor initialises and, on secure-boot systems, verifies the firmware before the main processor is released.

Firmware: BIOS then UEFI

BIOS — Basic Input/Output System, from the original IBM PC in 1981 — runs a power-on self test, initialises the memory controller and basic devices, and then does something remarkably crude: reads the first 512-byte sector of the boot device into memory at 0x7C00, checks that its last two bytes are 0x55 0xAA, and jumps to it. That sector is the Master Boot Record. It has 512 bytes total, of which 64 are the partition table and 2 are the signature — leaving 446 bytes for code, which is not enough to do anything except load a larger loader. Hence multi-stage bootloaders. BIOS also starts the processor in 16-bit real mode, compatible with the 1978 8086, so an operating system's first job is to switch modes.

UEFI replaced it and is what any machine built in the last decade uses. It is a small operating system in its own right: it understands the FAT32 filesystem, so it can read files from an EFI System Partition rather than raw sectors; it starts the processor in 32- or 64-bit mode; it has a boot manager with a variable store (efibootmgr edits it); and it supports Secure Boot, verifying each stage's cryptographic signature before executing it. That chain is why an unsigned kernel module fails to load on a Secure Boot system, and why installing a proprietary GPU driver requires enrolling a key or disabling the feature.

The bootloader

GRUB2 on most Linux systems, systemd-boot on some, and cloud images often use a minimal one. Its job: present a choice of kernels, then load the kernel image and the initramfs into memory, assemble the kernel command line, and jump to the kernel's entry point.

The kernel command line is worth knowing because it is where several things you configure end up: root=UUID=... (which filesystem to mount as /), ro, quiet, and options like systemd.unified_cgroup_hierarchy=1 (Node 27), transparent_hugepage=never (Node 10), nvme_core.io_timeout, or mitigations=off (Node 40 — a real performance choice with a real security cost). It is visible at run time in /proc/cmdline.

The kernel starts

The kernel image is compressed with a small decompressor stub at the front, which unpacks the real kernel into memory. Then, in rough order: set up early page tables and switch to virtual addressing (Node 10); initialise the interrupt descriptor table (Node 2); detect processors and bring the secondary cores out of halt; initialise the memory allocator, the scheduler (Node 7), and the timers (Node 8); initialise built-in drivers; and mount the initramfs.

The initramfs deserves an explanation because its existence is a chicken-and-egg fix. The kernel must mount the root filesystem, which requires a driver for the storage controller and for the filesystem — but those may be modules living on that filesystem. So the bootloader loads a small compressed archive into memory, the kernel unpacks it as a temporary root, and it contains exactly the modules and tools needed to find and mount the real root: storage drivers, LVM, disk encryption (this is where the passphrase prompt comes from), and network filesystem support. Once the real root is mounted, the initramfs is discarded.

Finally the kernel executes /sbin/init as PID 1 — its only exec, and the first user-mode process on the machine. Every process that will ever run descends from it (Node 5). If it cannot be started, the kernel panics with Kernel panic - not syncing: No working init found, which is what a broken initrd or a wrong root= parameter produces.

Where this is in your stack

A container has no boot, and that is the whole reason it starts in milliseconds. [EXPLAIN] Nothing in this node happens: no firmware, no bootloader, no kernel decompression, no device initialisation, no initramfs, no init system. Starting a container is clone() plus execve() (Node 28) on a kernel that is already running. A virtual machine, by contrast, performs this entire sequence — virtual firmware, virtual bootloader, a full kernel boot — which is why it takes seconds and why Firecracker's 125-millisecond boot (Node 29) is an engineering achievement: it is a stripped virtual machine monitor that skips almost all of the legacy sequence, uses a minimal kernel with direct boot, and emulates five devices.

Cloud instance startup is this node plus a configuration phase. An EC2 instance boots the sequence above, then cloud-init runs as an early service: it fetches instance metadata from the link-local address 169.254.169.254, sets the hostname, installs SSH keys, grows the root partition to the volume size, and runs your user-data script. Understanding that it is an ordinary service explains why user-data runs once by default, why its logs are in /var/log/cloud-init-output.log, and why the metadata endpoint being reachable from your application is a security concern — SSRF against it was the mechanism of the 2019 Capital One breach, and IMDSv2's session-token requirement exists to make that harder.

The kernel is the one thing containers do not bring with them, which follows from Node 26 and lands here concretely. Your Alpine container running on an Ubuntu host uses the Ubuntu kernel. So a container cannot require a newer kernel feature than the host provides, and features like cgroups v2, io_uring, and newer seccomp actions depend on the host. This is why "it works on my machine" can be a kernel version difference, and why managed Kubernetes providers publish node image versions as a meaningful thing to track.

Immutable infrastructure is a statement about this node. Rather than booting a machine and configuring it, you build an image containing the configuration and boot that. The boot sequence is unchanged; what changes is that no step after it modifies the system. Container images are the same principle, one layer up, without the boot.

What's still broken: PID 1 is running and the machine has exactly one process. Something must now start every service, in the right order, with the right dependencies, restarting them when they fail — and the design of that program was the most divisive argument in Linux for a decade.
