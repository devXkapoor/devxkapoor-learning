Node 26 — namespaces: giving a process its own view of the machine

The limitation: every process can see every other process, every mount, every network interface, and every user on the machine.

The idea, stated once

Every global resource the kernel names — the process ID space, the mount tree, network interfaces, the hostname, user IDs, the inter-process communication namespace — is turned from a single global table into a per-process pointer to a table. Processes sharing a pointer see the same table; processes with different pointers see different ones.

That is the whole mechanism. Namespaces do not restrict what a process may do; they change what exists as far as that process is concerned. [EXPLAIN] A process in its own PID namespace does not fail to kill PID 4321 on the host — it simply has no PID 4321, because in its numbering there is no such process. The isolation is by construction rather than by check, which is why it is both cheap (no per-access enforcement) and complete for the resources it covers.

Namespaces are per-task, they were added over more than a decade (the mount namespace in 2002, the user namespace only completing in 2013), and a process can be in a different namespace of each kind independently. That independence is what makes Kubernetes pods expressible.

The seven

Mount (CLONE_NEWNS, 2002) — a private copy of the mount tree. The first one, which is why its flag is generically named. Combined with pivot_root (a safer replacement for chroot), this gives a process a completely different filesystem tree: its / is the container image, and the host's filesystem simply is not present in its namespace. This is the "filesystem isolation" half of a container.

PID (CLONE_NEWPID, 2008) — a private process ID space. The first process created in a new PID namespace becomes PID 1, and processes inside cannot see or signal anything outside. They are nested: a process has a PID in its own namespace and a different one in each ancestor, so the host sees your container's PID 1 as, say, PID 28471. Two important behaviours attach to PID 1 (from Node 5, and covered fully in Node 30): signals with default actions are not delivered to it, and it inherits orphans and must reap them.

Network (CLONE_NEWNET, 2009) — a private set of interfaces, routing tables, firewall rules, and port number space. A new network namespace contains only a loopback device, initially down. To connect it to anything you create a veth pair — a virtual cable with two ends — put one end inside and attach the other to a bridge on the host. That is exactly what docker0 is, and it is why containers on the default bridge can reach each other and why publishing a port (-p 8080:80) installs a NAT rule via iptables. Because the port space is private, two containers can both bind port 3000 with no conflict, which is the single most visible benefit and follows from one sentence of this node.

UTS (CLONE_NEWUTS, 2006) — a private hostname and domain name. Named for the uname system call's utsname struct. This is why a container's hostname is its container ID.

IPC (CLONE_NEWIPC, 2006) — private System V message queues, semaphores and shared memory segments, and a private POSIX message queue mount.

User (CLONE_NEWUSER, completed 2013) — the most consequential and the most complicated. It provides a private UID and GID space with a mapping to the parent's. So UID 0 inside can map to UID 100000 outside. A process can be root in its namespace with no privilege whatsoever on the host — which is the correct solution to Node 25's ownership problems and the basis of rootless containers. It is also the only namespace an unprivileged user may create, which is what makes rootless Podman and unprivileged Docker possible. That same property has made it a recurring source of kernel privilege-escalation vulnerabilities, because it exposes a great deal of kernel code to unprivileged callers, and several distributions restrict it by default.

Cgroup (CLONE_NEWCGROUP, 2016) — hides the process's true position in the cgroup hierarchy, so a container sees its own cgroup as the root.

The calls, and what is not namespaced

Three system calls operate on them. clone() with CLONE_NEW* flags creates a process in new namespaces — the same clone() that makes processes and threads (Node 14). unshare() moves the calling process into new ones. setns() joins an existing namespace given a descriptor, and it is what docker exec and kubectl exec do. A namespace exists as long as a process is in it or something holds a descriptor to it, visible as /proc/<pid>/ns/*, and lsns lists them.

What is not namespaced is the important part, because it defines exactly how much a container is not a virtual machine:

  • The kernel itself. One kernel, shared by everything. A kernel vulnerability is a vulnerability for all containers on the machine, and a kernel panic takes them all down. This is the fundamental difference from a virtual machine (Node 29).
  • The system clock. A time namespace exists since Linux 5.6 (2020) but only virtualises the boot-time offset, and container runtimes do not generally use it. You cannot give a container a different wall-clock time.
  • Most of /proc/sys. Kernel parameters are mostly global, which is why some are settable per-container (the namespaced networking ones) and most are not.
  • The CPU count and total memory as reported by /proc. This is a real, practical gap: a container sees the host's /proc/cpuinfo and /proc/meminfo. It is why os.cpus().length lies (Node 7), why the JVM needed explicit container awareness, why nproc is wrong inside a container, and why lscpu shows 64 cores in a pod limited to one. Limits are enforced by cgroups, and cgroups are not what /proc reports.

Where this is in your stack

A Kubernetes pod is a namespace-sharing decision, and this is the clearest possible definition of one. [EXPLAIN] Containers in a pod share the network and IPC namespaces and (usually) the UTS namespace, while keeping separate mount and PID namespaces. Everything about pod behaviour follows mechanically:

  • They reach each other on localhost — same network namespace.
  • They cannot both bind port 8080 — same port space. This is the number one surprise for people who expect containers to be isolated from each other.
  • They do not share files unless you mount the same volume into both — separate mount namespaces.
  • They cannot see each other's processes unless shareProcessNamespace: true — separate PID namespaces. Setting it is how a debug sidecar can inspect the main container, and how one PID 1 can reap for all of them.
  • The pod's network namespace is created and held by an infrastructure container (the pause container) that does nothing but sleep, so the namespace survives individual containers restarting. That is why you see a pause container per pod on a node.
  • A sidecar — a service mesh proxy like Envoy — works by being in the same network namespace and having iptables rules redirect the application's traffic through it. The application needs no awareness at all, and this node is why that is possible.

Container networking, all of it, is the network namespace plus routing. Docker's bridge mode is a veth pair into a bridge with NAT. host mode is simply not creating a network namespace — the container shares the host's, so no NAT, no port mapping, full performance, and no isolation. none creates an empty one. Kubernetes CNI plugins (Calico, Cilium, Flannel) all do the same core work — create a namespace, wire an interface into it, program routes — and differ in how packets get between nodes. When you debug container networking with nsenter -t <pid> -n ip addr, you are entering a namespace explicitly.

Rootless containers are the user namespace. Podman's default mode, and Docker's rootless mode, create a user namespace mapping your UID to root inside. The container's processes believe they are root, can install packages and bind low ports inside their own namespace, and on the host are your unprivileged user. This removes the entire class of "container escape gives you host root" and is the direction the ecosystem has moved. The costs are real: some workloads need capabilities that do not survive the mapping, and file ownership inside mounted volumes goes through the ID map, which takes getting used to.

What you can do at this point: explain namespaces as per-process views rather than restrictions, name all seven and what each virtualises, explain precisely what is not namespaced and why that matters for CPU detection and for security, define a Kubernetes pod in terms of shared namespaces and derive its behaviour, and explain rootless containers.

What's still broken: a namespaced process cannot see the rest of the machine and can still consume all of it. It can allocate every byte of memory, saturate every core, and fill the disk. Isolation of view is not isolation of resources, and multi-tenancy needs both.
