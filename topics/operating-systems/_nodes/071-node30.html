Node 30 — signals, and why your container ignores docker stop

The limitation: a process is isolated and running, and nothing can tell it that something happened — that a user pressed Ctrl-C, that its child exited, that the system is shutting down.

What a signal is

A signal is a software interrupt delivered to a process: a small integer, and nothing else. No payload, no arguments, no return value. It is the mechanism from Node 2, applied one level up — asynchronous delivery that interrupts whatever the process was doing.

Delivery works like this. The kernel sets a bit in the target's pending-signal mask in its task_struct. When that process is next about to return to user mode — from a syscall, an interrupt, or a context switch — the kernel checks for pending signals. For each one it either applies the default action, or, if a handler is installed, arranges the stack so that the process resumes inside the handler and returns to where it was afterwards. So a signal is delivered when the process next runs, not at the instant it is sent, which is why signalling a stopped or uninterruptibly-sleeping process appears to do nothing (Node 5's D state).

The three restrictions that cause real bugs

One: SIGKILL and SIGSTOP cannot be handled. Deliberately — there must be a way to stop a process that refuses to cooperate. So there is no such thing as cleanup on SIGKILL: no flush, no close, no final log line. Every graceful-shutdown design must therefore happen on SIGTERM, and the OOM killer's use of SIGKILL (Node 13) is why an OOM kill gives you nothing.

Two: what a handler may do is severely restricted. A handler runs at an arbitrary point in the program — possibly in the middle of malloc, holding the allocator's lock. Calling malloc from the handler then deadlocks against the interrupted code. POSIX defines a short list of async-signal-safe functions that may be called; printf and malloc are not on it. The standard technique is the self-pipe trick: the handler writes one byte to a pipe and returns, and the main loop reads the pipe as an ordinary event. Linux later added signalfd, which turns signals into a readable descriptor directly. libuv uses exactly this, which is why in Node your process.on('SIGTERM') callback is ordinary JavaScript with no restrictions at all — by the time it runs, it is a normal event-loop callback, not a signal handler.

Three: standard signals do not queue. The pending set is a bitmask, so ten SIGCHLDs arriving while one is blocked result in one pending bit. This is why a SIGCHLD handler must reap in a loop — while (waitpid(-1, &st, WNOHANG) > 0); — rather than reaping once. Real-time signals (SIGRTMIN..SIGRTMAX) do queue and carry a small value, and are rarely used.

PID 1 is special, and this is the node's payoff

Two kernel behaviours attach specifically to PID 1 in its PID namespace:

Signals with default actions are not delivered to it. The kernel refuses, on the grounds that killing init would take down the system. So if PID 1 has not installed a handler for SIGTERM, the signal is silently discarded.

It inherits orphans and is expected to reap them (Node 5).

Now put that together with Node 28: your container's entrypoint is PID 1. Therefore:

  • docker stop sends SIGTERM, waits ten seconds, then sends SIGKILL. A Node process as PID 1 with no SIGTERM handler ignores the first signal entirely and is killed at ten seconds, dropping every in-flight request. The container appears to "take ten seconds to stop", and the cause is not slowness — it is that the polite request was discarded.
  • If your entrypoint is a shell (CMD npm start, which runs sh -c "npm start"), the shell is PID 1 and does not forward signals to its child. Your Node process never even hears about the shutdown. This is what ENTRYPOINT ["node", "server.js"] — exec form, not shell form — fixes, and it is the most common Dockerfile defect in the wild.
  • If your app spawns subprocesses, nothing reaps them, and zombies accumulate. docker run --init inserts tini as PID 1 to forward signals and reap; Kubernetes' shareProcessNamespace makes the pause container do it.

Where this is in your stack

Correct graceful shutdown in Node, with every line justified:

const server = app.listen(3000);
let shuttingDown = false;

async function shutdown(signal) {
  if (shuttingDown) return;          // a second Ctrl-C shouldn't re-enter
  shuttingDown = true;

  // 1. Fail readiness first, so the load balancer stops sending new work
  //    BEFORE we stop accepting it. Ordering matters — see below.
  healthy = false;
  await sleep(5000);                 // let the LB notice (its probe period)

  // 2. Stop accepting new connections; existing ones finish.
  server.close(() => console.log('http closed'));
  server.closeIdleConnections?.();   // Node 18.2+: drop keep-alive idlers

  // 3. Drain the rest: queue workers, then the DB pool.
  await worker.close();
  await pool.end();

  // 4. A hard deadline, below the orchestrator's grace period, so we
  //    always exit on our own terms rather than being SIGKILLed.
  setTimeout(() => process.exit(1), 10000).unref();
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));

The ordering in step 1 is the part people get wrong, and it is a race between two systems. In Kubernetes, when a pod is deleted, two things happen concurrently: the kubelet sends SIGTERM, and the endpoints controller removes the pod from the Service's endpoint list. The second propagates through kube-proxy or the service mesh on every node, which takes time. If you stop accepting connections the instant you get SIGTERM, traffic still being routed to you is refused — visible to users as a burst of 502s during every deploy. Delaying the actual shutdown by a few seconds (or using a preStop hook with a sleep) lets the removal propagate first. This is one of the most common causes of "we get errors during every rolling update", and it is not a bug in Kubernetes; it is a distributed-systems race that your process is expected to absorb.

terminationGracePeriodSeconds is the SIGKILL deadline — 30 seconds by default. Your own hard timeout must be below it, or you never exit cleanly. If your requests can legitimately take longer, raise the grace period rather than hoping.

SIGPIPE and EPIPE. Node ignores SIGPIPE and surfaces the condition as an EPIPE error on the stream instead — which is why a write to a socket the client already closed emits an 'error' event, and why an unhandled 'error' listener on a stream crashes the process. A client that navigates away mid-response is the common cause, and it is normal traffic rather than a fault.

SIGHUP as reload. nginx, Postgres, and most daemons re-read their configuration on SIGHUP rather than restarting — this is convention, not kernel behaviour, and it is why nginx -s reload keeps connections alive. SIGUSR1 and SIGUSR2 are similarly conventional: SIGUSR1 on a Node process opens the debugger port, which is a genuinely useful way to attach a profiler to a running production process.

kill does not mean kill. The command sends a signal, defaulting to SIGTERM. kill -9 is SIGKILL. Reaching for -9 first is a habit worth losing: it skips every cleanup path the program has, and if SIGTERM did not work, the reason is worth knowing — usually a missing handler, a shell as PID 1, or a D-state hang that -9 will not fix either.
