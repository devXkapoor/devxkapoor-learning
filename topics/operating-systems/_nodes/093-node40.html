Node 40 — the cost of the boundary, and the interface built to stop crossing it

The limitation: every crossing between user mode and the kernel costs real time, that cost rose sharply in 2018 for reasons unrelated to software, and high-performance systems make millions of crossings per second.

What the crossing costs, and why it grew

Node 4 put a bare syscall at roughly 50–100 nanoseconds. That figure is the register save and restore, the stack switch, the table dispatch, and the return. In processor terms it is several hundred instructions' worth of time to accomplish nothing.

Then, on 3 January 2018, Meltdown and Spectre were disclosed — a class of vulnerability arising from speculative execution (Node 0). The processor executes down a predicted path before knowing whether the prediction is right, and although it discards the architectural results, it does not undo the effects on the caches. So code can speculatively read memory it is not permitted to read, and then infer the value by timing subsequent cache accesses. Meltdown specifically let user-mode code read kernel memory, which was mapped into every process's address space for the efficiency reason in Node 11.

The mitigations were expensive and are still with us:

  • KPTI (Kernel Page Table Isolation) unmaps kernel memory from the user page table entirely. Every syscall now also switches the page table root, which means a cr3 write and, without PCID support, a TLB flush (Node 10). Syscall-heavy workloads lost anywhere from five to thirty percent.
  • Retpoline, IBRS and IBPB constrain branch prediction across privilege boundaries, adding cost to indirect calls and to context switches.
  • MDS, L1TF and later mitigations added buffer-flushing on transitions, and on some hardware disabling hyperthreading was the only complete answer — halving the apparent core count.

cat /sys/devices/system/cpu/vulnerabilities/* lists what your machine is mitigating and how. Booting with mitigations=off recovers the performance and is a real, defensible choice on a single-tenant machine running only trusted code — and an indefensible one on anything that runs untrusted code, which includes any machine running a browser or a multi-tenant workload. It is worth knowing the option exists and knowing exactly what it costs you.

The three ways to cross less

One: do not cross at all. The vDSO (Node 8) maps kernel-maintained data and a little code into every process, so clock_gettime, gettimeofday and getcpu are answered entirely in user mode at about twenty nanoseconds. This is why Date.now() shows no syscall in strace.

Two: batch. Every buffered interface in this document is this. writev and readv take an array of buffers and do one call instead of many — scatter-gather I/O, and exactly what Node's writev on a socket does when you write several chunks. sendfile copies from one descriptor to another entirely inside the kernel: no copy into user memory and back, which is the actual meaning of "zero copy" and why nginx serving a static file is dramatically cheaper than an application reading and writing it. epoll itself (Node 19) is batching: learn about a thousand ready sockets in one call.

Three: replace the interface. io_uring, by Jens Axboe, merged in Linux 5.1 (May 2019), is the most significant new kernel interface in twenty years and its design is worth understanding.

io_uring

Two ring buffers in memory shared between the process and the kernel — a submission queue and a completion queue. To request an operation you write an entry into the submission ring and advance a shared index. The kernel reads it, performs the operation, and writes a completion entry. You read completions from the other ring.

The properties that follow:

  • Many operations per crossing. Write a hundred submission entries and make one io_uring_enter call.
  • Optionally zero crossings. In polled mode (SQPOLL) a kernel thread watches the submission ring, so a busy process submits work and receives completions with no system calls at all.
  • Completion-based, not readiness-based. You are told the operation is done, not that it would not block. This is the crucial difference from epoll, and it is what makes it work for regular files — which Node 19 established that readiness fundamentally cannot handle. It is the first interface that lets a single-threaded event loop do genuinely asynchronous file I/O on Linux without a threadpool.
  • It covers almost everything — read, write, openat, close, accept, connect, send, recv, fsync, statx — with operations chainable so that one's completion triggers the next without user-space involvement.

It is not free of trade-offs. Its rapid growth in surface area produced a run of security vulnerabilities serious enough that Google disabled it in ChromeOS and Android, and several container runtimes block it in their default seccomp profiles — which is itself a nice illustration of Node 4, since blocking an interface is done by filtering its syscall numbers.

Where this is in your stack

libuv has used io_uring for some file operations since version 1.45 (2023), gated on kernel version, which for file-heavy Node workloads removes threadpool round trips and can be a large improvement. It does not change socket handling, which remains epoll. If a Node file benchmark differs markedly between two hosts with the same Node version, kernel version and libuv's io_uring gate are worth checking.

Syscall cost is a real design axis in your own code, and now you can reason about it quantitatively. A request handler that makes 2,000 syscalls at 100 ns each spends 200 microseconds in boundary crossings alone — which, on a handler with a 2 ms budget, is ten percent. So: keep a log file descriptor open rather than opening per line; write a response once rather than in forty res.write calls; use HTTP keep-alive so a request does not pay socket, connect, and a TLS handshake (Node 32); prefer a Unix socket to loopback TCP for local services (Node 31); and use stream.pipeline rather than manual read-write loops, since it uses the efficient paths. strace -c -f gives you the count directly, and it is a measurement almost nobody takes.

The same reasoning scales up unchanged. A syscall crossing is ~100 ns; a local database round trip is ~200 microseconds — two thousand times more; a cross-region call is ~100 ms. So the N+1 query problem is the syscall-batching problem at a scale where it costs a thousand times as much: 100 queries at 200 µs is 20 ms of pure round-trip time, and one query returning the same rows is 200 µs. DataLoader batching, IN (...) instead of a loop, Redis pipelining, and HTTP/2 multiplexing are all the same optimisation as writev, and recognising that is worth more than any of them individually.
