Git

A content-addressed object store that turned version control from server-side file copies into a tamper-evident graph of snapshots — walked node by node as a causal chain, from "why can't I just keep folder copies" to secrets and irreversibility.

Node 0 — The problem that exists before Git does

You have a folder of files. It changes over time. Three things go wrong immediately, and every feature in Git is a response to one of them.

The first is that you lose the past. You edit a file, the edit is bad, and the version that worked is gone. The obvious fix is to copy the folder before editing — project-old, project-backup, project-final-v2. This works for about a week, and then you have eleven folders, no idea which is authoritative, no record of what changed between any two of them, and no record of why anything changed.

The second is that you can't work on two things at once. If you're halfway through a risky change and something urgent comes up, your options are to finish the risky change first, or to abandon it, or to make yet another folder copy. All three are bad.

The third is that you can't combine work with another person. If two people each edit their own copy of the folder, there's no mechanical way to produce a folder containing both sets of edits. Someone has to sit down and manually reconcile the files, and if both edited the same file, someone has to decide line by line.

Everything below is a chain of solutions to these three, and each solution creates the conditions for the next problem.

Node 1 — Save whole snapshots, addressed by their content

The limitation: copies of a folder are unnamed, undated, unexplained, and duplicated wholesale on disk.

The first move is to stop copying folders manually and let a program keep the copies, in one hidden place, permanently. That place is .git/, and specifically .git/objects/. When you record a version, Git stores the state of every file at that instant. Not the changes — the whole state.

The interesting decision is how the stored things get named. Git doesn't number them. It runs the content through a hash function and uses the resulting forty-character string as the name. This has two consequences that matter enormously downstream: deduplication (identical content always hashes to the same name, so it's never stored twice) and integrity (tampered content produces a mismatched hash, so tampering is detectable).

  • Blob — the contents of one file, and only the contents; no filename, no path, no permissions.
  • Tree — a directory listing: a sorted set of (mode, type, hash, name) entries pointing at blobs and other trees.
  • Commit — a pointer to one tree, zero or more parent commits, author, committer, message.

Because filenames live in trees rather than blobs, renaming a file creates a new tree but reuses the existing blob. Because a tree can only contain entries, an empty directory is literally unrepresentable — hence the .gitkeep convention.

What you can do at this point: git init to create the store, and record a snapshot. Nothing else.

What's still broken: you have a pile of snapshots with no relationship between them — no notion of "before" and "after," so no history, just an unordered collection.

Node 2 — Link each snapshot to the one it came from

The limitation: snapshots exist but aren't ordered.

The fix is one field: each commit records the identifier of the commit that preceded it — its parent. That single pointer turns the pile into a chain.

Because a commit's identifier is a hash of its full content, and its content includes its parent's identifier, and that parent's identifier was a hash including its parent — the identifier of the most recent commit transitively depends on the entire history behind it. Change anything anywhere in the past and every identifier after it changes. This is the actual mechanism behind Git's tamper-evidence.

A commit with no parent is a root commit — the first one in a repository.

What you can do: git log, which walks parent pointers backward and prints each commit. git show <commit> to inspect any single one.

What's still broken: a snapshot is all-or-nothing, but your working state is never all one thing.

Node 3 — Choose what goes into the next snapshot

The limitation: a snapshot captures everything currently in the folder, but the folder always mixes finished work, half-finished work, and junk.

Git inserts a middle layer between your folder and the snapshot: the index, also called the staging area. It's a real file — .git/index — holding a list of paths and the identifier of the blob that will be recorded for each.

So there are three states of your project at any moment: the working tree (files on disk), the index (what the next snapshot will contain), and HEAD (what the last snapshot did contain). Almost every Git command is a movement between them.

git add hashes a file and points the index at it. git commit turns the index into trees and writes a commit. git status is two comparisons: index-vs-HEAD gives "staged," working-tree-vs-index gives "unstaged," and anything on disk the index never heard of is "untracked." git diff has three forms for the same reason — bare, --staged, and HEAD.

git add -p stages hunks instead of whole files, which is what makes one-logical-change-per-commit realistic. git commit -a skips the index for tracked files, which is convenient and the single habit most likely to produce incoherent history.

The index also caches each file's size and mtime from when it was last hashed — which is why git status doesn't re-hash everything on a large project.

.gitignore handles files that should never be tracked, with negation, anchoring, and directory-only matching. The rule that trips everyone: ignore rules only apply to files Git isn't already tracking — a tracked file stays tracked until you git rm --cached it.

What's still broken: you can only ever be in one place in history, so you still can't work on two things at once.

Node 4 — Name positions in history so you can be in more than one

The limitation: one line of work at a time; no way to mark a position.

A ref is a file inside .git/refs/ whose entire contents is a commit identifier. A branch is therefore a movable pointer to a commit — creating one costs one file write, which is why branching is cheap. Committing while on a branch writes the new commit, then overwrites the branch's file with the new identifier.

HEAD is how Git knows which branch you're on — normally a file containing ref: refs/heads/main, a pointer to a pointer.

A commit does not know what branch it's on — "commits on a branch" means commits reachable by walking parent links from that branch's pointer. Detached HEAD is when HEAD points directly at a commit instead of at a branch — a normal state Git uses deliberately.

Revision syntax: HEAD~3 walks back three first-parents; HEAD^2 means the second parent of a merge; main@{1} means one reflog move back. Range syntax: main..feature means reachable from feature but not main; main...feature is the symmetric difference.

Tags mark fixed points — lightweight tags are plain pointers, annotated tags are a real object with tagger/date/message/signature. Tags aren't pushed unless asked.

What's still broken: you can split into two lines of work. You cannot put them back together.

Node 5 — Combine two lines of history

The limitation: parallel branches diverge and there's no mechanical way to recombine them.

Git first finds the merge base — the most recent commit reachable from both branches. If the base is your current commit, it's a fast-forward: Git just slides your pointer, no new commit. Otherwise it's a three-way merge: compare base-to-ours and base-to-theirs per file; one side changed → take it; both changed identically → take once; both changed differently in the same region → conflict.

A conflict is not an error — it means two people edited overlapping lines since the base. Git marks it with <<<<<<< / ======= / >>>>>>>. Setting merge.conflictStyle=zdiff3 also shows the base's version, converting most guesswork conflicts into obvious ones.

A successful non-fast-forward merge produces a merge commit — a commit with two parents. This is why real history is a graph, not a line.

--no-ff forces a merge commit for traceability. Squash merge collapses a branch to one commit with no merge link. Semantic conflicts — no textual conflict, but the combined code breaks — are exactly why CI runs on the merge result.

What's still broken: history now records what actually happened, including every false start and "wip" commit — honest, but unreadable.

Node 6 — Reshape history before anyone else sees it

The limitation: the history you produce while working isn't the history you'd want read.

Foundational fact: objects are immutable. Every operation here creates new commits and moves a pointer; originals stay in the store, unreferenced.

git commit --amend replaces the tip commit with a new one. git cherry-pick takes one commit's change and reapplies it elsewhere — internally a three-way merge whose base is the picked commit's parent. git rebase is cherry-pick in a loop: replay every commit unique to your branch onto a new base, then move the pointer to the end.

Interactive rebase (rebase -i) gives an editable list: pick, reword, edit, squash, fixup, drop, exec. commit --fixup with --autosquash lets you mark corrections as you go and fold them in automatically. --onto transplants a range onto an arbitrary base.

The merge-vs-rebase trade-off: merge preserves what actually happened at the cost of readability; rebase produces a clean line at the cost of claiming events that didn't happen in that order, and changing identifiers. That's the entire reason for the rule against rewriting history others have already pulled — their copy still references the old identifiers.

What's still broken: you now have several operations that can discard work, and you're going to run one by mistake.

Node 7 — Undo, and recover from having undone

The limitation: Node 6's operations (and Node 3's add, Node 4's branch deletion) can destroy work.

Recovery is possible because nothing is ever deleted — commits become unreferenced, not gone, and unreferenced objects are only cleaned up eventually.

git reset as a table: --soft moves HEAD only (changes stay staged); --mixed (default) moves HEAD and resets the index (changes stay on disk, unstaged); --hard moves HEAD, resets the index, and overwrites the working tree (uncommitted work is gone). git restore splits the file-level cases: --staged to unstage, --worktree to discard.

git revert is different in kind — a new commit applying the inverse of an old one, so nobody's history is invalidated. It's the correct tool once something is shared.

git stash shelves uncommitted work (stashes are real commits under a hidden ref). The safety net under everything: the reflog — every HEAD/branch value change gets appended locally, with a default expiry around 90 days (reachable) / 30 days (unreachable). After a bad reset or rebase, git reflog plus git reset --hard <that> puts you back.

git clean deletes untracked files irreversibly — always -n first. ORIG_HEAD is set before every dangerous operation specifically so you can get back.

What's still broken: all of this is on one machine — one disk failure ends it, and no one else can contribute.

Node 8 — Move history between machines

The limitation: the repository lives on one computer.

A remote is just a name mapped to a URL. Every clone is a complete, independent repository with the full object store — there's no partial copy and no central authority in the protocol itself.

git fetch downloads what the other side has that you don't and updates your remote-tracking branches (origin/main) — it touches nothing else. origin/main is a local snapshot of the remote's state at your last fetch, not live. git pull is fetch plus an integration step (merge by default) — its implicitness is why so many repos have accidental merge commits. git push uploads objects and asks the remote to move a ref; it's refused if the move wouldn't be a fast-forward.

That refusal connects back to Node 6: rebasing a pushed branch means your history no longer descends from the remote's, so the push is rejected. --force-with-lease refuses if the remote moved since your last fetch — targeting the real danger (clobbering someone else's push) rather than the harmless case (rewriting your own unshared history).

Supporting machinery: upstream tracking, refspecs, fetch --prune, bare repositories, shallow/partial clones, credential helpers.

What's still broken: multiple people can now push to the same place — which means you need agreements about who pushes what, when, and after whose review.

Node 9 — Agree on how a group uses the shared repository

The limitation: Git enforces nothing socially. Two people can both push to main at 2pm.

Nothing here is a Git feature — these are conventions and platform features layered on top, necessary because Node 8 makes collaboration possible without making it orderly.

Trunk-based development (frequent integration via short-lived branches) is the dominant modern model. Feature branch + pull request is what you'll actually describe in interviews. Git Flow (heavyweight, permanent develop/release/hotfix branches) has mostly fallen out of favor for continuous delivery. Fork-and-PR is the open-source model.

The three merge buttons: regular merge preserves the branch's commits plus a two-parent commit; squash collapses to one commit with no merge link; rebase-merge replays with new identifiers and no merge commit. Small PRs reduce conflict risk mechanically — the longer a branch lives, the further the merge base recedes.

What's still broken: conventions that depend on people remembering them get violated on the day someone is tired.

Node 10 — Make the agreements automatic

The limitation: conventions are only as reliable as the least-careful person on the least-careful day.

Hooks are scripts Git runs at defined moments — pre-commit, commit-msg, pre-push locally, pre-receive on the server. .git/hooks isn't versioned, which is the entire reason Husky/lefthook/core.hooksPath exist — pointing Git at a tracked, shareable directory instead.

--no-verify bypasses hooks entirely, which tells you what a hook actually is: a convenience, never a control.

Conventional Commits (feat:, fix:, chore:) is machine-readable, enabling automated changelogs and version bumps. CI running on the merge result (not either branch) is what catches semantic conflicts. Commit signing turns authorship from an unverified text claim into something verifiable. Secret-scanning pre-commit hooks stop a credential from entering history at all — far cheaper than the Node 13 cleanup.

What's still broken: you now have a large history authored mostly by other people, and you need to interrogate it.

Node 11 — Ask questions of a history you didn't write

The limitation: history is big, old, and largely not yours. "When did this break, and why" isn't answerable by scrolling.

git log flags (--oneline, --graph, --stat, -p, --author, --since). Pickaxe (-S) finds commits where a string's occurrence count changed — the fastest way to find when a line was introduced; -G is the regex-presence variant.

git blame gives per-line last-modifier, with -w to skip whitespace and -M/-C to see through moves and copies; .git-blame-ignore-revs skips bulk-reformat commits.

git bisect binary-searches history between a known-good and known-bad commit, halving the range each step — bisect run automates it fully, and it depends on commits being atomic and individually buildable, which is the practical payoff of Node 3's discipline. git grep searches tracked content at any revision, faster than a plain recursive grep. git range-diff compares two versions of a rewritten branch.

What's still broken: the repository has been accumulating for years and has started to be slow and large.

Node 12 — Deal with size and scale

The limitation: an append-only store that never deletes eventually gets big.

Packfiles consolidate many loose objects into one file, storing similar objects as deltas against each other — this is the actual source of Git's storage efficiency, a layer beneath the snapshot model, not a contradiction of it. git gc packs objects, packs refs, and prunes unreferenced objects past their expiry window — the operation that finally makes Node 7's "recoverable but unreferenced" genuinely gone.

A committed binary is permanent — deleting it in a later commit changes nothing about storage, because the old snapshot still references it; only rewriting history removes it. Git LFS stores large binaries outside the repository. Submodules pin another repo at an exact commit (and land in detached HEAD, because a pin is a commit, not a branch). Worktrees check out a second branch into a second directory sharing one object store — often a better answer than stashing.

What's still broken: history is permanent, which is a problem when what's in it shouldn't be.

Node 13 — Trust, secrets, and irreversibility

The limitation: permanence is a feature until you commit an API key.

A pushed secret is compromised the instant it's pushed — not "at risk," compromised. The correct first action is always to rotate the credential, before any cleanup. git filter-repo is the modern tool for rewriting history to remove a file or string (filter-branch is deprecated and dangerously slow). Rewriting can't fix what it can't reach — existing clones and forks retain the old objects; cleanup makes a secret harder to find, not un-leaked.

A deployed .git directory exposes the entire source and history — a real and common vulnerability. Tokens embedded in remote URLs end up in .git/config and shell history. Signed tags extend commit signing's integrity guarantee to release points.

Where the chain gets misread

  • "A commit stores the changes." It stores a complete tree. Diffs are computed on demand; storage stays reasonable because identical content is deduplicated and packfiles compress later.
  • "A branch contains commits." A branch is one pointer. Membership is reachability — deleting a branch deletes nothing, and one commit can be on many branches.
  • "Rebase edits commits." It creates new commits with the same changes and different parents. Originals remain until garbage collection.
  • "git pull just downloads." It downloads and integrates, usually by merging — the source of most unintentional merge commits.
  • ".gitignore will untrack this file." Ignore rules only apply to untracked files. A tracked file stays tracked until explicitly removed from the index.
  • "I deleted the secret in a new commit, so it's gone." The old snapshot still references it, and it was already exposed regardless.
  • "Force-push is always dangerous." Force-pushing your own unshared branch is routine; the danger is specific — overwriting someone else's work — and --force-with-lease targets exactly that.
  • "Detached HEAD means something is broken." It means HEAD points at a commit rather than a branch — a state Git enters deliberately.
  • "Conflicts mean someone made a mistake." They mean two people edited overlapping lines since the merge base — a normal consequence of parallel work.
  • "Git and GitHub are the same." Pull requests, reviews, issues, Actions, forks-as-a-feature, and permissions are all GitHub. Git has objects, refs, and a transport protocol.

The chain in one paragraph

Git starts by storing whole snapshots of your project in a hidden database, naming each stored thing by a hash of its own contents, which gives it deduplication and tamper-detection for free. Linking each snapshot to its predecessor turns the pile into a history; inserting a staging area between your disk and the snapshot lets you choose what each entry contains; and naming positions in that history with tiny files containing commit identifiers gives you branches, which are cheap precisely because nothing is copied. Once two branches exist they must be recombinable, which requires finding their common ancestor and doing a three-way comparison, which is where conflicts come from and why they aren't errors. The history you actually produce while working is messier than the history you want read, so Git lets you replay commits onto new bases to reshape it — safely, because it never edits anything, only writes new objects and moves pointers, which is also why a log of every pointer movement makes almost any disaster recoverable within a known expiry window. Pushing history to another machine turns those pointer moves into a negotiation, and the refusal to accept a non-fast-forward push is what connects reshaping to collaboration. Everything above that layer — branching strategies, reviews, commit conventions, signing, hooks — is social agreement that Git itself does not enforce, automated only because people forget. And the permanence that makes all of it trustworthy is the same permanence that makes a leaked secret unfixable, which is the one place the design's central property becomes a liability.
