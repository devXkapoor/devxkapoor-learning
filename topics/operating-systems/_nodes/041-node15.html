Node 15 — threads: sharing an address space on purpose

The limitation: processes are isolated by design, so cooperating work must copy data through the kernel, and one process cannot use more than one core for its own computation.

The answer follows directly from Node 5's list of what a process owns. Take that list and split it in two: the things that are properties of the program as a whole, and the things that are properties of one path of execution through it.

Shared by every thread of a process: the address space and all its contents — code, globals, heap, and therefore every object; the file descriptor table; the credentials; the current directory; the signal dispositions; the resource limits; the cgroup and namespaces.

Private to each thread: the registers, including the instruction pointer; the stack; the thread ID; the signal mask; errno; scheduling priority; and thread-local storage.

A thread is that private set. [EXPLAIN] Everything else is common ground. It follows immediately that threads can pass data by writing to a shared variable — no copying, no system call, nanoseconds — and that a thread can corrupt every other thread's data by writing to the wrong place, because there is no boundary between them. Both properties come from the same fact and you cannot take one without the other.

On Linux, a thread is a process with more sharing

Linux does not implement threads as a separate concept. It has one creation call, clone(), taking flags for what the new task shares with its creator. fork() is clone() with almost nothing shared. Creating a thread is clone() with CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD — share the address space, the filesystem context, the descriptors, the signal handlers, and the thread group.

So the kernel's schedulable unit is a task, and both processes and threads are tasks. This is why threads appear in ps -eLf and in /proc/<pid>/task/, each with its own ID; why top -H shows per-thread CPU; and why the scheduler in Node 7 needs no special knowledge of threads at all. The name for a thread's own ID is the TID, and for the main thread it equals the PID.

The history is worth one paragraph because it explains an old debate you will meet in interviews. Threads can be implemented entirely in user space — a library that swaps stacks and registers without the kernel knowing — which is fast to switch and needs no privilege, but has a fatal flaw: if one such thread makes a blocking system call, the kernel blocks the whole process, and every other thread stops. The kernel cannot know they exist. That is the "N:1" or green-thread model, used by early Java and by GNU Portable Threads. The alternative, "1:1", gives every user thread a real kernel task, so blocking affects only that thread and multiple threads genuinely run on multiple cores. Linux settled 1:1 with NPTL (Native POSIX Thread Library, Ulrich Drepper and Ingo Molnár, 2003), which was a large enough improvement that it became one of the reasons Java became viable on Linux servers.

Modern language runtimes have reintroduced user-space scheduling on top of 1:1 rather than instead of it — Go's goroutines are M:N, with a runtime scheduler multiplexing many goroutines onto a pool of kernel threads and, crucially, intercepting blocking operations so that a goroutine blocking on I/O parks rather than blocking its thread. Java's virtual threads (Project Loom, final in Java 21, September 2023) do the same thing. Both are answers to the same problem the event loop answers, with a different ergonomic choice, and Node 18 gives the numbers that make all three make sense.

Where this is in your stack

A Node process has threads, and knowing which is which makes profiling possible. Run top -H -p $(pgrep -n node) on a busy server and you will see, at minimum:

  • The main thread, running the event loop and all your JavaScript. Only one, ever, per process.
  • Four libuv threadpool threads by default (UV_THREADPOOL_SIZE, max 1024). These execute file system operations, dns.lookup, and the CPU-heavy parts of crypto and zlib. They exist entirely because those operations cannot be done without blocking — Node 19 explains why file I/O in particular resists the event-loop treatment.
  • V8's background threads — concurrent marking and sweeping for the garbage collector, and background compilation and optimisation.
  • Any threads created by native addons, which is why a single sharp image resize can saturate several cores.

Two things follow. A Node process can exceed 100% CPU in top — the claim "Node uses one core" is false at the process level and true only of your JavaScript. And when a Node process is slow, the first diagnostic question is which thread: a busy main thread means a blocked event loop and the fix is in your code; four busy threadpool threads with an idle main thread means threadpool saturation and the fix is sizing or offloading; busy V8 background threads mean GC pressure and the fix is allocation behaviour.

worker_threads is a deliberately restricted version of this node. A worker shares the process — same PID, same descriptor table, same cgroup — but gets its own V8 isolate, which means its own heap, its own copy of every built-in, and no shared JavaScript objects. That last restriction is not a limitation Node imposed for simplicity; it is forced by V8's design, and V8's design is forced by the language. JavaScript has no memory model for concurrently mutated objects, and a garbage collector that can move objects cannot safely do so while another thread holds raw pointers to them. So the boundary is explicit:

  • postMessage copies, using the structured clone algorithm — deep, and therefore expensive for large payloads, and unable to carry functions, class instances' prototypes, or DOM nodes.
  • transferList moves an ArrayBuffer — the memory is not copied, ownership passes, and the sender's buffer becomes detached and zero-length. Constant time regardless of size.
  • SharedArrayBuffer is genuinely shared — the same physical pages mapped into both isolates, the one place where JavaScript has real shared mutable memory across threads. It is also the only place where JavaScript can have a data race, which is exactly why Atomics exists and why Node 16 is next.

The practical rule: workers are for CPU-bound work, because I/O-bound work is already handled better by the event loop, and each worker costs a full V8 isolate — on the order of several megabytes and tens of milliseconds to start. A pool created once at boot is the right shape; a worker per request is not. Roughly: workers when the work is computation and you want cores; the threadpool when the work is blocking I/O; a separate process when you want isolation or a separate heap; the event loop for everything else.

Browser Web Workers are the same design with a stricter boundary. A worker has no DOM, no window, no document. That restriction is not arbitrary either: the DOM is a large mutable object graph with no locking and no memory model, and permitting concurrent access to it would make every DOM operation require synchronisation. So the platform's position is that the DOM is single-threaded, permanently, and workers communicate by message. Every heavy client-side thing — a WebAssembly module, a large parse, a client-side search index, image processing, crypto — belongs in one, and OffscreenCanvas and SharedArrayBuffer exist to make that boundary less painful. Cross-origin isolation headers, from Node 3, are the price of the latter.

Postgres chose processes and MySQL chose threads, and the trade is exactly this node's: Postgres's per-connection process gives crash isolation and requires shared memory to be arranged explicitly (shared_buffers is a shared mapping); MySQL's per-connection thread is cheaper to create and shares the buffer pool naturally, at the cost that one backend corrupting memory takes the server down. Neither is wrong. Knowing which one a system chose predicts its connection-scaling behaviour immediately.

What you can do at this point: list precisely what threads share and what they do not, explain why Linux threads are tasks and what clone() unifies, identify every thread in a Node process and use that to localise a performance problem, and explain why worker_threads copies by default and what SharedArrayBuffer and transferList change.

What's still broken: two threads can now write the same variable at the same time. That sounds like a small problem and it is the hardest one in this document — it is not solvable by being careful, because the hardware does not do what the source code says.
