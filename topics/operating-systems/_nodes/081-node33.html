Node 33 — compiling, linking, and the ELF file

The limitation: programs have been assumed to exist as bytes in a file, with nothing said about how source text becomes those bytes.

The pipeline

Four stages, and they are separate programs, which is why each can fail with its own kind of error:

  1. Preprocessing — textual substitution: includes, macros, conditional compilation. Output is still source.
  2. Compiling — parse, type-check, optimise, and emit assembly for one translation unit. The compiler sees one file at a time and nothing else, which is the fact that makes stage 4 necessary.
  3. Assembling — turn assembly text into machine code (Node 0), producing an object file.
  4. Linking — combine object files into one executable.

What an object file contains, and why linking is a real problem

An object file holds machine code for its own functions, but the compiler could not know the addresses of anything defined elsewhere. So it emits placeholders and two tables describing them:

  • The symbol table — names this file defines (with offsets) and names it references but does not define (undefined symbols).
  • Relocations — a list of positions in the code that contain a placeholder, and instructions for how to patch each one once the real address is known.

The linker then does exactly two things. Symbol resolution: for every undefined symbol, find the object file that defines it. Relocation: assign final addresses to everything and patch every placeholder. [EXPLAIN]

Its two failure modes are the two ways that can go wrong, and both have exact counterparts in your daily work:

  • Undefined reference — nothing defines this symbol. A missing library, a typo, or a declaration with no definition.
  • Multiple definition — two objects define the same symbol and the linker cannot choose.

A static library (.a) is just an archive of object files with an index. The linker pulls out only the members that resolve something still undefined — which is why link order matters in C and why a library listed before the code that uses it silently contributes nothing.

ELF

The output format on Linux is ELF — Executable and Linkable Format, adopted from System V in the 1990s, replacing the older a.out. (macOS uses Mach-O; Windows uses PE/COFF. Same concepts, different containers.)

The structure worth knowing is that ELF has two views of the same bytes:

  • Section headers — the linker's view. Fine-grained: .text (code), .rodata (constants), .data (initialised globals), .bss (zero-initialised globals, which occupy no space in the file — only a size — which is why a program with a 100 MB zeroed array is a small file), .symtab, .debug_*.
  • Program headers — the loader's view. Coarse: a handful of segments, each of which is a region to mmap into memory with given permissions. This is the direct input to Node 11's address space layout: one read-execute segment for code, one read-only for constants, one read-write for data.

Useful tools: readelf -h (header — architecture, type, entry point), readelf -l (segments), nm (symbols), objdump -d (disassembly), file (a one-line summary including whether it is static or dynamic). [USE]

Two ELF types matter. ET_EXEC is a fixed-address executable. ET_DYN is position-independent — loadable at any address, which is what ASLR (Node 10) requires, and which is why essentially all modern binaries are built as position-independent executables and why file reports them, confusingly, as "shared object".

Where this is in your stack

A JavaScript bundler is a linker. The correspondence is exact rather than suggestive, and internalising it makes bundler behaviour predictable. [EXPLAIN]

Several bundler behaviours become obvious once you read that table. Tree shaking requires static imports for the same reason dead-code elimination requires static references: a linker cannot remove a function if something might look it up by name at run time, and a bundler cannot remove an export if the module might be accessed dynamically. That is why ES modules can be tree-shaken and CommonJS's require largely cannot — require(someVariable) is unresolvable at build time, exactly like a function pointer defeats a linker's reachability analysis. "sideEffects": false in a package.json is you telling the bundler that importing a module for its side effects alone never happens, which lets it drop unreferenced modules entirely — the same promise --gc-sections relies on. And two copies of React is a multiple-definition problem that the JavaScript module system, unlike a linker, does not report as an error: it silently gives you two module instances with two separate pieces of internal state, which is why hooks fail with an error about an invalid hook call rather than about duplication.

Native Node addons are this node exactly. A .node file is an ELF shared object compiled from C++ by node-gyp, linking against the Node and V8 headers. Hence: it is architecture-specific and platform-specific (Node 0), which is why npm install on your Mac produces artefacts a Linux container cannot load; it must match the ABI of the Node version, which is what NODE_MODULE_VERSION mismatch means, and what N-API was introduced to fix by providing a stable ABI across Node versions; and it needs a compiler toolchain at install time unless the package ships prebuilt binaries, which is what prebuild-install and node-pre-gyp do and why sharp installs instantly on common platforms and slowly on unusual ones.

The stages explain the errors. A syntax error is stage 2; a missing header is stage 1; undefined reference to ... is stage 4. In the TypeScript world the parallel is worth drawing carefully: tsc is stages 1–3 per file and there is no linker — type errors are compile-time and module resolution happens at run time or at bundle time. That is precisely why a project can type-check cleanly and fail at run time with a module-not-found error: the two checks are performed by different tools looking at different things, and tsc's paths being satisfied does not mean the runtime's resolver will agree.

What you can do at this point: describe the four stages and attribute an error to the right one, explain what an object file's symbol table and relocations are for and what a linker does, read an ELF file's two views, and map every bundler concept to its linker counterpart well enough to predict tree-shaking and duplicate-module behaviour.

What's still broken: the executable still contains unresolved references — to printf, to malloc, to every library function. Baking a copy of every library into every program means one security fix requires rebuilding everything on the machine, and a hundred programs carrying a hundred copies of the same code. The alternative introduces a whole new failure surface, and it is the reason an Alpine image sometimes will not run your binary.
