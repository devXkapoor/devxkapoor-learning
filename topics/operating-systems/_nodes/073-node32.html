Node 32 — the kernel network stack, from the wire to your socket

The limitation: everything so far is local. Between machines, packets are lost, reordered, duplicated and delayed, and no shared kernel arbitrates.

The socket

Introduced in 4.2BSD in 1983 by Bill Joy's group at Berkeley, the socket API deliberately reused the file descriptor (Node 22) so that network endpoints could be read and written like anything else — the "everything is a file" decision from Node 21 paying off again. socket() creates one; bind() attaches a local address and port; listen() marks it passive; accept() returns a new descriptor for one connection; connect() initiates one.

Note the shape of accept: the listening socket stays listening and each connection gets its own descriptor. A connection is identified by a four-tuple — source address, source port, destination address, destination port. That tuple is what the kernel hashes to route an incoming packet to the right socket, and it explains several limits later.

Establishing a connection, and the two queues

TCP's three-way handshake: the client sends SYN with its initial sequence number; the server replies SYN-ACK with its own; the client sends ACK. One full round trip before any data moves — and TLS adds one more (two in TLS 1.2), which is the entire reason connection reuse matters as much as it does.

The kernel keeps two queues, and conflating them is a common error:

  • The SYN queue holds half-open connections that have received a SYN and are awaiting the final ACK. Sized by net.ipv4.tcp_max_syn_backlog. Flooding it with SYNs from forged addresses is a SYN flood, and the defence — SYN cookies — is elegant: encode the connection state cryptographically into the sequence number itself so no state need be kept until the handshake completes.
  • The accept queue holds fully established connections waiting for your program to call accept(). Sized by the backlog argument to listen(), capped by net.core.somaxconn (512 on Linux by default, 4096 on recent kernels; Node passes 511 by default). When this queue is full, new connections are dropped — silently, from the client's point of view, appearing as a connection timeout or a reset.

That second queue is a real production signal. It fills when your process is not calling accept fast enough, which for a Node server means the event loop is blocked (Node 20). ss -lnt shows Recv-Q as the current accept-queue depth and Send-Q as its limit, and nstat -az TcpExtListenOverflows counts the drops. [USE] A rising ListenOverflows with healthy CPU is one of the cleanest possible diagnoses of a blocked loop.

Reliability, and flow, and congestion

TCP turns a lossy packet channel into an ordered byte stream using: sequence numbers on every byte; acknowledgements for what has been received (with selective acknowledgement, SACK, to report holes precisely); retransmission on timeout, where the timeout is derived from a smoothed round-trip-time estimate and doubles on each failure; and reordering tolerance, buffering out-of-order data until the gap fills.

Two separate limits govern how fast data flows, and people routinely confuse them:

  • Flow control protects the receiver. Every acknowledgement carries a receive window — how much buffer space remains — and the sender may not exceed it. A receiver that reads slowly shrinks the window to zero and the sender stops. This is TCP-level backpressure, and it is the same principle as the pipe in Node 22 and the stream in Node 19.
  • Congestion control protects the network. The sender maintains a congestion window it grows on success and shrinks on loss. Slow start begins with about ten packets and doubles each round trip — which is why the first ~14 KB of a response arrives in one round trip and larger responses take several, and why "keep your critical CSS under 14 KB" was ever meaningful advice. CUBIC is Linux's default: grow aggressively, halve on loss. BBR (Google, 2016) instead models the path's bandwidth and round-trip time directly rather than treating loss as the congestion signal, which performs far better on links that drop packets for reasons other than congestion — mobile networks, long-distance links — and is why enabling it on an edge server sometimes produces a startling improvement.

Bandwidth-delay product is the number that ties them together: a 100 ms round trip at 1 Gbps needs about 12 MB in flight to keep the pipe full. If the receive buffer is smaller than that, throughput is capped by latency regardless of available bandwidth. This is why net.ipv4.tcp_rmem and tcp_wmem autotuning exists and why long-distance transfers are slow until buffers are sized for them.

Closing, and TIME_WAIT

Closing is a four-way exchange (FIN, ACK, FIN, ACK) because each direction closes independently. The side that closes first then enters TIME_WAIT and stays there for twice the maximum segment lifetime — 60 seconds on Linux, not tunable without recompiling.

Two genuine reasons, both worth knowing: a delayed duplicate packet from this connection must not be delivered to a new connection reusing the same four-tuple; and if the final ACK is lost, the peer will retransmit its FIN and someone must be there to answer.

The consequence is that the side that closes first accumulates sockets in TIME_WAIT for a minute each, and since a client's source ports come from the ephemeral range (net.ipv4.ip_local_port_range, about 28,000 ports by default), a client opening more than roughly 470 connections per second to the same destination exhausts them and gets EADDRNOTAVAIL. Hence:

  • SO_REUSEADDR lets a server bind a port that has connections in TIME_WAIT. Without it, restarting a server fails with EADDRINUSE for a minute — which is why every server framework sets it, Node included.
  • SO_REUSEPORT (Linux 3.9, 2013) is different and more powerful: several processes may bind the same port, and the kernel load-balances incoming connections between them by hashing the four-tuple. This is an alternative to Node's cluster primary distributing descriptors, and it is what nginx workers use.
  • tcp_tw_reuse allows reusing TIME_WAIT sockets for new outbound connections. Note that tcp_tw_recycle, which older tuning guides recommend, was removed in Linux 4.12 because it broke badly behind NAT.
  • The real fix is not to open so many connections — keep-alive and pooling, below.

Where this is in your stack

Every network error you have seen, decoded:

  • ECONNREFUSED — the destination replied with RST: the host is reachable and nothing is listening on that port. Fast, and definitive. Usually the wrong port, or the service has not started.
  • ETIMEDOUT on connect — no reply at all. A firewall dropping silently, a wrong address, or a security group. Slow, because it waits out retransmissions.
  • ECONNRESET — the peer sent RST on an established connection: it crashed, its socket had unread data when it closed, an idle timeout expired at a load balancer, or a keep-alive connection was reused just as the server closed it. That last case is the common one in Node, and it is a race: your agent picks a pooled socket the server is simultaneously closing. Mitigations are to keep the client's idle timeout below the server's, and to retry idempotent requests on ECONNRESET.
  • EPIPE — you wrote to a connection the peer has closed (Node 30).
  • EADDRINUSE — the port is taken, or held in TIME_WAIT without SO_REUSEADDR.
  • EMFILE — descriptor limit (Node 19).

HTTP keep-alive is the direct answer to the handshake cost. A new HTTPS connection costs a TCP round trip plus a TLS round trip plus slow start; reusing one costs nothing. Node's http.Agent had keepAlive: false by default until Node 19, which meant every outbound request paid the full cost — a genuinely significant and widely unnoticed latency tax on service-to-service calls. Set keepAlive: true, set maxSockets deliberately, and prefer undici (Node's modern HTTP client, and the implementation behind global fetch), whose pooling and pipelining are considerably better. In AWS Lambda this is the single highest-value line of configuration for anything calling other services, because a function instance handles many invocations and without pooling every one re-handshakes.

A Kubernetes Service is packet rewriting, not a proxy. A ClusterIP has no process behind it. kube-proxy programs the kernel — historically with iptables DNAT rules, then IPVS for large clusters, and now increasingly eBPF via Cilium — so that a packet addressed to the Service IP has its destination rewritten to a randomly chosen pod IP by netfilter, in the kernel, on the sending node. Consequences that follow directly: load balancing is per connection, not per request, so a long-lived HTTP/2 or gRPC connection pins to one pod forever and traffic distributes badly — which is exactly why service meshes and gRPC clients need explicit load balancing. Also, the iptables ruleset grows with the number of endpoints, which is why very large clusters moved to IPVS and eBPF.

Connection tracking is a finite table and it fills up. NAT and stateful firewalling require the kernel to remember every connection in nf_conntrack. The table has a size (nf_conntrack_max), and when it is full new connections are dropped and the kernel logs nf_conntrack: table full, dropping packet. On a busy Kubernetes node with many short-lived connections this is a real and confusing outage — intermittent connection failures across every workload on the node, with all applications healthy. Diagnose with conntrack -C against nf_conntrack_max.

Head-of-line blocking, at three layers, which is the clearest way to see why HTTP evolved. HTTP/1.1 has it at the request layer: one response must complete before the next on that connection, which is why browsers open six connections per host. HTTP/2 multiplexes streams over one connection and removes it at the HTTP layer — but not at the TCP layer, because a single lost packet stalls every stream until it is retransmitted, since TCP must deliver bytes in order. HTTP/3 solves that by abandoning TCP entirely for QUIC over UDP, implementing reliability per-stream in user space, so one stream's loss does not block the others. It also merges the transport and TLS handshakes into one round trip. Every step of that evolution is a response to something in this node.

MTU and the mysteries it causes. Ethernet's payload limit is 1500 bytes, and TCP negotiates a maximum segment size accordingly. Overlay networks — VXLAN in Kubernetes, WireGuard, IPsec VPNs — add encapsulation headers, so the effective MTU inside is smaller. If a packet is too large and the "don't fragment" bit is set, a router should return an ICMP "fragmentation needed" message, and path MTU discovery adjusts. When a firewall blocks that ICMP message — which many do, in the name of security — you get a PMTU black hole: small requests succeed and large ones hang forever. The classic symptom is that curl of a health endpoint works and a POST with a large body times out, on the same connection path. It is one of the most maddening network bugs there is, and recognising the signature saves days.

DNS in Kubernetes is a latency source people miss. The default ndots: 5 in a pod's /etc/resolv.conf means any name with fewer than five dots is first tried against every search domain — so resolving api.example.com issues four or five failing queries before the right one, for both A and AAAA records. Fixes: a trailing dot to make the name absolute, an explicit dnsConfig with a lower ndots, or NodeLocal DNSCache. Also relevant from Node 19: dns.lookup uses the threadpool, so slow DNS blocks file I/O too.
