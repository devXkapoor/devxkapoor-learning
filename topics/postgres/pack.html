Postgres

Files lose updates and corrupt on crash, so one server takes ownership of the bytes — and every layer after that, from B-trees to MVCC to VACUUM to pooling, exists because the layer before it left something specifically broken.

Read this in order. Each node exists because the one before it left something specifically broken, and the broken thing is named at the bottom of every node. If you follow the chain you should be able to derive most of Postgres rather than memorise it.

Depth markers appear inline. [EXPLAIN] means you should be able to explain it out loud, from first principles, with no notes. [USE] means you must be able to use it correctly and debug it when it breaks, without needing the internals cold. [AWARE] means know it exists, know what problem it solves, and know roughly when to reach for it.

Node 0 — before a database: your data is files

You have a program, and the program has data it must not forget when it stops running. The obvious move — the one everybody makes first, and the one most tutorials start from — is to write the data into a file. A JSON file, a CSV, a folder of files with one per record. This works, and it keeps working for a surprisingly long time, which is exactly why it is worth understanding what eventually kills it.

The first thing that breaks is concurrency. One process reads the whole JSON file into memory, changes one field, writes the whole file back. A second process does the same thing at the same time. Whichever one writes second wins completely, and the other one's change is gone with no error, no warning, and nothing in any log. This is called a lost update, and it is not a rare race — on a web server handling two requests at once it is the normal case. You can try to fix it with a lock file, and then you discover the second problem: if the process holding the lock is killed, the lock file stays on disk forever and your application is dead until a human deletes it.

The second thing that breaks is crash safety. Writing a file is not one action. The operating system takes your bytes, holds them in memory, and writes them to the physical disk whenever it feels like it — possibly seconds later. If the machine loses power in that window, you get a file that is half the old content and half the new, or a file of the correct length full of zeroes. There is no "half-written" state you designed for, so your program will either crash reading it or, worse, read it successfully and act on garbage.

The third is finding things. With a thousand records you read the file and filter in a loop. With ten million you cannot hold the file in memory, and even if you could, answering "which users signed up in March" means touching every single record. There is no way to ask a question and have the answer arrive in time.

The fourth is structure and truth. Nothing stops one record having "age": 30 and the next having "age": "thirty" and a third having no age at all. Nothing stops an order referring to a customer who was deleted last week. Every one of those invariants has to be enforced by every piece of code that ever writes to the file, forever, including the code you write at 2am and the one-off script you ran once.

And the fifth is partial failure. "Move money from account A to account B" is two writes. If the process dies between them, the money has vanished. There is no mechanism in a filesystem for "these two changes happen together or neither happens."

Every one of those five failures is something a database management system exists to solve, and Postgres in particular solves them with a specific set of mechanisms that the rest of this chain walks through in the order they became necessary.

What's still broken: files give you no concurrency control, no crash safety, no way to search efficiently, no way to enforce that the data means anything, and no way to group changes so they happen together or not at all.

Node 1 — a server that owns the data

The limitation: every one of Node 0's problems comes from many independent processes touching the same bytes with no coordinator.

The foundational move is to stop letting application code touch storage at all. Instead, one long-running program — the database server — is the only thing that ever reads or writes the data files. Everyone else asks it. That single decision is what makes concurrency control, crash recovery, and enforced structure possible, because now there is one place where all the rules can live.

Postgres [EXPLAIN] is that program. It came out of Berkeley in 1986, led by Michael Stonebraker, as the successor to an earlier database called Ingres — hence "post-Ingres", POSTGRES. It originally had its own query language called QUEL. In 1994 two Berkeley students bolted SQL onto it and called the result Postgres95; in 1996 it was renamed PostgreSQL, given to a volunteer community, and it has shipped roughly one major version a year ever since. The current major version is 18, released September 2025; 19 is expected around September 2026. It is not owned by a company. The name is officially PostgreSQL, everyone says Postgres, and the project accepts both.

You talk to it over a network socket. The default port is 5432 [USE] — an arbitrary number the project registered as its own; nothing about the digits is meaningful. Your program opens a TCP connection to that port, authenticates, and then speaks a documented binary format called the frontend/backend protocol [AWARE]. You almost never write that protocol yourself; you use a driver — pg or postgres.js in Node, psycopg in Python — which is a library that speaks it for you. psql [USE] is the official command-line client, and it is worth being fluent in: psql "postgres://user:pass@host:5432/dbname" connects, \dt lists tables, \d tablename describes one, \l lists databases, \q quits.

The thing you connect to is a cluster [EXPLAIN] — a confusing word, because it does not mean multiple machines. A Postgres cluster is one server process managing one directory on disk (the data directory, usually something like /var/lib/postgresql/18/main) which contains multiple databases. A connection is to exactly one database and cannot see another one's tables; to query across two databases you need extensions or a second connection. Inside a database, tables are grouped into schemas [USE], which are namespaces. Every database has a schema called public that you get by default, which is why most people never think about schemas until they need multi-tenancy or want to keep an extension's objects out of the way.

The data itself lives in tables [EXPLAIN]. A table has a fixed set of named columns, each with a type, and an unordered bag of rows. "Unordered" is important and routinely misunderstood: a table has no inherent order, and a query without ORDER BY may return rows in any order at all — including a different order tomorrow, for the same data, because the server chose a different way to read it. This is the relational model, proposed by Edgar Codd at IBM in 1970, and the point of it is that data is stored as plain values in named columns rather than as pointers between records, so that new questions can be asked later without restructuring anything.

What you can do at this point: run a server, create a database, create tables, insert rows, and read them back from more than one process without the file itself being corrupted.

What's still broken: the server accepts whatever you put in the columns. A user row with no email, a negative price, an order pointing at a customer that does not exist — all of it goes in, and now every piece of code that reads the table has to defend against data that should never have existed.

Node 2 — the database as the last line of defence: types and constraints

The limitation: application code cannot be the only guardian of what is true, because there is always more than one piece of application code, and one of them is a migration script someone runs by hand.

The insight here is a shift in how you think about a database. It is not a bucket you put things in. It is a set of enforced invariants — statements that are true of your data at every moment, guaranteed by the server, regardless of which client wrote it. If the rule lives in the database, it is true. If it lives only in your validation layer, it is a hope.

The first layer of enforcement is the type [EXPLAIN] on each column. Postgres is strict about types in a way that surprises people coming from MongoDB or from MySQL's older defaults: putting a string into an integer column is an error, not a silent conversion to zero. Choosing types well is real design work, and the choices that matter most in practice are these. Use text for strings — varchar(n) is not faster, and in Postgres text and varchar are the same underlying type with varchar(n) merely adding a length check; pick varchar(n) only when the limit is a genuine business rule. Use numeric for money and anything where exactness matters, never float8, because binary floating point cannot represent 0.1 and your invoice totals will drift by fractions of a cent. Use timestamptz for every point in time [EXPLAIN] — despite the name it does not store a timezone; it converts the value you give it to UTC on the way in and renders it in the session's timezone on the way out, which is exactly what you want. Plain timestamp stores a wall-clock reading with no idea what part of the world it refers to, and is a bug waiting to be found in October. Use boolean, use uuid when identifiers must be generatable by clients or must not leak volume, and use bigint for surrogate keys because a 32-bit integer runs out at about 2.1 billion and the migration to fix that under load is genuinely painful.

The second layer is constraints [EXPLAIN], and there are five that matter. NOT NULL says the column must always have a value. CHECK (price > 0) enforces an arbitrary boolean expression per row. UNIQUE says no two rows share this value. PRIMARY KEY is UNIQUE plus NOT NULL plus the declaration that this is the row's identity. And FOREIGN KEY [EXPLAIN] says this column's value must exist as a primary key in another table — this is what makes "orders always belong to a real customer" a fact rather than an aspiration. Foreign keys also decide what happens on delete: ON DELETE RESTRICT (the default) refuses to delete a customer who has orders, ON DELETE CASCADE deletes the orders too, and ON DELETE SET NULL orphans them deliberately.

NULL [EXPLAIN] deserves its own explanation because it is the most common source of quietly wrong query results. NULL does not mean zero and does not mean empty string; it means unknown. This makes SQL's logic three-valued: NULL = NULL is not true, it is NULL, which is why you must write IS NULL and never = NULL. WHERE status != 'archived' will silently exclude every row where status is NULL, because "unknown is not equal to archived" evaluates to unknown, and unknown rows are not returned. Aggregates skip nulls, so AVG(score) over ten rows where four are null averages six numbers, not ten. And by default UNIQUE permits many NULLs in the same column, because two unknowns are not known to be equal — Postgres 15 added UNIQUE NULLS NOT DISTINCT if you want the other behaviour.

Two smaller things belong here because they appear in every schema. Identity columns: the old way to get an auto-incrementing key was SERIAL, which is not a type at all but a macro that creates an integer column plus a sequence object plus a default. The modern spelling, since Postgres 10, is GENERATED ALWAYS AS IDENTITY [USE], which is standard SQL and has cleaner ownership semantics. Either way, sequences are not transactional — a rolled-back insert still consumed the number, so your IDs will have gaps, and that is normal and not a bug. And DEFAULT, which fills in a value when the insert does not supply one, most usefully DEFAULT now() on a created_at column.

What you can do at this point: design a schema where the impossible states are actually impossible, and where a bug in one service cannot poison the data for every other reader.

What's still broken: you can store correct data and retrieve rows, but the moment you want to answer a real question — combining tables, grouping, summarising — you need a language for asking, and you need to understand that you are asking rather than instructing.

Node 3 — SQL is a question, not a program

The limitation: you know how to store rows; you have no way to express "the ten customers who spent the most last quarter" without writing a loop in your application and pulling every row across the network.

SQL [EXPLAIN] is declarative. This is the single most important thing to internalise about it, and it is what separates people who use databases from people who fight them. When you write a query, you are not writing instructions for how to get the data. You are writing a description of the result you want, and the server decides how to produce it. Two queries that look completely different can execute identically; one query can execute in two entirely different ways on Tuesday and Wednesday because the amount of data changed. This is why "optimising SQL" so rarely means rewriting the text, and so often means giving the server better information or better tools.

The core shape is SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT. It is worth knowing the logical evaluation order, which is not the order you write them in: FROM (assemble the source rows, including joins), then WHERE (discard rows), then GROUP BY (collapse rows into groups), then HAVING (discard groups), then SELECT (compute the output columns), then ORDER BY, then LIMIT. That order explains two things that otherwise look arbitrary — why you cannot use a SELECT alias in the WHERE clause (the alias does not exist yet) but can use it in ORDER BY (it does by then), and why WHERE filters rows while HAVING filters groups.

Joins [EXPLAIN] are how the relational model pays off. Because a customer's data lives in one table and their orders in another, connected by an id, you can ask questions that were never anticipated when the schema was designed. INNER JOIN keeps only rows that matched on both sides. LEFT JOIN keeps every row from the left table, filling the right side with NULLs where nothing matched — this is the one you want for "all customers and their order count, including customers with none." The classic bug here is putting a condition on the right-hand table in WHERE instead of in the ON clause of a LEFT JOIN: WHERE o.status = 'paid' throws away the null-filled rows and silently turns your left join back into an inner join. FULL OUTER JOIN keeps unmatched rows from both sides. CROSS JOIN produces every combination, which is occasionally what you want and much more often what you accidentally wrote by forgetting a join condition.

Aggregates — COUNT, SUM, AVG, MIN, MAX — collapse many rows into one value, and GROUP BY says which rows collapse together. COUNT(*) counts rows; COUNT(column) counts non-null values in that column; the two differ and interviewers know it. Subqueries let a query contain a query, either producing a value (WHERE price > (SELECT AVG(price) FROM products)), a set (WHERE id IN (SELECT ...)), or a whole table you join against. EXISTS is usually the right way to ask "does a matching row exist", because it can stop at the first hit.

Three modern pieces belong in your working vocabulary. INSERT ... ON CONFLICT [USE], added in 9.5, is Postgres's upsert: ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name inserts or updates atomically without a read-then-write race. RETURNING [USE] is a Postgres speciality — INSERT ... RETURNING id gives you back the generated row in the same round trip, and it works on UPDATE and DELETE too. And MERGE, added in Postgres 15, is the SQL-standard multi-way version for when ON CONFLICT is not expressive enough.

What you can do at this point: ask essentially any question of your data and get a correct answer.

What's still broken: correct, but not necessarily fast. To understand why a query takes ten milliseconds or ten seconds, you have to stop treating the table as an abstract set of rows and find out what it actually is on disk.

Node 4 — what a table really is: pages, tuples and the heap

The limitation: query performance is invisible while a table is an abstraction. Every performance concept from here on is a consequence of the physical layout.

A table's data lives in a file — actually a set of files, since Postgres splits them at 1 GB — collectively called the heap [EXPLAIN]. The word "heap" here means unordered pile, and that is literal: rows sit wherever there was room, in no particular order, and inserting a row does not put it anywhere meaningful.

The heap is divided into fixed-size blocks called pages, and a page is 8192 bytes — 8 KB [EXPLAIN]. This number is a compile-time constant, effectively universal, and it is the atom of everything Postgres does with storage: it reads a page, it writes a page, it caches a page, it never deals in half a page. Almost every performance number you will ever look at is really a count of pages.

Inside a page there is a small header, then a line pointer array growing downward from the top, then the row data growing upward from the bottom, with free space in the middle. Each row — Postgres calls a stored row a tuple — has a 23-byte header (padded to 24) before its actual column data. That header is where the transaction machinery in Node 8 lives, so remember it exists. A row's physical address is its ctid [AWARE], a pair of numbers (page, line-pointer), and you can literally SELECT ctid, * FROM t to see it. A ctid is not stable: any update can move the row, so never store one.

Two consequences follow immediately and both matter. First, a row cannot span pages, so a row cannot exceed 8 KB — which would make storing a long article impossible, except for TOAST [EXPLAIN] ("The Oversized-Attribute Storage Technique"). When a row would exceed roughly 2 KB, Postgres compresses the large variable-length values, and if that is not enough it moves them out into a hidden side table, chopped into chunks, leaving a small pointer in the main row. This happens automatically and invisibly. Its practical effect is that a text column holding a megabyte of JSON costs you almost nothing to SELECT unless you select that column, and that SELECT * on a wide table can be dramatically more expensive than selecting the four columns you needed.

Second, column order affects table size [AWARE]. Postgres aligns values on boundaries — an int8 must start at an 8-byte boundary — so a table declared as bool, int8, bool, int8 wastes seven bytes of padding after each boolean, while int8, int8, bool, bool does not. On a small table this is irrelevant; on a billion rows it is gigabytes. The rule of thumb is to declare fixed-width columns largest-first, then variable-length, then nullable.

Now the performance consequence. To answer SELECT * FROM users WHERE email = 'x' with nothing but a heap, Postgres must read every page of the table and check every row. This is a sequential scan [EXPLAIN], and it is not inherently bad — reading a small table sequentially is the fastest possible thing, because it is one long streaming read and modern disks love those. It becomes catastrophic with size: a 50 GB table means reading 6.5 million pages to find one row, and doing that for every request means the table is read hundreds of times per second while 99.99% of the work is discarded.

Before we can fix that, one more piece: Postgres does not read from disk directly on every access. It keeps a cache of pages in memory called shared_buffers [EXPLAIN], shared across all connections, defaulting to a very conservative 128 MB and conventionally set to about 25% of the machine's RAM. Underneath it, the operating system keeps its own cache of the same files, so a page not in shared_buffers is often still in memory. This double-caching is peculiar to Postgres and it is why effective_cache_size, a setting that changes no memory allocation at all, still changes query plans — it tells the planner how much total caching to assume exists.

What you can do at this point: reason about a query's cost in pages read, and explain why SELECT * is not free.

What's still broken: finding one row in a large table still means reading the whole table, because nothing in the heap knows where anything is.

Node 5 — indexes: a second structure that knows where things are

The limitation: the heap is unordered, so every lookup is a full scan.

An index [EXPLAIN] is a completely separate data structure, stored in its own files, that maps values to the physical locations of the rows containing them. It is a redundant copy of one part of your data, maintained automatically, kept in an order that makes searching cheap. That framing explains its costs immediately: an index takes disk space, and every INSERT, UPDATE and DELETE must update every index on the table, so indexes make reads faster and writes slower. Ten indexes on a hot write table is a real problem, and unused indexes are pure cost.

The default and overwhelmingly most important type is the B-tree [EXPLAIN] — specifically a B+tree. Picture a shallow, extremely wide tree. The leaves hold every indexed value in sorted order, each paired with the ctid of its row, and the leaves are linked to each other. Above them, internal pages hold separator values that say "keys below this go left, above it go right." Because each 8 KB page holds hundreds of keys, the fan-out is enormous: a table of a hundred million rows typically has a B-tree only four levels deep. So finding a row is four page reads instead of six million, and the top levels are always cached. That is the entire magic, and you should be able to say it in one breath.

Because the leaves are sorted and linked, a B-tree serves more than equality. It serves range queries (>, <, BETWEEN), because you descend once and then walk sideways. It serves ORDER BY on the indexed column, letting Postgres skip the sort entirely. It serves prefix matching (LIKE 'abc%', but not LIKE '%abc' — a suffix has no position in a sorted structure, which is a very common interview question). And it serves MIN/MAX by reading one end.

Composite indexes [EXPLAIN] are where most real index knowledge lives. An index on (tenant_id, created_at) sorts by tenant_id first and, within equal tenants, by created_at. This means it can answer "rows for tenant 7", "rows for tenant 7 ordered by date", and "rows for tenant 7 in a date range" — but it is nearly useless for "all rows in a date range regardless of tenant", because the dates are scattered across every tenant's section. This is the leftmost prefix rule: a composite index is usable for a query that constrains a prefix of its columns. The corollary for ordering: put equality columns first, then the range or sort column.

Several refinements are worth knowing by name. A partial index [USE] — CREATE INDEX ... WHERE deleted_at IS NULL — indexes only some rows, which for a table where 98% of rows are soft-deleted or completed makes the index a fiftieth of the size. An expression index — CREATE INDEX ON users (lower(email)) — is required if you query WHERE lower(email) = ..., because a plain index on email cannot help a query about a function of email. A covering index with INCLUDE (...), added in Postgres 11, carries extra columns in the leaves without them being part of the sort key.

That last one exists to enable an index-only scan [EXPLAIN], and understanding why requires one honest admission about Postgres. Normally an index gets you a ctid, and then Postgres must go read the heap page to fetch the row — because, and this is the crucial part, the index does not know whether the row is visible to you (Node 8 explains why). So an index scan is two reads, not one. If every column the query needs is in the index, Postgres would like to skip the heap entirely, and it can — but only for pages marked all-visible in a structure called the visibility map, which is maintained by VACUUM (Node 9). This is why "my index-only scan is doing heap fetches" is a vacuum problem, not an index problem.

When a query matches many rows, following the index one row at a time produces random heap access all over the disk, which is slow. So Postgres has a middle strategy: a bitmap scan [EXPLAIN]. It reads the index, builds an in-memory bitmap of which pages contain matching rows, sorts it, and then reads those pages in physical order, checking rows as it goes. This is why EXPLAIN shows a Bitmap Index Scan feeding a Bitmap Heap Scan, and it is also how Postgres combines two separate indexes for one query by AND-ing or OR-ing their bitmaps.

The other index types exist because B-trees only understand ordering. GIN [USE] (Generalized Inverted Index) is for values that contain many searchable items — array elements, JSONB keys, full-text search lexemes — and it maps each item to the list of rows containing it. GiST [AWARE] is a framework for indexing things with overlap and containment rather than order: geometric shapes, ranges, nearest-neighbour searches; PostGIS is built on it. BRIN [AWARE] (Block Range INdex) stores only the min and max value per group of pages, making it tiny — it is superb for an append-only time-series table where physical order already correlates with time, and useless otherwise. Hash indexes support only equality and are rarely worth choosing. And HNSW/IVFFlat, from the pgvector extension, index embedding vectors for similarity search — the thing qbank would need for semantic retrieval.

Finally, a specific trap: Postgres does not automatically create an index on the referencing side of a foreign key [USE]. It indexes the referenced primary key, because that already has one, but orders.customer_id gets nothing. So SELECT * FROM orders WHERE customer_id = 7 is a sequential scan, and deleting a customer scans the whole orders table to check the constraint. Almost every slow schema has this bug somewhere.

What you can do at this point: make specific queries fast on purpose, and explain the cost you paid for it.

What's still broken: you can create an index and the query gets slower, or stays the same, and nothing tells you why — because you cannot see what the server decided to do.

Node 6 — the planner, and reading EXPLAIN

The limitation: SQL is declarative, so the mapping from your query to actual work is invisible, and guessing at it is how people spend a week on the wrong index.

Between your query text and the data there is a planner (or optimiser) [EXPLAIN]. It takes the parsed query, enumerates many possible ways to execute it — which index to use or none, which order to join the tables, which join algorithm — assigns each a cost, and picks the cheapest. Cost is an abstract number, not milliseconds; it is built from tunable constants where a sequential page read is defined as 1.0, a random page read defaults to 4.0, and processing one row is 0.01. Those defaults were calibrated for spinning disks; on SSDs random_page_cost is conventionally lowered to about 1.1, and that single change is one of the most impactful pieces of Postgres tuning there is, because at 4.0 the planner systematically undervalues indexes.

To assign costs, the planner needs to guess how many rows each step will produce, and for that it uses statistics [EXPLAIN]: per-column samples stored in pg_statistic, including the fraction of nulls, the most common values and their frequencies, and a histogram of the distribution. These are gathered by ANALYZE, run automatically by autovacuum. When statistics are stale or unrepresentative, the estimates are wrong, and a wrong estimate is the root cause of most catastrophic plans — the planner thinks a step returns 5 rows, chooses a nested loop, and the step actually returns 500,000.

EXPLAIN [EXPLAIN] shows you the chosen plan. EXPLAIN ANALYZE actually runs the query and shows the plan annotated with reality — and the single most valuable habit you can build is reading it as a comparison: rows=100 versus actual rows=98000 in the same line tells you the planner was wrong by three orders of magnitude, and that is your bug. Add BUFFERS to see pages read and whether they came from cache: EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT .... Read the output inside out — the most indented lines execute first and feed their parents. Note that timings and row counts on inner nodes are usually per loop, so a node showing actual time=0.02 rows=1 loops=200000 did forty seconds of work, not twenty microseconds.

The node types you must recognise: Seq Scan (read the whole table), Index Scan (walk the index, fetch each row from the heap), Index Only Scan (walk the index, skip the heap), Bitmap Index Scan / Bitmap Heap Scan (the two-phase strategy from Node 5), Sort, Hash, Aggregate, Gather (parallel workers merging).

The three join algorithms are worth genuinely understanding, because choosing between them is most of what the planner does. A Nested Loop takes each row from the outer side and looks up matches on the inner side — brilliant when the outer side is tiny and the inner side is indexed, disastrous when the outer side turns out to be large. A Hash Join builds a hash table of the smaller side in memory, then streams the larger side past it — the workhorse for joining two big tables on equality, and it needs enough work_mem or it spills to disk in batches. A Merge Join requires both sides sorted on the join key and walks them together like merging two sorted lists — good when the sorts are free because indexes already provide the order.

Which brings us to work_mem [USE], the most consequential and most misunderstood memory setting. It is the amount of memory allowed per sort or hash operation, defaulting to 4 MB — not per query and certainly not per server. A single complex query can have several such operations, and a hundred connections can run them concurrently, so the real worst-case memory usage is roughly work_mem × operations × connections. Set it too low and sorts spill to temporary files on disk, which EXPLAIN ANALYZE will tell you (Sort Method: external merge Disk: 24000kB). Set it too high and the machine runs out of memory under load.

Two practical notes. The planner can be nudged but not commanded: Postgres deliberately has no query hints [AWARE], unlike Oracle or MySQL, on the philosophy that hints become permanently wrong as data changes. The escape hatches are SET enable_seqscan = off for diagnosis only, CREATE STATISTICS for correlated columns whose combination the planner misjudges, and raising the statistics target on a skewed column. And since 9.6, Postgres can use parallel workers for large scans, joins and aggregates, controlled by max_parallel_workers_per_gather — which is why plans on big tables show Gather and why the row counts underneath it are per worker.

What you can do at this point: take a slow query, read its plan, identify whether the problem is a missing index, a bad estimate, or a spill to disk, and fix the right one.

What's still broken: you can now make a single query fast and correct, but you still have no way to make several statements happen as one indivisible change — Node 0's "move money between accounts" is still unsolved.

Node 7 — transactions, the WAL, and why a commit is trustworthy

The limitation: every statement so far has been independent. A failure between two of them leaves the database in a state your application logic says is impossible.

A transaction [EXPLAIN] is a group of statements that either all take effect or none do. You write BEGIN, then your statements, then COMMIT to make them permanent or ROLLBACK to discard them. If the connection drops or the server crashes mid-transaction, the effect is a rollback. In Postgres every statement is always inside a transaction — if you did not open one, the server wraps that single statement in its own, which is called autocommit and is the default in psql and in every driver.

The guarantees are the four letters of ACID [EXPLAIN], and it is worth stating each in terms of a specific failure it prevents. Atomicity: all or nothing, so money never disappears between two updates. Consistency: constraints hold at commit, so no transaction can leave a foreign key dangling. Isolation: concurrent transactions do not see each other's half-finished work — this one is large enough that Node 10 is devoted to it. Durability: once COMMIT returns, the change survives the machine losing power one millisecond later.

Durability is the interesting one mechanically, because Node 0 established that writing to a file does not mean the data is on disk. Postgres solves it with the WAL, the Write-Ahead Log [EXPLAIN]. The rule is in the name: before any change to a data page is allowed to reach disk, a record describing that change must be written to the log and physically flushed. The log is a sequence of files, written strictly sequentially, in pg_wal/. When you COMMIT, Postgres writes a commit record to the WAL and calls fsync — the operating system call that says "do not return until this is genuinely on the physical medium" — and only then tells you the commit succeeded. The modified data pages themselves are still sitting dirty in shared_buffers and may not be written for minutes.

This looks like extra work but it is the opposite. Sequential writes to one log file are enormously faster than scattered random writes across a large table, so the WAL turns every commit into one append. The dirty pages are written out lazily and in bulk by background processes, and periodically Postgres runs a checkpoint [USE] that flushes all dirty pages and records that everything before this point is safely on disk. If the server crashes, recovery replays the WAL from the last checkpoint forward, redoing every change that was logged but not yet written to its data page. Because the replay is deterministic and idempotent, the database comes back exactly as it was at the last successful commit — and this is why "Postgres crashed and I lost data" is essentially always a configuration problem (fsync = off, or lying disk hardware) rather than a Postgres problem.

Two more consequences of the WAL, both of which pay off later. Because the WAL is a complete description of every change, shipping it to another machine and replaying it there produces an identical copy — that is replication, in Node 18. And because you can stop replaying at any point, keeping a base backup plus the WAL since then lets you restore the database to any moment — point-in-time recovery, also Node 18.

Two practical settings. synchronous_commit [USE] can be set to off, which makes commits return before the WAL is flushed. This is not corruption-unsafe — the database stays consistent — but it means the last fraction of a second of committed transactions can be lost in a crash. For a background job queue that is often a perfectly good trade for a large throughput gain; for payments it is not. And full_page_writes exists because an 8 KB page write can be torn by a power failure mid-write, so the first change to a page after each checkpoint logs the entire page image. It is why WAL volume spikes right after a checkpoint.

One Postgres-specific delight: DDL is transactional [EXPLAIN]. CREATE TABLE, ALTER TABLE, DROP TABLE, CREATE INDEX all participate in transactions and roll back cleanly. Oracle and MySQL cannot do this. It is the reason a Postgres migration tool can wrap a whole migration in BEGIN ... COMMIT and guarantee you never end up half-migrated, and it is a genuinely strong answer when an interviewer asks why a team chose Postgres.

What you can do at this point: group changes so they are atomic, and explain precisely why a returned COMMIT is a promise the hardware will keep.

What's still broken: transactions are safe against crashes but you have not been told what happens when two of them touch the same row at the same time — and the obvious implementation, locking everything, would mean one writer freezes every reader.

Node 8 — MVCC: how readers and writers stop blocking each other

The limitation: if a transaction must lock a row before reading it so that nobody changes it mid-read, then a single long report query blocks all writes, and a single slow write blocks all reads. That is unusable.

Postgres's answer is MVCC — Multi-Version Concurrency Control [EXPLAIN] — and it produces the single most quotable property of the system: readers never block writers, and writers never block readers. Only two writers touching the same row block each other.

The mechanism is simpler than the name suggests, and it lives in the 23-byte tuple header from Node 4. Every transaction gets a monotonically increasing transaction id (xid). Every stored tuple carries two of them: xmin, the transaction that created this version, and xmax, the transaction that deleted or superseded it (zero if still live). You can see them: SELECT xmin, xmax, * FROM accounts.

Now the crucial part. An UPDATE in Postgres does not modify the row in place. It writes an entirely new tuple with the new values and xmin set to the current transaction, and sets xmax on the old tuple. Both versions physically exist in the heap simultaneously. A DELETE merely sets xmax on the existing tuple and writes nothing new.

When a transaction starts a statement, it takes a snapshot: the set of transactions that had committed at that instant. Every time it considers a tuple, it applies visibility rules — roughly, this version is visible if its xmin committed before my snapshot and its xmax is either absent or belongs to a transaction that had not committed. So each transaction sees a consistent version of the whole database as of a single instant, without holding a single lock on anything it reads.

That is why the report query does not block writers: the writer is appending new versions, and the reader is looking at old ones that still exist. It is also why SELECT count(*) in Postgres is genuinely slow on a big table — the count depends on who is asking, so there is no maintained counter to read; every row's visibility must be checked. And it is the deep reason an index scan must visit the heap: the index entry points to a tuple, but only the tuple's header knows whether your transaction may see it.

One important optimisation: HOT updates [AWARE] (Heap-Only Tuples, since 8.3). If an update changes no indexed column and the new version fits on the same page as the old, Postgres chains the new version to the old within the page and does not touch any index at all. This makes updates dramatically cheaper, and it is why leaving some free space per page via fillfactor (default 100, often lowered to 90 on heavily-updated tables) can matter, and why indexing a column that changes constantly costs more than the index's own size.

It is worth naming what is distinctive here. Oracle and MySQL's InnoDB also do MVCC, but they keep old versions in a separate undo log and update the row in place. Postgres keeps every version in the table itself. That choice makes rollback instantaneous and reads simple — and it creates a problem those other systems do not have, which is the entire subject of the next node.

What you can do at this point: explain why a long-running analytics query on a busy Postgres does not block the application, and why count(*) is not free.

What's still broken: every update leaves a dead body in the table. Nothing so far removes them, so the table grows forever even if the row count never changes.

Node 9 — the price of MVCC: dead tuples, bloat, and VACUUM

The limitation: old row versions accumulate in the heap and in every index. A table where you update one row a million times contains a million dead tuples and one live one.

A tuple is dead once no running transaction could possibly still need to see it. Dead tuples cost you in three ways: they occupy disk, they occupy shared_buffers when their page is read, and every scan must read past them. A table whose physical size is far larger than its live data is bloated [EXPLAIN], and bloat is the most common cause of a Postgres database that was fast six months ago and is slow now with the same data.

VACUUM [EXPLAIN] is the process that reclaims them. Ordinary VACUUM scans the table, finds dead tuples, removes their index entries, and marks their space as reusable — recording it in the free space map so future inserts land there. It does not return space to the operating system; the file stays the same size and the holes get refilled. It runs concurrently with everything and takes no exclusive lock. It also updates the visibility map, which is what makes index-only scans possible (Node 5).

VACUUM FULL [USE] is a different beast that people reach for by accident. It rewrites the entire table into a new file, genuinely returning disk to the OS — while holding an ACCESS EXCLUSIVE lock, meaning nothing can read or write the table until it finishes, which on a large table is hours. It is not routine maintenance; it is a scheduled outage. The online alternative is the pg_repack extension [AWARE].

You almost never run vacuum by hand, because autovacuum [EXPLAIN] does it. A background daemon watches statistics and triggers a vacuum on a table when its dead tuple count exceeds a threshold — by default autovacuum_vacuum_threshold (50) plus autovacuum_vacuum_scale_factor (0.2) times the row count. That 0.2 is the number to remember and usually the number to change: it means a table is vacuumed after 20% of it has churned, which is fine at ten thousand rows and terrible at a hundred million, where it means waiting for twenty million dead tuples. Per-table overrides are the standard fix: ALTER TABLE big_table SET (autovacuum_vacuum_scale_factor = 0.01). Autovacuum also runs ANALYZE on its own threshold, which is how the planner's statistics stay current — so a table that autovacuum cannot keep up with has both bloat and bad plans.

The classic way autovacuum is defeated: it can only remove tuples that are invisible to every transaction, so a single connection sitting idle in transaction for six hours pins the horizon and prevents cleanup database-wide. Long-running queries, abandoned transactions in application code that forgot to commit, unused replication slots, and orphaned prepared transactions all do this. It is one of the highest-value production debugging patterns in the whole topic: table growing, autovacuum running constantly and reclaiming nothing, SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction' finds the culprit.

Then there is transaction id wraparound [EXPLAIN], which sounds exotic and has taken down real companies. The xid is a 32-bit number, so it wraps after about 4 billion transactions. Visibility is determined by comparing xids, so if the counter wraps, ancient rows would suddenly appear to be from the future and become invisible — silent, total data loss. Postgres prevents this by freezing: vacuum marks sufficiently old tuples as "committed forever, visible to everyone", removing them from the comparison. autovacuum_freeze_max_age (default 200 million) forces an anti-wraparound vacuum even on tables autovacuum would otherwise skip, and these cannot be cancelled. If freezing falls far enough behind, Postgres starts refusing writes to protect itself, and the only cure is a vacuum you can no longer run online. Monitoring age(datfrozenxid) is real production practice.

What you can do at this point: explain why a Postgres table can be 400 GB with 40 GB of data, diagnose it, and name the transaction that caused it.

What's still broken: you understand that each transaction sees a snapshot, but not when the snapshot is taken — and that single detail determines which concurrency bugs your application can still have.

Node 10 — isolation levels: which anomalies you are still exposed to

The limitation: MVCC gives each transaction a consistent view, but a transaction that reads, decides, and then writes can still be wrong if the world changed between the read and the write.

Isolation level [EXPLAIN] is the dial that says how strongly transactions are separated. The SQL standard defines four; Postgres implements three distinct behaviours (READ UNCOMMITTED is accepted as a synonym for READ COMMITTED, because MVCC makes dirty reads impossible in the first place).

Name the anomalies first, because the levels are defined by which ones they permit. A dirty read is seeing another transaction's uncommitted change — impossible in Postgres at any level. A non-repeatable read is running the same SELECT twice in one transaction and getting different values, because someone committed in between. A phantom read is running the same range query twice and finding new rows. A lost update is two transactions reading the same value, each computing a new one, and the second overwriting the first — the Node 0 problem, still live. And write skew is the subtle one: two transactions read overlapping data, each checks an invariant that holds, and each writes something that individually is fine but together breaks the invariant. The standard example is two doctors both cancelling their on-call shift, each having verified that at least one other doctor is on call.

READ COMMITTED [EXPLAIN] is Postgres's default, and its defining detail is that the snapshot is taken per statement, not per transaction. So each statement sees everything committed before that statement began. Two identical SELECTs in one transaction can absolutely return different data. It permits non-repeatable reads, phantoms and lost updates. There is one extra behaviour that catches people: if an UPDATE reaches a row that another transaction is concurrently updating, it blocks, waits for that transaction to commit, then re-evaluates its WHERE clause against the new version of the row and proceeds if it still matches. This is called an EPQ re-check and it means an UPDATE ... WHERE status = 'pending' can act on a row that was pending when the statement started but is not any more, or skip one it should have seen.

REPEATABLE READ [EXPLAIN] takes one snapshot at the first statement and holds it for the whole transaction. Every read is consistent with every other read; non-repeatable reads and phantoms are gone. In Postgres this level is stronger than the standard requires — it is really snapshot isolation. The cost is that it can now fail: if you try to update a row that was modified after your snapshot, you get ERROR: could not serialize access due to concurrent update (SQLSTATE 40001) and the transaction aborts. Your application must be prepared to retry. That is not an edge case, it is the contract.

SERIALIZABLE [EXPLAIN] guarantees the result is identical to some order of running the transactions one after another — every anomaly including write skew is eliminated. Postgres implements this with SSI, Serializable Snapshot Isolation, added in 9.1 and genuinely a piece of research-grade engineering. Rather than locking, it tracks read/write dependencies between concurrent transactions and aborts one when it detects a cycle that could not have occurred in any serial order. So it is optimistic: no blocking, but more 40001 errors under contention, and again a retry loop is mandatory.

The practical guidance: stay on READ COMMITTED, which is what everyone does, and handle the specific races explicitly with the tools in Node 11. Reach for REPEATABLE READ for reports that must be internally consistent, and for SERIALIZABLE when an invariant spans multiple rows and you would rather pay in retries than reason about every interleaving. Whatever you choose, know that any transaction can fail with a serialization error or a deadlock, so retry-on-40001-and-40P01 belongs in your database layer, once, wrapping everything.

What you can do at this point: name the anomaly a given piece of application code is exposed to, and pick the level or the lock that closes it.

What's still broken: you know when to want stronger guarantees, but you have not been told what Postgres is actually doing to enforce them, or why an innocent-looking ALTER TABLE can freeze your entire application.

Node 11 — locks: rows, tables, deadlocks, and the DDL trap

The limitation: MVCC removes locking from reads, but writes still have to be ordered somehow, and schema changes have to exclude everyone.

Locks in Postgres come in two families and they behave completely differently.

Row-level locks [EXPLAIN] are taken when you modify a row, and — a genuinely elegant detail — they are stored in the tuple itself, in the xmax field, not in a lock table. So there is no limit on how many rows you can lock; locking a million rows costs no extra memory. A transaction that wants to modify a locked row simply waits for the locking transaction to end. You can take these locks explicitly on a read: SELECT ... FOR UPDATE [USE] locks the returned rows as if you were about to update them, which is how you close the lost-update hole — read with FOR UPDATE, compute, write, commit, all while nobody else can touch those rows. FOR NO KEY UPDATE is weaker and is what a plain UPDATE of non-key columns actually takes; FOR SHARE allows other readers but blocks writers.

SELECT ... FOR UPDATE SKIP LOCKED [USE], added in 9.5, deserves special mention because it is how you build a job queue in Postgres: each worker asks for the next N pending jobs, skipping any row another worker has already locked, so there is no contention and no double-processing. This is the pattern people reach for when they do not want to run Redis and BullMQ, and knowing it is a strong signal in an interview. Its sibling NOWAIT errors immediately instead of waiting.

Table-level locks [EXPLAIN] are the ones that cause outages. Postgres has eight modes with a compatibility matrix, but you only need to reason about the ends of it. Every SELECT takes ACCESS SHARE. Every INSERT/UPDATE/DELETE takes ROW EXCLUSIVE. These are compatible with each other, which is why normal traffic never blocks. At the other end, most ALTER TABLE forms and VACUUM FULL take ACCESS EXCLUSIVE, which conflicts with everything, including plain SELECT.

And here is the trap that is worth more than any other single fact in this node. ALTER TABLE may take only a few milliseconds of actual work, but to start it must acquire the exclusive lock, and it cannot do that while any transaction — even a long-running read — holds a lock on the table. So it queues. And because lock requests are granted in order, every subsequent query queues behind it. One ALTER TABLE waiting on one slow SELECT will pile up thousands of blocked queries and take down a site that was perfectly healthy, and the ALTER never even ran. The mitigation is standard practice: always run DDL with SET lock_timeout = '3s' so it gives up rather than queueing, and retry.

Deadlocks [EXPLAIN] happen when transaction A holds a lock B wants while B holds a lock A wants. Neither can proceed. Postgres detects this — not instantly, but after deadlock_timeout (default one second) it runs a cycle-detection check on the wait graph, and kills one transaction with ERROR: deadlock detected (SQLSTATE 40P01). The most common cause in real code is updating multiple rows in an order determined by a hash map or a set, so two requests process the same rows in different orders. The fix is almost always to establish a consistent ordering — ORDER BY id before locking — rather than anything clever.

Advisory locks [USE] are Postgres's general-purpose mutex, unrelated to any row: pg_advisory_lock(key) for a session-scoped lock, pg_advisory_xact_lock(key) for one released at commit. They are how you make sure only one instance of a scheduled job runs across all your app servers, without adding another piece of infrastructure.

To see any of this, pg_locks joined against pg_stat_activity shows who holds what and who is waiting, and pg_blocking_pids(pid) gives you the blocking chain directly.

What you can do at this point: close a lost-update race deliberately, build a safe queue on a table, diagnose a stuck production database, and run schema changes without causing an outage.

What's still broken: all of this assumes the connection exists. Under real load, the act of connecting turns out to be one of the most expensive things in the entire system.

Node 12 — connections, and why pooling is not optional

The limitation: everything so far is per-connection, and you have not asked what a connection costs.

Postgres uses a process-per-connection model [EXPLAIN]. A supervisor process called the postmaster listens on port 5432, and for every client that connects it forks a new operating-system process dedicated to that client for its entire lifetime. Not a thread — a full process. This is a design from the 1980s that Postgres has kept through version 18, and it is defensible: process isolation means a crash in one backend cannot corrupt another, and it made the code much simpler for decades.

The cost is real. Each backend has its own memory overhead — a few megabytes of private structures before it does anything — and each is a separate entry in the OS scheduler. Forking takes single-digit milliseconds, which is enormous next to a 0.2 ms query. And crucially, throughput does not increase with connections beyond a point; it decreases. Past roughly the number of CPU cores times a small factor, more backends means more context switching, more contention on shared memory structures, and a well-documented collapse in throughput. The default max_connections is 100, and raising it to 5000 to "handle more load" is one of the most reliable ways to make a database slower.

The consequence is that a Node.js application must never open a connection per request. It needs a connection pool [EXPLAIN]: a fixed set of connections opened once and handed out to requests, returned when the request finishes. In Node this is pg.Pool, and its important settings are max (how many connections, usually far smaller than people expect — 10 to 20 per app instance is typical), idleTimeoutMillis, and connectionTimeoutMillis. The arithmetic that catches teams out: max is per process, so 20 connections times 4 Node instances times 3 containers is 240, against a max_connections of 100, and you get FATAL: sorry, too many clients already under load.

Which is why there is often a second pooler outside the application: PgBouncer [EXPLAIN] (or a cloud provider's equivalent like RDS Proxy or Supabase's Supavisor). It sits between your apps and Postgres, accepting thousands of client connections and multiplexing them onto a small number of real backends. Its pooling mode is the thing to understand:

Session pooling assigns a real backend to a client for the whole connection — safe, but barely better than no pooler. Transaction pooling assigns a backend only for the duration of a transaction and returns it to the pool at commit — this is the mode that gives the huge win, and it is the default at every serverless Postgres provider. But it changes the rules: because your next statement may land on a different backend, anything that carries session state breaks. That means no SET that you expect to persist, no session-level advisory locks, no LISTEN/NOTIFY, no cursors held across statements, no temporary tables, and — the one that bites hardest — server-side prepared statements, which is why drivers and ORMs need an explicit flag (prepare: false in postgres.js, ?pgbouncer=true in Prisma) when running behind PgBouncer in transaction mode. Statement pooling is stricter still and forbids multi-statement transactions entirely.

Two more things belong here. Prepared statements [EXPLAIN] themselves: sending a query as a parameterised template that Postgres parses and plans once, then executes with different values. They save parse and plan time on repeated queries, and — far more importantly — they are the correct defence against SQL injection, because parameters are sent separately from the query text and are never parsed as SQL. String-concatenating user input into a query is the vulnerability; a parameterised query is structurally immune. Note the subtlety that after five executions Postgres may switch to a generic plan that ignores the specific parameter values, which very occasionally produces a worse plan for skewed data — controlled by plan_cache_mode.

And statement_timeout [USE]: set it. A query with no timeout can run for hours, holding locks and pinning the vacuum horizon. Setting statement_timeout (and idle_in_transaction_session_timeout) at the role or application level is basic production hygiene that most teams add only after their first incident.

What you can do at this point: size a pool correctly, explain why more connections made things worse, and know what transaction pooling silently forbids.

What's still broken: the schema you designed in Node 2 is now in production with a hundred million rows, and you need to change it without taking the exclusive lock from Node 11 and without downtime.

Node 13 — changing a live schema

The limitation: every schema is wrong eventually, and the naive ALTER TABLE now blocks the whole application.

A migration [EXPLAIN] is a versioned, ordered, checked-in script that moves the schema from one state to the next, applied identically in every environment. The essential properties are that migrations run in order, each runs exactly once (tracked in a table the tool owns), and the schema is therefore reproducible from an empty database. Because Postgres has transactional DDL (Node 7), a migration tool can wrap each migration in a transaction and guarantee it is all-or-nothing — a real advantage over MySQL, where a failed migration leaves you to clean up by hand.

The knowledge that matters is which operations are cheap and which rewrite the table [EXPLAIN]. A table rewrite means Postgres writes out every row into a new file while holding an exclusive lock, which on a large table is minutes to hours of downtime.

Safe and near-instant, because they only change catalog metadata: adding a column that is nullable, or (since Postgres 11) adding a column with a constant default — 11 stores the default in the catalog and materialises it lazily, which turned one of the most notorious downtime causes into a metadata change. Dropping a column is instant too; Postgres just marks it dropped and stops showing it, and the bytes are reclaimed by later rewrites. Renaming is instant. Adding an index CONCURRENTLY is safe. Widening varchar(50) to varchar(100) or to text is free.

Expensive or blocking: adding a column with a volatile default (e.g. DEFAULT gen_random_uuid()), because each row needs a distinct value; changing a column's type in a way that changes its representation (integer to bigint rewrites the whole table — which is exactly why you choose bigint up front); adding NOT NULL to an existing column, because it must verify every row while holding the lock; and adding a CHECK or foreign key constraint, for the same reason.

The techniques that make the expensive ones safe are worth memorising as a set:

CREATE INDEX CONCURRENTLY [USE] builds an index without blocking writes, by scanning the table twice and tracking concurrent changes. It takes longer, cannot run inside a transaction block (so your migration tool needs to be told), and if it fails it leaves an INVALID index behind that you must drop and retry. DROP INDEX CONCURRENTLY and REINDEX CONCURRENTLY (Postgres 12+) exist too.

NOT VALID then VALIDATE [USE] is the two-step for constraints. ALTER TABLE ... ADD CONSTRAINT ... CHECK (...) NOT VALID adds the constraint so it is enforced on all new rows, taking only a brief lock and not scanning anything. Later, ALTER TABLE ... VALIDATE CONSTRAINT ... scans the existing rows under a much weaker lock that does not block reads or writes. The same pattern makes NOT NULL safe: add a CHECK (col IS NOT NULL) NOT VALID, validate it, and then (Postgres 12+) SET NOT NULL is instant because the planner can prove it from the validated check.

Expand–migrate–contract [EXPLAIN] is the general pattern for anything the two above cannot cover, and it is what "zero-downtime migration" actually means. Add the new column alongside the old one. Deploy code that writes to both and reads from the old. Backfill the existing rows in batches with a commit between each — never one giant UPDATE, which would create a hundred million dead tuples, generate enormous WAL, and hold locks for hours. Deploy code that reads the new column. Then, in a later release, drop the old one. Every step is independently reversible, and at no point do the running application and the schema disagree — which matters because during a rolling deploy, old and new application code are running simultaneously against the same database.

Two habits complete the node: always set lock_timeout in migrations, per Node 11, and always write the down migration or at least know how you would reverse it.

What you can do at this point: ship a schema change to a large live table without an outage, and explain to a reviewer why a given migration is or is not safe.

What's still broken: the schema itself has been limited to scalar columns. Real applications have documents, tags, ranges, and search — and modelling all of that in scalar columns and join tables is not always the right answer.

Node 14 — the types that make Postgres unusual

The limitation: normalised scalar tables are the right default, but a great deal of real data is naturally a document, a list, an interval, or a body of text, and forcing all of it into join tables produces schemas nobody enjoys.

Postgres's distinguishing feature as a product is the breadth of its type system, and the fact that indexing is extensible enough to make those types fast rather than decorative.

JSONB [EXPLAIN] is the headline. Postgres has two JSON types: json stores the text you gave it verbatim, preserving whitespace and key order and duplicate keys, and reparses on every access; jsonb parses it once into a decomposed binary form, which loses key order and duplicates but makes access fast and, decisively, makes it indexable. Use jsonb unless you have a specific reason not to. The operators to know: -> gets a JSON value, ->> gets it as text, #> follows a path, and @> asks "does this document contain this structure". A GIN index on a jsonb column makes containment queries — WHERE data @> '{"status":"active"}' — fast across millions of documents, and the jsonb_path_ops operator class makes a smaller, faster index if containment is all you need. Since Postgres 12 there is also JSONPath (jsonb_path_query) for querying inside documents.

The design judgment matters more than the syntax: jsonb is right for genuinely schemaless data — a webhook payload you must store verbatim, per-tenant custom fields, an LLM's raw response — and wrong as a way to avoid designing a schema. Fields you filter on, join on, or constrain belong in real columns where the type system and constraints from Node 2 can defend them. The common good pattern is a hybrid: proper columns for everything the application reasons about, one jsonb column for the long tail.

Arrays [USE] let a column hold text[] or integer[], queried with = ANY(...) and @>, and indexed with GIN. They are excellent for small, stable lists like tags that you never need to join or constrain, and a trap when the "array" is really an entity with its own attributes and lifecycle.

ENUM [USE] types give a column a fixed set of allowed labels with a compact storage representation. Adding a value is easy (ALTER TYPE ... ADD VALUE, non-transactional before Postgres 12); removing one is genuinely painful, which is why many teams prefer a text column with a CHECK constraint or a small lookup table.

UUID [USE] as a native 16-byte type, with gen_random_uuid() built into core since Postgres 13. The trade-off against bigint identity columns is worth knowing: UUIDs let clients generate ids and do not leak how many rows exist, but they are random, so inserting them scatters writes across the whole B-tree instead of appending to one end, causing page splits and index bloat. UUIDv7, which puts a timestamp in the high bits so values sort roughly by creation time, fixes this and is built into Postgres 18 as uuidv7().

Range types [AWARE] — tstzrange, int4range, daterange — store an interval as one value with real containment and overlap operators, and combined with an exclusion constraint (EXCLUDE USING gist (room_id WITH =, during WITH &&)) they let the database itself guarantee that two bookings for the same room never overlap. That is a genuinely hard invariant to enforce in application code and a memorable thing to have used.

Full-text search [USE] is built in. to_tsvector breaks text into normalised lexemes (stemming "running" to "run", dropping stop words), to_tsquery or websearch_to_tsquery parses a search string, the @@ operator matches them, ts_rank ranks, and ts_headline produces snippets with the matches highlighted. A GIN index on the tsvector — usually a generated column (Postgres 12+) so it maintains itself — makes it fast. The honest framing for an interview: this is genuinely good and removes the need for Elasticsearch for a large fraction of applications, and it is genuinely weaker on relevance tuning, fuzzy matching and analytics at very large scale. Alongside it, the pg_trgm extension gives trigram similarity for fuzzy matching and typo tolerance, and makes LIKE '%foo%' indexable.

Generated columns [USE] compute a value from other columns and store it, maintained by the database — ideal for a search vector, a normalised email, or a computed total. Postgres 18 adds virtual (non-stored) generated columns.

And timestamptz arithmetic with interval, date_trunc, age(), and generate_series() — the last of which produces a table of values on demand and is the standard trick for filling gaps in time-series reports.

What you can do at this point: model documents, tags, intervals and searchable text natively, and defend the choice between a jsonb column and a proper table.

What's still broken: all of this is still logic that your application invokes. Some rules and some computation genuinely belong next to the data, and there is nothing yet that lives inside the database and runs on its own.

Node 15 — logic inside the database

The limitation: if every rule lives in application code, then every application, script and human that touches the database can violate it, and every derived value costs a round trip.

Views [USE] are the simplest form: a named query that behaves like a table. They do not store anything; selecting from a view inlines its definition into your query, so a view is an abstraction with no runtime cost and no caching. They are excellent for hiding a complicated join behind a name, and for exposing a restricted subset of a table.

Materialized views [USE] do store the result, on disk, and are refreshed only when you say so with REFRESH MATERIALIZED VIEW. That makes an expensive aggregation instant to read at the price of being stale. Plain refresh takes an exclusive lock; REFRESH ... CONCURRENTLY does not, but requires a unique index on the view. This is the standard answer to "our dashboard query takes 40 seconds."

CTEs [EXPLAIN] — WITH x AS (...) — name a subquery and make long queries readable. An important version-specific fact people still get wrong: before Postgres 12, a CTE was always an optimisation fence, materialised separately and never inlined, which people exploited as a poor man's hint. From 12 onward, a CTE referenced once and free of side effects is inlined by default, and you can force either behaviour with MATERIALIZED / NOT MATERIALIZED. Recursive CTEs (WITH RECURSIVE) walk hierarchies — category trees, org charts, graph traversals — in a single query.

Window functions [EXPLAIN] are the piece of SQL that most reliably separates people who know SQL from people who know SELECT. They compute a value across a set of rows related to the current row without collapsing the rows the way GROUP BY does. ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) numbers each user's rows newest-first, and filtering that to 1 is the canonical "most recent row per group" — a question asked in interviews constantly. RANK, DENSE_RANK, LAG and LEAD (compare a row to the previous or next), and running totals with SUM(...) OVER (ORDER BY ...) round out the set.

Functions [USE] let you store procedural code in the database, written in SQL or in PL/pgSQL, Postgres's procedural language with variables, loops and exception handling. A function's volatility classification matters more than it looks: IMMUTABLE (same input always gives same output — required for expression indexes), STABLE (constant within one statement), or VOLATILE (the default; may do anything, so the planner cannot optimise around it). Procedures, added in Postgres 11, differ from functions in that they can COMMIT internally, which is what you need for a batched backfill loop.

Triggers [USE] run a function automatically BEFORE or AFTER an INSERT, UPDATE or DELETE, per row or per statement. They are perfect for a small class of jobs — maintaining an updated_at timestamp, writing an audit log, keeping a denormalised counter — and they are dangerous as a general home for business logic, because they are invisible at the call site: a developer reading the application code has no way to know that an insert also did five other things. The rule of thumb is that triggers should maintain data integrity, not implement features.

LISTEN / NOTIFY [USE] is a lightweight pub/sub built into the server. A session runs LISTEN channel, another runs NOTIFY channel, 'payload', and the listener is woken. Notifications are delivered at commit, which makes them transactionally correct — a notification is never sent for a rolled-back change. The limits: the payload is capped at 8000 bytes, there is no persistence (a listener that is not connected misses the message entirely), and it does not survive PgBouncer's transaction pooling. It is the right tool for cache invalidation or nudging a worker to check a queue table, and the wrong tool when delivery must be guaranteed.

Row-level security [AWARE], from Postgres 9.5, attaches a policy to a table so that each query implicitly gets an extra WHERE clause based on the current user or a session setting. ENABLE ROW LEVEL SECURITY plus a policy like USING (tenant_id = current_setting('app.tenant_id')::uuid) makes multi-tenant isolation a property of the database rather than of every query your team writes. It is what Supabase is built on, and it is increasingly asked about.

What you can do at this point: put invariants and expensive computation where they cannot be bypassed, and write the class of query that most candidates cannot.

What's still broken: everything so far is what Postgres ships with. Real deployments need capabilities core does not have, and adding them by forking the database would be absurd.

Node 16 — extensions

The limitation: a general-purpose database cannot contain geospatial indexing, vector search, time-series compression and query telemetry in core — but applications need them.

Extensions [EXPLAIN] are Postgres's answer, and they are the reason it has outlasted its competitors. An extension is a packaged bundle of types, functions, operators, index operator classes and sometimes C code that you install into a database with CREATE EXTENSION name. Because Postgres's type system, operator system and index framework (particularly GiST and GIN) were designed from the Berkeley days to be extended, an extension can add a genuinely new kind of data with genuinely fast indexing — not a bolt-on. Extensions live per-database, and \dx lists what is installed. Some, including the most important one below, require the server to load a shared library at startup via shared_preload_libraries, which means a restart.

The ones worth knowing by name:

pg_stat_statements [EXPLAIN] is the one you should install on every server you own. It aggregates every executed query, normalised so that queries differing only in parameter values are grouped, and records call count, total and mean execution time, rows returned, and cache hit rates. Ordering it by total time answers the only question that matters when a database is slow — what is actually consuming this server — and the answer is very often a fast query run ten million times rather than the slow one everybody is staring at.

pgvector [USE] adds a vector type and distance operators (<-> for L2, <=> for cosine, <#> for inner product) plus two index types: IVFFlat, which clusters vectors into lists and searches the nearest few, and HNSW (added in pgvector 0.5.0, 2023), a graph index that is slower to build and larger but substantially better on the recall/speed trade-off. Both are approximate — you trade exactness for speed, tuned by lists/probes or m/ef_construction/ef_search. This is the direct bridge to your pgvector-embeddings and rag topics, and the reason many teams never adopt a dedicated vector database: keeping embeddings in the same transaction as the rows they describe removes an entire class of consistency problem.

pgcrypto [USE] for hashing and encryption functions, historically the source of gen_random_uuid() before core absorbed it. pg_trgm [USE] for trigram similarity and indexable LIKE '%x%'. uuid-ossp [AWARE], now mostly superseded. postgis [AWARE], the geospatial extension that is so complete it is a major reason organisations choose Postgres at all. TimescaleDB [AWARE] for time-series, adding automatic partitioning and columnar compression. Citus [AWARE] for distributing tables across multiple nodes — sharding, as an extension. pg_repack [AWARE] to remove bloat without the exclusive lock of VACUUM FULL. postgres_fdw [AWARE], a foreign data wrapper that makes tables in another Postgres server queryable as if local, with a whole family of siblings for querying MySQL, S3 files and REST APIs.

The strategic point, and a good interview answer: the extension mechanism is why "just use Postgres" is a defensible architecture for a startup. Search, geospatial, vector similarity, time-series, queues and pub/sub can all live in one system with one backup story, one set of transactions and one operational burden — until scale genuinely forces specialisation.

What you can do at this point: add capability without adding infrastructure, and identify the query that is really costing you.

What's still broken: you can now build almost anything, but the database is a black box in production — you have no habitual way to see what it is doing, what it is spending memory on, or what is about to go wrong.

Node 17 — running it: observability and configuration

The limitation: every mechanism in this chain has a failure mode, and none of them announce themselves. Bloat, lock queues, bad plans and connection exhaustion all present as "the site is slow."

Postgres exposes its own state as tables you can query, which means monitoring it needs no special tooling.

pg_stat_activity [EXPLAIN] is the first place to look, always. One row per connection: what query it is running, how long it has been running (now() - query_start), its state (active, idle, idle in transaction), and what it is waiting on (wait_event_type and wait_event — Lock, IO, LWLock, or Client). The two queries to have memorised are "show me everything running longer than a minute, newest first" and "show me everything in idle in transaction", because between them they explain a large share of incidents. pg_blocking_pids(pid) turns a stuck query into a blocking chain, pg_cancel_backend(pid) cancels a query, and pg_terminate_backend(pid) kills the connection.

pg_stat_statements answers "where is the time going" over hours rather than right now. pg_stat_user_tables gives per-table sequential versus index scan counts, live and dead tuple estimates, and — critically — last_autovacuum and last_autoanalyze, which is where you confirm a vacuum problem. pg_stat_user_indexes gives idx_scan per index, and an index with idx_scan = 0 after a month of production is pure write overhead you should drop. pg_stat_database gives the cache hit ratio (blks_hit / (blks_hit + blks_read); below ~99% on an OLTP workload suggests shared_buffers is too small), plus deadlock and rollback counts. pg_locks shows the lock table. And pg_size_pretty(pg_total_relation_size('t')) gives a table's size including its indexes and TOAST.

The logs matter as much. log_min_duration_statement = 500 records every query slower than half a second, which is the highest-value single logging setting there is. log_lock_waits = on records anything that waited longer than deadlock_timeout. log_autovacuum_min_duration surfaces slow vacuums. log_checkpoints and log_temp_files catch the two most common configuration mistakes.

The configuration you should be able to reason about, all in postgresql.conf and most changeable with ALTER SYSTEM SET plus a reload: shared_buffers (Postgres's own page cache; ~25% of RAM), effective_cache_size (a hint to the planner about total cache including the OS; ~50–75% of RAM, allocates nothing), work_mem (per sort/hash operation — the dangerous multiplier from Node 6), maintenance_work_mem (for vacuum, index builds; can be much larger, ~1 GB), max_connections (Node 12), random_page_cost (~1.1 on SSD), wal_compression, and the autovacuum scale factors from Node 9. SHOW setting_name reads one; pg_settings lists all with their sources; some changes need a reload and some need a restart, and pg_settings.pending_restart tells you which.

The mental model to carry: Postgres's defaults are deliberately conservative so that it starts on any machine, which means an untuned production server is running with 128 MB of buffers and 4 MB of work memory on a box with 64 GB of RAM. Tuning it is not exotic; it is the first hour of operating one.

What you can do at this point: answer "why is the database slow" with evidence in under five minutes, and configure a server so it uses the machine it is on.

What's still broken: all of it is one process on one machine. That machine will fail, its disk will fail, someone will run a DELETE without a WHERE, and eventually one machine will not be enough.

Node 18 — surviving failure and outgrowing one machine

The limitation: a single server is a single point of failure and a single ceiling.

Backups [EXPLAIN] come in two kinds and the difference is not optional knowledge. A logical backup is pg_dump, which produces SQL statements or a custom-format archive that recreates the data. It is portable across versions and architectures, can restore a single table, and is slow to restore at scale because everything is re-inserted and every index is rebuilt. A physical backup is pg_basebackup (or pgBackRest / WAL-G in production), a byte-level copy of the data directory, which restores fast and only to a compatible version. Physical backups plus continuous WAL archiving give you point-in-time recovery [EXPLAIN]: restore the base backup, replay WAL up to 2026-08-29 14:32:00, and you have the database as it was one second before the bad DELETE. That is the capability that turns an incident into an inconvenience, and it exists entirely because of the WAL from Node 7. And the rule that outranks all of this: a backup you have not restored is not a backup.

Streaming replication [EXPLAIN], since Postgres 9.0, is the same idea pointed at a live server. A primary streams its WAL to one or more standbys, which continuously replay it. Standbys are read-only and can serve queries (hot standby), which gives you both high availability and read scaling from one mechanism. It is physical replication: byte-identical, all databases, same major version.

The trade-off is replication lag [EXPLAIN], and it produces the most common real bug in this area. By default replication is asynchronous: the primary commits and returns without waiting for any standby, so a standby may be a few milliseconds — or, under load, many seconds — behind. So an application that writes to the primary and immediately reads from a replica can read its own write as absent. This "read-your-writes" violation is why routing reads to replicas is a decision with application consequences, not a transparent optimisation. Setting synchronous_commit = on with synchronous_standby_names makes the primary wait for a standby's acknowledgement, eliminating the window and any data loss on failover, at the cost of commit latency and — importantly — the risk that if the synchronous standby dies, the primary stops accepting writes. pg_stat_replication on the primary shows the lag.

There is one more collision worth knowing: a long query on a standby can conflict with WAL replay that removes rows the query still needs, and Postgres will either cancel the query or pause replay. hot_standby_feedback = on tells the primary to hold back vacuum for the standby's benefit — which fixes the queries and reintroduces bloat on the primary. Nothing here is free.

Failover [USE] is promoting a standby when the primary dies. Postgres does not do this itself; you need an external tool — Patroni, repmgr — or a managed provider that does it for you. Getting it right involves consensus and fencing so that two nodes never both think they are primary (split brain), which is one of the honest reasons managed Postgres is worth paying for.

Logical replication [USE], since Postgres 10, is a different mechanism with different powers: it decodes the WAL into row-level changes and publishes them by table, via CREATE PUBLICATION and CREATE SUBSCRIPTION. Because it is logical rather than byte-level, it can replicate between major versions, replicate a subset of tables, and write into a target that has other tables of its own. That makes it the standard tool for near-zero-downtime major version upgrades and for feeding change-data-capture pipelines into analytics systems or Kafka.

Partitioning [USE] splits one logical table into many physical ones by range, list or hash, declaratively since Postgres 10. The parent is empty; the data lives in partitions; Postgres routes inserts and, when the query filters on the partition key, prunes away the partitions it does not need. The genuine wins are on time-series data: dropping last year's data becomes an instant DROP TABLE instead of a DELETE of a hundred million rows, and vacuum and index maintenance operate on manageable pieces. Partitioning is not a general performance fix — for most tables a good index is better — and it costs you the ability to have a globally unique constraint that does not include the partition key.

Sharding [AWARE] — splitting data across separate servers — is where Postgres stops being simple. Citus does it as an extension; otherwise you do it in the application. The correct instinct for almost every situation you will be in: vertical scaling, read replicas, partitioning and correcting the queries will carry you much further than most people assume, and sharding is what you do when you have exhausted them.

Finally, managed Postgres [USE] — RDS and Aurora, Cloud SQL, Neon, Supabase, Railway — takes backups, failover, patching and monitoring off you, and takes away superuser, shared_preload_libraries freedom, and arbitrary extensions. Neon and Aurora additionally separate storage from compute, which is what makes branching a database or scaling to zero possible. Knowing that "we use RDS Multi-AZ" means synchronous physical replication to a standby in another availability zone with automatic failover is exactly the level of fluency an interview expects.

What you can do at this point: state a recovery objective and meet it, scale reads, upgrade without downtime, and know which problem sharding is actually for.

What's still broken: everything in this chain has been described from inside the database. Your application talks to it through a driver and probably an ORM, and almost every Postgres problem you will personally cause will be caused there.

Node 19 — the application boundary, where the problems actually happen

The limitation: the database is correct and the application still generates a thousand queries per request, leaks connections, and holds transactions open across HTTP calls.

The driver [USE] is the library speaking the wire protocol. In Node the two real choices are pg (the long-standing, callback-era-descended standard, with pg.Pool) and postgres.js (newer, faster, tagged-template API). Things the driver decides that you should know about: whether it uses server-side prepared statements (and therefore whether it works behind PgBouncer in transaction mode, per Node 12), how it maps Postgres types to JavaScript — notably that bigint and numeric come back as strings by default, because they do not fit safely in a JavaScript number, and that a date becomes a JS Date in the server's timezone unless you tell it otherwise — and how it handles connection errors and reconnection.

Parameterised queries [EXPLAIN] are the non-negotiable: client.query('SELECT * FROM users WHERE email = $1', [email]). Postgres numbers parameters $1, $2 rather than using ?. Concatenating user input into SQL is the SQL injection vulnerability, and it is still, decades later, in the OWASP top ten. Note the one place parameters cannot help: identifiers. You cannot parameterise a table or column name, so dynamic ORDER BY must be validated against an allow-list, never interpolated.

Transactions in application code [USE] have a shape that must be exact: acquire a client from the pool, BEGIN, work, COMMIT, and in a catch block ROLLBACK, and in a finally block release the client. Miss the release and you leak a connection; leak enough and the pool is exhausted and the application deadlocks against itself with no error from Postgres at all. The most damaging version of this mistake is holding a transaction open across an await on something slow — an HTTP call to a payment provider, an LLM completion — which pins a connection, holds locks, and blocks vacuum (Node 9) for the duration. Do the slow thing outside the transaction.

ORMs [EXPLAIN]. Prisma and Drizzle both sit on top of everything in this chain, and both are in your track. What matters is the failure modes they introduce. The N+1 query problem is the big one: fetching a hundred posts and then, for each, lazily fetching its author, producing 101 round trips where one join would do. Every ORM has an eager-loading escape (include in Prisma, a relational query or explicit join in Drizzle), and knowing to look for it is the skill. Beyond that: ORMs happily generate SELECT * on tables with a TOASTed column (Node 4), can produce queries with far worse plans than the obvious hand-written one, and abstract away the transaction boundary in ways that make it easy to open one accidentally. The professional stance, and a good thing to say out loud: use the ORM for the 95% of queries that are trivial, drop to raw parameterised SQL for the ones that matter, and be able to see the generated SQL — every ORM has a query-logging switch, and turning it on for a day is the fastest education available.

Timeouts and retries [USE] close the loop with Node 10 and Node 11. Set statement_timeout so no query can run forever. Catch 40001 (serialization failure) and 40P01 (deadlock) and retry the whole transaction with backoff — and note that this is only safe if the transaction is idempotent or the retry is genuinely a fresh attempt, which is why writes that have external side effects need care.

And health: expose the pool's waiting-count and the database's connection count in your metrics, because "the pool is exhausted" and "the database is slow" look identical from the outside and are fixed in completely different places.

What you can do at this point: write application code whose database behaviour you can predict, and debug the class of problem that never shows up in EXPLAIN because it is not one query, it is a thousand.

Where the chain gets misread

  • "An index always makes a query faster." (Node 5/6) It makes reads faster only when the query can use it, when the planner believes it is cheaper, and when it is selective enough to beat a sequential scan. It always makes writes slower. On a table where a query matches 40% of rows, a sequential scan is genuinely the better plan and the planner is right to choose it.
  • "EXPLAIN tells you how long the query takes." (Node 6) Plain EXPLAIN shows estimates only and does not run the query. EXPLAIN ANALYZE runs it — including running the UPDATE or DELETE, so wrap it in a transaction you roll back. The number that matters most is not the time, it is rows versus actual rows.
  • "varchar(50) is faster and smaller than text." (Node 2) It is not. They are the same type internally; the length is a constraint check. Choose the limit for correctness, never performance.
  • "timestamptz stores a timezone." (Node 2) It stores a UTC instant. It uses the session timezone only to interpret input and format output. Plain timestamp is the one that loses information.
  • "An UPDATE changes the row." (Node 8) It writes a new version and marks the old one dead. This is why updates cause bloat, why they can be as expensive as inserts, and why updating one row a million times leaves a million dead tuples.
  • "VACUUM frees disk space." (Node 9) Plain VACUUM marks space reusable within the file; the file does not shrink. Only VACUUM FULL (exclusive lock, effectively an outage) or pg_repack returns space to the OS.
  • "READ COMMITTED protects me from concurrency bugs." (Node 10) It prevents dirty reads and nothing else. Lost updates and write skew are fully available to you at the default isolation level, and closing them requires SELECT FOR UPDATE, a higher isolation level with retries, or a constraint that makes the bad state impossible.
  • "Adding a column locks the table for a long time." (Node 13) Since Postgres 11, adding a nullable column or one with a constant default is a catalog-only change taking milliseconds. Adding one with a volatile default, or adding NOT NULL or a validating constraint, is what rewrites or scans the table.
  • "More connections means more throughput." (Node 12) Past roughly a small multiple of the core count, throughput falls. Postgres forks a process per connection; the fix for load is a pool with a small max, not a larger max_connections.
  • "A read replica is a transparent way to scale reads." (Node 18) Asynchronous replication means a replica can be behind, so a read after a write may not see it. Routing reads to replicas is an application-visible decision.
  • "count(*) should be instant, the database knows how many rows there are." (Node 8) Under MVCC, how many rows exist depends on which transaction is asking, so there is no single maintained number. An approximate count is available from pg_class.reltuples if approximate is acceptable.
  • "Postgres created an index for my foreign key." (Node 5) It did not. It indexes the referenced primary key, which already had one. The referencing column gets nothing, and this is one of the most common causes of an unexpectedly slow join or a slow DELETE on the parent.
  • "A CTE is just a readable subquery, it has no effect on the plan." (Node 15) True from Postgres 12 onward for a single-reference, side-effect-free CTE. Before 12 every CTE was an optimisation fence and could not be inlined — so this depends entirely on the version, and old advice on the internet reflects the old behaviour.
  • "JSONB means I don't need a schema." (Node 14) It means the shape is not enforced, which is exactly the guarantee Node 2 exists to provide. Anything you filter, join, or constrain on should be a real column; jsonb is for the genuinely variable remainder.

The chain in one paragraph

Data in files loses updates, corrupts on crash, cannot be searched, and enforces nothing, so you put one server in front of it that owns the bytes and enforces the rules — types and constraints so impossible states are impossible, and SQL as a declarative question the server decides how to answer. Answering it means reading 8 KB pages from an unordered heap, which is fine until the heap is large, so you add B-tree indexes that turn a million-page scan into four page reads, and a planner that uses table statistics to guess how many rows each step yields and picks a plan accordingly — which is why EXPLAIN ANALYZE's estimate-versus-actual gap is where slow queries are actually diagnosed. Grouping statements so they succeed or fail together requires the write-ahead log, which makes commits durable by appending sequentially and flushing, and which incidentally makes replication and point-in-time recovery possible later. Letting many transactions run at once without locking reads requires MVCC, where an update writes a new row version and every transaction reads through a snapshot — which is why readers never block writers, why count(*) is slow, and why dead tuples accumulate until VACUUM reclaims them, making autovacuum tuning and transaction-id freezing real operational concerns. Snapshots still allow lost updates and write skew, so isolation levels and explicit row locks close those, while table-level locks explain why one ALTER TABLE queued behind one slow SELECT can take down a site. Every connection is a forked process, so pooling is mandatory and transaction-mode pooling silently forbids session state; schema changes on live tables need CONCURRENTLY, NOT VALID, and expand–migrate–contract. On top of that foundation Postgres is unusual for its types — JSONB, arrays, ranges, full-text search — and for the extension mechanism that adds vectors, geospatial and query telemetry without forking the database, all of it observable through pg_stat_activity and pg_stat_statements, survivable through WAL-based backups and streaming replication, and, finally, reachable only through a driver and an ORM where the N+1 queries, leaked connections and transactions held open across network calls are the problems you will personally cause.
