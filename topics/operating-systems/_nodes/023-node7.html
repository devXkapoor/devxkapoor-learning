Node 7 — the scheduler: deciding who runs, and taking the processor back

The limitation: switching is possible but only when a process cooperates by entering the kernel, and nothing chooses who runs next.

Preemption needs one piece of hardware

Fix the fatal half first. A program that loops forever without making a system call never enters the kernel voluntarily, so the kernel needs an entry that does not depend on the program at all. Node 2 already supplies the mechanism: an interrupt. So the machine contains a device whose only job is to raise an interrupt at a fixed rate — a programmable interval timer.

Now the loop is closed. The timer fires. Control enters the kernel regardless of what the process was doing, because interrupts are checked between instructions and the process cannot disable them (cli is privileged — Node 3). The kernel checks whether this process has had enough time; if so, it context-switches to another. The process, when it eventually resumes, cannot tell.

Being able to take the processor away without the running program's consent is preemption, and it is the difference between a system where one bad program hangs the machine and one where it does not. [EXPLAIN] The historical division is exactly here: classic Mac OS through version 9 and Windows 3.x used cooperative multitasking, in which a program kept the processor until it called a system function that yielded. One badly written application froze the entire machine, and everyone who used those systems remembers it. Windows 95 brought preemption for 32-bit applications, Windows NT had it from the start (1993), and Mac OS X had it in 2001 by way of a Unix kernel. Every mainstream system has been preemptive for twenty-five years — except, notably, the JavaScript event loop, which is cooperative, and that is why a single slow function freezes a page or stalls a server. The failure you experience in JavaScript is the failure operating systems solved in 1962, reintroduced one layer up.

The problem is that the goals conflict

Given a set of runnable processes, which one? There is no neutral answer, because the objectives genuinely oppose each other:

  • Throughput — total work done. Favours long slices, since switching is pure overhead.
  • Latency — how fast something that becomes ready starts running. Favours short slices and aggressive preemption.
  • Fairness — every process gets a reasonable share. Opposed by priority.
  • Priority — some work matters more. Opposed by fairness, and risks starving the low-priority work entirely.
  • Interactivity — a process that just received a keystroke should run now, even though it has been asleep and has no claim under any fairness rule.

Every scheduler ever written is a particular position on those trade-offs, which is why there have been so many and why the argument continues.

The lineage, and what each one fixed

Round robin is the first idea: a circular queue, everyone gets an equal slice, next. Perfectly fair and completely wrong for interactivity — an interactive process that sleeps waiting for a keystroke goes to the back of the queue on waking, so typing lags behind a batch job that never sleeps.

Multi-level feedback queues, introduced in CTSS at MIT around 1961 by Fernando Corbató (the same lineage that produced Multics), fixed that with a genuinely clever inference. Several queues at different priorities. New processes start high. A process that uses its entire slice is assumed to be compute-bound and is moved down a level, getting a longer slice but running less often. A process that blocks before using its slice is assumed to be interactive and stays high. The scheduler does not need to be told which processes are interactive; it deduces it from behaviour. That inference is still the core idea in most schedulers, and it is what makes your editor responsive while a build runs.

Traditional Unix used a priority value that decayed with accumulated processor time, which achieves something similar, and gave the world the nice command — a program can voluntarily lower its own priority, hence "being nice to other users". Linux's early schedulers scanned every runnable task on every decision, which is O(n) and fell over on large machines. The O(1) scheduler (Ingo Molnár, Linux 2.6, 2003) used per-priority queues and a bitmap so the decision took constant time — but the heuristics it used to detect interactivity were a pile of special cases that misbehaved in ways nobody could fully predict.

CFS, the Completely Fair Scheduler, replaced it in Linux 2.6.23 (October 2007) and is the design worth actually knowing, because it ran the world for sixteen years and its concepts survive into its successor. Its idea is to model an ideal machine that runs all N runnable processes simultaneously at 1/N speed each, and then approximate it. Every task carries a vruntime — virtual runtime — which advances as it runs, scaled by its weight. The rule is: always run the task with the smallest vruntime. Tasks are kept in a red-black tree ordered by vruntime, so the choice is the leftmost node, and insertion is logarithmic. There is no explicit time slice; a task runs until someone else's vruntime is smaller, bounded below by sched_min_granularity_ns (typically 1–3 ms) so that switching does not dominate. A task that wakes from sleep is given a vruntime just below the minimum in the tree, so it runs almost immediately — interactivity falls out of the model rather than being a special case, which is exactly what the O(1) scheduler could not do.

nice maps onto weights, and the mapping is specified: each step of nice changes the weight by a factor of about 1.25, arranged so that one nice level is roughly a ten percent change in processor share. The range is −20 (most favoured) to +19. nice -n 19 npm run build is a real and underused way to run a build on a machine that is also serving traffic. [USE]

EEVDF — Earliest Eligible Virtual Deadline First — replaced CFS in Linux 6.6 (October 2023). It keeps the virtual-time accounting but adds an explicit notion of a deadline, so that latency-sensitive tasks can request short slices and be scheduled against a stated requirement rather than being inferred at. If you read a benchmark comparing kernel versions on latency, this is usually the change involved. [AWARE]

Classes: not everything is fair-share

Linux runs several scheduling classes in strict order of precedence, and a task in a higher class always preempts anything below it:

  • SCHED_DEADLINE — you state a runtime, a period and a deadline, and the kernel admits the task only if it can guarantee them.
  • SCHED_FIFO and SCHED_RR — real-time priorities 1–99. A SCHED_FIFO task runs until it blocks or yields; nothing below it runs at all. Used for audio, industrial control, and anything with a hard timing requirement. Also an excellent way to hang a machine, which is why sched_rt_runtime_us reserves five percent of each period for everything else.
  • SCHED_OTHER — the fair-share class. Everything you run is here.
  • SCHED_BATCH and SCHED_IDLE — below normal; SCHED_IDLE runs only when the machine would otherwise be idle.

Many cores changes the problem

With multiple cores there is not one queue but one per core, because a single global queue would need a lock that every core contends for on every scheduling decision. Per-core queues mean cores can go idle while another is backed up, so a periodic load balancer migrates tasks between them — and migration is expensive for the reason in Node 6: the task's cache lines are on the old core. So the balancer is deliberately reluctant, and it is aware of the machine's topology: two hyperthreads on one physical core share execution units, cores in one socket share L3, and on a NUMA machine each socket has memory that is fast for it and slower for the other, so moving a task across sockets can silently halve its memory performance. taskset and sched_setaffinity pin a task to specific cores, and numactl controls memory placement. [AWARE] On a large cloud instance this is not academic: a database or a Node process pinned badly can lose a third of its throughput to remote memory access.

Priority inversion is the classic scheduler failure. A low-priority task holds a lock; a high-priority task needs it and blocks; a medium-priority task, which needs no lock, preempts the low-priority one and now runs indefinitely — so the high-priority task is blocked by a medium-priority task it outranks. This happened on the surface of Mars: the Mars Pathfinder lander in July 1997 repeatedly reset itself in flight, and the cause was exactly this, in VxWorks, on a shared information bus. The fix, uploaded to the spacecraft, was priority inheritance — a task holding a lock temporarily inherits the priority of the highest-priority task waiting for it. Linux's PTHREAD_PRIO_INHERIT mutexes implement it.

Where this is in your stack

"Node is single-threaded so it only uses one core" is half right and the wrong half is the important one. Node's JavaScript runs on one thread, so one Node process executes at most one JavaScript instruction at a time. But the process has other threads — four libuv threadpool threads by default, plus V8's background compiler and garbage-collection helpers — and the kernel scheduler in this node will happily run those on other cores simultaneously. So a single Node process can and does exceed 100% CPU in top. What it cannot do is run two of your functions at once.

There are two schedulers stacked on top of each other, and every Node performance problem is about which one is failing. [EXPLAIN] This is the single most valuable framing in this part of the document.

  • The kernel scheduler — this node — is preemptive. It arbitrates between processes and threads and it can always take control back, because it has the timer interrupt.
  • The event loop — Node 20 — is a scheduler too: it decides which callback runs next. But it is cooperative. It has no timer interrupt, no privileged mode, no way to stop a running callback. Its only mechanism for regaining control is the callback returning.

So when a request handler runs a 400-millisecond synchronous loop, the kernel scheduler behaves perfectly — it preempts the thread whenever it likes and other processes on the machine run fine. It is the userspace scheduler that has failed, because it cannot preempt, and every other request in that process waits the full 400 milliseconds regardless of urgency. The event loop is a 1970s cooperative scheduler running inside a preemptive one. Understanding that tells you the whole class of fixes: yield voluntarily (await, setImmediate, chunking a loop), or move the work to something the kernel scheduler can arbitrate — a worker thread, a threadpool task, a separate process, a queue.

React's scheduler is a third one, and it is this node reimplemented in JavaScript because the browser will not preempt either. React 18's concurrent renderer breaks rendering into units and checks shouldYield() between them, returning to the browser roughly every 5 milliseconds so that input and painting can happen. It assigns work to lanes with different priorities — discrete input highest, transitions lower — which is priority scheduling; startTransition is you marking work as low-priority, exactly like nice; and interrupting a low-priority render when a keystroke arrives is preemption implemented by cooperative yielding. The platform is catching up to this with scheduler.postTask() (priorities), scheduler.yield(), navigator.scheduling.isInputPending(), and the older requestIdleCallback, which is SCHED_IDLE for the main thread. Every concept in React's scheduler has a direct ancestor in this node, and knowing that makes concurrent React considerably easier to reason about.

Kubernetes CPU requests and limits are two different scheduler features and confusing them is a common and expensive mistake. A requests.cpu of 500m becomes a cgroup weight — a relative share, which only matters when the machine is contended, and which is CFS's task weight from earlier in this node. A limits.cpu of 500m becomes a cgroup quota: at most 50 milliseconds of processor time per 100-millisecond period, enforced by hard throttling. When the quota is exhausted, every thread of the container is stopped until the next period begins, even if the machine is completely idle. For a Node service this shows up as latency spikes with no corresponding CPU graph — average utilisation of 40% while p99 doubles, because the container burned its quota in the first 30 milliseconds of each period and slept for 70. nonvoluntary_ctxt_switches from Node 6 rises, and /sys/fs/cgroup/cpu.stat shows nr_throttled and throttled_usec climbing. Node 27 covers the cgroup mechanics; the point here is that a CPU limit is not a safety measure, it is a latency cost you are choosing to pay, and for latency-sensitive services setting requests without limits is a defensible and common position.

Container CPU detection is a related trap. os.cpus().length reports the host's cores, not your quota, because the kernel has no per-container view of that (Node 26 explains why namespaces do not cover this). So a library sizing a pool as cpus().length inside a container limited to one core creates 64 threads that will fight over 100 milliseconds of quota. Node added os.availableParallelism() in v18.14 for this reason, and libraries that read cgroup files directly exist because of it.

What you can do at this point: explain preemption and why it requires a timer interrupt, describe CFS's virtual-runtime model well enough to predict its behaviour, use nice, explain the two-stacked-schedulers framing for Node and React, and diagnose CPU throttling in a container from the specific symptom of high latency at low utilisation.

What's still broken: the timer interrupt was introduced as a bare mechanism — something fires periodically. But "periodically" hides a great deal. How often, and what does the rate cost? What does the machine do when nothing is running at all? And a scheduler needs to answer questions like "has this task run for 3 milliseconds", which requires a notion of time that is accurate, cheap to read, and — critically — never goes backwards. The clock deserves its own node, because almost everything you believe about time in a computer is wrong in a way that has cost people money.
