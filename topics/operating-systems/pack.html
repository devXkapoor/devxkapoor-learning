Operating systems

From a wire that is either on or off to a Kubernetes pod being throttled — the complete causal chain of why an operating system exists, what every one of its mechanisms is for, and how each one shows up in the stack you actually write.

This is the landscape for operating systems, written as a causal chain. It is not a list of topics. Each node exists because the node before it left something specifically broken, and every node ends by naming what is still broken so that the next node has a reason to exist. Read top to bottom and you should end up able to derive most of an operating system rather than memorise it.

It starts at absolute zero — a wire with electricity in it or not — and assumes nothing whatsoever. Every term is defined before it is used. Every mechanism is given its origin: who hit the problem, in what year, on what machine, and what they tried that failed first. Nothing is explained by analogy. An analogy tells you what something is like; this document is about what things are.

Every node has a section called Where this is in your stack. That section is not a courtesy. The reason to learn this material is that you already use every one of these mechanisms hundreds of times per second and currently experience them as unexplained behaviour: an event loop that stalls, a container that dies with exit code 137, a Postgres write that is slow for no visible reason, a EADDRINUSE after a restart, a Node process whose memory graph does not match its heap graph, a Kubernetes pod whose p99 latency spikes while its CPU graph shows forty percent. Each of those is one specific kernel mechanism visible from the outside. The full-stack sections trace each one all the way down and all the way back up, at the same depth as the rest of the node.

Depth markers

Capabilities are marked inline, attached to the specific thing rather than collected in a table.

  • [EXPLAIN] — you must be able to explain this from first principles, out loud, under pressure, with no notes and no diagram.
  • [USE] — you must be able to use it correctly and debug it when it breaks. You do not need the internals cold.
  • [AWARE] — you must know it exists, what problem it solves, and roughly when to reach for it.

The forces that recur

Operating systems are not an arbitrary pile of features. Almost everything in this chain is one of a small number of forces reappearing in a new place, and it is worth naming them now so that you can spot them as they come round again. When you meet a mechanism you have never seen, the fastest way to understand it is to ask which of these it is answering.

  • Sharing — one physical resource, many claimants. Every part of the machine that exists only once (the processor, memory, the disk, the network card, a port number) needs a story for how many things use it at once.
  • Protection — sharing immediately means one claimant can destroy another, by accident or on purpose. Every sharing mechanism drags a protection mechanism in behind it.
  • Indirection — the standard move for both of the above. Stop letting programs touch the real thing; give them a name or a number that the kernel translates. Virtual memory, file descriptors, process IDs, namespaces, and sockets are all the same move applied to different resources.
  • Latency — the parts of a computer differ in speed by factors of a hundred million. Almost every optimisation in the chain is one layer hiding the slowness of the layer below by caching, buffering, or overlapping.
  • The boundary — crossing between a program and the kernel costs real time, and every generation of systems software is partly an attempt to cross less often.
  • Compatibility — nothing here was designed cleanly. Interfaces from 1970 survive because a hundred million lines of code call them, and the newer, better interface has to live alongside the older one forever.

How the parts are grouped

Ten parts. Part I builds the machine and shows why software must sit between it and you. Part II introduces the process and the sharing of the processor. Part III does memory. Part IV does concurrency and arrives at the event loop with everything needed to explain it exactly. Part V does files and storage. Part VI does isolation, and by the end of it a container is fully assembled from parts you have already seen. Part VII does communication. Part VIII takes a source file all the way to a running process, and the machine all the way from power-on. Part IX is how you see inside a running system. PART I — THE BARE MACHINE, AND WHY IT CANNOT BE SHARED

Five nodes. By the end of them there is a processor, a memory, a running program, a way for the outside world to interrupt that program, a hardware wall that stops the program from wrecking the machine, and exactly one legal door through that wall. That door is the system call, and every line of code you have ever written eventually goes through it.

Node 0 — the machine with nothing on it

There is no operating system yet. There is no file, no process, no folder, no window. There is a machine, and this node builds it, from a piece of metal upward, and then shows the specific way it fails when two people want to use it. That failure is the whole reason the rest of this document exists.

A wire, and why there are only two values

Start with a wire — a strip of metal with electricity pushed into one end. At the far end you can measure how hard the electricity is being pushed. That measure is called voltage. The wire either has a push in it or it does not, and that is the entire capability of the object: it can distinguish two situations.

The obvious objection is the right one. A wire can carry any voltage at all, so why agree on only two? Why not say zero volts means the digit 0, one tenth of a volt means 1, two tenths means 2, and so on to nine — ten times as much meaning carried on the same piece of metal, for free?

People built machines that way. ENIAC, switched on in 1945 at the University of Pennsylvania, was a decimal machine: each digit was a ring of ten circuits with exactly one of them lit. So this was not an oversight that hindsight corrected. It was a live design that lost a fight.

It lost to noise. A wire is not a sealed pipe. Its voltage sags slightly over distance, wobbles when the wire beside it switches, drifts as the room warms, and dips when something else in the machine draws current. All of this is small — hundredths of a volt. That is fatal when your digits are one tenth of a volt apart, because 0.3 volts sagging to 0.28 is now ambiguous between three and two, and — this is the part that kills it — nothing downstream can tell that an error happened. The wrong value is indistinguishable from a right one and propagates silently through every subsequent calculation.

With two legal values the same wobble is nothing. Anything under about 0.4 volts is read as off, anything over about 0.6 is read as on, and the band between them is a no-man's-land that circuits are designed never to rest in. A 0.05 volt disturbance moves a signal from 0.9 to 0.85, which is still unambiguously on, and the disturbance is discarded at that point rather than carried forward. Noise is thrown away at every single step instead of accumulating.

So binary is an engineering trade and not a mathematical truth, and it is worth being able to state it in one sentence: you give up nine tenths of the information a wire could carry, and in exchange every value is either exactly right or catastrophically wrong, never slightly wrong. [EXPLAIN] A machine that is occasionally slightly wrong is worth nothing, because you cannot tell which answers to trust. A machine that is exactly right is something you can build a banking system on.

The two states are named: on is 1, off is 0, and one wire's worth of on-or-off is a bit, a contraction of "binary digit" that Claude Shannon put into print in his 1948 paper A Mathematical Theory of Communication. In this document a bit is not an abstract unit of information. It is a wire, and whether there is electricity in it.

The switch that is operated by electricity

Wires alone compute nothing. A machine made only of wires carries values you put in by hand; it is a bundle of cables. What is needed is a wire whose state is controlled by another wire.

That component is the transistor, demonstrated at Bell Labs in December 1947 by John Bardeen and Walter Brattain, with the theory largely due to William Shockley. It has three connections: an input, an output, and a control. Put voltage on the control and current flows from input to output; take the voltage off and the flow stops. It is a switch that is thrown by electricity rather than by a finger. [EXPLAIN] That is the atom. A processor in a phone today contains somewhere north of ten billion of them, and there is nothing else in there — the entire machine is that one component, made very small and repeated.

Switches are enough because they can be arranged to make decisions. Put two transistors in series, so current must pass through both: the output is on only when both controls are on. That arrangement is called an AND gate. Put two in parallel, so current can take either path: the output is on when either control is on — an OR gate. A single transistor wired to pass current when its control is off gives a NOT gate. Those three are enough to build every operation any computer performs; this was known before the hardware existed, from Claude Shannon's 1937 master's thesis at MIT, which showed that switching circuits and Boolean algebra are the same subject.

From gates you get arithmetic, mechanically. Adding two bits produces a sum and a carry: the sum is on when exactly one input is on (an XOR, built from the three primitives), and the carry is on when both are (an AND). That two-gate object is a half adder. Chain a row of them so that each one's carry feeds the next one's input, and thirty-two of them in a row add two thirty-two-bit numbers. Subtraction is addition with one input inverted and a carry forced in. Multiplication is repeated shift-and-add. There is no further magic anywhere in the arithmetic of a computer. [AWARE]

Holding a number, and holding many

Gates compute but forget instantly — the output follows the input and nothing persists. Wire two NOT gates in a loop, each feeding the other, and the pair has two stable states it will sit in indefinitely. That is one bit of storage, called a latch, and with a control wire added so that it only accepts a new value when told to, a flip-flop.

Put sixty-four flip-flops side by side and you can hold a sixty-four-bit number. Such a row, sitting directly next to the arithmetic circuits, is a register. [EXPLAIN] Registers are the fastest storage in the machine because they are physically adjacent to the gates that use them — the signal travels a fraction of a millimetre. A processor has only a few dozen of them. On the x86-64 processor in a typical laptop or server there are sixteen general-purpose integer registers with historical names — rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, and r8 through r15. Those names will come back in Node 4, because the way your program asks the kernel for anything is by putting numbers in specific ones of them.

A few dozen numbers is not a computer. You need millions. But you cannot put a million registers next to the arithmetic unit — there is no room, and the wires would be long enough that the signal delay would dominate. So a second kind of storage exists, further away and much larger, built from a simpler and denser cell: one transistor and one tiny capacitor holding a charge. That is DRAM, the main memory of the machine, and the capacitor leaks, which is why it must be read and rewritten thousands of times a second. The D stands for dynamic, and it means exactly that: the memory forgets unless continuously refreshed.

Because there are billions of these cells, they need names. The names are consecutive integers starting at zero, and one such integer is an address. [EXPLAIN] Memory is therefore, physically and precisely, a very long row of numbered boxes, each holding eight bits — a byte — and the machine has exactly two operations on it: load the contents of box N into a register, and store the contents of a register into box N. Every data structure you have ever used is made of those two operations and nothing else.

Eight is not a natural number here; it is a decision. IBM's System/360, announced in April 1964, standardised the eight-bit byte because eight bits hold one character in the encoding IBM was using and because eight is a power of two, which makes address arithmetic a matter of shifting bits rather than dividing. Machines before it used six-bit and seven-bit and nine-bit units. Eight won because System/360 won.

The idea that makes it a computer: instructions are numbers

Here is the pivot the whole field turns on, and it is worth slowing down for.

ENIAC was programmed by physically rewiring it. To change what it computed, a team moved cables between plugboards and set switches, and this took days. The machine's behaviour lived in its wiring; its data lived in its circuits; the two were different kinds of thing.

The alternative was written down in June 1945 in a document titled First Draft of a Report on the EDVAC, circulated under John von Neumann's name alone although it recorded work done with J. Presper Eckert and John Mauchly — an attribution dispute that has never fully settled. The idea: put the instructions in the same memory as the data, encoded as numbers. [EXPLAIN]

Concretely, agree that when the machine reads the number 0x48 0x01 0xd8 it will interpret it as "add the contents of register rbx into register rax". That agreement — a table mapping bit patterns to operations, fixed in the wiring of the machine — is an instruction set architecture, an ISA. The bit patterns themselves are machine code. x86-64 is one such agreement, ARM64 is another, RISC-V a third; they are mutually unintelligible, which is why a compiled binary for one does not run on the other, and why Docker images carry an architecture tag and why an image built on an Apple laptop can fail to start on a cloud server.

The consequences of instructions being data are not small conveniences. They are the field:

  • A program can be loaded — copied into memory like any other data — instead of being wired. Changing programs takes seconds rather than days.
  • A program can be stored on a card, a tape, a disk. Software becomes a thing that can exist separately from a machine.
  • A program can write a program, because writing instructions is just writing numbers into memory. That is what a compiler is, and it is what V8's JIT is doing at runtime inside every Node process and every browser tab you have open.
  • A program can, by mistake, overwrite itself or another program. Every security vulnerability in the class that includes buffer overflows exists because of this single design decision, and Node 3 is where the machine first fights back.

The first machine actually to run a stored program was the Manchester Baby on 21 June 1948, a test rig that ran a seventeen-instruction program to find the highest factor of a number. The first practically useful one was EDSAC at Cambridge, under Maurice Wilkes, which ran its first program on 6 May 1949. Every computer since is the same design, and the phrase "von Neumann architecture" means precisely this: one memory, holding both instructions and data, with a processor that fetches from it.

The loop that is the entire processor

Given a memory full of instruction-numbers, the processor does one thing, forever, from the moment it is powered on until it is powered off. It needs one special register to do it: a register holding the address of the next instruction to run. On x86-64 it is called rip, the instruction pointer; the vendor-neutral name is the program counter.

1. FETCH    read the bytes at the address in rip
2. DECODE   look up what that bit pattern means
3. EXECUTE  do it — add, load, store, compare, jump
4. ADVANCE  add the instruction's length to rip
   repeat

That is the whole processor. [EXPLAIN] There is no scheduler in there, no notion of a program, no notion of a user, no notion of a file. Those are all software, and every one of them is built later in this document. The hardware knows only: fetch, decode, execute, advance.

Two details in that loop carry enormous weight later.

First, a jump is just writing to rip. An if statement is a comparison followed by a conditional write to rip. A loop is a backward write to rip. A function call is a write to rip plus a note of where to come back to. Control flow is not a concept the hardware has; it is arithmetic on one register.

Second, the loop never stops and never asks anything. It cannot pause and wait for a decision. It cannot notice that something else would be a better use of its time. It executes whatever is at rip with total obedience. Everything in the rest of this document is an answer to the question: given a device with that property, how do you get it to do more than one thing, safely, for more than one person?

A modern processor complicates this picture without changing it. It fetches many instructions ahead (pipelining), guesses which way a branch will go and starts executing down that path before it knows (speculative execution, which is where the Spectre vulnerabilities of January 2018 come from — Node 40), and executes instructions out of order while preserving the appearance of order (out-of-order execution). All of that is an optimisation that the machine is contractually required to make invisible. The model above remains exactly correct as a description of what the results look like.

What a program actually is, at this point

A program, right now, is a run of bytes that you place into memory starting at some address, followed by setting rip to that address. Nothing more. There is no header, no name, no owner, no permissions, no isolation, no concept of it "starting" or "ending" other than by convention. If the bytes run off the end into whatever happens to be in memory next, the processor executes that too, cheerfully, because it cannot tell the difference.

And this program owns the machine completely. It can read and write any memory address, because there is nothing to stop it. It can talk directly to the disk controller and the printer, because those are reached by writing to specific memory addresses or specific hardware ports and any code can do that. It runs until it decides to stop.

How this was actually used, and what it cost

This is not a thought experiment. It is how computing worked into the late 1950s, and the specific misery of it drove everything that follows.

A machine like the IBM 704 (1954) filled a room and cost the equivalent of several million pounds today. It ran one program at a time, and to run yours you booked a slot on a sign-up sheet — typically an hour, possibly next week. At your slot you walked in carrying a deck of punched cards. Each card was a stiff piece of paper with rectangular holes in it; the pattern of holes on one card encoded one line of your program. A large program was a box of several thousand cards, and dropping the box was a genuine catastrophe, which is why people drew a diagonal line across the top edge of the deck — a dropped and reshuffled deck could be re-sorted by lining the diagonal back up.

You loaded your deck into the card reader, set switches on the console to point the machine at the loading address, and pressed start. If your program had a bug, it did not print a stack trace; it either stopped dead with lights showing the contents of registers, or it kept running and produced wrong output, or it wandered into arbitrary memory and did something undefined. You had no debugger. You examined the console lights, thought about it, punched corrected cards, and — if your hour had run out — signed up for another slot next week.

The economics are the point. The machine cost a fortune per hour and was almost always idle: idle while you walked to the reader, idle while cards fed through at a few hundred a minute, idle while the operator mounted a tape, idle while you stared at the lights, idle between your slot ending and the next person's beginning. Actual computation was a small fraction of the wall clock. The scarce resource was processor time and it was being wasted at enormous cost, and every single mechanism in this document is, at root, a response to some version of that observation.

Where this is in your stack

Nothing above has been superseded. It is all running right now, underneath everything you write, and several things you already deal with are this node showing through.

Your JavaScript is these instructions. When you run node server.js, the file is not executed by anything that understands JavaScript. It is read by V8, a C++ program compiled to x86-64 or ARM64 machine code, which parses your source into a tree, walks that tree in an interpreter called Ignition, and — for functions that run often enough to be worth it — hands them to an optimising compiler (TurboFan, and since 2021 also a mid-tier one called Sparkplug) which writes machine code into memory and jumps to it. That is the stored-program property from 1945 being used at runtime, in your process, thousands of times. It is also why a JIT-compiled runtime needs memory that is both writable and executable, which is a security problem serious enough that browsers and modern kernels go to some lengths to narrow the window in which a page is both.

A stack trace is a list of instruction pointer values. When your Node process throws, the frames you read are recovered by walking a chain of saved rip values in memory and mapping each address back to a function name using a table the runtime kept. This is why a stack trace from a stripped native binary is a column of hexadecimal numbers, why source maps exist (they are the same mapping problem one level up: bundled line and column back to original line and column), and why Error.stackTraceLimit exists at all — collecting frames costs real time because it is a walk through memory.

An architecture mismatch is the ISA agreement failing. exec format error when you run a container image on the wrong machine is the processor being handed bit patterns encoded under a different agreement about what the bits mean. It is why docker build --platform linux/amd64 exists, why Apple Silicon machines run amd64 images through emulation (QEMU translating each instruction, roughly five to twenty times slower — a real reason your local Docker build feels sluggish), and why docker manifest lists can carry several architectures under one tag. The same fact makes native Node modules architecture-specific: a .node file is compiled machine code, so npm install on an ARM Mac produces binaries a linux/amd64 container cannot load, which is the actual reason node_modules must not be baked into an image from the host and must be installed inside the build.

Byte-level thinking surfaces in JavaScript. ArrayBuffer, Uint8Array, and Node's Buffer are a run of the numbered boxes described above, exposed directly. buf.readUInt32BE versus readUInt32LE is the question of which end of a four-byte number is stored first — endianness, a genuine hardware difference where x86 and ARM store the least significant byte at the lowest address (little-endian) while network protocols by convention use the other order. That is why it is called "network byte order" and why you convert.

Speculative execution reaches all the way into your web app. The out-of-order machinery mentioned above is what made Spectre possible, and the mitigation on the web side was to remove precise timing from JavaScript: performance.now() was deliberately coarsened, and SharedArrayBuffer was disabled in browsers in January 2018 and only restored behind the Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers. If you have ever had to set those two headers to make a WebAssembly threading library work, the reason is a processor optimisation described three paragraphs ago.

What you can do at this point: describe, without hand-waving, what a computer is — a memory of numbered bytes holding both data and instructions, and a processor that repeats fetch, decode, execute, advance — and explain why it is binary, why instructions being data is the decisive idea, and what your JavaScript actually becomes before it runs.

What's still broken: the machine runs exactly one program, and a human being is the loader. Between one program ending and the next beginning, a person walks across a room. The processor — the most expensive thing in the building — sits idle for the overwhelming majority of every hour, waiting on humans and on cards. Nobody can share the machine, because there is nothing in it that could arbitrate. The first fix is obvious once stated: if loading the next program is itself a job, then a program could do it.

Node 1 — the program that loads the next program

The limitation: the machine runs one program and a human loads it, so the processor idles between jobs and nobody can share it.

The fix is available the moment you accept the stored-program idea from Node 0, and it is almost embarrassingly simple to state: if loading a program is a job, write a program that does it. Keep that program permanently in memory. When a job finishes, control returns to it, and it loads the next one. No human walks anywhere.

This program has a name that says exactly what it does — the resident monitor. Resident because it stays in memory while jobs come and go; monitor because it watches over the sequence. It is the first operating system, and it is worth noticing how little it is: a loop that reads a job, jumps to it, and gets control back.

The first one, and what it consisted of

The generally recognised first operating system is GM-NAA I/O, written in 1956 by Robert L. Patrick of General Motors Research and Owen Mock of North American Aviation, for their IBM 704 machines. The name is worth unpacking because both halves of it are the two functions an operating system still performs today.

GM-NAA is the batch part: the monitor loop. A tape holds a sequence of jobs. The monitor reads the first, loads it into memory at a known address, sets the instruction pointer to it, and the job runs. When the job finishes, it jumps back to a fixed address inside the monitor, and the monitor loads the next. The processor's idle time between jobs falls from minutes to milliseconds. The word job enters computing here and never leaves it: a unit of work submitted to a system that will run it later, without you present. You use that word every day — a CI job, a cron job, a BullMQ job — and it means the same thing it meant in 1956.

I/O is the other half, and it was the part the users cared about more. Every program needed to read cards and write tape and drive the printer, and every program was writing that code itself, badly and differently. Talking to a card reader means writing precise bit patterns to a hardware port, waiting a precise time, checking a status bit, handling the case where the card jammed. Getting it wrong wasted a machine hour. So the monitor shipped a set of shared input/output subroutines that any job could call instead of driving the hardware itself.

That is the origin of two things at once, and both are still exactly here. A device driver is the piece of code that knows the specific bit-level protocol of one piece of hardware, written once so that nothing above it has to know. [EXPLAIN] And a system library is the shared code an operating system provides so that programs are not each reimplementing the same fiddly thing. The reason your code says fs.readFile rather than issuing commands to an NVMe controller is a straight line from this decision in 1956.

Job control: configuration files are older than you think

The monitor needs to be told things about each job before it runs it. Which compiler does this job need? How much memory? Whose account gets billed? What should happen if it fails — skip to the next job, or stop the whole tape?

None of that can live inside the job's own code, because the monitor has to read it before the job runs, and because the job might be written in a language the monitor cannot parse. So it goes in separate control cards at the front of the deck, written in a small dedicated language. IBM's version, shipped with OS/360 in 1964, was called Job Control Language — JCL — and it looked like this, with two slashes marking a control card:

//PAYROLL  JOB  (ACCT1234),'D KAPOOR',CLASS=A,TIME=(,30)
//STEP1    EXEC PGM=IEBGENER
//SYSUT1   DD   DSN=INPUT.CARDS,DISP=SHR
//SYSUT2   DD   DSN=OUTPUT.RPT,DISP=(NEW,CATLG,DELETE)
//SYSIN    DD   DUMMY

Read that structure rather than the syntax. There is a named job, an account for billing, a resource limit (thirty minutes), a sequence of named steps, and for each step a declaration of its inputs and outputs and what to do with them on success versus failure. [AWARE] It is a pipeline definition file. The reason it is worth putting in front of you is that you write one of these most weeks and may not have noticed the lineage.

Spooling: the first time a queue solved a speed mismatch

Batching fixed the gap between jobs. It did not fix the gap inside one. A card reader took cards at a few hundred a minute; a line printer managed perhaps a thousand lines a minute; the processor executed tens of thousands of instructions per second and, later, millions. A job that printed a long report spent nearly all its wall-clock time with the processor stopped, waiting for mechanical parts to move.

The first fix was crude and effective. Buy a cheap, slow machine — an IBM 1401 — and use it purely to copy card decks onto magnetic tape. Tape could be read far faster than cards. Carry the tape to the expensive machine, which now reads jobs at tape speed. Output goes to another tape, which is carried back to the cheap machine to be printed. The expensive processor never waits on a card reader again. This was called offline operation because the slow devices were off the main machine's line.

The better fix, once the hardware of Node 2 existed, kept everything on one machine and overlapped it in time: while job N computes, the system reads job N+1's cards to disk in the background, and prints job N−1's output from disk in the background. The processor works continuously and the slow devices work continuously and neither waits for the other. This is spooling, an acronym for Simultaneous Peripheral Operations On-Line, and the general principle it establishes is one you use constantly: when a fast producer meets a slow consumer, put a queue between them and let each run at its own rate. [EXPLAIN] Your print spooler still has this name. So does every message queue you have ever configured.

Where this is in your stack

This node is not history you have moved past. It is the shape of your deployment pipeline, and once you see the correspondence it is difficult to unsee.

A CI runner is a resident monitor. A GitHub Actions runner process sits permanently alive on a machine, polling a queue. It receives a job, prepares an environment, runs the job's steps, collects the output, reports status, tears the environment down, and goes back to polling. That is Patrick and Mock's loop, unchanged, with HTTPS where the tape drive was. The vocabulary survived intact: the file is a list of jobs, each job has steps, each job declares runs-on (which machine class — CLASS=A in the JCL above), a timeout-minutes (TIME=(,30)), and needs to express that one step's output is another's input (DD statements). Your .github/workflows/deploy.yml is JCL with better syntax and worse error messages.

A BullMQ worker is the same loop again, and its design decisions are forced by the same problems. In your qbank repository, a producer pushes a job onto a Redis list and a worker process blocks on that list, pops a job, runs its handler, and marks it complete. Every hard part of that design is a batch-monitor problem that 1956 also had. What happens if the worker dies mid-job? The 704's answer was that the operator noticed and resubmitted the deck; BullMQ's answer is a visibility timeout — the job is moved to an active set with a lock that must be renewed, and a stalled-job checker returns it to waiting when the lock expires. What happens if a job fails? JCL had COND codes deciding whether to skip the remaining steps; BullMQ has attempts and a backoff strategy and a failed set. What stops one bad job from consuming the machine? JCL had TIME=; BullMQ has a job timeout and you also want a cgroup limit from Node 27. The problems are not similar to the old ones; they are the same problems.

The producer–consumer queue is spooling, everywhere. Every buffer in your stack exists because a fast thing met a slow thing. A Node Writable stream holds an internal buffer, and write() returning false means that buffer has passed highWaterMark — that is the system telling you the consumer is slower than you are, and ignoring it is how a Node process's memory climbs until it is killed. That signal, and the 'drain' event that clears it, are backpressure, which is the one thing 1950s spooling did not have to solve because the tape was finite. Yours is not: an HTTP client that reads a response slowly while your server writes fast is an unbounded queue in your heap. Postgres has the same shape internally — a commit writes to an in-memory WAL buffer that a background writer drains to disk. So does the operating system itself: write() to a file returns as soon as the bytes are in the kernel's page cache, long before any disk has moved, which is Node 23's entire subject.

Cron is batch processing with a clock. A daemon holds a table of jobs and times, and at each minute runs whatever is due, capturing output and mailing it somewhere. It has the monitor's exact structure with a scheduling predicate bolted on, and it has the monitor's exact failure modes: if a run takes longer than the interval, the next one starts anyway and you now have two, which is why every real cron job needs a lock. Kubernetes CronJob makes that explicit as concurrencyPolicy: Forbid — a field that exists because of a problem inherent to this node.

What you can do at this point: explain what an operating system minimally is — a program that stays resident and arranges for other programs to run — and recognise the batch model in the pipeline tooling you use, including which of its ancient failure modes your configuration is guarding against.

What's still broken: three things, and each one is fatal.

First, the processor still stops dead whenever a job touches a device. The monitor's shared I/O routine, underneath, is a loop that reads a hardware status bit over and over until the device says it is ready. That is called polling, and during it the processor executes millions of instructions that accomplish nothing. Spooling helps between jobs but cannot help a single job that is waiting.

Second, control only returns to the monitor if the job chooses to return. A job with an infinite loop owns the machine until someone power-cycles it. A job that jumps to a wrong address never comes back.

Third, and worst: the monitor is just bytes in memory, at addresses the job can write to. A job with a bad array index overwrites the monitor and the next job loads into a corrupted system. There is no mechanism anywhere in Node 0's machine that could prevent this, because the processor's only rule is fetch, decode, execute.

The first of those needs a new piece of hardware: a way for a device to get the processor's attention rather than the processor having to ask.

Node 2 — the interrupt, and the birth of asynchrony

The limitation: a program that wants something from a device has to ask the device repeatedly whether it is ready, and every one of those questions is a wasted instruction.

Fix the ratio in your head first, because the whole node follows from it. A card reader in 1960 delivered around ten cards per second. The IBM 7094 executed roughly half a million instructions per second. So between one card and the next there was room for about fifty thousand instructions, and the program spent every one of them re-reading a status bit that said "not yet". The proportions have not improved; they have got worse. A processor today executes on the order of ten billion instructions per second. Fetching one byte from main memory takes it about eighty nanoseconds, during which it could have executed several hundred instructions. Reading a block from a solid-state disk takes around one tenth of a millisecond — a million instructions. A network round trip to a server in another country takes a hundred milliseconds — a billion instructions. The gap between the processor and everything else is the central physical fact of computing, and nearly every mechanism after this point is a way of not wasting it. [EXPLAIN]

The mechanism, exactly

Polling is the wrong direction. The processor should not ask the device; the device should tell the processor. That requires a physical wire from the device into the processor, and a rule in the processor's fetch-decode-execute loop about what to do when that wire goes high.

The rule is inserted between instructions, and its placement matters. The processor completes the instruction it is currently executing — it never stops halfway, because a half-executed instruction would leave registers in a state nothing could recover from — and then, before fetching the next one, it checks whether the interrupt line is raised. If it is:

1. finish the current instruction
2. check the interrupt line — raised?
3. save rip (and the flags register) somewhere it can be recovered from
4. look up the handler address for this interrupt number
5. set rip to that address
   ... the handler runs ...
6. a special "return from interrupt" instruction restores rip and flags
7. the interrupted program resumes at exactly the instruction it was about to run

That is an interrupt. [EXPLAIN] Note precisely what has happened: a piece of code ran, in the middle of another piece of code, without that other code having any instruction that called it and without it being able to tell afterwards that anything happened. The interrupted program's registers are exactly as it left them, its instruction pointer resumes where it was, and nothing in its own logic ever mentioned the device. Execution stopped being a continuous, self-determined sequence and became something that can be entered from outside at essentially any point.

That is what "asynchronous" physically is. Not a language feature, not a callback style — a wire, and a rule about checking it between instructions. Every asynchronous thing you have ever written bottoms out here.

Which interrupt, and where the handler lives

A machine has many devices and one processor, so there must be a way to say which device is calling. Historically an interrupt controller chip sat between the devices and the processor, collecting many device lines and presenting the processor with one line plus a number. On the IBM PC that chip was the Intel 8259 PIC, with eight inputs, later two chained for fifteen; those inputs are the IRQ numbers still visible today in /proc/interrupts on any Linux machine, and the reason IRQ conflicts were a routine part of installing hardware in the 1990s is that there were only fifteen of them. Modern machines use the APIC — the Advanced Programmable Interrupt Controller — and PCI Express devices use MSI-X (Message Signalled Interrupts), where the "wire" is not a wire at all but a write to a special memory address, which lets one network card have dozens of distinct interrupt vectors, one per receive queue. That detail matters later: it is how a modern server spreads network interrupt handling across all its cores.

The number is used as an index into a table of handler addresses. On x86 this is the Interrupt Descriptor Table, the IDT: 256 entries, each holding the address of the code to run for that vector, with a register (idtr) holding the table's own address. The processor's step 4 above is literally an array lookup. [EXPLAIN]

The same table serves two other sources of entry, and lumping them together is one of the most useful simplifications available:

  • Hardware interrupts — a device raised a line. Asynchronous: they arrive with no relation to what the program was doing.
  • Exceptions (also called faults or traps) — the current instruction could not complete. Divide by zero, an invalid opcode, or, crucially, an access to a memory address the program is not allowed to touch. Synchronous: caused by the instruction itself. Node 10's page fault is one of these, and it is the single most important entry in the table.
  • Software interrupts — an instruction that deliberately triggers the mechanism, so a program can jump into the system on purpose. That is Node 4, the system call.

One table, one mechanism, three reasons for entry. Every transition from your code into the kernel — every one, without exception — is one of those three.

The history, and one machine worth knowing

The first machine with anything called an interrupt was the UNIVAC 1103 around 1953, which needed to capture readings from a wind tunnel that would not wait. The DYSEAC, built at the US National Bureau of Standards in 1954, is usually credited as the first with general input/output interrupts. But the machine that turned interrupts into an operating system design is the Ferranti Atlas at the University of Manchester, operational in 1962 under Tom Kilburn — the same group that had run the Manchester Baby fourteen years earlier.

Atlas is the most under-known machine in this document and it introduced, in one design: a full interrupt system with priorities; extracodes, which were instruction patterns the hardware did not implement and which trapped into a supervisor routine instead — a system call, in 1962, before the term existed; the Supervisor program itself, which is the direct ancestor of the word "kernel"; and virtual memory with demand paging, which is Node 10 and was not adopted by mainstream commercial machines for another decade. When you read that an idea in this document is from the 1960s, there is a good chance the specific answer is Atlas.

The three hard problems interrupts create

Interrupts solve the waiting problem and immediately create three new ones. All three are still live and all three have consequences you can observe in your own systems.

One: an interrupt can arrive halfway through something that must not be halved. Suppose the system is updating a linked list — it has set the new node's next pointer but not yet made the previous node point at it. An interrupt fires and the handler walks that list. It walks a structure that is, at this instant, inconsistent. So there must be a way to say "not now": on x86, the cli instruction clears the interrupt-enable flag and sti sets it. Regions between them are critical sections, and the general problem — a data structure being observed midway through a multi-step update — is the same problem that produces every race condition in Node 16 and every isolation level in a database. It appears here first, in hardware.

Two: while the handler runs, the machine is not doing its real work, and often cannot even take another interrupt. So handlers must be extremely short, which conflicts directly with the fact that reacting properly to a network packet involves a great deal of work. Linux resolves this by splitting the response in two, and the names are worth knowing because they appear in every profiling tool. The top half — the actual interrupt handler — does the minimum: acknowledge the device, note that there is work, and schedule the rest. The bottom half — implemented as softirqs, tasklets, or kernel work queues — runs later with interrupts enabled and does the real processing. When you run top on a busy server and see a percentage under si, that is time in softirqs, and on a machine serving a lot of traffic it is mostly network receive processing. High si on one core and idle on the others is a real and diagnosable production condition: interrupts are not spread across queues.

Three: at high rates, interrupting is worse than polling. A ten-gigabit network card receiving small packets can generate over a million interrupts a second, and at that rate the machine does nothing but enter and leave handlers — a condition with the excellent name receive livelock. The fix inverts the node: when the rate is high, the driver turns interrupts off and polls, because at high rates polling is guaranteed to find work and costs nothing wasted. Linux's mechanism for this is NAPI ("New API", named in 2001 and still called that), and it switches between interrupt-driven and polled mode automatically based on load. [AWARE] The general lesson is worth carrying: interrupts win when events are rare, polling wins when events are dense, and that same trade decides between WebSocket push and HTTP polling, between database triggers and batch scans, and between filesystem watching and periodic scanning.

DMA: the device writes to memory itself

One more piece completes the hardware picture. Even with interrupts, if the processor has to copy each byte from the device into memory itself, a large transfer occupies it entirely. So devices are given the ability to write to main memory directly, without the processor's involvement: Direct Memory Access. The processor tells the device "put the data at address X, length N, and interrupt me when you are done", and then goes and does something else entirely while the device and the memory controller move the bytes.

This is why an interrupt from a network card means the packet is already in memory, not a packet is available if you would like to fetch it. It is also the reason a whole class of performance work exists: if the device can write straight into memory, the remaining copies are the ones software does, and eliminating them is what "zero-copy" means. Node's sendfile-backed file serving, and the reason a static file served by nginx is dramatically cheaper than the same file read into a JavaScript buffer and written to a socket, is exactly this — the second path copies the bytes from the kernel into your heap and back into the kernel for no reason.

Where this is in your stack

This is the node where the phrase "Node.js is asynchronous" stops being a slogan. Here is the complete path of one HTTP request arriving at your server, from the wire to your callback, with nothing skipped. Every step is a real component with a real name.

  1. Electrical signals arrive at the network interface card. The card reassembles them into a frame and checks its integrity.
  2. The card writes the packet by DMA into a region of main memory the driver set up in advance — a ring buffer. No processor involvement.
  3. The card raises an MSI-X interrupt on a specific core.
  4. The processor finishes its current instruction — which may well be a piece of JIT-compiled JavaScript from your own code — saves rip, and jumps into the driver's handler through the IDT.
  5. The handler (top half) does almost nothing: it disables further interrupts from that queue and schedules a NET_RX softirq. It returns. Your JavaScript resumes, having noticed nothing.
  6. Shortly after, the softirq runs. It pulls packets from the ring, walks them up the network stack — Ethernet, then IP, then TCP — checks sequence numbers, sends acknowledgements, reassembles the byte stream, and appends the payload to the receive buffer of the socket it belongs to. This is Node 32's subject in full.
  7. That socket now has readable data. The kernel marks the corresponding file descriptor ready and, because your process registered interest in it, adds it to the ready list of an epoll instance. That is Node 19.
  8. Your Node process, meanwhile, is blocked inside a call to epoll_wait. That call now returns, carrying a list of ready descriptors. The process was consuming zero processor time until this moment.
  9. libuv, the C library underneath Node, is the code that called epoll_wait. It maps each ready descriptor back to a handle and invokes the C callback registered for it. That is Node 20.
  10. The callback reads the bytes with a read system call, hands them to Node's HTTP parser, and when a complete request has been parsed, calls into V8 to invoke your JavaScript function.
  11. Your app.get('/users', handler) runs.

Steps 1 through 5 are this node. Nothing else in the chain would work without them. And the framing that matters: your callback did not run because anything in your program asked for it. It ran because a wire went high. [EXPLAIN] The event loop is not the origin of asynchrony in your system; it is a piece of software that organises asynchrony that the hardware creates.

The same path explains a browser click. Pressing a mouse button closes a physical contact; the USB controller raises an interrupt; the kernel's input subsystem turns it into an event on /dev/input/eventN; the display server (X11, Wayland, or the platform equivalent) reads it and routes it to the window under the pointer; the browser's UI process receives it, works out which renderer process owns that region, and forwards it over an IPC channel; the renderer does a hit test against the layout tree to find the target element; and only then does a MouseEvent object get constructed and a task queued on the renderer's event loop to dispatch it through capture, target, and bubble phases to your React onClick. Roughly eight layers, and the bottom one is this node.

Interrupt coalescing explains a class of latency you may have measured. Network cards deliberately delay interrupts to batch packets — ethtool -c shows the setting, typically tens of microseconds. Cloud providers tune it for throughput. If you have ever found that a request's server-side timing accounts for less than the time the client observed, and network transit does not explain the rest, some of the missing time is here, together with the kernel's own delays: Nagle's algorithm holding a small write to coalesce it, and delayed acknowledgement on the other side. The interaction of those two is a classic forty-millisecond stall, and socket.setNoDelay(true) — which Node's HTTP server sets by default, and which you must set yourself on raw sockets — disables the first half of it.

And "top half / bottom half" is a pattern you already write. A webhook endpoint that validates a signature, pushes a job onto a queue, and returns 202 Accepted in four milliseconds is a top half. The worker that processes it is a bottom half. You arrived at that design because the sender times out, which is the same pressure — get out of the handler fast, do the real work where you are allowed to take your time — that shaped the Linux network stack. It is the same pattern at a different scale, and recognising it as such is worth more than either instance alone.

What you can do at this point: explain what asynchronous execution physically is, trace a network packet from the wire to a JavaScript callback naming every layer, and read the si column in top and /proc/interrupts to see whether a machine's interrupt load is balanced.

What's still broken: everything in this node is code sitting in memory, and from Node 0 any program can write to any memory address. A job can overwrite the interrupt table and point the timer handler at its own code. A job can execute cli, disable interrupts, and loop forever, at which point no device and no clock can ever regain control and the machine is dead until someone cuts the power. A job can write directly to the disk controller and destroy another user's data. The monitor is a convention that programs are politely following, and conventions are not enforcement. The machine needs a distinction it does not currently have: some code is allowed to do these things, and other code is not.

Node 3 — privilege: one bit that splits the machine in two

The limitation: every mechanism built so far — the monitor, the interrupt table, the device drivers — is ordinary bytes in ordinary memory, and any program can overwrite them, disable interrupts, or drive the hardware itself. Protection is currently a request, not a rule.

Software cannot fix this. Whatever check you write in software runs as instructions that the offending program could simply jump past, or overwrite, or never call. A guard that the guarded party can remove is not a guard. The enforcement has to be in the hardware, below the level at which any instruction can reach it. [EXPLAIN]

The mode bit

The mechanism is one bit inside the processor, not in memory, holding the current mode. Two values. Call them kernel mode (also supervisor mode, privileged mode, ring 0) and user mode (unprivileged, ring 3).

Certain instructions are then declared privileged. If the processor decodes one while the mode bit says user mode, it does not execute it. Instead it raises an exception — one of the three entry types from Node 2 — which transfers control to a handler that the kernel installed. The user program does not get to decide what happens next; the hardware has already taken control away from it.

On x86-64 the privileged set includes, concretely:

  • cli and sti — disable and enable interrupts. This closes Node 2's hole where a program could freeze the machine permanently.
  • lidt — load the interrupt descriptor table register. A user program cannot repoint the interrupt table at its own code.
  • mov cr3, ... — change the page table root. This is Node 10's mechanism and it is the one that makes memory isolation possible at all.
  • in and out — read and write hardware I/O ports. A user program cannot address the disk controller directly.
  • hlt — stop the processor until the next interrupt. This is what an idle machine executes, and it is why an idle server draws less power.

Notice what this list is. It is exactly the set of things the operating system needs in order to remain in control: control of the clock, control of the interrupt table, control of memory mapping, control of devices. Everything else — arithmetic, loads, stores, jumps, function calls — is unprivileged, which is why the vast majority of a normal program's instructions run at full speed with no involvement from anything.

The other half: memory protection

The mode bit alone is not enough, because a user program could still write over the kernel's memory with an ordinary mov instruction, which is not privileged. So the hardware must also enforce which addresses a program may touch, and the check has to happen on every single memory access without slowing the machine down.

The earliest form was two extra registers: a base and a limit. Every address the program produces has base added to it and is checked against limit; out of range raises an exception. Both registers are loadable only in kernel mode. This is crude — it gives each program one contiguous region — but it establishes the shape of the answer, which is that address translation and permission checking happen in hardware, on every access, from tables only the kernel can modify. Node 10 replaces base-and-limit with page tables, which are the modern form, but the principle is fixed here.

The violation, when it happens, is an exception that lands in a kernel handler, and on Unix systems that handler's normal response is to deliver the signal SIGSEGV to the offending process, whose default action is to terminate it. "Segmentation fault" is the user-visible name of this exact hardware event. [EXPLAIN] The word "segmentation" is a fossil from an older scheme where memory was divided into segments; the mechanism today is paging, but the message stayed.

The single most useful thing to understand about the kernel

It is very common, and completely wrong, to picture the kernel as a program that is running alongside your programs — a big process that takes its turn. Correct this now, because a great deal downstream depends on it.

The kernel is not a process. It is a mode the processor is in. [EXPLAIN]

There is one processor, executing one instruction stream. Most of the time that stream is your program's instructions and the mode bit says user. When your program makes a request, or a device interrupts, or an instruction faults, the processor switches the mode bit to kernel and jumps to kernel code — the same processor, continuing to execute, now with different permissions and running different instructions. When it is finished it flips the bit back and resumes where it was. There is no scheduling in between, no other program involved. The kernel is a body of code that your process executes, on your process's time, with the privilege bit raised.

Three things follow immediately and they are all observable:

When you run top and see us and sy, you are seeing this split measured. us is time your process spent executing with the mode bit at user; sy is time your process spent executing kernel code on its own behalf. A process doing heavy file or network work can show most of its time in sy, and that time is still charged to it. This is also why process.cpuUsage() in Node returns { user, system } as two separate numbers.

When a kernel bug is hit, there is no process to kill — the failing code is the system — so the machine panics, which is why a kernel bug takes down everything and a user-space bug takes down one process. That asymmetry is the entire argument of Node 41's microkernel debate.

And the boundary crossing is a real cost that you can count, which is Node 40's subject and the reason interfaces like io_uring were designed.

How the split was found, historically

The Ferranti Atlas Supervisor (1962) had it, as did the Burroughs B5000 the same year. The design that thought hardest about it was Multics — Multiplexed Information and Computing Service — a joint MIT, Bell Labs and General Electric project begun in 1965 whose stated goal was a computing utility that many mutually untrusting users could share. Multics generalised two modes into eight protection rings, numbered 0 (most privileged) outward, with hardware checking on every cross-ring call. It was, in security terms, far ahead of anything that followed.

Multics was also enormous, late, and slow, and in 1969 Bell Labs withdrew. Two of its people, Ken Thompson and Dennis Ritchie, then wrote a much smaller system on a spare PDP-7, which Brian Kernighan named Unics as a joke on Multics — one of everything where Multics had many — and which became Unix. That withdrawal is the single most consequential event in this document: Linux, macOS, iOS, Android, and every server you deploy to are descendants of the small thing built in reaction to the large one.

Intel's x86 line inherited the ring model, offering four rings (0 to 3) when the 80286 introduced protected mode in 1982 and the 80386 completed it in 1985. In practice essentially every operating system uses only ring 0 and ring 3, because the paging hardware only distinguishes "supervisor" from "user" anyway and because portable kernels cannot rely on a feature x86 alone has. Rings 1 and 2 sat unused for thirty years, then found a use in early paravirtualised Xen, and then hardware virtualisation added a genuinely new level below ring 0 — informally "ring −1" — where a hypervisor runs, which is Node 29.

Where this is in your stack

This is the boundary that defines what your language can and cannot do. There is no JavaScript that opens a file. There cannot be. Opening a file requires talking to a storage controller, which requires privileged instructions, which user-mode code cannot execute. Every capability your runtime appears to have — files, sockets, timers, spawning processes, allocating memory, knowing the time — is a request across this boundary, and the complete list of things your program can ask for is the list of system calls, which is Node 4. When people say a language is "sandboxed", what they usually mean is that a layer above this one narrows the list further.

Native crashes in Node are this node firing. A JavaScript error throws an exception you can catch. A crash inside a native addon — better-sqlite3, sharp, bcrypt, anything with a .node file — reaching a bad pointer produces a memory access violation, an exception in hardware, a SIGSEGV, and process death with no JavaScript stack, because by the time the signal is delivered there is nothing left to unwind. This is precisely why process.on('uncaughtException') cannot save you from it: the failure happened below the level at which V8 has any say. It is also why a crash of this kind is a real argument for running workloads in separate processes with a supervisor — a design decision Node 5 and Node 31 make concrete.

Browser site isolation is this idea copied upward. A browser tab runs untrusted code from the internet, so it needs the same guarantee: this code may compute, and may ask for things, but may not touch anything else. Originally that was enforced in software inside one process — V8 isolates and contexts separating one site's objects from another's. Spectre, in January 2018, broke that: speculative execution let code read memory in its own address space that it had no logical right to, and software-level separation within a process is not a defence against a hardware side channel. Chrome's response, shipped fully in Chrome 67 (May 2018), was Site Isolation — put each site in its own operating system process, so that the boundary is the hardware one from this node rather than a software convention. This is why your browser shows dozens of processes in the task manager, why memory use went up by roughly ten to thirteen percent, and why SharedArrayBuffer requires cross-origin isolation headers before it is handed back to you. A JavaScript feature is gated on a processor's speculation behaviour, mediated by a 1962 idea about rings.

WebAssembly is a software re-derivation of the same design. A Wasm module has a linear memory — a single ArrayBuffer — and every memory access it makes is bounds-checked against that buffer's length. It cannot form a pointer to anything outside. It has no instruction that reaches the host. Its only way out is a list of imported functions the host chose to provide — which is a system call table, built in software, with the host as the kernel. WASI, the WebAssembly System Interface, makes the resemblance total: it is a POSIX-shaped syscall list for Wasm. If you understand Node 3 and Node 4, you understand Wasm's security model completely, because it is the same model.

Container privilege flags are ring-0 access. docker run --privileged means: do not drop the capabilities that would let this container reconfigure the kernel. It is not a general "more permissions" switch; it specifically re-grants abilities like loading kernel modules, changing the interrupt configuration, and accessing raw devices — the kernel-mode powers of this node, exposed to a process. That is why running a container privileged is close to giving it the host, and why the fix for a container that needs one specific ability is a single capability (--cap-add NET_ADMIN) rather than the whole set. Node 25 breaks capabilities down properly.

eBPF is the interesting modern exception. It lets ordinary user-space tools load small programs that run in kernel mode, attached to kernel events. Since Node 3 says that is exactly what must never be allowed, the resolution is worth knowing: the kernel runs a verifier over the bytecode before loading it, statically proving that it terminates, that every memory access is in bounds, and that it only calls an allowed set of helpers. It is a proof obligation substituting for a hardware boundary, and it is how modern observability (Node 39), modern container networking (Cilium), and modern security policy are implemented.

What you can do at this point: explain why an operating system cannot be enforced in software, state precisely what the kernel is (a mode, not a process), read us versus sy correctly, and explain what a segmentation fault physically is and why no JavaScript handler can catch one.

What's still broken: the wall is now absolute, and that is useless. A user program can execute arithmetic and nothing else — it cannot read input, cannot write output, cannot allocate memory, cannot even stop cleanly. A program that cannot affect the world is not a program. What is needed is a door in the wall: a way for user code to deliberately enter kernel mode, but only at an address the kernel chose, running code the kernel wrote, with the kernel deciding whether the request is permitted.

Node 4 — the system call: the only door

The limitation: user mode can compute but cannot do anything, and kernel mode can do anything but must not be enterable at an address the user program picks.

The resolution reuses the third entry type from Node 2 — the software interrupt. A single instruction exists whose entire effect is: switch the mode bit to kernel, and jump to one specific address that the kernel registered in advance. The user program controls when the crossing happens. It does not control where it lands. That asymmetry is the whole design, and everything else is detail.

The instruction is a trap, and the resulting request is a system call — syscall. It is the complete and only interface between every program on the machine and the machine itself. [EXPLAIN] Linux has roughly 350 of them on x86-64. That number is the true size of the API you are programming against, whatever language you write in.

The instruction, and the agreement around it

Since the destination is fixed, the request itself has to be encoded some other way, and the only place available is the registers. So there is a convention — an ABI, an Application Binary Interface — fixing which register holds what. On Linux x86-64 it is:

  • rax — the system call number. 0 is read, 1 is write, 2 is open, 60 is exit. These numbers are permanent; changing one would break every binary ever compiled.
  • rdi, rsi, rdx, r10, r8, r9 — up to six arguments, in that order.
  • the syscall instruction — trap.
  • rax on return — the result. A negative value between −1 and −4095 means failure, and its negation is the error number: 2 is ENOENT (no such file), 13 is EACCES (permission denied), 9 is EBADF (bad file descriptor), 11 is EAGAIN (try again — the one that Node 19 turns into an entire architecture). These are the same strings you see in Node errors, because Node passes them straight through.

Writing "hi" to the terminal, complete, with nothing hidden:

mov rax, 1          ; syscall number 1 = write
mov rdi, 1          ; first argument: file descriptor 1 = standard output
mov rsi, message    ; second argument: address of the bytes
mov rdx, 2          ; third argument: how many bytes
syscall             ; trap into the kernel

That is console.log("hi") at the bottom. Every layer between — your JavaScript, V8, Node's C++ bindings, libuv, glibc's write wrapper — exists to arrange those five lines and interpret the answer.

What the processor and the kernel actually do in the crossing

Worth walking once in full, because the cost of it drives design decisions in Nodes 19, 20, 23 and 40.

  1. The syscall instruction saves the return address into rcx and the flags into r11, sets the mode bit to kernel, and loads rip from a special register (MSR_LSTAR) that only kernel mode could ever have written. The kernel wrote it at boot. There is no way for user code to influence the destination.
  2. The kernel's entry code executes swapgs, which swaps in a pointer to this processor's per-core kernel data — because at this instant the kernel does not yet know where anything of its own is.
  3. It switches to a kernel stack. Every process has two stacks: its user stack, and a small kernel stack (typically 16 KB on x86-64) used only while executing kernel code on its behalf. It must switch, because trusting the user stack pointer would let a program point it at kernel memory.
  4. It saves the full user register set onto that kernel stack. This saved block is called the pt_regs structure, and it is what ptrace and debuggers read, and what Node 6's context switch will save further.
  5. It checks rax against the size of the syscall table and uses it as an index: sys_call_table[rax]. Another array lookup, exactly like the IDT.
  6. Before touching any pointer the user passed, it validates it. A user program can pass any address at all, including a kernel address, and if the kernel dereferenced it directly, every process could read kernel memory by calling read with a kernel buffer. So all user memory is accessed through copy_from_user and copy_to_user, which check the address range and handle faults. This is the single most security-critical code in the kernel and the historical source of a long line of vulnerabilities.
  7. The work happens.
  8. The return value is placed in rax, registers are restored, and sysret flips the mode bit back and returns to the saved address.

The cost of all that, on modern hardware, is roughly 50 to 100 nanoseconds in the best case — a few hundred instructions' worth of time to do nothing but cross a line. It used to be less. The Meltdown vulnerability, disclosed 3 January 2018, forced a mitigation called KPTI (Kernel Page Table Isolation) which unmaps kernel memory from the user page table entirely, so every crossing now also reloads the page table root and flushes address translations. On some workloads that cost five to thirty percent of throughput, and it hit syscall-heavy workloads — databases, network servers, exactly your servers — hardest. If you administered anything in early 2018 and watched cloud instance performance drop after a host reboot, that was this.

The syscall boundary is the actual stable contract on Linux

This point separates people who understand Linux from people who use it. Linus Torvalds's rule, stated repeatedly and with force, is "we do not break userspace": the kernel's internal structures change freely between versions, but the syscall interface is permanent. A binary compiled against Linux 2.6 in 2005 will still run on Linux 6.x, because syscall number 1 is still write and it still takes the same three arguments.

This is why a statically linked Go binary can be dropped into a container built FROM scratch — no libraries, no shell, no filesystem to speak of — and simply work. Go's runtime issues syscalls directly rather than going through the C library, so the binary depends on nothing but the kernel's permanent contract. It is also why Windows is different: there, the syscall numbers change between builds without warning, and the stable contract is one level higher, in kernel32.dll and ntdll.dll. Programs are expected to call the DLL, which knows the current numbers. Two coherent designs, opposite choices, and the difference explains a great deal about how software is distributed on each platform.

What a "library function" is versus a system call

A distinction people routinely blur. strlen is a library function: it runs entirely in user mode, looping over bytes, never entering the kernel. write is a system call: it must enter the kernel because only the kernel may touch a device. And printf is a library function that eventually makes a system call — it formats into a buffer in user memory and calls write when the buffer fills or a newline appears.

That buffering is not a detail; it is a performance strategy, and it has a famous failure mode. Because printf to a pipe is fully buffered (typically 4 KB) rather than line-buffered as it is to a terminal, a program that prints steadily and then crashes shows all its output when run interactively and loses the last chunk when run under a pipe or redirected into a log file. Every language has a version of this problem. It is the origin of "my logs stop just before the crash".

The general principle underneath is worth stating plainly, because it is the reason for a whole category of optimisation in this document: a system call costs far more than an instruction, so software batches work in user space to make fewer of them. [EXPLAIN] Buffered output, the page cache, socket buffers, writev, sendfile, epoll, and io_uring are all instances of that one sentence.

Seeing them: strace

strace shows every system call a process makes, with arguments and return values. [USE] It is the single most direct way to see this node and it works on any program in any language, because every program is ultimately doing this and nothing else.

$ strace -f -e trace=openat,read,write,epoll_wait node server.js
$ strace -c -f node -e 'require("fs").readFileSync("/etc/hostname")'

The -c form prints a summary table: how many of each call, and how much time in each. Running it against a Node process doing real work is genuinely worth doing once, and the shape of the output is instructive — an idle Node server is a process sitting in a single epoll_wait, and a Node server under load is epoll_wait, then a burst of read, write, futex, and back. That is the whole runtime, visible.

Where this is in your stack

Every asynchronous API in Node is a system call plus a strategy for not waiting on it. The mapping is direct and worth memorising, because it makes Node's design legible:

  • fs.readFile → openat, fstat, read, close — issued on a threadpool thread, because regular files cannot usefully be polled for readiness (Node 19 explains exactly why).
  • net, http, dgram → socket, bind, listen, accept4, read, write — driven by epoll on the main thread, never the threadpool.
  • setTimeout → no dedicated call; the delay becomes the timeout argument to epoll_wait. Node 8 and Node 20.
  • child_process.spawn → clone/fork, execve, pipe2, waitpid. Nodes 14, 31 and 35.
  • crypto.pbkdf2, zlib, dns.lookup → no syscall at all for the work itself; they are pure computation pushed to the threadpool because they would otherwise block the loop. Note that dns.lookup is in this list because it calls getaddrinfo, which is a blocking library function, whereas dns.resolve speaks DNS over a socket and is genuinely asynchronous — a distinction that has caused real production incidents.

The console.log gotcha, explained properly. In Node, process.stdout is synchronous when it points at a file or a TTY, and asynchronous when it points at a pipe. That is not a quirk; it follows from this node. Writing to a terminal or a regular file will not block for long, so Node does the write syscall immediately and inline. Writing to a pipe can block indefinitely if the reader is slow, so Node makes it non-blocking and buffers. The consequences are real: logging heavily in a hot path is a synchronous syscall per call when you run it in a terminal, which slows the loop measurably; and when the same code runs in Docker or under a process manager — where stdout is a pipe — output can be lost on an abrupt exit because it was still in Node's buffer. That is the printf failure mode from two sections ago, arriving in your production logs.

Seccomp: a container is partly defined by which syscalls it may make. seccomp-bpf lets a process install a filter — a small program, checked and run by the kernel — that inspects each syscall's number and arguments and decides allow, deny, or kill. Docker applies a default profile that blocks about 44 of the roughly 350 calls, including mount, reboot, kexec_load, and the ones for loading kernel modules. This is why some tooling fails inside a container with EPERM for no apparent reason and works with --security-opt seccomp=unconfined. Kubernetes exposes the same thing as seccompProfile: RuntimeDefault, and turning it on is one of the cheapest genuine security improvements available for a Node workload, because a Node server needs a small syscall set and an exploit needs a larger one.

gVisor puts a second kernel in user space. Google's gVisor intercepts a container's syscalls and services them in a user-mode process called Sentry rather than passing them to the host kernel, so that a container escape has to break Sentry first. It works because this node's interface is the complete boundary — if you implement all 350 calls, you have implemented Linux as far as any program can tell. It is also why gVisor is slower: every syscall now costs several real crossings instead of one.

Syscall count is a real performance axis you can measure. A loop doing fs.appendFileSync per log line makes an openat, write, and close per line — three crossings each. Holding the descriptor open and batching lines makes one crossing per batch. On a busy service this is not a micro-optimisation; it is the difference between logging costing one percent of your loop and twenty. The same reasoning is why res.write called forty times per response is worse than building the body and writing once, why HTTP keep-alive matters (a new connection is socket plus connect plus a TLS handshake), and why io_uring — which lets a process submit thousands of operations through a shared memory ring with zero or one crossings — is the most significant kernel interface added in twenty years. Node has experimental io_uring support in libuv for some file operations from libuv 1.45 (2023) onward.

What you can do at this point: explain what a system call is at the instruction level, name the ABI, read strace output, map any Node API to the calls it makes, explain why the syscall boundary rather than the C library is Linux's stable contract, and explain seccomp as a filter on this exact interface.

What's still broken: there is a wall, a door, and code running. But "the running program" is still just bytes at an address with an instruction pointer. There is no name for it, no owner, no accounting, nothing that could be stopped and restarted, nothing the kernel could keep a list of. If two programs are to share this machine, the kernel needs a data structure representing one of them — everything it owns, everything it is allowed to do, and everything needed to pause it and resume it later as if nothing happened.

PART II — THE PROCESS, AND SHARING ONE PROCESSOR

Four nodes. The kernel gets a data structure for "a running program", a mechanism for putting one down and picking another up, a policy for deciding which, and a clock to make the whole thing possible. By the end of this part the machine genuinely runs many programs at once, and you can explain precisely why your Node event loop stalls, why a Kubernetes CPU limit makes latency worse rather than better, and what setTimeout(fn, 0) actually promises.

Node 5 — the process: giving the kernel something to hold

The limitation: the kernel can protect itself and can service requests, but "a running program" is not a thing it has any record of — just an instruction pointer that happens to be pointing at some bytes.

Start with the distinction the whole node rests on. A program is a file on disk: a passive sequence of bytes. A process is that program in execution, together with every piece of state the execution needs and every resource it currently holds. [EXPLAIN] One program can have many processes — running node server.js four times gives four processes from one file, each with its own memory, its own open sockets, its own place in its own execution. The file is a recipe; the process is the cooking.

What the kernel actually stores

For each process the kernel keeps one structure. Generically it is called the process control block; in Linux it is struct task_struct, defined in include/linux/sched.h, and it is around ten kilobytes. Every one of its fields exists because some earlier node in this chain created a need for it, and going through them is a genuinely efficient way to see what a process is:

  • Identity — the pid (process ID, a number), the ppid (the process that created it), a process group and a session. Names, so that a process can be referred to at all.
  • Saved registers — where the whole register set goes when the process is not running, including rip and rsp. This is what makes stopping and resuming possible, and it is Node 6.
  • Memory map — a pointer to an mm_struct describing every region of the address space and the page tables that implement it. Node 10 and Node 11.
  • Open file table — an array mapping small integers (0, 1, 2, 3…) to the things they refer to. Node 22, and the reason every Unix API takes a number rather than a name.
  • Credentials — the user ID and group IDs it runs as, and its capability set. Node 25, and the reason USER node in a Dockerfile does anything.
  • Signal state — which signals are blocked, which are pending, and what handler each one has. Node 30.
  • Filesystem context — the current working directory, the root directory, and the umask. Note that the current directory is per-process state held by the kernel; this is why a child process cannot change its parent's directory, and why cd must be a shell builtin rather than a program.
  • Scheduling state — priority, nice value, accumulated runtime, which processor it last ran on. Node 7.
  • Resource limits and accounting — maximum open files, maximum memory, total user and system time consumed.
  • Namespaces and cgroup — pointers to which view of the system it has and which resource budget it belongs to. Nodes 26 and 27, and together the definition of a container.

The list is the answer to "what is a process". A process is: an identity, a saved processor state, an address space, a set of open things, a set of permissions, a set of pending signals, a position in the filesystem, a scheduling record, a budget, and a view. Nothing else.

Process states, and the one that surprises people

At any instant a process is in one state, and ps prints it as a single letter. These matter operationally.

  • R — running or runnable. Either executing right now on some core, or sitting in the run queue ready to. ps does not distinguish them, which is why R counts can exceed core counts.
  • S — interruptible sleep. Waiting for something — data on a socket, a timer, a lock — and can be woken early by a signal. The overwhelming majority of processes on any machine are here, including your idle Node server sitting in epoll_wait. A sleeping process consumes exactly zero processor time. This is the whole payoff of Node 2.
  • D — uninterruptible sleep. Waiting inside the kernel at a point where it cannot safely be woken — typically partway through a disk or network filesystem operation, holding kernel state that a signal delivery would corrupt. A process in D state cannot be killed, not even with SIGKILL. [EXPLAIN] It leaves D when the operation completes, and if the operation never completes — a hung NFS mount, a detached cloud block device, a failing disk — it never leaves. This is the true answer to "why won't this process die", it is not a bug, and the only remedies are to fix the underlying device or reboot. It also inflates Linux load average, because load average counts R and D, which is why a machine with a stuck storage device can show a load of 40 while its processors are idle.
  • T — stopped. Suspended by SIGSTOP or by Ctrl-Z. Still exists, still holds everything, simply not scheduled.
  • Z — zombie. Finished executing, released its memory, but its task_struct still exists because its exit status has not yet been collected by its parent. Covered below and in Node 31.

Creation, the tree, and PID 1

Processes are created by other processes, so every process has a parent and the whole set forms a tree. The root of that tree is PID 1, started by the kernel at boot (Node 36), which on a modern Linux machine is systemd and inside a container is whatever your image's entrypoint is.

Unix made an unusual choice about creation which Node 14 examines in full: creating a process and running a new program are two separate operations. fork() makes a copy of the calling process, identical in every respect except the returned PID; execve() replaces the current process's program with a different one, keeping the identity, the open files, and the credentials. Every process on the machine except PID 1 came into being through some version of that pair. The reason for the split is that it makes the gap between the two into a place where the child can adjust itself — redirect its output, drop privileges, change directory, close descriptors — using ordinary calls, before the new program starts. Shell redirection and pipes are that gap being used, and it is one of the most elegant things in this document.

Two consequences of the tree are pure operations knowledge:

Orphans. If a parent dies while its children are alive, the children are reparented to PID 1 (or, on modern Linux, to the nearest ancestor marked as a subreaper). They keep running. This is how a process survives the terminal that started it.

Zombies. When a process exits, the kernel cannot discard its record immediately, because its parent may still want to know how it ended. So a small husk remains until the parent calls wait() and collects the status. A parent that never calls wait leaks these. One zombie is harmless — it holds no memory and no files, just a PID — but a process that spawns children in a loop and never reaps them will eventually exhaust the PID space and the machine will be unable to start anything. You cannot kill a zombie; it is already dead. You fix the parent, or you kill the parent, at which point PID 1 inherits the zombies and reaps them. [EXPLAIN]

Where this is in your stack

Your Node server is one process, and that is a design constraint with teeth. One task_struct, one address space containing the entire V8 heap, one main thread executing JavaScript, plus a handful of extra threads that belong to the same process (the libuv threadpool, V8's compiler and garbage collector helpers). Because it is one process, every item in the list above is shared by all your request handlers: one file descriptor table, so all connections compete for the same limit; one address space, so a memory leak in any route affects the whole server; one set of credentials; one cgroup budget. And because it is one process, a native crash from Node 3 takes all in-flight requests with it. This is the honest engineering reason people run several Node processes instead of one — not raw throughput alone, but blast radius.

The cluster module is fork plus descriptor passing, exactly. cluster.fork() spawns a full child process with its own V8 heap. The primary creates the listening socket and passes the descriptor to the children, which is possible because a file descriptor is a per-process number pointing at a kernel object (Node 22) and Unix sockets can transfer that reference between processes. Since Node 0.12 the default is round-robin distribution by the primary rather than letting the kernel choose, because kernel-level distribution turned out to be badly unbalanced under real load. The reason nothing is shared between workers — no shared cache, no shared counter, no shared session store, no shared rate limiter — is that separate processes have separate address spaces by definition, and that single fact forces Redis into more architectures than any other design consideration.

worker_threads is deliberately not this. A worker thread shares the process — the same descriptor table, the same address space, the same PID — but gets its own V8 isolate and therefore its own JavaScript heap. That is why you can pass a SharedArrayBuffer between workers but not between cluster children, why transferList exists to move an ArrayBuffer without copying, and why a worker that crashes V8 still kills the process. Node 15 does threads properly; the distinction to hold now is that cluster gives isolation and workers give sharing, and you pick based on which of those you need.

A container is a process tree, and this is the most useful correction available about containers. A container is not a small virtual machine. It is one or more ordinary Linux processes on the host — you can see them in the host's ps output with their real PIDs — that have been given restricted views (Node 26) and a resource budget (Node 27). Everything in this node applies to them unchanged. Which is why:

  • Your container's entrypoint is PID 1 inside it, and PID 1 has special kernel behaviour: signals with default actions are not applied to it. A plain node index.js as PID 1 that has not installed a SIGTERM handler will simply ignore docker stop, and be SIGKILLed ten seconds later, dropping every in-flight request. This is Node 31 and it is one of the most common real production defects in containerised Node.
  • PID 1 is also expected to reap orphans. Node does not do this. If your container shells out to subprocesses, you accumulate zombies — which is exactly why docker run --init and Kubernetes' shareProcessNamespace exist, and why the tiny tini init program ships inside Docker.
  • docker exec starts a new process inside the container's namespaces; it is not a session on a machine. When the container's PID 1 exits, everything goes, including your exec shell.

A Kubernetes pod is a set of containers sharing a subset of this state. Containers in one pod share the network namespace — hence localhost between them, and hence they cannot both bind port 3000 — and optionally the PID namespace, but they do not share a filesystem unless you mount a volume into both. Once you know exactly which parts of a task_struct are shared and which are not, pod semantics stop needing to be memorised.

Everything ps and top print comes from this structure. They read /proc/<pid>/, which is a view onto the task_struct rendered as text (Node 38). /proc/<pid>/status is the fields; /proc/<pid>/fd/ is the descriptor table as symbolic links; /proc/<pid>/maps is the address space; /proc/<pid>/limits is the resource limits; /proc/<pid>/cmdline is the arguments. Debugging a stuck Node process starts by reading those five files, and doing so tells you more in thirty seconds than most application-level instrumentation.

What you can do at this point: state precisely what a process is by listing what the kernel keeps for it, read process states and correctly diagnose a D-state hang and a zombie leak, explain why cluster workers share nothing and worker threads share almost everything, and explain why a container's PID 1 needs a signal handler.

What's still broken: the kernel now has a record of many processes, but the processor still executes exactly one instruction stream. There is a list of programs and one machine, and no mechanism yet for putting one program down mid-execution, in a way that lets it be picked back up later without it ever noticing.

Node 6 — the context switch, and what it costs

The limitation: the kernel has a list of processes and a processor that can only be executing one of them.

The mechanism is fully determined by Node 0. If a process's entire execution state is its registers — and it is, because everything else lives in memory that stays where it is — then swapping which process runs means nothing more than: write this process's registers into its task_struct, and load the other one's out of its own. When you later put the registers back, execution resumes at the exact instruction it was about to run, with every value exactly as it was. The process cannot detect that it was ever stopped. [EXPLAIN] Not "does not usually notice" — has no mechanism by which it could notice, because its entire observable state was restored. The only way to tell is by looking at a clock and seeing that time has passed.

That is a context switch, and it is the trick that makes one processor look like many.

The steps, precisely

  1. Enter the kernel. Always. A switch can only be initiated from kernel mode, so it is always triggered by one of Node 2's three entries: a system call that must wait (the process blocks on a read), a device interrupt (a higher-priority process just became runnable), or the timer interrupt (this process's slice is up). There is no fourth way in.
  2. Save the user registers. Mostly already done by the syscall or interrupt entry path from Node 4, which pushed them onto the kernel stack.
  3. Save the remaining kernel-side state — the callee-saved registers and the kernel stack pointer — into the outgoing task_struct.
  4. Pick the next process. That is the scheduler, Node 7.
  5. Switch the address space. Load the incoming process's page table root into cr3 — a privileged instruction from Node 3. From this instruction on, the same numeric addresses refer to entirely different physical memory. This is the expensive step and the next section explains why.
  6. Switch the kernel stack and restore the incoming process's saved registers.
  7. Return to user mode with sysret or iret. The incoming process resumes.

The cost, in two parts

This is where the numbers matter, because they are the quantitative argument behind most of Part IV.

The direct cost — the instructions above — is roughly one to three microseconds on current hardware. Not free, but small.

The indirect cost is much larger and is invisible in any profile that only counts instructions. The processor's caches and prediction structures are full of the outgoing process's data, and they are now all wrong.

  • The caches. Between the registers and main memory sit small, fast copies of recently used memory: L1 (roughly 32–64 KB per core, about 4 cycles away), L2 (a few hundred KB to a couple of MB, about 12–20 cycles), and L3 (tens of megabytes, shared, around 40 cycles). Main memory is around 80 nanoseconds — some 200 to 300 cycles. The incoming process finds none of its data in L1 or L2, so its first thousands of memory accesses go to a slower level. It runs at a fraction of full speed until the caches refill.
  • The TLB. The hardware that translates virtual addresses to physical ones (Node 10) caches its recent translations in a small table. Changing cr3 historically invalidated all of it, meaning every subsequent memory access needed a full table walk until it refilled. Modern processors tag entries with an address-space identifier (Intel calls it PCID) so that the flush can be avoided — but KPTI, the Meltdown mitigation from Node 4, reintroduced much of the cost.
  • Branch prediction. The processor's record of which way each branch usually goes is now describing the wrong program, so mispredictions spike, and each one costs fifteen to twenty cycles of discarded speculative work.

Add it up and the honest figure for a full process switch, including the recovery period, is on the order of several microseconds to a few tens of microseconds depending on how much memory the incoming process touches. Hold that number. It is the number the entire event-loop architecture exists to avoid paying.

A thread switch within the same process is cheaper, and now you can say exactly why rather than repeating that it is: step 5 is skipped, because threads of one process share an address space, so cr3 does not change, the TLB is not disturbed, and the caches likely still hold shared data. That is the whole of the difference. [EXPLAIN]

Voluntary and involuntary, and how to tell them apart

A switch happens for one of two reasons and Linux counts them separately for every process. Reading those two counters is one of the highest-yield diagnostic moves available.

$ grep ctxt /proc/<pid>/status
voluntary_ctxt_switches:        184203
nonvoluntary_ctxt_switches:     46

Voluntary means the process gave up the processor because it had nothing to do — it called something that blocks, so the kernel put it to sleep. A healthy I/O-bound service, including any normal Node server, shows a large voluntary count. Each one corresponds to a request being waited on.

Nonvoluntary means the kernel took the processor away because the slice expired or something more urgent appeared. A large and growing nonvoluntary count means the process wants more processor time than it is getting: it is competing, either with other work on the machine or against a cgroup quota. On a container that is being CPU-throttled, this is the number that moves.

Machine-wide, vmstat 1 gives the same thing in its cs column — total switches per second. A few thousand is unremarkable. Hundreds of thousands, on a machine that is not obviously busy, means something is thrashing: too many threads, a lock being contended (Node 17), or a poll loop with a tiny timeout.

Where this is in your stack

This node is the actual, quantitative argument for asynchronous I/O, and it is worth being able to state as arithmetic rather than as a preference.

Consider a server handling ten thousand concurrent connections that are mostly idle — a chat backend, a dashboard with live updates, an API where clients hold connections open. Two designs:

One thread per connection. Ten thousand threads. Each has a kernel stack, a task_struct, and — the killer — a user stack, which on Linux defaults to 8 MB of reserved address space each (though only the touched pages are backed by real memory). Every time data arrives on any connection, a thread must be woken and switched to. At even a modest rate of events, you are paying microseconds of switch cost per event, plus a scheduler that now has ten thousand entries to reason about, plus caches that are useless because the working set rotates constantly.

One thread, one event loop. One process, one thread, one context. Data arrives on any of the ten thousand connections; the single thread is woken once, learns about all ready connections in one call, and handles each one by calling a function. A function call is a handful of instructions with warm caches — on the order of nanoseconds. Switching from handling connection 4,000 to connection 7,000 costs nothing at all, because there is no switch: it is the same thread, the same stack, the same caches, the same page table.

The event loop's advantage is three orders of magnitude, and its source is precisely that it replaces a context switch with a function call. [EXPLAIN] That is the whole thesis of Node.js as a design, and it is the correct answer when an interviewer asks why Node handles many connections well. Note carefully what it does not claim: it says nothing about being faster at computation, and Node 7 explains the price paid.

Postgres pays this cost by design, and that is why you need a pool. Postgres uses one operating system process per connection — a decision from the 1980s that gives real robustness, since a backend crashing cannot corrupt others. But it means each connection costs a task_struct, several megabytes of private memory, and a scheduler entry, and that a few hundred connections is a genuinely heavy load on the machine. That is why max_connections is typically 100–200 rather than 10,000, why a connection pool in your application is not optional, and why pgbouncer exists to multiplex thousands of client connections onto a few dozen real ones. When your serverless functions each open their own connection and the database falls over, the resource being exhausted is the one described in this node.

Threadpool sizing is this node in one variable. libuv's threadpool defaults to four threads, and people commonly raise UV_THREADPOOL_SIZE when file or crypto work is queueing. Raising it beyond the number of cores does not add capacity — it adds context switching, because more runnable threads than cores means the kernel starts rotating them, paying the full cost above each time while getting no extra work done. The correct value is bounded by cores for CPU-bound work (crypto, zlib) and can exceed cores for genuinely blocking work (file I/O that waits on a disk), and the way to tell which you have is whether the threads are in R or in D.

What you can do at this point: explain what a context switch is mechanically, why a thread switch is cheaper than a process switch and by exactly which step, read voluntary versus nonvoluntary switch counts to distinguish an I/O-bound process from a starved one, and give the numeric argument for the event loop rather than the slogan.

What's still broken: the kernel can now swap processes, but nothing decides which process and for how long. Worse, a switch can currently only happen when a process voluntarily enters the kernel. A program with an infinite loop that makes no system calls never enters the kernel, so the kernel never gets a chance to take the processor back — exactly the failure from Node 1, still unfixed.

Node 7 — the scheduler: deciding who runs, and taking the processor back

The limitation: switching is possible but only when a process cooperates by entering the kernel, and nothing chooses who runs next.

Preemption needs one piece of hardware

Fix the fatal half first. A program that loops forever without making a system call never enters the kernel voluntarily, so the kernel needs an entry that does not depend on the program at all. Node 2 already supplies the mechanism: an interrupt. So the machine contains a device whose only job is to raise an interrupt at a fixed rate — a programmable interval timer.

Now the loop is closed. The timer fires. Control enters the kernel regardless of what the process was doing, because interrupts are checked between instructions and the process cannot disable them (cli is privileged — Node 3). The kernel checks whether this process has had enough time; if so, it context-switches to another. The process, when it eventually resumes, cannot tell.

Being able to take the processor away without the running program's consent is preemption, and it is the difference between a system where one bad program hangs the machine and one where it does not. [EXPLAIN] The historical division is exactly here: classic Mac OS through version 9 and Windows 3.x used cooperative multitasking, in which a program kept the processor until it called a system function that yielded. One badly written application froze the entire machine, and everyone who used those systems remembers it. Windows 95 brought preemption for 32-bit applications, Windows NT had it from the start (1993), and Mac OS X had it in 2001 by way of a Unix kernel. Every mainstream system has been preemptive for twenty-five years — except, notably, the JavaScript event loop, which is cooperative, and that is why a single slow function freezes a page or stalls a server. The failure you experience in JavaScript is the failure operating systems solved in 1962, reintroduced one layer up.

The problem is that the goals conflict

Given a set of runnable processes, which one? There is no neutral answer, because the objectives genuinely oppose each other:

  • Throughput — total work done. Favours long slices, since switching is pure overhead.
  • Latency — how fast something that becomes ready starts running. Favours short slices and aggressive preemption.
  • Fairness — every process gets a reasonable share. Opposed by priority.
  • Priority — some work matters more. Opposed by fairness, and risks starving the low-priority work entirely.
  • Interactivity — a process that just received a keystroke should run now, even though it has been asleep and has no claim under any fairness rule.

Every scheduler ever written is a particular position on those trade-offs, which is why there have been so many and why the argument continues.

The lineage, and what each one fixed

Round robin is the first idea: a circular queue, everyone gets an equal slice, next. Perfectly fair and completely wrong for interactivity — an interactive process that sleeps waiting for a keystroke goes to the back of the queue on waking, so typing lags behind a batch job that never sleeps.

Multi-level feedback queues, introduced in CTSS at MIT around 1961 by Fernando Corbató (the same lineage that produced Multics), fixed that with a genuinely clever inference. Several queues at different priorities. New processes start high. A process that uses its entire slice is assumed to be compute-bound and is moved down a level, getting a longer slice but running less often. A process that blocks before using its slice is assumed to be interactive and stays high. The scheduler does not need to be told which processes are interactive; it deduces it from behaviour. That inference is still the core idea in most schedulers, and it is what makes your editor responsive while a build runs.

Traditional Unix used a priority value that decayed with accumulated processor time, which achieves something similar, and gave the world the nice command — a program can voluntarily lower its own priority, hence "being nice to other users". Linux's early schedulers scanned every runnable task on every decision, which is O(n) and fell over on large machines. The O(1) scheduler (Ingo Molnár, Linux 2.6, 2003) used per-priority queues and a bitmap so the decision took constant time — but the heuristics it used to detect interactivity were a pile of special cases that misbehaved in ways nobody could fully predict.

CFS, the Completely Fair Scheduler, replaced it in Linux 2.6.23 (October 2007) and is the design worth actually knowing, because it ran the world for sixteen years and its concepts survive into its successor. Its idea is to model an ideal machine that runs all N runnable processes simultaneously at 1/N speed each, and then approximate it. Every task carries a vruntime — virtual runtime — which advances as it runs, scaled by its weight. The rule is: always run the task with the smallest vruntime. Tasks are kept in a red-black tree ordered by vruntime, so the choice is the leftmost node, and insertion is logarithmic. There is no explicit time slice; a task runs until someone else's vruntime is smaller, bounded below by sched_min_granularity_ns (typically 1–3 ms) so that switching does not dominate. A task that wakes from sleep is given a vruntime just below the minimum in the tree, so it runs almost immediately — interactivity falls out of the model rather than being a special case, which is exactly what the O(1) scheduler could not do.

nice maps onto weights, and the mapping is specified: each step of nice changes the weight by a factor of about 1.25, arranged so that one nice level is roughly a ten percent change in processor share. The range is −20 (most favoured) to +19. nice -n 19 npm run build is a real and underused way to run a build on a machine that is also serving traffic. [USE]

EEVDF — Earliest Eligible Virtual Deadline First — replaced CFS in Linux 6.6 (October 2023). It keeps the virtual-time accounting but adds an explicit notion of a deadline, so that latency-sensitive tasks can request short slices and be scheduled against a stated requirement rather than being inferred at. If you read a benchmark comparing kernel versions on latency, this is usually the change involved. [AWARE]

Classes: not everything is fair-share

Linux runs several scheduling classes in strict order of precedence, and a task in a higher class always preempts anything below it:

  • SCHED_DEADLINE — you state a runtime, a period and a deadline, and the kernel admits the task only if it can guarantee them.
  • SCHED_FIFO and SCHED_RR — real-time priorities 1–99. A SCHED_FIFO task runs until it blocks or yields; nothing below it runs at all. Used for audio, industrial control, and anything with a hard timing requirement. Also an excellent way to hang a machine, which is why sched_rt_runtime_us reserves five percent of each period for everything else.
  • SCHED_OTHER — the fair-share class. Everything you run is here.
  • SCHED_BATCH and SCHED_IDLE — below normal; SCHED_IDLE runs only when the machine would otherwise be idle.

Many cores changes the problem

With multiple cores there is not one queue but one per core, because a single global queue would need a lock that every core contends for on every scheduling decision. Per-core queues mean cores can go idle while another is backed up, so a periodic load balancer migrates tasks between them — and migration is expensive for the reason in Node 6: the task's cache lines are on the old core. So the balancer is deliberately reluctant, and it is aware of the machine's topology: two hyperthreads on one physical core share execution units, cores in one socket share L3, and on a NUMA machine each socket has memory that is fast for it and slower for the other, so moving a task across sockets can silently halve its memory performance. taskset and sched_setaffinity pin a task to specific cores, and numactl controls memory placement. [AWARE] On a large cloud instance this is not academic: a database or a Node process pinned badly can lose a third of its throughput to remote memory access.

Priority inversion is the classic scheduler failure. A low-priority task holds a lock; a high-priority task needs it and blocks; a medium-priority task, which needs no lock, preempts the low-priority one and now runs indefinitely — so the high-priority task is blocked by a medium-priority task it outranks. This happened on the surface of Mars: the Mars Pathfinder lander in July 1997 repeatedly reset itself in flight, and the cause was exactly this, in VxWorks, on a shared information bus. The fix, uploaded to the spacecraft, was priority inheritance — a task holding a lock temporarily inherits the priority of the highest-priority task waiting for it. Linux's PTHREAD_PRIO_INHERIT mutexes implement it.

Where this is in your stack

"Node is single-threaded so it only uses one core" is half right and the wrong half is the important one. Node's JavaScript runs on one thread, so one Node process executes at most one JavaScript instruction at a time. But the process has other threads — four libuv threadpool threads by default, plus V8's background compiler and garbage-collection helpers — and the kernel scheduler in this node will happily run those on other cores simultaneously. So a single Node process can and does exceed 100% CPU in top. What it cannot do is run two of your functions at once.

There are two schedulers stacked on top of each other, and every Node performance problem is about which one is failing. [EXPLAIN] This is the single most valuable framing in this part of the document.

  • The kernel scheduler — this node — is preemptive. It arbitrates between processes and threads and it can always take control back, because it has the timer interrupt.
  • The event loop — Node 20 — is a scheduler too: it decides which callback runs next. But it is cooperative. It has no timer interrupt, no privileged mode, no way to stop a running callback. Its only mechanism for regaining control is the callback returning.

So when a request handler runs a 400-millisecond synchronous loop, the kernel scheduler behaves perfectly — it preempts the thread whenever it likes and other processes on the machine run fine. It is the userspace scheduler that has failed, because it cannot preempt, and every other request in that process waits the full 400 milliseconds regardless of urgency. The event loop is a 1970s cooperative scheduler running inside a preemptive one. Understanding that tells you the whole class of fixes: yield voluntarily (await, setImmediate, chunking a loop), or move the work to something the kernel scheduler can arbitrate — a worker thread, a threadpool task, a separate process, a queue.

React's scheduler is a third one, and it is this node reimplemented in JavaScript because the browser will not preempt either. React 18's concurrent renderer breaks rendering into units and checks shouldYield() between them, returning to the browser roughly every 5 milliseconds so that input and painting can happen. It assigns work to lanes with different priorities — discrete input highest, transitions lower — which is priority scheduling; startTransition is you marking work as low-priority, exactly like nice; and interrupting a low-priority render when a keystroke arrives is preemption implemented by cooperative yielding. The platform is catching up to this with scheduler.postTask() (priorities), scheduler.yield(), navigator.scheduling.isInputPending(), and the older requestIdleCallback, which is SCHED_IDLE for the main thread. Every concept in React's scheduler has a direct ancestor in this node, and knowing that makes concurrent React considerably easier to reason about.

Kubernetes CPU requests and limits are two different scheduler features and confusing them is a common and expensive mistake. A requests.cpu of 500m becomes a cgroup weight — a relative share, which only matters when the machine is contended, and which is CFS's task weight from earlier in this node. A limits.cpu of 500m becomes a cgroup quota: at most 50 milliseconds of processor time per 100-millisecond period, enforced by hard throttling. When the quota is exhausted, every thread of the container is stopped until the next period begins, even if the machine is completely idle. For a Node service this shows up as latency spikes with no corresponding CPU graph — average utilisation of 40% while p99 doubles, because the container burned its quota in the first 30 milliseconds of each period and slept for 70. nonvoluntary_ctxt_switches from Node 6 rises, and /sys/fs/cgroup/cpu.stat shows nr_throttled and throttled_usec climbing. Node 27 covers the cgroup mechanics; the point here is that a CPU limit is not a safety measure, it is a latency cost you are choosing to pay, and for latency-sensitive services setting requests without limits is a defensible and common position.

Container CPU detection is a related trap. os.cpus().length reports the host's cores, not your quota, because the kernel has no per-container view of that (Node 26 explains why namespaces do not cover this). So a library sizing a pool as cpus().length inside a container limited to one core creates 64 threads that will fight over 100 milliseconds of quota. Node added os.availableParallelism() in v18.14 for this reason, and libraries that read cgroup files directly exist because of it.

What you can do at this point: explain preemption and why it requires a timer interrupt, describe CFS's virtual-runtime model well enough to predict its behaviour, use nice, explain the two-stacked-schedulers framing for Node and React, and diagnose CPU throttling in a container from the specific symptom of high latency at low utilisation.

What's still broken: the timer interrupt was introduced as a bare mechanism — something fires periodically. But "periodically" hides a great deal. How often, and what does the rate cost? What does the machine do when nothing is running at all? And a scheduler needs to answer questions like "has this task run for 3 milliseconds", which requires a notion of time that is accurate, cheap to read, and — critically — never goes backwards. The clock deserves its own node, because almost everything you believe about time in a computer is wrong in a way that has cost people money.

Node 8 — time: the clock, and every lie you were told about it

The limitation: the scheduler needs a periodic interrupt and an accurate, cheap, monotonic measure of elapsed time, and neither has been built.

Where a computer gets time at all

There are several sources and they are not interchangeable.

A crystal oscillator — a piece of quartz that vibrates at a fixed frequency when voltage is applied — is the physical basis. Divide its frequency down and you have a pulse at a known rate. Every clock in the machine descends from one of these, and each one is slightly wrong: a typical crystal is accurate to perhaps 20 parts per million, which is about 1.7 seconds of drift per day, and its rate changes measurably with temperature. Two computers left alone will disagree, and the disagreement grows. That is the root fact behind everything in the distributed-systems part of this node.

On top of that, several devices expose time in different ways:

  • The RTC (real-time clock) is a small battery-backed chip that keeps date and time while the machine is off. It is read exactly once, at boot, to initialise the system clock. It is coarse — one-second resolution — and it is the reason a machine with a dead motherboard battery boots believing it is 2010.
  • The PIT (8253/8254, 1981) and later HPET are programmable timers that raise an interrupt at a chosen rate. This is the hardware Node 7 needed.
  • The TSC (Time Stamp Counter) is a register inside the processor that counts cycles, readable with the rdtsc instruction in a couple of nanoseconds without entering the kernel. It is the fastest source by a wide margin and is what all high-resolution timing uses — but it was historically treacherous, because it counted actual cycles and processors change frequency, and each core had its own counter that could disagree with its neighbours. Modern processors provide an invariant TSC that ticks at a constant rate regardless of frequency scaling and is synchronised across cores, which is what made cheap high-resolution timing possible. /sys/devices/system/clocksource/clocksource0/current_clocksource tells you which source your kernel picked; on a virtual machine it may be kvm-clock or xen rather than tsc, and the difference is roughly twenty nanoseconds versus several hundred per reading.

The tick, and why it went away

Classically the kernel programmed a timer to interrupt at a fixed rate called HZ — 100 on early Linux, later configurable at 100, 250, 300 or 1000. Each interrupt is a tick, and the count of ticks since boot is jiffies. On every tick the kernel updated time, charged the running process, and checked whether its slice had expired.

A fixed tick has a real cost that only became obvious when the context changed. At HZ=1000 the machine takes a thousand interrupts per second even when completely idle, which prevents the processor from entering deep low-power states — bad for battery life, and, on a virtualisation host running two hundred idle guest machines, two hundred thousand pointless interrupts a second, all of which the host must handle. So Linux moved to a tickless design (NO_HZ_IDLE, and later NO_HZ_FULL for cores running a single task): rather than a fixed drumbeat, the kernel programs the timer for whenever the next thing is actually due. An idle machine takes essentially no timer interrupts. [AWARE] This is why "the kernel wakes up every 4 ms" is no longer true and why power-management advice from 2008 does not apply.

The clocks a program can read, and choosing wrongly

Linux exposes several clocks through one call, clock_gettime(clockid, &ts). The distinction between the first two is the single most practically important thing in this node.

  • CLOCK_REALTIME — wall-clock time: seconds since 00:00:00 UTC on 1 January 1970, the Unix epoch. It is what you want when you need to know what time it is in the world. It can jump. Forwards or backwards, at any moment, because an administrator set it or because NTP corrected it. Subtracting two readings of it can yield a negative number.
  • CLOCK_MONOTONIC — nanoseconds since some unspecified point (in practice, boot). It only ever increases. It is meaningless as a date and it is the only correct thing to use for measuring a duration. It does not advance while the machine is suspended.
  • CLOCK_BOOTTIME — like monotonic, but does include suspended time. The right one for a laptop-facing timeout.
  • CLOCK_PROCESS_CPUTIME_ID — processor time consumed by this process, not elapsed time. This is what process.cpuUsage() reads.

The rule that follows: never measure an interval with a wall clock. [EXPLAIN] A rate limiter, a timeout, a cache expiry, a retry backoff, or a benchmark that subtracts two wall-clock readings is a bug waiting for an NTP correction. It has happened at scale repeatedly — a clock step of a few seconds turns "has this token expired" into nonsense, and a backwards step makes durations negative, which then flows into code that assumed non-negative.

Keeping the clock right: NTP, slew, step, and leap seconds

Since the crystal drifts, machines synchronise against reference clocks over the network. NTP (Network Time Protocol, David Mills, 1985, and still in use) estimates both offset and round-trip delay by exchanging timestamps, and organises servers into strata — stratum 0 is a physical reference such as an atomic clock or GPS receiver, stratum 1 is a machine directly attached to one, and so on.

Correcting the clock is done in one of two ways, and knowing which your machine does matters. Stepping jumps the clock to the right value — fast, and it makes time discontinuous, which is exactly the hazard above. Slewing changes the clock's rate slightly, running it fast or slow until it catches up — so time stays monotonic and continuous, at the cost of taking a while. Standard practice is to slew small corrections and step large ones; chrony, now the default on most distributions, does this and converges much faster than the original ntpd, which matters on virtual machines whose clocks drift more.

Leap seconds are the ugliest case. The Earth's rotation is not exactly 86,400 SI seconds per day, so occasionally a second is inserted into UTC, and the time 23:59:60 exists. Unix time, by definition, has exactly 86,400 seconds per day, so it cannot represent it, and systems handle it by repeating a second — meaning wall-clock time genuinely goes backwards. On 30 June 2012 a leap second caused a wave of outages: a Linux kernel bug produced a livelock in hrtimer code that spiked CPU to 100% on huge numbers of machines, and Java applications using Thread.sleep hung. Reddit, Mozilla, Qantas's booking system and others went down. The industry's answer since is leap smearing — Google's approach, now widespread, spreading the extra second across a 24-hour window as a tiny rate change, so no discontinuity ever occurs. Machines using smeared NTP disagree with machines using standard NTP by up to a second during the smear, which is its own hazard.

The vDSO: reading the clock without a system call

Reading the time is one of the most frequent requests a program makes — every log line, every metric, every timeout check. At 50 to 100 nanoseconds per system call (Node 4), a program calling it a million times a second spends five to ten percent of a core purely crossing the boundary.

The fix is elegant. The kernel maps a small page of code and data into every process's address space, read-only, called the vDSO (virtual dynamic shared object). It contains a copy of the current time-keeping parameters, updated by the kernel, and a function that reads the TSC and applies them — entirely in user mode. So clock_gettime usually costs about twenty nanoseconds and makes no system call at all. [EXPLAIN] You can see it in any process: it appears as [vdso] in /proc/<pid>/maps. This is also why strace shows no syscall for Date.now() — a fact that confuses people the first time they look. Note that when the clock source is not the TSC (some virtual machines), the vDSO path is unavailable and every time reading becomes a real syscall, which is a genuine and measurable performance difference between instance types.

Where this is in your stack

The three JavaScript time functions, and which to use. Date.now() is CLOCK_REALTIME in milliseconds — correct for "what time is it", wrong for durations. performance.now() is monotonic, sub-millisecond, and measured from a page or process start — correct for durations. process.hrtime.bigint() is monotonic in nanoseconds — correct for durations where you need the resolution. Anything that computes Date.now() - start to enforce a timeout or record a latency is subtly wrong, and the bug appears only when a clock correction lands mid-measurement, which is to say rarely and at the worst time.

performance.now() is deliberately degraded, and the reason is a processor bug. After Spectre (January 2018) high-resolution timers became an attack tool, because a side-channel attack needs to distinguish a cache hit from a miss — a difference of tens of nanoseconds. Browsers responded by coarsening performance.now() to 100 microseconds and adding random jitter; the current position is around 5 microseconds in cross-origin-isolated contexts and coarser otherwise. So the resolution of a browser timer is set by a 2018 hardware vulnerability. Node, not being a hostile-code environment in the same way, keeps full resolution.

setTimeout(fn, 1000) guarantees a minimum, never a maximum, and the reasons stack up. Node's timers are held in lists sorted by expiry, and the loop's epoll_wait is given a timeout equal to the time until the nearest one. So a timer fires only when the loop reaches its timers phase, which means: if a callback is running when the timer expires, the timer waits (the cooperative scheduler from Node 7); if the machine is loaded, the kernel scheduler adds its own delay; and the kernel's own timer granularity adds a little more. A 1000 ms timer under load can fire at 1400 ms and nothing is broken. setTimeout(fn, 0) is not "run immediately" — it is clamped to 1 ms in Node, and in browsers the HTML specification clamps to 4 ms once five nested timeouts have accumulated, a rule that dates from 2010 and exists because sites used setTimeout(f, 0) as a busy loop. If you want "after this callback finishes, before any I/O", the correct tool is setImmediate in Node or a microtask (queueMicrotask, or an already-resolved promise) anywhere — and Node 20 explains exactly where each of those lands.

Background tabs are throttled aggressively, and this breaks polling code. A hidden tab's timers are limited to roughly once per second; Chrome added "intensive throttling" in version 88 (2021) reducing that to once per minute after five minutes hidden. So a dashboard that polls with setInterval stops polling when you switch tabs and produces a burst on return. The correct designs are visibilitychange plus an explicit refetch, a Server-Sent Events or WebSocket push, or a Service Worker — and libraries like TanStack Query have refetchOnWindowFocus precisely because of this platform behaviour.

setInterval drifts and setTimeout chains do not overlap. setInterval(f, 1000) schedules from a fixed base, so if f takes 300 ms the executions land at 1000, 2000, 3000 — but if f is async and takes 1200 ms you get overlapping executions, which for a polling job means two requests in flight and, for a cron-like job, double processing. A self-rescheduling setTimeout at the end of the work cannot overlap, at the cost of drifting by the work's duration each round. Neither is right in general; choose knowing which failure you prefer.

Clock skew breaks authentication, and the errors are unhelpful. A JWT carries iat, nbf and exp as wall-clock seconds. If the issuing server's clock is 30 seconds ahead of the verifying server's, a freshly issued token is not yet valid and verification fails with an error about the token not being active, which reads like a bug in your code. Every JWT library therefore has a clockTolerance option, typically set to 30 or 60 seconds, and this is what it is for. TOTP two-factor codes have the same problem, which is why they accept the adjacent time window, and TLS certificate validation has it too — a machine with a badly wrong clock cannot establish HTTPS connections at all, which is a genuinely confusing failure to debug on an embedded device or a fresh virtual machine.

Postgres distinguishes the clocks explicitly and most people use the wrong one by accident. now() and CURRENT_TIMESTAMP return the time the transaction started and do not change within it — so a thousand rows inserted in one transaction all share a timestamp, which is usually what you want for consistency. clock_timestamp() reads the actual clock each call. statement_timestamp() is per-statement. Similarly timestamptz stores an absolute instant (in UTC) while timestamp stores a wall-clock reading with no zone at all, and storing local times in a timestamp column is one of the most durable sources of data corruption in application development — the ambiguity becomes unrecoverable at a daylight-saving transition, where one local hour occurs twice.

Across machines, timestamps cannot order events, and this is a hard limit rather than an engineering shortfall. Two servers' clocks differ by milliseconds at best. So if server A writes at its 10:00:00.100 and server B writes at its 10:00:00.050, you cannot conclude B happened first. Systems that need ordering therefore do not use wall clocks: they use logical clocks (Lamport timestamps, vector clocks), hybrid logical clocks (CockroachDB), or, in Google Spanner's case, an explicitly bounded uncertainty interval maintained by GPS and atomic clocks in every datacentre — TrueTime returns a range rather than an instant, and the database waits out the uncertainty before committing. That design exists because the alternative is incorrect. For your own systems the practical version is: use database-generated sequences or monotonic IDs (ULID, Snowflake) for ordering, not client timestamps, and never resolve a conflict with "last write wins by wall clock" unless you have accepted that it will sometimes discard the newer write.

Node 9 — physical memory, and the three ways sharing it naively fails

The limitation: processes exist and are scheduled, but they all live in one flat array of numbered bytes with nothing between them.

The naive scheme is: keep the memory in use by the kernel at the bottom, and give each process a contiguous region above it. This fails in three separate ways, and each failure names a requirement that Node 10's design has to satisfy. Understanding the failures is what makes the solution feel inevitable rather than arbitrary.

Failure one: relocation

A compiler turns your source into machine code containing absolute addresses — "jump to 0x4012A0", "load from 0x601040". Those numbers are baked into the bytes. But the loader has no idea where in physical memory the process will be placed; that depends on what else is running. So the addresses in the file are wrong the moment the program is loaded anywhere other than where the compiler assumed.

Two historical fixes. Static relocation: the loader walks the program and rewrites every address as it loads it, using a table of locations the compiler left behind. It works, it makes loading slow, and it makes the loaded copy unique to its location — so the program cannot be moved afterwards and cannot be shared between processes. Dynamic relocation: a hardware base register holds the process's start address, and the processor adds it to every address the program produces. The program is compiled as though it starts at zero, and translation happens at run time. Cheap, and it makes moving a process a matter of changing one register. This is the beginning of the crucial idea: the addresses a program uses are not the addresses the memory hardware uses. [EXPLAIN]

Failure two: protection

Nothing stops process A from reading or writing an address inside process B. Node 3 introduced a limit register alongside the base to check the upper bound, and that closes the hole for this crude layout. Keep the shape of the answer — a hardware check on every access, using values only the kernel can set — because it survives; only the mechanism gets replaced.

Failure three: fragmentation, which is the one that kills the design

Processes come and go with different sizes, so the free memory becomes scattered. Suppose memory is 1 GB, and processes of 100, 300, 200 and 400 MB are loaded in order. The second and fourth exit. There is now 700 MB free, in two pieces of 300 and 400 MB. A new process needing 500 MB cannot start, despite 700 MB being free.

That is external fragmentation: free memory exists but not in a usable shape, because the design demands one contiguous run. Allocation policies help a little and none of them solve it — first-fit is fast, best-fit leaves slivers of useless space, worst-fit destroys the large blocks. Compaction — sliding every process down to squeeze out the gaps — solves it and costs an enormous amount, because it means copying gigabytes while every affected process is stopped.

And two related consequences follow from the same contiguity requirement:

  • A process cannot be larger than physical memory. Programmers dealt with this by hand, using overlays: splitting the program into pieces and writing explicit code to load one piece over another when needed, making sure that no two pieces that call each other were ever swapped out at once. This was a genuine and hated part of the job into the 1970s, and its existence is the reason virtual memory was pursued so hard.
  • Processes cannot share anything. Twenty copies of the same program each need their own full copy of its code, because there is no way to say "these two regions are the same physical memory".

What this establishes

The requirements are now fully specified by the failures. A memory design must: translate program addresses into physical addresses in hardware, check permissions on every access, place a process's memory in non-contiguous physical pieces so fragmentation cannot block it, let a process be larger than physical memory without the programmer doing anything, and let two processes share the same physical memory when they want to.

One mechanism satisfies all five.

What's still broken: everything above. Contiguity is the root of it, so the fix is to abandon contiguity.

Node 10 — virtual memory: the page table, the MMU, and the page fault

The limitation: requiring a process's memory to be one contiguous physical run causes fragmentation, caps process size at physical memory, and makes sharing impossible.

The idea

Cut both sides into fixed-size blocks of the same size, and allow any block on one side to map to any block on the other.

The blocks of a process's address space are pages. The blocks of physical memory are frames. Both are 4096 bytes on essentially every current system. A per-process table — the page table — records, for each page, which frame it lives in. Hardware consults that table on every single memory access and substitutes the physical address. [EXPLAIN]

Every one of Node 9's failures dies at once. Fragmentation is gone, because a process's pages can be scattered anywhere and any free frame is as good as any other — the only waste left is internal fragmentation, the unused remainder of the last page, averaging 2 KB per region, which is nothing. Protection is per-page and enforced by hardware. Sharing is trivial: two processes' page tables point at the same frame. And a process can be larger than physical memory, because a page can be marked "not here right now" and fetched on demand.

Why 4096? It is a balance. Smaller pages waste less on the final partial page but need more table entries — at 4 KB, a 64 GB address space needs sixteen million entries, and at 512 bytes it would need eight times that. Larger pages need fewer entries but waste more and make disk transfers coarser. 4 KB was settled on by the VAX in 1977 and has stuck through a factor of a million in memory sizes, mostly because changing it would break too much. Modern processors also support huge pages — 2 MB and 1 GB — for exactly the reason the next section explains.

The address, split

The page table is not consulted by a search. The address is simply cut in two. On a 32-bit machine with 4 KB pages, the low 12 bits of an address (since 212 = 4096) are the offset within the page and are passed through untouched; the upper 20 bits are the page number and are looked up. Translation is an array index and a concatenation — a handful of gate delays, not a search. [EXPLAIN]

A flat table does not scale, though. Twenty bits of page number means a million entries per process, at 4 bytes each, which is 4 MB of table for every process even if it uses almost no memory. On 64-bit it is absurd: a full table would be larger than the universe's supply of matter. So the table is made a tree, and only the branches that are actually used exist.

x86-64 uses 48 bits of address (recent processors optionally 57), split into four levels of nine bits each plus the 12-bit offset:

  47..39      38..30      29..21      20..12      11..0
 ┌────────┬────────────┬───────────┬───────────┬─────────┐
 │  PML4  │    PDPT    │    PD     │    PT     │ offset  │
 │ 9 bits │   9 bits   │  9 bits   │  9 bits   │ 12 bits │
 └────────┴────────────┴───────────┴───────────┴─────────┘

Nine bits indexes 512 entries; 512 entries of 8 bytes each is exactly 4096 bytes — one page. Every level of the tree is itself one page. That is why nine, and it is a satisfying piece of design. The root of the tree is held in the cr3 register, which Node 6's context switch reloads and which Node 3 made privileged, and those two facts together are the whole of memory isolation: changing cr3 changes the meaning of every address in the machine, and only the kernel can do it.

Each entry holds a frame number plus flag bits, and the flags are where the interesting behaviour lives:

  • Present — is this page currently in physical memory? If not, everything else in the entry is free for the kernel to use for its own bookkeeping, such as where on disk the page lives.
  • Writable — clearing this on a present page is the mechanism behind copy-on-write (Node 14).
  • User/supervisor — may user-mode code touch this? This is how the kernel's own memory is mapped into every process yet unreachable from it, and undoing that mapping is what KPTI does.
  • Accessed and Dirty — set by hardware on read and on write. The kernel reads and clears them to decide which pages to evict (Node 13) and which need writing back to disk.
  • NX / execute-disable — added by AMD in 2003, this marks a page as non-executable. It is why a buffer overflow can no longer simply place instructions on the stack and jump to them, and it is why JIT engines like V8 need explicitly executable pages.

The TLB, and why the tree does not cost four memory accesses

Walking a four-level tree means four memory reads before the real access — a fivefold slowdown on every load and store, which would be catastrophic. So the processor caches recent translations in the Translation Lookaside Buffer, a small fully-associative cache of perhaps 64 to 1536 entries. A hit costs essentially nothing. Hit rates on ordinary code are well above 99%, because programs touch the same pages repeatedly.

Three consequences that matter in practice:

A process with a large, randomly accessed working set — a database index, a big hash map, a graph — misses the TLB constantly and pays the walk. Huge pages exist for this: one 2 MB page covers 512 times as much memory with one TLB entry, so a Postgres instance with 32 GB of shared buffers can drop from eight million entries' worth of coverage to sixteen thousand. That is why huge_pages = try is standard advice for large Postgres deployments, and why Linux's transparent huge pages exist — and also why THP is often disabled for databases, because its background defragmentation causes latency spikes. MongoDB and Redis both tell you to turn it off.

Changing cr3 historically invalidated the TLB, which is the expensive part of Node 6's context switch. Address-space identifiers (PCID) let entries survive.

And cache and TLB behaviour is why data layout affects speed by large factors. An array of numbers walked in order touches each cache line once and each page 512 times consecutively; a linked list of the same values scattered across the heap misses cache on nearly every step. This is the real reason typed arrays outperform arrays of objects in JavaScript, and why V8 works so hard to keep arrays of small integers in a packed representation.

The page fault: the most important exception in the machine

When the processor translates an address and the page table says the page is not present, or that the access is not permitted, it raises a page fault — an exception, Node 2's second entry type — with the offending address in register cr2. The kernel handler then works out which of several very different situations this is:

  • The page is valid but not in memory. Read it in from disk, fix the entry, return, and the faulting instruction is re-executed and now succeeds. The process never knows. This is a major fault and it costs a disk access.
  • The page is valid and in memory but not mapped into this process yet — for instance it is already in the page cache from another process. Just point at it. A minor fault, costing microseconds.
  • This is the first touch of freshly allocated memory. Allocation only reserved address space; now a physical frame is found, zeroed, and mapped. This is why allocating a gigabyte is instant and using it is not.
  • It is a write to a page marked read-only that is shared copy-on-write. Copy it, mark the copy writable, return. Node 14.
  • It is just below the stack. The stack grows automatically by mapping another page.
  • None of the above — the address is genuinely not part of this process. Deliver SIGSEGV. The process dies.

Every one of those is the same hardware event, distinguished only by kernel bookkeeping. [EXPLAIN] Lazy allocation, demand loading, copy-on-write, growable stacks, memory-mapped files, and segmentation faults are one mechanism wearing six hats, and that is the most elegant thing in the operating system.

Distinguishing major from minor faults is directly operational: ps -o min_flt,maj_flt -p <pid>, or the majflt/s column in pidstat -r. Minor faults in the millions are normal and cheap. Major faults climbing during steady-state operation mean the machine is fetching pages from disk to run, which is Node 13's thrashing and which will show up as latency that no application-level profiler can explain.

Where this is in your stack

The two numbers in every memory graph, defined exactly. VSZ (virtual size) is the total address space the process has mapped — how much it has asked for, including regions never touched. RSS (resident set size) is how many of those pages are actually in physical memory right now — what it is using. VSZ can be wildly larger than RSS and it does not matter: a Node process routinely shows several gigabytes of VSZ because V8 reserves large regions of address space it may never populate, and address space on 64 bits is free. RSS is the number that consumes a resource, and RSS is what a container limit and the OOM killer count. [EXPLAIN] Anyone alarmed by a Node process's VSZ is reading the wrong column. RSS has its own subtlety, though: it includes shared pages, counted in full against every process sharing them, so summing RSS across a process tree overcounts badly. PSS (proportional set size, in /proc/<pid>/smaps_rollup) divides shared pages among sharers and is the honest number.

ASLR is a page-table feature and it shapes your crash reports. Address Space Layout Randomisation places the stack, heap, libraries and (for position-independent executables) the program itself at different addresses on every run, so that an attacker who can corrupt memory cannot predict where to jump. That is why a native crash address differs every time, why reproducing a memory bug is hard, and why symbolising a core dump requires knowing the load addresses. It is also why /proc/sys/kernel/randomize_va_space gets turned off during debugging.

V8's pointer compression is a direct consequence of page tables and cache lines. Since V8 8.0, on 64-bit builds, object references in the heap are stored as 32-bit offsets from a base rather than full 64-bit pointers. Two reasons, both from this node: half the memory for pointers, and — more importantly — twice as many pointers per cache line, so pointer-chasing through the heap misses cache half as often. The price is that a single V8 heap is capped at 4 GB of compressed address space, which is the real reason --max-old-space-size above about 4096 does nothing useful on a standard build. If you have ever wondered why the answer to "how do I give Node 16 GB of heap" is "you don't, you run four processes", that is why.

A memory-mapped file is this node used deliberately. mmap maps a file's contents into the address space, so reading the file is reading memory: pages fault in on first touch, the kernel loads them from disk, and the page cache holds them so a second process mapping the same file shares the same physical frames with no extra memory at all. SQLite and LMDB use it as their primary access method; V8 uses it to map its code cache and snapshots (which is why Node starts in tens of milliseconds despite V8 needing to build its entire built-in object graph — it is mapped from a pre-built snapshot, not constructed). It is also why a container running twenty copies of the same image's binaries costs far less than twenty times the memory: the executable's text pages are one set of frames, mapped everywhere.

Cache-line and page thinking explains real JavaScript performance. A Float64Array of a million numbers is eight megabytes of contiguous, sequentially-prefetchable memory. An array of a million {x, y} objects is a million pointers to a million separately allocated objects scattered over the heap — each access a potential cache miss, each miss around eighty nanoseconds. The factor between them on a numeric loop is routinely five to twenty times, and it is not V8 being clever or stupid; it is the memory hierarchy from this node. It is the same reason columnar databases exist.

What you can do at this point: explain paging from the address split upward, state exactly what the page table entry flags do, explain the page fault as one mechanism serving six purposes, read RSS versus VSZ versus PSS correctly, distinguish major from minor faults when diagnosing, and explain why huge pages matter for a database and why V8 compresses pointers.

What's still broken: a process now has an address space, but nothing has said what is in it — where the code goes, where the stack goes, why the heap grows upward, what happens when the stack grows into something, or how a program asks for more memory in the first place.

Node 11 — the address space: what is actually in a process's memory

The limitation: a process has a private, translated address space and nothing has said what lives where in it, or how a program obtains more.

The layout is not arbitrary; every region is where it is for a reason, and the reasons explain several errors you have seen.

  high addresses
  ┌──────────────────────────┐  0xFFFFFFFFFFFFFFFF
  │  kernel space            │  mapped in every process, unreachable
  │                          │  from user mode (the U/S flag)
  ├──────────────────────────┤  0x00007FFFFFFFFFFF  (128 TB on x86-64)
  │  [stack]        ↓ grows  │  locals, return addresses, saved registers
  ├──────────────────────────┤
  │        (unmapped gap)    │
  ├──────────────────────────┤
  │  mmap region             │  shared libraries, large mallocs,
  │                          │  memory-mapped files, thread stacks
  ├──────────────────────────┤
  │        (unmapped gap)    │
  ├──────────────────────────┤
  │  [heap]         ↑ grows  │  small mallocs, via brk
  ├──────────────────────────┤
  │  .bss                    │  zero-initialised globals (occupies no
  │                          │  space in the file, only in memory)
  ├──────────────────────────┤
  │  .data                   │  initialised globals — writable
  ├──────────────────────────┤
  │  .rodata                 │  constants, string literals — read-only
  ├──────────────────────────┤
  │  .text                   │  the machine code — read+execute, no write
  └──────────────────────────┘  0x400000 (or randomised, with PIE)
  low addresses — page 0 deliberately unmapped

Several details there are load-bearing.

Page zero is deliberately left unmapped. That is why dereferencing a null pointer produces a segmentation fault rather than silently reading whatever happens to be at address 0. The safety of null is a page-table decision.

.text is read-only and executable; the stack and heap are writable and non-executable. No region is both writable and executable, a policy called W^X, enforced by the NX bit from Node 10. This is what stops classical shellcode injection, and it is exactly the rule a JIT compiler must break — V8 has to write machine code and then run it, so it allocates pages, writes, and flips them to executable, keeping the window as narrow as possible. On systems that forbid this entirely (iOS outside Safari, some hardened kernels, OpenBSD by default) JIT is impossible, which is why JavaScript engines on locked-down platforms fall back to an interpreter and run several times slower.

The stack grows downward and the heap upward — a convention from when a process had one contiguous region and putting them at opposite ends let either grow into the shared middle. The gaps between regions are unmapped on purpose, so that growth past the intended limit hits nothing and faults rather than silently overwriting the neighbour.

Kernel space is mapped into every process, marked supervisor-only, so that a system call does not need to change the page table. Meltdown made that mapping readable through a speculative side channel, and KPTI's response — unmapping it and paying a page-table switch per syscall — is the cost described in Node 4.

The stack, and the error you have definitely seen

The stack holds one frame per active function call: its local variables, its arguments beyond the register-passed ones, and the return address. Calling pushes a frame; returning pops it. That is all "the call stack" is — a region of memory and a pointer (rsp) to the current top. A stack trace is that chain walked.

Its size is bounded: 8 MB by default on Linux for the main thread (ulimit -s), and typically much less for additional threads — libuv uses far smaller stacks for threadpool threads. Below the stack sits a guard page, permanently unmapped, so that runaway growth faults immediately instead of quietly corrupting the mmap region below. Infinite recursion therefore ends as a page fault on the guard page, delivered as SIGSEGV.

But in JavaScript you do not see SIGSEGV; you see RangeError: Maximum call stack size exceeded. That is because V8 imposes its own, smaller limit and checks it on entry to each function, so that it can throw a catchable JavaScript error before the real hardware limit is reached. The V8 limit is around 1 MB by default, which is why the recursion depth is typically ten to twelve thousand frames rather than a hundred thousand, and why it varies with how many locals each frame holds. node --stack-size=4000 raises V8's check — and raising it past the real OS stack turns a catchable RangeError into a hard segmentation fault, which is a genuinely bad trade. [USE] Deep recursion in JavaScript is a design problem, not a flag problem: JavaScript engines still do not implement proper tail calls (only Safari does, despite it being in ES2015), so the fix is an explicit stack, a queue, or iteration.

How a program gets more memory: two calls

There are only two mechanisms, and everything above them is library code.

brk / sbrk moves a single pointer marking the top of the heap. Simple, ancient, and limited: memory can only be returned by moving the pointer back down, so a single live allocation at the top pins everything below it.

mmap is the general one and is what everything modern uses. It asks for a region of address space with stated properties, and it is worth knowing its four combinations because each is a different familiar thing:

  • Anonymous, private — plain memory, not backed by any file, visible only to this process. This is what a large malloc becomes and what a JavaScript heap is made of.
  • File-backed, private — a file mapped in, with writes kept private via copy-on-write. This is how an executable's .data section is loaded.
  • File-backed, shared — a file mapped in, with writes going to the file and visible to every other process mapping it. This is mmap-based I/O and shared memory between unrelated processes.
  • Anonymous, shared — memory with no file, shared between a process and its children. This is how fork-based servers share state, and what /dev/shm provides.

MAP_ANONYMOUS memory is guaranteed zero-filled, and this is a security requirement rather than a convenience: without it, a fresh allocation could contain another process's freed data. The kernel keeps a supply of pre-zeroed pages for this.

Reading a real address space

cat /proc/<pid>/maps prints every region: address range, permissions, and what it is. [USE] Doing this once on a running Node process is worth more than any diagram. You will see the node binary's r-xp text region, its data, an anonymous [heap], dozens of large anonymous regions that are V8's heap spaces and the allocator's arenas, mapped shared libraries (libc, libstdc++, any .node addons), one stack per thread, [vdso] from Node 8, and [vvar]. /proc/<pid>/smaps_rollup summarises the same thing with RSS and PSS totals.

Where this is in your stack

V8's heap is a set of these regions, and its structure explains its performance. Inside the process's address space, V8 maintains several spaces, and knowing them makes a heap snapshot legible:

  • New space (the young generation) — small, typically 1–8 MB per semi-space, split in two halves. All new objects are allocated here by simply incrementing a pointer, which is why allocation in JavaScript costs a handful of instructions. Collection is a scavenge: live objects are copied to the other half and the whole half is then free. Because the overwhelming majority of objects die young, a scavenge touches very little and takes under a millisecond. --max-semi-space-size tunes it, and raising it is one of the few Node GC flags that reliably helps a high-allocation server.
  • Old space — objects that survived two scavenges are promoted here. Collected by mark-sweep-compact, incrementally and concurrently since the "Orinoco" work in 2016–2018. --max-old-space-size is the flag people know, and Node 10 explained why values above ~4096 are ineffective under pointer compression.
  • Large object space — anything above roughly 128 KB is allocated directly here and never moved, because copying it would cost more than it saves.
  • Code space — executable pages holding JIT output. The only writable-then-executable memory in the process.

The generational hypothesis — "most objects die young" — is why this works, and it is why creating short-lived objects in JavaScript is genuinely cheap while holding onto them is expensive. The cost of garbage collection scales with surviving data, not with allocated data. A handler that allocates ten thousand short-lived objects per request costs almost nothing; one that adds ten objects per request to a module-level cache costs increasingly much, forever.

Buffers live outside the V8 heap, which is why your numbers do not add up. Buffer.allocUnsafe and ArrayBuffer data are allocated outside V8's managed heap — Buffer uses a pooled 8 KB slab allocator for small buffers and direct allocation for large ones. So process.memoryUsage() returns several distinct numbers and you must read them as such: heapTotal and heapUsed are V8's spaces only; external is memory held by C++ objects tied to JavaScript ones, including buffers; arrayBuffers is the subset that is ArrayBuffer; and rss is the operating system's number from Node 10, which is all of the above plus the binary, the libraries, the thread stacks, and the allocator's overhead. A leak of buffers shows up in rss and external while heapUsed stays flat — and since most Node memory-leak tooling looks at the heap, that class of leak is often hunted for a long time in the wrong place. It is also why --max-old-space-size cannot protect you from it: the limit only governs old space.

Node's own limits are per-region, not per-process, and this is the reason for the standard sizing rule: set --max-old-space-size meaningfully below your container's memory limit, because RSS will exceed old space by hundreds of megabytes of binary, code, stacks, buffers and fragmentation. A container limited to 512 MB running Node with a default heap cap will usually be killed by the kernel before V8 ever decides to collect aggressively — which is Node 13, and one of the most common container misconfigurations in production.

What you can do at this point: read /proc/<pid>/maps, explain why null dereferences fault and why W^X exists and what it costs a JIT, explain a stack overflow at both the V8 and the hardware level, name the four kinds of mmap, describe V8's spaces and the generational hypothesis, and read all five numbers from process.memoryUsage() correctly.

What's still broken: mmap hands out whole pages. Real programs allocate sixteen bytes at a time, millions of times. Something has to sit between them, and that something has properties that will surprise you.

Node 12 — the allocator, and why freed memory does not come back

The limitation: the kernel deals in 4096-byte pages, and programs allocate sixteen bytes at a time, millions of times a second. A system call per allocation would be absurd.

So a memory allocator lives in user space, inside your process. It obtains large regions from the kernel with mmap or brk and carves them up. It is ordinary library code with no privileges — malloc and free are not system calls, a fact that surprises people and explains most of this node. [EXPLAIN]

What it has to do, and why it is hard

Given a request for N bytes it must find a free run of at least N, mark it used, and return a pointer. On free it must know how big the block was — so it stores a small header immediately before the returned pointer, which is why writing before the start of an allocated block corrupts the heap in ways that crash much later somewhere else entirely — and it must merge the block with adjacent free ones to avoid ending up with a heap of unusable slivers.

glibc's allocator, the one your Node process is using unless you changed it, works like this:

  • Free blocks are kept in bins by size — fast bins for small blocks, sorted bins for large ones — so finding a fit is not a linear scan.
  • Requests above MMAP_THRESHOLD (128 KB by default, and dynamically adjusted) bypass the heap entirely and get their own mmap, which is returned to the kernel exactly when freed.
  • Every thread gets its own arena, so that threads do not contend on a single lock for every allocation. The number is capped at eight times the core count by default — which on a 64-core machine is 512 arenas, each of which can grow to 64 MB of address space.

The property that catches everyone

free() usually does not return memory to the operating system. [EXPLAIN] It returns it to the allocator's own free lists, inside your process, so the next malloc can reuse it without a system call. RSS stays where it was.

This is correct behaviour and it is the right default — releasing pages and re-faulting them costs far more than keeping them. But it means a process's memory use is a high-water mark, not a current measurement. A Node service that handles one enormous request and then goes idle keeps the elevated RSS. That is not a leak. It is not a bug. It is the allocator holding memory it will happily reuse.

Worse, memory cannot always be returned even when the allocator wants to. The heap shrinks only from the top (that is brk's nature), so one small live allocation near the top pins everything below it. And a page can only be returned if every object on it is free — a page holding one live 32-byte object and 4064 bytes of free space is fully resident. That is internal fragmentation at the allocator level, and for a long-running server with variable object sizes it can account for a large and permanent gap between "bytes my program considers live" and "bytes the machine has committed to me".

Which is the answer to the question that brings people to this material: why does my Node container use 800 MB when heapUsed says 200 MB? The full accounting, in order of typical size:

  1. V8 old space and new space — heapTotal, which is always larger than heapUsed because V8 keeps headroom.
  2. External memory — buffers, ArrayBuffers, and native addon allocations. Node 11.
  3. The node binary itself and its shared libraries — roughly 50–100 MB resident.
  4. V8's code space, compiled from your JavaScript and every module you required.
  5. Thread stacks — the main thread, four libuv threadpool threads, V8's helper threads.
  6. glibc arena fragmentation — often the largest surprise, especially on many-core machines where dozens of arenas each hold unreturned memory.

Setting MALLOC_ARENA_MAX=2 is a real and frequently effective fix for the last one, and it is one of the few genuinely useful environment variables for containerised Node and Java services alike. [USE] It trades a little allocation contention for a substantial reduction in resident memory.

Other allocators exist for exactly these reasons

jemalloc (Jason Evans, originally for FreeBSD in 2005, then Facebook) is designed around fragmentation avoidance and scalability, with size-class-based allocation and aggressive page reclamation. tcmalloc (Google) uses per-thread caches for the same goal. Swapping glibc's allocator for jemalloc via LD_PRELOAD — no recompilation, just an environment variable, which Node 34 will explain — is a standard move for Ruby, Python and Postgres deployments and routinely reduces RSS by twenty to forty percent on allocation-heavy workloads. It is worth knowing this exists, because "our service uses too much memory" sometimes has a one-line answer that involves no code.

Garbage collection is a third layer on top

Everything so far is manual: the program says when a block is free. Managed languages remove that obligation by tracking reachability. It is worth stating the layering precisely, because the three layers are routinely conflated:

  1. The kernel hands out pages via mmap.
  2. The allocator (or, in V8's case, V8's own page allocator) carves those into objects.
  3. The garbage collector decides which objects are still reachable and reclaims the rest, returning them to layer 2 — which usually does not return them to layer 1.

The reachability question is answered by tracing: start from the roots — the global object, the current call stack, and handles held by native code — and mark everything reachable. Anything unmarked is garbage. This is why "unreferenced" is the wrong mental model and "unreachable from a root" is the right one, and it is why reference counting alone (which Python uses, with a cycle collector bolted on) cannot collect a cycle while tracing can.

Two consequences you will meet:

A memory leak in JavaScript is always a reference you forgot. The classic sources: a module-level Map or array that grows per request; an event listener added per connection and never removed, keeping the whole handler closure and everything it captured alive; a setInterval whose callback closes over a large object; a promise that never settles, keeping its continuation and captured scope alive forever; and — specific to closures — the fact that in V8 all closures created in the same function share one context object, so an unrelated small closure can keep a large captured variable alive. WeakMap, WeakRef and FinalizationRegistry exist for the cases where you genuinely need a reference that does not prevent collection.

Collection pauses are real and they land in your latency percentiles. A scavenge is sub-millisecond. A full mark-compact of a 2 GB old space can be tens to low hundreds of milliseconds, and although V8 does most of the marking concurrently and incrementally, the compaction pause is a genuine stop. If your p99 latency has spikes that do not correlate with request complexity, capture GC events (--trace-gc, or perf_hooks's PerformanceObserver on the gc entry type) and check. The mitigations are architectural — allocate less per request, keep the live set small, and split large heaps across processes — rather than flags.

Where this is in your stack

The container sizing rule, derived rather than memorised. Given everything above: RSS is heap plus external plus binary plus code plus stacks plus fragmentation, and the kernel kills on RSS. So the heap cap must leave room for the rest. A workable starting point is --max-old-space-size at roughly 60–75% of the container limit — for a 1 GB container, around 640–768 MB — and then measuring. Setting no cap at all in a container is the common error: V8's default heap size is derived from the host's physical memory, not the cgroup limit, so on a 64 GB node a container limited to 512 MB gets a V8 that believes it may grow to gigabytes and will not collect urgently until far past the point where the kernel kills it. Node has improved its cgroup awareness over time, but setting the flag explicitly remains the reliable answer. [USE]

Postgres has the same three-layer structure and the same trap. shared_buffers is memory the server maps once at startup; work_mem is per sort or hash operation, per node of the plan, per concurrent query — so a value that looks modest can multiply by a hundred under load and exhaust the machine; maintenance_work_mem is for index builds and vacuum. Setting work_mem without thinking about concurrency is the Postgres version of setting no heap cap, with the same ending.

Native addons allocate outside everything V8 knows about. sharp, canvas, better-sqlite3 and their kind call malloc directly. V8 has no idea that memory exists, so it does not count towards the heap limit and does not create GC pressure — meaning a leak in native code produces a steadily climbing RSS with a perfectly flat heap graph and no GC activity at all. ExternalMemoryAccounting (napi_adjust_external_memory) exists so well-behaved addons can tell V8 about it; many do not. When RSS climbs and the heap does not, look at the addons before you look at your JavaScript.

What you can do at this point: explain why malloc is not a system call, why freed memory does not reduce RSS, and what fragmentation costs; account fully for the gap between heapUsed and container memory; state the three layers of allocation and where a garbage collector sits; derive a heap cap from a container limit rather than guessing; and recognise the signature of a native leak.

What's still broken: the allocator can hand out memory only if the kernel has frames to give. Nothing has said what happens when it does not — when every frame is spoken for and another allocation arrives. That question has three answers, and one of them is the reason for exit code 137.

Node 13 — demand paging, the page cache, swap, and the OOM killer

The limitation: physical frames are finite, and nothing has said what happens when they run out.

Nothing is loaded until it is touched

Start with what the page fault made possible. When a program is executed, the kernel does not read it into memory. It sets up page table entries marked not-present, recording where on disk each page lives, and jumps to the entry point. The first instruction immediately faults; the kernel reads that one page; execution proceeds. Pages arrive as they are needed, and pages of a hundred-megabyte binary that are never executed are never read.

That is demand paging, and its consequences are worth stating: a program starts in milliseconds regardless of size, memory holds only what is actually used, and a process can have far more mapped than the machine has. It is also why the very first request to a freshly started server is slower than the ones after it — the code paths it exercises are being faulted in — which is a real and measurable effect in serverless cold starts, in JVM and .NET warm-up, and in the first request to a newly rolled-out Kubernetes pod.

The page cache: free memory is wasted memory

Once pages of a file are in memory, throwing them away when the process closes the file would be foolish. So the kernel keeps them, in the page cache, and uses all otherwise-unused memory for it.

This is the single most misread thing on a Linux dashboard. Every ordinary file read and write goes through the page cache. [EXPLAIN] A read checks the cache first and only touches the disk on a miss. A write copies your bytes into a cache page, marks it dirty, and returns immediately — no disk has moved. Kernel threads write dirty pages back later, governed by vm.dirty_ratio, vm.dirty_background_ratio and vm.dirty_expire_centisecs. Node 23 covers what that means for durability, which is a great deal.

So on a healthy server, free -m shows very little "free" memory and a large "buff/cache" figure, and that is correct and desirable. Free memory is doing nothing; cached memory is saving disk reads and is instantly reclaimable. The column to read is available, which is free plus reclaimable cache — the honest answer to "how much could a new process get". Anyone reporting a memory problem because free is small is reading the wrong column, and it is worth being able to say so precisely.

Choosing what to evict

When frames are needed and none are free, something must go. The theoretically optimal policy is to evict the page that will be used furthest in the future, which requires knowing the future, so it exists only as a benchmark. The practical approximation is least recently used, and true LRU is also too expensive — it would mean updating a timestamp on every single memory access.

So hardware and kernel cooperate cheaply. The processor sets the accessed bit in a page table entry on any access (Node 10). The kernel periodically clears those bits and, on the next pass, sees which were set again. That is the clock or second-chance algorithm. Linux refines it into two lists, active and inactive: a page must be referenced while on the inactive list to be promoted to active, which stops a single large sequential file read from evicting the entire useful working set — a failure mode with the excellent name cache pollution, and the reason a nightly backup used to make a database slow for an hour afterwards.

The concept underneath is Peter Denning's working set (1968): the set of pages a process has touched in the recent past, which is a good predictor of what it will touch next. If the sum of all processes' working sets exceeds physical memory, the machine enters thrashing — every process constantly faults in a page by evicting a page another process is about to need, and the machine spends all its time moving pages and none doing work. Thrashing does not degrade gracefully; it collapses. A thrashing machine shows near-zero user CPU, huge major faults, and enormous disk activity, and it is often easier to reboot than to log into.

Swap: extending memory onto disk

File-backed pages can always be evicted, because the file is their home. Anonymous pages — heap, stack, anonymous mmap — have nowhere to go unless a dedicated area exists. That is swap. With it, total memory is RAM plus swap; without it, anonymous memory can never be evicted at all.

vm.swappiness (0–200, default 60) biases the kernel between reclaiming file pages and swapping anonymous ones. Low values favour keeping anonymous memory resident. Note that swappiness=0 does not disable swap; it makes the kernel avoid it until it is nearly desperate.

The reason swap has a bad reputation is latency. A page from RAM is 80 nanoseconds; from an SSD, around 100 microseconds — a thousand times slower; from a spinning disk, ten thousand times. A process whose active data is swapped out is not slow, it is unusable. Hence Kubernetes historically refused to run at all with swap enabled: swap makes memory limits unenforceable and makes latency unpredictable, and the scheduler's model assumes memory is memory. Support for swap on nodes has been reintroduced gradually (beta from 1.28, with further work through 1.30+), but the default position for a latency-sensitive service remains: no swap, and size the memory correctly.

Overcommit, and the killer

Linux, by default, grants more address space than it has memory to back. It has to, in practice: fork plus copy-on-write (Node 14) means a doubling of address space that will almost never be realised, programs routinely reserve large sparse regions they never touch, and V8 is one of them. vm.overcommit_memory controls the policy — 0 is a heuristic (the default), 1 always says yes, 2 refuses beyond a computed limit.

The consequence is that the machine can promise more than it can deliver, and the debt comes due at a page fault: a process touches a page it was legitimately given, and there is no frame. There is nothing sensible to return — the faulting instruction cannot be failed, because mov has no error path.

So the kernel picks a process and kills it. The OOM killer scores every process, roughly by memory footprint, adjusted by oom_score_adj (−1000 to +1000, where −1000 makes a process exempt), and sends the highest scorer SIGKILL. Not SIGTERM. SIGKILL cannot be caught, blocked, or handled (Node 30), so the process gets no chance to flush anything, close anything, finish an in-flight request, or log a word about it. It simply ceases.

The evidence is in the kernel log — dmesg -T | grep -i "killed process", or journalctl -k — and it is the first place to look when a process vanishes with no application log entry explaining why. [USE]

Where this is in your stack

Exit code 137, decoded. A process killed by a signal reports, by shell convention, 128 + signal number. SIGKILL is 9. So 137 means killed by SIGKILL, and in a container that almost always means the cgroup's memory limit was hit and the cgroup OOM killer fired. (143 is 128 + 15, SIGTERM — a normal shutdown. 139 is 128 + 11, SIGSEGV — Node 3.) Kubernetes reports it as OOMKilled in the container's lastState.terminated.reason. [EXPLAIN] You can derive all of these rather than memorising them, which is exactly the point of this document.

The cgroup memory limit is a separate, per-container OOM domain, which is why a container is killed on a machine with plenty of free memory: it exhausted its budget, not the machine's. Node 27 covers the mechanism; the operational points are that memory.max is a hard wall enforced by killing, while memory.high is a soft limit that throttles reclaim instead — meaning a container over memory.high gets slow rather than dead, which is often the behaviour you actually want, and which Kubernetes does not expose directly.

A container's page cache counts against its memory limit, and this kills containers that have no memory leak at all. [EXPLAIN] This one is genuinely non-obvious and causes real incidents. If your containerised service writes heavily to a file — logs, a temp file, an upload buffer, a SQLite database — those dirty and clean page-cache pages are charged to the container's cgroup. The kernel will reclaim cache before killing, so it usually works out, but under memory pressure combined with heavy write throughput a container can be OOM-killed while its actual anonymous usage is far below the limit. Symptoms: OOMKilled with a flat heap graph and a healthy process.memoryUsage(). Remedies: log to stdout and let the runtime handle it rather than writing files, put genuinely large scratch data on a volume mounted with different semantics, and read memory.stat in the container to see the split between anon and file.

Why a Node process gets no graceful shutdown on OOM. Because it is SIGKILL. Your process.on('SIGTERM') handler, your connection draining, your "finish in-flight requests" logic — none of it runs. This is the strongest argument for sizing memory generously and for setting a heap cap (Node 12) so that V8 hits its limit first: a V8 heap-limit failure throws a JavaScript FATAL ERROR: Reached heap limit with a stack trace and can trigger a heap snapshot via --heapsnapshot-near-heap-limit, which is diagnosable. A kernel OOM kill produces one line in the host's kernel log and nothing else. Choosing which limit you hit first is a real design decision.

Postgres is built on the page cache and its configuration only makes sense in that light. Postgres deliberately keeps shared_buffers modest — the conventional 25% of RAM — rather than claiming everything, because it expects the operating system's page cache to hold the rest. A page can therefore exist twice, once in shared buffers and once in the page cache: double buffering, wasteful in principle and accepted in practice because the kernel's cache is good and its readahead is good. effective_cache_size is not an allocation at all; it is a hint to the query planner about how much total caching it can assume, and setting it too low makes the planner avoid index scans it should be choosing. And this is why running Postgres in a container with a tight memory limit performs badly in a way that adding shared_buffers does not fix: you have taken away the page cache it was designed to rely on.

Cold starts are demand paging. A serverless function's first invocation faults in the runtime, the dependency tree, and the JIT-compiled code, page by page from storage. That is a large part of why a cold start is hundreds of milliseconds while a warm one is single digits, why bundle size affects cold start more than it affects steady-state performance, and why techniques that pre-warm — snapshots, AWS Lambda SnapStart, V8 startup snapshots, Node's --snapshot-blob — attack it by having the pages already laid out rather than by making the code faster.

What's still broken: overcommit was justified above by "fork plus copy-on-write", which has been referenced four times now and never explained. It is also the mechanism behind the strangest system call in Unix, the one that returns twice.

Node 14 — fork, copy-on-write, and the pattern that is everywhere

The limitation: processes must be created, and copying an entire address space to do it would make process creation cost as much as the process's whole memory.

The call that returns twice

Unix's process creation call is fork(). It takes no arguments. It creates a new process that is a duplicate of the caller — same program, same memory contents, same open file descriptors, same current directory, same credentials, same instruction pointer.

Which raises the obvious question: if the child is identical and resumes at the same instruction, how does either one know which it is? The answer is the one piece of asymmetry in the whole call. fork() returns twice. In the parent it returns the child's PID, a positive number. In the child it returns 0. (And −1 in the parent on failure, with no child.)

pid_t pid = fork();
if (pid == 0) {
    /* child: this is a completely separate process */
    execve("/usr/bin/node", argv, envp);   /* becomes a different program */
} else if (pid > 0) {
    /* parent: pid is the child's process ID */
    waitpid(pid, &status, 0);              /* collect the exit status */
} else {
    /* failed */
}

That is every process on your machine except PID 1. It is also, at bottom, what child_process.spawn does, what a shell does for every command you type, what a shell pipeline does twice, and what Postgres does per connection.

The design is genuinely unusual — most systems have a single "create a process running this program" call, as Windows does with CreateProcess and its ten arguments. The Unix split into fork then execve exists because it makes the interval between them a place where the child can configure itself using perfectly ordinary calls: close a descriptor, redirect one onto another, change directory, drop privileges, set a resource limit, join a namespace. Shell redirection, pipes, and every container runtime's setup step live in that interval, and none of them needed a special API. Node 22 and Node 26 both depend on it.

Copy-on-write

Duplicating an address space by copying it would mean a process using 2 GB takes 2 GB and a substantial amount of time to fork — and then, in the overwhelmingly common case, immediately calls execve and throws all of it away.

So no copy is made. Instead:

  1. The child gets its own page table, whose entries point at the same physical frames as the parent's.
  2. Every writable page is marked read-only in both page tables, and flagged internally as copy-on-write.
  3. Both run. Reads are free and fully shared.
  4. When either writes to such a page, the hardware raises a protection fault — Node 10's page fault, again.
  5. The kernel sees the copy-on-write flag, allocates a fresh frame, copies the 4 KB, points the writer's entry at the copy, and marks both writable again. The instruction is re-executed and succeeds.

Only pages actually written are ever copied, one page at a time, at the moment of writing. [EXPLAIN] A fork of a 2 GB process costs the page tables and nothing else — a millisecond or two — and if the child immediately execs, essentially zero pages are ever copied. This is why overcommit (Node 13) is not merely a permissive default but a practical necessity: the kernel promised 2 GB twice and expects to deliver it once.

Two refinements exist for the fork-then-exec case: vfork, which shares the address space and suspends the parent until the child execs (fast, dangerous, largely historical), and posix_spawn, which packages the whole sequence into one call so the library can pick the best mechanism. Linux implements all of them, plus fork itself, on top of one general call, clone(), whose flags say exactly what is shared and what is copied — address space, descriptor table, signal handlers, namespaces. Node 15 will show that a thread is the same clone() with more flags set to "share", and Node 26 that a container is the same call with namespace flags set. Threads, processes and containers are one system call with different arguments. That is the single most clarifying fact in Part VI.

Where this is in your stack

Redis BGSAVE is the textbook case, and it bites people in production. To write a point-in-time snapshot without blocking, Redis calls fork(); the child has a frozen, consistent view of the dataset and writes it out at leisure while the parent keeps serving. Copy-on-write makes this nearly free — if the parent is not writing. Under a heavy write load, the parent dirties pages, each of which is copied, and memory usage can approach double the dataset size during the save. Redis's documentation warns about exactly this, and it is why vm.overcommit_memory=1 is Redis's explicit recommendation: with the default heuristic, the fork itself can fail on a machine with slightly more than half its memory in use. A Redis instance that dies during background saves is usually this.

Postgres forks per connection, which is where Node 6's connection-pool argument comes from. The postmaster process accepts a connection and forks a backend; copy-on-write makes the fork cheap, but each backend then accumulates its own private memory for sorts, caches, and query state, so the cost is real and grows with activity. That is the mechanical reason max_connections is small and pooling is mandatory.

You cannot safely fork() a Node process, and it is important to know why. fork duplicates only the calling thread. Every other thread in the process ceases to exist in the child — but every lock they were holding remains held, forever, by a thread that is not there. If a libuv threadpool thread or a V8 background compiler thread held the allocator's lock at the instant of the fork, the child deadlocks the first time it allocates. POSIX's rule for this is that between fork and exec in a multithreaded program you may only call async-signal-safe functions, a very short list that excludes malloc. Node is thoroughly multithreaded, so it does not expose fork(). Note the naming trap: cluster.fork() and child_process.fork() are not this system call — they spawn a brand-new node process (posix_spawn, then execve) with an IPC channel attached. The name is inherited vocabulary, and confusing the two is a common interview stumble.

Copy-on-write is a pattern, not a kernel detail, and naming it pays off repeatedly. [EXPLAIN] The same idea — share until someone writes, then diverge only the part that changed — appears at every level of your stack:

  • Docker images. An image is a stack of read-only layers; a running container adds one thin writable layer on top. Reading a file finds it in a lower layer. Writing it triggers a copy-up: the whole file is copied into the writable layer first, then modified. That is copy-on-write at file granularity (Node 24), and it is why writing to a large file inside a container is slow the first time, why a container that rewrites a 2 GB file needs 2 GB of writable-layer space, and why databases in containers must use volumes rather than the layered filesystem.
  • Filesystem snapshots. btrfs, ZFS, LVM and every cloud provider's disk snapshot are copy-on-write at block granularity — the snapshot costs nothing until the original changes.
  • Postgres MVCC. An UPDATE does not overwrite a row; it writes a new version and leaves the old one visible to transactions that started earlier. That is copy-on-write for durability and isolation, and the reason VACUUM must exist is that the old versions accumulate.
  • Git. Objects are immutable and content-addressed; a commit that changes one file shares every unchanged blob and tree with its parent. Branching is free for exactly the reason forking is.
  • React and Immutable.js. Updating a nested state object creates new objects only along the path from the root to the change, sharing every untouched subtree. That is structural sharing, which is copy-on-write in a heap, and it is why an identity comparison at the top is a valid change check — the same reasoning as the copy-on-write page fault.

When you meet a new system that claims cheap snapshots, cheap branching, or cheap forking, this is almost always the mechanism, and knowing the pattern lets you immediately ask the right question: what does it cost when things do get written?

And a process still runs one instruction stream, so a machine with sixteen cores runs one program on one of them. Something is needed that shares an address space by design.

Node 15 — threads: sharing an address space on purpose

The limitation: processes are isolated by design, so cooperating work must copy data through the kernel, and one process cannot use more than one core for its own computation.

The answer follows directly from Node 5's list of what a process owns. Take that list and split it in two: the things that are properties of the program as a whole, and the things that are properties of one path of execution through it.

Shared by every thread of a process: the address space and all its contents — code, globals, heap, and therefore every object; the file descriptor table; the credentials; the current directory; the signal dispositions; the resource limits; the cgroup and namespaces.

Private to each thread: the registers, including the instruction pointer; the stack; the thread ID; the signal mask; errno; scheduling priority; and thread-local storage.

A thread is that private set. [EXPLAIN] Everything else is common ground. It follows immediately that threads can pass data by writing to a shared variable — no copying, no system call, nanoseconds — and that a thread can corrupt every other thread's data by writing to the wrong place, because there is no boundary between them. Both properties come from the same fact and you cannot take one without the other.

On Linux, a thread is a process with more sharing

Linux does not implement threads as a separate concept. It has one creation call, clone(), taking flags for what the new task shares with its creator. fork() is clone() with almost nothing shared. Creating a thread is clone() with CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD — share the address space, the filesystem context, the descriptors, the signal handlers, and the thread group.

So the kernel's schedulable unit is a task, and both processes and threads are tasks. This is why threads appear in ps -eLf and in /proc/<pid>/task/, each with its own ID; why top -H shows per-thread CPU; and why the scheduler in Node 7 needs no special knowledge of threads at all. The name for a thread's own ID is the TID, and for the main thread it equals the PID.

The history is worth one paragraph because it explains an old debate you will meet in interviews. Threads can be implemented entirely in user space — a library that swaps stacks and registers without the kernel knowing — which is fast to switch and needs no privilege, but has a fatal flaw: if one such thread makes a blocking system call, the kernel blocks the whole process, and every other thread stops. The kernel cannot know they exist. That is the "N:1" or green-thread model, used by early Java and by GNU Portable Threads. The alternative, "1:1", gives every user thread a real kernel task, so blocking affects only that thread and multiple threads genuinely run on multiple cores. Linux settled 1:1 with NPTL (Native POSIX Thread Library, Ulrich Drepper and Ingo Molnár, 2003), which was a large enough improvement that it became one of the reasons Java became viable on Linux servers.

Modern language runtimes have reintroduced user-space scheduling on top of 1:1 rather than instead of it — Go's goroutines are M:N, with a runtime scheduler multiplexing many goroutines onto a pool of kernel threads and, crucially, intercepting blocking operations so that a goroutine blocking on I/O parks rather than blocking its thread. Java's virtual threads (Project Loom, final in Java 21, September 2023) do the same thing. Both are answers to the same problem the event loop answers, with a different ergonomic choice, and Node 18 gives the numbers that make all three make sense.

Where this is in your stack

A Node process has threads, and knowing which is which makes profiling possible. Run top -H -p $(pgrep -n node) on a busy server and you will see, at minimum:

  • The main thread, running the event loop and all your JavaScript. Only one, ever, per process.
  • Four libuv threadpool threads by default (UV_THREADPOOL_SIZE, max 1024). These execute file system operations, dns.lookup, and the CPU-heavy parts of crypto and zlib. They exist entirely because those operations cannot be done without blocking — Node 19 explains why file I/O in particular resists the event-loop treatment.
  • V8's background threads — concurrent marking and sweeping for the garbage collector, and background compilation and optimisation.
  • Any threads created by native addons, which is why a single sharp image resize can saturate several cores.

Two things follow. A Node process can exceed 100% CPU in top — the claim "Node uses one core" is false at the process level and true only of your JavaScript. And when a Node process is slow, the first diagnostic question is which thread: a busy main thread means a blocked event loop and the fix is in your code; four busy threadpool threads with an idle main thread means threadpool saturation and the fix is sizing or offloading; busy V8 background threads mean GC pressure and the fix is allocation behaviour.

worker_threads is a deliberately restricted version of this node. A worker shares the process — same PID, same descriptor table, same cgroup — but gets its own V8 isolate, which means its own heap, its own copy of every built-in, and no shared JavaScript objects. That last restriction is not a limitation Node imposed for simplicity; it is forced by V8's design, and V8's design is forced by the language. JavaScript has no memory model for concurrently mutated objects, and a garbage collector that can move objects cannot safely do so while another thread holds raw pointers to them. So the boundary is explicit:

  • postMessage copies, using the structured clone algorithm — deep, and therefore expensive for large payloads, and unable to carry functions, class instances' prototypes, or DOM nodes.
  • transferList moves an ArrayBuffer — the memory is not copied, ownership passes, and the sender's buffer becomes detached and zero-length. Constant time regardless of size.
  • SharedArrayBuffer is genuinely shared — the same physical pages mapped into both isolates, the one place where JavaScript has real shared mutable memory across threads. It is also the only place where JavaScript can have a data race, which is exactly why Atomics exists and why Node 16 is next.

The practical rule: workers are for CPU-bound work, because I/O-bound work is already handled better by the event loop, and each worker costs a full V8 isolate — on the order of several megabytes and tens of milliseconds to start. A pool created once at boot is the right shape; a worker per request is not. Roughly: workers when the work is computation and you want cores; the threadpool when the work is blocking I/O; a separate process when you want isolation or a separate heap; the event loop for everything else.

Browser Web Workers are the same design with a stricter boundary. A worker has no DOM, no window, no document. That restriction is not arbitrary either: the DOM is a large mutable object graph with no locking and no memory model, and permitting concurrent access to it would make every DOM operation require synchronisation. So the platform's position is that the DOM is single-threaded, permanently, and workers communicate by message. Every heavy client-side thing — a WebAssembly module, a large parse, a client-side search index, image processing, crypto — belongs in one, and OffscreenCanvas and SharedArrayBuffer exist to make that boundary less painful. Cross-origin isolation headers, from Node 3, are the price of the latter.

Postgres chose processes and MySQL chose threads, and the trade is exactly this node's: Postgres's per-connection process gives crash isolation and requires shared memory to be arranged explicitly (shared_buffers is a shared mapping); MySQL's per-connection thread is cheaper to create and shares the buffer pool naturally, at the cost that one backend corrupting memory takes the server down. Neither is wrong. Knowing which one a system chose predicts its connection-scaling behaviour immediately.

What's still broken: two threads can now write the same variable at the same time. That sounds like a small problem and it is the hardest one in this document — it is not solvable by being careful, because the hardware does not do what the source code says.

Node 16 — races, atomicity, and why the hardware does not do what you wrote

The limitation: two threads share memory and can write the same location at the same time.

The smallest possible example, and why it is not a coding mistake

Two threads each run counter++ a million times. The final value is not two million. It is some smaller, unpredictable number, and it changes between runs.

The reason is Node 0. counter++ is not an operation the machine has. It compiles to three:

mov  rax, [counter]     ; load
add  rax, 1             ; add
mov  [counter], rax     ; store

Two threads can interleave between any two of those. Both load 5. Both compute 6. Both store 6. Two increments, one net effect. Nothing was written incorrectly. The source-level operation simply was not atomic, and no amount of care at the source level can make it so. [EXPLAIN]

Atomic means indivisible: an operation that no other thread can observe partway through. It is the central word of this node. A race condition is when the result depends on the relative timing of operations that were not made atomic — and a data race, specifically, is two threads accessing the same location with at least one write and no synchronisation, which in C and C++ is not merely a bug but formally undefined behaviour, meaning the compiler is entitled to assume it never happens and optimise accordingly.

The property that makes this brutal is that races are timing-dependent, so they do not reproduce. A race that fires once in ten million iterations passes every test on your laptop and fails in production twice a week. It is sensitive to core count, to load, to compiler version, to whether a profiler is attached. This is why concurrency correctness must be established by reasoning and by design rather than by testing.

The hardware layer that makes it stranger

Three separate mechanisms, each of which independently breaks the assumption that memory operations happen in the order you wrote them.

Caches, and coherence. Each core has its own L1 and L2 (Node 10). If two cores both hold a copy of the same memory, one core's write would be invisible to the other. Hardware prevents this with a cache coherence protocol — MESI, in which every cache line is in one of four states: Modified, Exclusive, Shared, or Invalid. To write a line, a core must first acquire it in Modified state, which requires broadcasting an invalidation and waiting for every other core to drop its copy. Coherence is not free; it is a negotiation over the interconnect costing tens to hundreds of cycles.

That cost produces a performance failure with no correctness symptom at all: false sharing. Two threads writing to two different variables that happen to occupy the same 64-byte cache line will bounce that line between their cores on every write, because coherence works at line granularity, not variable granularity. The code is correct and the throughput collapses — order-of-magnitude slowdowns are routine. The fix is padding, and the reason high-performance libraries litter their structures with alignment attributes and 64-byte padding is entirely this.

Store buffers, and reordering. Waiting for a cache line before every write would stall the processor constantly, so writes go into a store buffer and drain later. The consequence is that another core can see this core's operations in a different order than this core issued them. On x86, which has a relatively strong model (TSO, total store order), the only reordering visible is that a store can appear after a subsequent load. On ARM and POWER, which have weak models, almost anything can be reordered. This is why identical concurrent code can be correct on x86 and broken on ARM — a fact that stopped being a niche concern when Apple Silicon and AWS Graviton became ordinary development and deployment targets.

The compiler reorders too. An optimising compiler will hoist a loop-invariant read out of a loop, keep a variable in a register instead of re-reading memory, and merge or eliminate stores. All of that is valid under the assumption that no other thread is looking. A loop polling a flag can be optimised into an infinite loop, because the compiler proved the flag never changes within the thread.

The tools that impose order are memory barriers (or fences) — instructions that forbid reordering across them — and the atomic operations that carry ordering semantics with them. The formal framework is a memory model, which specifies exactly what a program is allowed to observe. C++11 introduced one, Java has had one since 2004, and JavaScript acquired one in ES2017 alongside SharedArrayBuffer.

The primitive underneath everything

Software cannot build atomicity out of non-atomic parts, so the hardware provides it. The essential instruction is compare-and-swap: atomically, if this location holds the value I expect, replace it with this new value, and tell me whether it did. On x86 it is lock cmpxchg; the lock prefix is what makes the read-modify-write indivisible. ARM uses a load-linked/store-conditional pair instead.

Compare-and-swap is universal — every lock, every lock-free queue, every reference counter, and every atomic increment is built from it. The characteristic usage is a retry loop: read the value, compute the new one, attempt the swap, and if someone else changed it in between, start again. That shape is optimistic concurrency, and you have written it at a higher level: a Postgres UPDATE ... WHERE version = $expected that retries on zero rows affected is compare-and-swap at the row level, and an HTTP If-Match with an ETag is compare-and-swap over the network. [EXPLAIN] The pattern is the same at all three scales and the failure mode is the same: under high contention the retries dominate, and you need a lock instead.

Where this is in your stack

JavaScript is immune to data races in one specific, narrow sense, and people over-generalise it. A single JavaScript thread runs one callback to completion before the next begins — run-to-completion semantics. So while your synchronous code runs, nothing else can observe or modify your objects. counter++ in JavaScript is safe. That is a genuine and valuable guarantee and it is a large part of why Node code is easier to get right than threaded C.

It is also narrower than it looks. It protects you from data races, not from race conditions, and the distinction is the difference between a working system and a broken one:

// This has a race condition, in single-threaded JavaScript.
async function transfer(from, to, amount) {
  const balance = await db.getBalance(from);   // ← await: other code runs here
  if (balance < amount) throw new Error("insufficient");
  await db.setBalance(from, balance - amount); // ← and here
  await db.setBalance(to, amount);
}

Every await is a yield point. The function suspends, the event loop runs other callbacks — including another invocation of this same function — and resumes later against state that may have changed. Two concurrent transfers can both read balance 100, both pass the check, and both write 50. This is precisely the interleaving from the top of this node, at a different granularity, and it is why "JavaScript is single-threaded so I don't need to worry about concurrency" is one of the most expensive false beliefs in backend development. The correct fixes are the same ones a threaded program would use: make the operation atomic in the database (UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1, which is one atomic statement, and check the row count), take a lock (SELECT ... FOR UPDATE inside a transaction, or an advisory lock), or use optimistic concurrency with a version column and a retry.

The in-process version of the same bug. A cache with if (!cache.has(k)) cache.set(k, await fetch(k)) will issue N concurrent fetches for N concurrent requests, because every one of them checks before any of them sets. This is cache stampede, and the standard fix is to store the promise rather than the value, so the second caller finds an in-flight promise and awaits it. Recognising it as a check-then-act race is what tells you the fix.

Atomics is JavaScript's compare-and-swap, and it exists for exactly one reason. SharedArrayBuffer is genuinely shared memory between a main thread and workers, so it is the one place JavaScript has real concurrent mutation and therefore real data races. Atomics.add, Atomics.compareExchange, Atomics.load and Atomics.store compile to the lock-prefixed instructions above; Atomics.wait and Atomics.notify are Node 17's futex, exposed to JavaScript. And Atomics.wait is forbidden on the browser main thread, because it blocks — which would freeze the page. This is the entire concurrency toolkit of the language, it maps one-to-one onto this node's hardware, and it exists only because WebAssembly needed real threads.

Database isolation levels are this node's problem at a larger scale. Read committed, repeatable read, and serializable are exactly a memory model: a specification of which interleavings a transaction is allowed to observe. Postgres's default, read committed, permits non-repeatable reads — two reads of the same row in one transaction can differ — which is the database equivalent of a compiler not being required to re-read a variable. SERIALIZABLE in Postgres is implemented with optimistic concurrency and can abort your transaction with a serialization failure, requiring a retry loop — the same compare-and-swap retry shape from earlier in this node. The parallel is exact, not decorative: a lock, an atomic operation, and a serializable transaction are three scales of one idea.

Idempotency in distributed systems is the same problem again. A client retries a request whose response was lost; the server processes it twice. That is a race between a retry and an original, and the fix — an idempotency key, checked and inserted atomically — is a compare-and-swap over the network. Once you have seen the pattern at the instruction level, the distributed version needs no separate learning.

What you can do at this point: explain why counter++ is not atomic and why races do not reproduce, explain cache coherence and false sharing, explain compiler and processor reordering and why ARM differs from x86, explain compare-and-swap and recognise it at three scales, and — most importantly — explain precisely what JavaScript's single thread does and does not protect you from, with await as the yield point.

What's still broken: compare-and-swap makes one word atomic. Real critical sections span many operations on many variables, and something must make a whole region exclusive. Building that naively wastes the processor, and building it correctly requires the kernel — but only sometimes, and getting that "only sometimes" right is the difference between a fast program and a slow one.

Node 17 — locks, the futex, and deadlock

The limitation: compare-and-swap makes a single word atomic; a real critical section spans many operations on many variables.

Building a lock, and the first design being wrong

A mutex — mutual exclusion lock — has two operations. Acquire: if free, take it; otherwise wait. Release: mark free.

With compare-and-swap the first version writes itself. A word holds 0 for free and 1 for held; acquire loops attempting to swap 0 for 1 until it succeeds. That is a spin lock, and it is genuinely used — but only in the right place, because when it is wrong it is very wrong:

  • While waiting, the thread burns processor time at full rate doing nothing.
  • Each attempt is a write, which under Node 16's coherence protocol means acquiring the cache line exclusively — so N spinning threads saturate the interconnect and slow down the thread that actually holds the lock. The refinement is test and test-and-set: spin on a plain read, which can be satisfied from a shared cache line, and only attempt the write when the read says free.
  • On a single core it is catastrophic. The spinning thread cannot make progress until the holder runs, and the holder cannot run until the spinner is preempted. The lock is held for the duration of a full time slice, every time.

Spin locks are correct when the hold time is shorter than a context switch — a few hundred nanoseconds — and there are more cores than contenders. That is true inside a kernel and almost never true in application code.

The alternative is to sleep: put the waiting thread into the S state from Node 5, remove it from the run queue, and wake it when the lock is released. That costs nothing while waiting. But it requires the kernel, because only the kernel can deschedule a thread, so both acquire and release become system calls — 50 to 100 nanoseconds each, from Node 4, every time, including the overwhelmingly common case where the lock was free and nobody was waiting.

The futex: pay only when contended

Linux's answer, added in 2.5.7 (2002) by Hubertus Franke, Rusty Russell and Matthew Kirkwood, is one of the most satisfying designs in the kernel. Futex — Fast Userspace muTEX.

The lock is an ordinary integer in the process's own memory. Acquire is a compare-and-swap in user space, no system call. If it succeeds, that is the whole operation — a handful of nanoseconds. Only if it fails does the thread call futex(FUTEX_WAIT, addr, expected), which atomically checks the value is still what it expected and puts the thread to sleep on a kernel wait queue keyed by that address. Release is a compare-and-swap back to 0, and calls futex(FUTEX_WAKE, addr, n) only if it can see that someone is waiting.

The uncontended path never enters the kernel; the contended path does. [EXPLAIN] Since real locks are uncontended the great majority of the time, this makes locking essentially free in the common case. Every pthread_mutex, every Java synchronized block, every Go mutex, and JavaScript's Atomics.wait and Atomics.notify are built on it. It is also an excellent diagnostic: a large number of futex calls in strace -c means genuine contention, because uncontended locks make no calls at all.

The other primitives, briefly

  • Semaphore — Edsger Dijkstra, 1965. A counter with atomic decrement-and-wait-if-negative and increment-and-wake. A semaphore initialised to N permits N holders, which makes it the natural expression of a resource pool. A mutex is the special case N=1.
  • Read-write lock — many readers or one writer. Worth it only when reads are frequent and long; otherwise the extra bookkeeping loses to a plain mutex, and naive implementations starve writers.
  • Condition variable — wait until a predicate becomes true, releasing the mutex while waiting and reacquiring on wake. Always used in a while loop, never an if, because of spurious wakeups and because another thread may have consumed the condition before you were scheduled.
  • Barrier — all N threads wait until all N arrive.

Deadlock, and the four conditions

Thread A holds lock 1 and wants lock 2. Thread B holds lock 2 and wants lock 1. Neither will ever proceed. Edward Coffman's 1971 paper established that deadlock requires all four of the following simultaneously, which is useful because breaking any one prevents it:

  1. Mutual exclusion — the resource cannot be shared.
  2. Hold and wait — a thread holds one resource while requesting another.
  3. No preemption — a resource cannot be taken away.
  4. Circular wait — a cycle exists in the waits-for graph.

In practice the fourth is the one you break, and the technique is lock ordering: define a total order over all locks and require that every thread acquires them in that order. A cycle then cannot form. [EXPLAIN] This is why database code that locks multiple rows should sort the identifiers first — SELECT ... FOR UPDATE over ORDER BY id — and it is the actual fix for the classic bank-transfer deadlock where transfer(A→B) and transfer(B→A) run concurrently.

Two related failures worth naming. Livelock: threads are running and responding to each other but no work completes — two processes each backing off and retrying in lockstep. Starvation: a thread never gets the resource because others keep taking it, which is what an unfair lock or a writer behind a stream of readers produces. And the thundering herd: releasing a lock wakes every waiter, all of whom race, all but one of whom immediately sleep again — which is why FUTEX_WAKE takes a count and why modern implementations wake one.

Where this is in your stack

Redis is single-threaded on purpose, and this node is the reason. Its command execution is one thread, so every command is atomic by construction — no locks, no races, no deadlock, no coherence traffic, and each operation is a simple in-memory manipulation. That is why INCR is a correct distributed counter, why SETNX is a usable lock primitive, and why a Lua script in Redis is atomic (it runs to completion on that same thread). The price is that one slow command blocks everything — KEYS * on a large database is a genuine outage, which is why SCAN exists — and that it uses one core for commands. Redis 6 added threaded I/O for reading and writing sockets, keeping execution single-threaded, which is precisely the split this part of the document has been building toward. Redis's design is Node's design, in C, for a database.

Postgres's locks are visible and diagnosable. Heavyweight locks are on tables and rows and appear in pg_locks; lightweight locks protect internal shared memory and appear as wait_event_type = 'LWLock' in pg_stat_activity. A query stuck with wait_event_type = 'Lock' is waiting on another transaction, and the query that finds the blocker via pg_blocking_pids() is one every backend engineer should have. Postgres detects deadlocks automatically after deadlock_timeout (1 second by default) and aborts one transaction with a message naming both — so a deadlock in Postgres is an error you can catch and retry, not a hang. It is worth knowing that this is unusual generosity; most systems just hang.

Advisory locks are the right tool more often than people realise. pg_advisory_lock(key) gives you a named mutex with the database as the arbiter, held for the session, and pg_try_advisory_lock returns immediately rather than waiting. That is the correct way to ensure only one instance of a cron job runs across a fleet, and it is safer than most Redis-based approaches for the reason below.

Distributed locks are not locks, and this is a genuinely contested area worth knowing both sides of. A lock in a process is backed by the kernel: the holder cannot vanish without the kernel knowing. Across a network nothing guarantees that. A process can acquire a lock, then be paused — by a GC pause (Node 12), by CPU throttling (Node 7), by a network partition — for longer than the lock's expiry, at which point another process acquires it and both believe they hold it. Martin Kleppmann's 2016 critique of Redlock made exactly this argument, and Salvatore Sanfilippo's reply is worth reading alongside it. The resolution is a fencing token: the lock service issues a monotonically increasing number with each grant, the holder passes it with every write, and the storage system rejects writes carrying a token lower than the highest it has seen. Without fencing, a distributed lock is an optimisation that reduces contention, not a correctness guarantee — and the honest engineering position is to say so out loud when you use one.

In-process JavaScript "locks" are cooperative queues, and they work for a narrow reason. Libraries like async-mutex hold a promise chain: acquiring returns a promise that resolves when the previous holder releases. No kernel involvement, no atomics needed — because JavaScript's run-to-completion property from Node 16 means the acquire check and the set cannot be interleaved. They are correct within one Node process and give you exactly nothing across cluster workers, which is the mistake people make with them.

What you can do at this point: explain why a spin lock is right in a kernel and wrong in an application, explain the futex's fast path and use futex counts as a contention signal, name the four Coffman conditions and apply lock ordering, explain why Redis being single-threaded is a design rather than a limitation, diagnose Postgres lock waits, and state honestly what a distributed lock does and does not guarantee.

What's still broken: all of this concerns threads competing for memory. The original problem was different — a program that waits for a device. Node 2 gave the hardware a way to signal readiness, and nothing has yet said what happens to the program in the meantime, or what it costs to have ten thousand of them waiting at once.

Node 18 — blocking I/O, thread-per-connection, and the C10K arithmetic

The limitation: a program that asks a device for data has to wait, and nothing has said what "wait" costs when a server is waiting on ten thousand clients at once.

What blocking is, exactly

A process calls read(fd, buf, 4096) on a socket with no data yet. Precisely what happens:

  1. The syscall enters the kernel (Node 4).
  2. The kernel checks the socket's receive buffer. Empty.
  3. It changes the task's state from R to S — interruptible sleep (Node 5).
  4. It adds the task to a wait queue attached to that socket.
  5. It calls the scheduler, which picks something else. Context switch (Node 6).
  6. Later, a packet arrives: interrupt, softirq, TCP processing, data appended to the socket buffer (Node 2).
  7. The kernel walks that socket's wait queue and marks the waiting task runnable.
  8. The scheduler eventually runs it. It copies the bytes to the user buffer and returns.

Blocking is not waste at the process level — a blocked process consumes zero processor time. That is worth stating clearly because "blocking is slow" is a slogan people repeat without knowing what it means. The cost is not spent cycles. The cost is that this thread can do nothing else until the wait ends, so serving many clients requires many threads, and threads are the expensive thing. [EXPLAIN]

The architectures, in the order they were tried

Process per connection. Accept, fork, child handles the connection and exits. This is what inetd did and what Apache's prefork module did for a decade. Robust — a crashing connection kills only its own process, which is why it survived so long in a world of buggy CGI scripts — and expensive: a full process per client, several megabytes each, a full context switch per event.

Thread per connection. Cheaper per client, since threads share an address space (Node 15), and this is Apache's worker module and classic Java servlet containers. Still a stack per client, still a scheduler entry per client, still a full context switch per event.

Bounded thread pool. N threads, a queue of connections. This bounds resource use, which is the point, and introduces head-of-line blocking: if all N threads are occupied by slow requests, fast requests queue behind them regardless of how cheap they are. This is the dominant server architecture in the Java and .NET world and it is why those systems have thread-pool sizing as a tuning discipline.

The arithmetic — this is the node's core

Dan Kegel wrote the "C10K problem" page in 1999, asking what it would take for one server to handle ten thousand simultaneous connections. The hardware of the day could clearly move the bytes; the software architecture could not. Run the numbers for thread-per-connection at ten thousand connections:

  • Memory. Default thread stack on Linux is 8 MB of reserved address space; actual resident use is more like 8–64 KB thanks to demand paging (Node 13), and a kernel stack of 16 KB is fully resident. Say 100 KB per thread all-in, being generous to the design. Ten thousand threads is 1 GB before a single byte of application data. At the naive 8 MB, it is 80 GB of address space.
  • Scheduler. Ten thousand tasks in the run queue structures. CFS is logarithmic, so the decision itself is fine — but the load balancer, the wake-ups, and the bookkeeping all scale with task count.
  • Context switches. This is the one that kills it. Suppose each connection sees ten events per second — a modest chat or dashboard workload. That is 100,000 wake-ups per second. At a few microseconds each including the cache and TLB damage from Node 6, that is a large fraction of a core spent purely switching. Push it to a hundred events per second per connection and the machine does nothing else.
  • Cache. The worst part, and invisible in any profile. Ten thousand threads rotating through the processor means the caches never hold anything useful. Every thread starts cold, every time.

Now the same workload on one thread that can wait on all ten thousand at once. One stack. One scheduler entry. One task. Data arrives on five hundred connections; the thread wakes once, learns about all five hundred, and handles each with a function call — warm caches, no page table change, no scheduler involvement. The switch cost per event drops from microseconds to nanoseconds, and the memory cost per connection drops from ~100 KB to a few hundred bytes of kernel socket state plus whatever your application keeps.

That is the entire argument, and it is arithmetic rather than taste. [EXPLAIN] Note its precise boundary: it says nothing about computation. If each event requires ten milliseconds of processing, one thread handles a hundred events per second and threads would have used all your cores. The event loop wins on concurrency of waiting, and loses on parallelism of computing — which is the exact shape of Node's strengths and weaknesses and the honest answer to "when should I not use Node".

The history this produced

nginx (Igor Sysoev, publicly released October 2004) was written specifically against the C10K problem, using an event-driven, non-blocking architecture with a small number of worker processes, one per core, each running an event loop. Apache at the time was thread- or process-per-connection. Under many idle or slow connections — which is what the real internet is, full of mobile clients on poor networks — nginx used a small fraction of the memory and stayed responsive where Apache thrashed. That difference is why nginx now fronts a large share of the web.

Node.js (Ryan Dahl, presented at JSConf EU in Berlin, November 2009) took the same architecture and made it the only option in the language. Dahl's stated motivation was that Apache's concurrency model was wrong and that existing languages made non-blocking code painful because they had a blocking standard library and no natural callback idiom. JavaScript had no I/O library at all — so nothing had to be deprecated — and it already had first-class functions and closures, so callbacks were natural. Node's central design decision is that every I/O operation is non-blocking and there is no alternative, which is what makes the guarantee hold: a library cannot accidentally block the loop with a blocking read, because the blocking read is not exposed. (Except where it is — the Sync functions — and that is why using them outside startup is the cardinal error.)

The other answer to the same problem is to keep the blocking programming model and make threads cheap enough that it does not matter. That is Go's goroutines (a few kilobytes of growable stack, multiplexed by a runtime scheduler that intercepts blocking calls) and Java's virtual threads (Project Loom, final in Java 21, September 2023). They are not a rejection of the event loop; they are an event loop hidden inside the runtime so you can write straight-line code. Knowing that lets you evaluate them properly: the concurrency mechanism is the same, the ergonomics differ, and the failure modes differ — a goroutine that runs a tight CPU loop is preemptible since Go 1.14, whereas a Node callback is not.

Where this is in your stack

Your database connection pool is a bounded thread pool, with all of its properties. A pool of 20 connections serving 200 concurrent requests means 180 requests waiting for a connection. That wait is invisible to your APM unless you instrument it, so the symptom is "the database is slow" when the database is idle and the queue is in your process. Head-of-line blocking applies exactly: one slow query holds a connection and every request behind it waits. The diagnostics are pool metrics — acquisition wait time and queue depth — and the fixes are statement timeouts so a slow query cannot hold a connection indefinitely, separate pools for fast and slow workloads (the same reasoning as separate queues), and sizing the pool against the database's capacity rather than your concurrency.

Slowloris is this node used as an attack. Open many connections and send headers one byte at a time, very slowly. Against thread-per-connection, each held connection occupies a thread, and a few hundred connections exhaust the pool with almost no bandwidth. Against an event loop, each costs a socket and a few hundred bytes, and the attack fails. This is a security property that follows from the architecture, and it is why header and body timeouts (server.headersTimeout, server.requestTimeout in Node) exist even so — the resource is small but not zero.

The Sync functions are the blocking model leaking back in. fs.readFileSync, execSync, crypto.pbkdf2Sync, and — the one that catches people — JSON.parse on a large payload, which is not named Sync but blocks just as thoroughly. In a thread-per-connection server, blocking for 200 milliseconds delays one client. In an event loop, it delays every client, because there is one thread and it is not preemptible (Node 7). This is why the rule is "sync calls at startup only", why reading a config file synchronously at boot is fine, and why the same call in a request handler is a production incident. Measuring it is perf_hooks' event-loop delay histogram (monitorEventLoopDelay), which is the single most valuable metric a Node service can export.

What you can do at this point: explain exactly what happens to a thread that blocks, give the C10K arithmetic with real numbers, state precisely what the event loop wins at and what it does not, explain why nginx beat Apache and why Node was created, place Go and Loom correctly as the same mechanism with different ergonomics, and recognise your connection pool as a bounded thread pool with head-of-line blocking.

What's still broken: the architecture is settled — one thread waiting on many connections — and the system call to do it does not exist yet. read blocks on one descriptor. There is no call that means "wait until any of these ten thousand has something for me". Building it turns out to take three attempts across twenty years.

Node 19 — readiness: select, poll, epoll, and why files are different

The limitation: the architecture requires one thread waiting on many connections, and no system call can wait on more than one descriptor.

First: non-blocking mode

Before there can be a "wait on many" call there must be a way to not wait. Setting O_NONBLOCK on a descriptor changes its semantics: read on an empty socket returns immediately with −1 and errno = EAGAIN (identically EWOULDBLOCK) instead of sleeping.

That alone is not a solution. A loop over ten thousand non-blocking descriptors, calling read on each, makes ten thousand system calls per pass and almost all of them return EAGAIN. At 50–100 nanoseconds each (Node 4), one pass costs a millisecond of pure overhead and finds, typically, nothing. This is polling, and Node 2 already established when polling loses.

So the requirement is precise: one call that takes a set of descriptors and returns when at least one is ready, or a timeout elapses. That call is where the entire event loop comes from.

select (1983) — the first attempt

From 4.2BSD. You pass three bitmaps — descriptors to watch for readability, writability, and errors — plus a timeout. It blocks until something is ready, then modifies your bitmaps in place to indicate which.

Three problems, all structural:

  • FD_SETSIZE is 1024, compiled into the bitmap type. Not a tunable — a hard ceiling. Ten thousand connections is not expressible.
  • You rebuild and re-pass the entire set on every call, because the call destroys it. The kernel then copies it in and scans all of it. O(n) per call in both directions, every iteration, forever.
  • The return tells you how many are ready, not which. You scan all n to find them. Another O(n).

At 10,000 descriptors with 10 ready, every loop iteration copies and scans 10,000 entries twice to find 10. The cost is proportional to the number of connections you have, not to the number of events that happened — which is the exact wrong scaling property, since real servers hold many mostly-idle connections. That sentence is the whole node.

poll (1986) — one problem fixed, two left

System V's version takes an array of struct pollfd instead of bitmaps, each holding a descriptor, the events wanted, and a field the kernel fills in with events that occurred. The array is not destroyed, so it need not be rebuilt, and there is no fixed limit.

But the array is still passed in full on every call, still copied into the kernel, still scanned entirely, and still scanned by you on return. The O(n) per call remains, which means poll was an ergonomic improvement rather than an architectural one. It is still the right choice for small descriptor counts and it is what libuv uses on platforms lacking anything better.

epoll (2002) — the fix, and why it is a fix

Linux 2.5.44, by Davide Libenzi. The insight is that the watch set changes rarely and is queried constantly, so it should live in the kernel rather than being re-uploaded every iteration. Three calls instead of one:

  • epoll_create1() — create a kernel-side set, returning a descriptor that refers to it.
  • epoll_ctl(epfd, ADD|MOD|DEL, fd, events) — register interest in one descriptor. Called once per connection, not once per loop.
  • epoll_wait(epfd, events, maxevents, timeout) — block until something is ready, and return only the ready ones.

The mechanism inside is what makes it O(1). When you register a descriptor, the kernel attaches a callback to that socket's wait queue — the same wait queue from Node 18 step 4. When data arrives and the network softirq (Node 2) appends it to the socket buffer, that callback runs and pushes the descriptor onto the epoll instance's ready list. So the ready list is maintained continuously by the events themselves. epoll_wait does not scan anything; it hands back the list.

The cost becomes proportional to the number of events, not the number of connections. [EXPLAIN] A hundred thousand idle connections cost nothing to wait on. That property — and only that property — is what makes a modern server possible, and it is the correct answer when an interviewer asks what makes epoll better than select.

Level-triggered versus edge-triggered is the one real subtlety. Level-triggered (the default) reports a descriptor as ready as long as data remains unread — so a partial read is safe, and the next epoll_wait reports it again. Edge-triggered (EPOLLET) reports only on a transition from not-ready to ready, so if you do not drain the socket completely you will never be told about the remainder and the connection hangs silently. Edge-triggered requires reading in a loop until EAGAIN, and it is faster because it avoids repeated notifications. libuv uses level-triggered, which is the safer choice; nginx uses edge-triggered.

Every platform has its own version — kqueue on BSD and macOS (Jonathan Lemon, FreeBSD 4.1, 2000, and in some respects a better design than epoll since it handles timers, signals and file events through one interface), IOCP on Windows (a completion-based rather than readiness-based model), and event ports on Solaris. libuv exists to hide these four behind one interface, which is most of its reason to exist and why "Node is built on libuv" is a meaningful statement rather than trivia.

The crucial exception: regular files

Here is the fact that explains the strangest thing about Node's architecture, and it is routinely omitted.

A regular file is always "ready". [EXPLAIN] Readiness notification answers "will this operation block?", and for a socket that is a meaningful question — the data either has arrived or has not. For a file on disk, the answer is always yes, you can read it; the question is how long the read will take, which readiness cannot express. epoll flatly refuses regular files: adding one returns EPERM.

Nor is O_NONBLOCK any help — on a regular file it is simply ignored. A read that must fetch from the disk will block for however long the disk takes, and there is no interface in the readiness model that avoids it.

So a single-threaded event loop cannot do file I/O without blocking. There are only three possible responses:

  1. Use threads. Hand the blocking call to a pool thread and post the result back to the loop. This is what libuv does, and it is the entire reason UV_THREADPOOL_SIZE exists.
  2. Use a genuine asynchronous file interface. Linux's aio (POSIX AIO) has existed for years and is widely regarded as broken — it silently falls back to blocking in many configurations and only works with O_DIRECT.
  3. io_uring (Jens Axboe, Linux 5.1, May 2019), which is a completion-based interface built on two shared-memory ring buffers between user space and the kernel: you write submission entries into one ring and read completions from the other, with zero or one system calls for thousands of operations. It works properly for files, sockets, and much else, and it is the first genuinely good asynchronous I/O interface Linux has had. libuv has used it for some file operations since 1.45 (2023), gated on kernel version.

The mixed model — sockets on epoll, files on threads — is therefore not an inconsistency in Node's design. It is a direct consequence of the kernel interfaces available. Knowing this makes several Node behaviours predictable rather than mysterious.

Where this is in your stack

An idle Node server is one thread in epoll_wait, and you can see it. strace -p $(pgrep -n node) on an idle server prints one line: a blocked epoll_wait. That is the entire runtime at rest. Under load, it becomes epoll_wait returning, a burst of read/write/futex, and back. Watching that once makes the event loop concrete in a way no diagram does. [USE]

Threadpool saturation is a specific, diagnosable failure and it comes straight from the exception above. Four threads by default. If four file reads are in flight, the fifth queues. Crucially, dns.lookup also uses the pool — because getaddrinfo is a blocking library call — and so do crypto.pbkdf2, scrypt, randomBytes for large sizes, and zlib. So a slow DNS server can stall your file reads, which is a genuinely surprising coupling until you know the pool is shared. Symptoms: rising latency on file or DNS operations while the main thread is idle and CPU is low. Fixes: raise UV_THREADPOOL_SIZE (bounded by cores for CPU-bound work, per Node 6), use dns.resolve instead of dns.lookup where possible since it uses sockets and epoll, and move heavy crypto and compression to worker threads or out of the process.

The ulimit -n ceiling. Each connection is a descriptor and each process has a limit — often 1024 by default, which is a fossil of select's FD_SETSIZE. Hitting it produces EMFILE: too many open files, and it is one of the classic production failures, usually caused by descriptors leaking rather than by real concurrency: HTTP responses never consumed, streams never closed, connections without keep-alive timeouts. Diagnose with ls /proc/<pid>/fd | wc -l and lsof -p. Raise with ulimit -n, LimitNOFILE= in a systemd unit, or a container's ulimit settings — but always check for a leak first, because a leak will exhaust any limit.

Backpressure is epoll's write side, and it is why streams have the API they do. A socket's send buffer is finite. When it is full, a non-blocking write returns EAGAIN having written fewer bytes than asked, and the correct response is to register for EPOLLOUT and resume when the socket becomes writable. libuv does that for you, and Node surfaces it as stream.write() returning false and later emitting 'drain'. Ignoring that return value means Node buffers the unwritten data in your heap, without limit — which is how a service streaming a large file to a slow client runs out of memory. pipeline() and pipe() handle it correctly, which is the actual reason to prefer them over manual write loops.

What you can do at this point: explain the progression select → poll → epoll in terms of what scales with what, explain edge versus level triggering, explain why regular files cannot be polled and what that forces on Node's architecture, diagnose threadpool saturation and descriptor exhaustion, and explain backpressure as the write side of readiness.

What's still broken: there is now one call that reports many ready descriptors. That is a mechanism, not a program. Something has to loop on it, decide the order in which the resulting work runs, interleave timers and completed threadpool tasks and promise callbacks, and decide what happens when a callback schedules more work. That something is a scheduler, in user space, and it is the last node of this part.

Node 20 — the event loop, completely

The limitation: epoll_wait reports ready descriptors. Nothing decides what runs, in what order, or how timers and threadpool completions and promise callbacks interleave with it.

The event loop is a scheduler in user space. Everything from Node 7 applies to it, with one decisive difference: it has no timer interrupt and no privileged mode, so it is cooperative. It regains control only when a callback returns. Hold that as the frame for this entire node.

The loop, at its simplest

while (there is still work to do) {
    timeout = time until the nearest timer expires
    ready   = epoll_wait(epfd, events, max, timeout)
    for (each ready descriptor) run its callback
    run any timers that are now due
    run any completions posted by threadpool threads
}

That is genuinely it. Everything below is the elaboration libuv adds so that the ordering is well-defined.

libuv's phases, in order

One iteration of the loop — a tick — passes through these phases in this fixed order. Each phase has its own queue and drains it fully (subject to a limit, so one phase cannot starve the rest) before moving on.

  1. timers — callbacks whose setTimeout or setInterval deadline has passed. Note it runs first, which is why a timer scheduled during the poll phase does not fire until the next iteration.
  2. pending callbacks — a small set of system operations deferred from the previous iteration, chiefly certain TCP errors like ECONNREFUSED.
  3. idle, prepare — internal to libuv. Nothing you write lands here.
  4. poll — the heart. Compute a timeout, call epoll_wait, and run the I/O callbacks for whatever is ready. This is the only phase that ever blocks.
  5. check — setImmediate callbacks. This phase exists precisely so that there is a way to say "after the current poll phase, before any timers".
  6. close callbacks — 'close' events, e.g. socket.on('close').

The poll timeout is the whole trick, and it is worth stating exactly:

  • If there are setImmediate callbacks pending, the timeout is 0 — poll must not block, because there is work waiting in the check phase.
  • Otherwise, if there are timers pending, the timeout is the time until the nearest one. This is how setTimeout is implemented: there is no timer syscall and no timer thread, just an argument to epoll_wait. [EXPLAIN]
  • Otherwise, the timeout is infinite — block until something happens. This is why an idle Node process consumes exactly zero CPU, and why it is a single blocked epoll_wait in strace.
  • If there is nothing at all pending — no handles, no requests, no timers — the loop exits and the process ends. This is why Node exits on its own and why a forgotten setInterval or an unclosed server keeps it alive forever. There is no "main is finished" concept; there is only "no work remains".

The two queues that are not phases

This is where most confusion lives, and the rule is simple once stated properly.

process.nextTick and the microtask queue (promise reactions, queueMicrotask, async function resumptions) are not phases. They are drained after every single callback, and between every phase transition, and they are drained completely — including anything added while draining.

The priority is: nextTick queue first, entirely; then the microtask queue, entirely; then continue.

Three consequences, all of which appear in interviews and in real bugs:

Starvation is possible. A process.nextTick that schedules another process.nextTick loops forever without the loop ever advancing. No I/O is served, no timer fires, the process appears hung at 100% CPU. The same is true of a promise chain that recursively resolves. setImmediate cannot do this, because it lands in the check phase of the next iteration — which is exactly the difference between the two and the reason to prefer setImmediate for yielding.

await is a microtask, not a phase. An async function is a state machine: it runs synchronously until the first await, then returns a promise and suspends. When the awaited promise settles, the continuation is queued as a microtask. So the code after an await runs before any timer and before any I/O callback — await is a very cheap yield, not a trip through the loop. Also worth knowing: await on a non-promise value still yields, still costs a microtask turn, and return await p inside a try differs from return p because the former keeps the frame alive to catch a rejection.

The classic non-determinism. At the top level of a module, setTimeout(f, 0) versus setImmediate(g) have no guaranteed order. The timer is clamped to 1 ms; whether that millisecond has elapsed by the time the loop first reaches the timers phase depends on how long process startup took, so the answer varies between runs on the same machine. Inside an I/O callback the order is guaranteed: setImmediate always runs first, because the loop is in the poll phase and check comes immediately after, while timers are a full iteration away. Being able to explain why it is nondeterministic in one place and deterministic in the other is the actual test of understanding the phases.

console.log('1: sync');
setTimeout(()  => console.log('5: timers phase'), 0);
setImmediate(() => console.log('6: check phase'));
process.nextTick(() => console.log('3: nextTick queue'));
Promise.resolve().then(() => console.log('4: microtask queue'));
console.log('2: sync');
// 1, 2 → then nextTick → then microtasks → then the loop starts.
// 5 and 6 may swap; everything before them will not.

The browser's event loop: the same idea, one more responsibility

The browser runs the same model with an extra job — it must paint — and that changes the structure in ways that matter for every React application.

Per iteration the browser: takes one task from a task queue (a click handler, a setTimeout, a parsed network response) and runs it to completion; then performs a microtask checkpoint, draining that queue entirely; then, if it is time to render (typically capped at the display's refresh rate, 60 Hz meaning roughly every 16.7 ms), it runs the rendering steps.

The rendering steps, in order: run requestAnimationFrame callbacks; recalculate style; do layout; update the compositing tree; paint. Then, if there is time left before the next frame, run requestIdleCallback callbacks.

Everything about frontend performance follows from that ordering:

  • One task per iteration, microtasks drained fully. So a long task blocks rendering entirely — this is precisely what Interaction to Next Paint measures, and why the guidance is to break work into chunks under 50 ms. And an infinite microtask chain freezes the page harder than an infinite task loop, because rendering never gets a turn at all.
  • requestAnimationFrame runs immediately before style and layout, which is why it is the correct place to make visual changes: they are applied in the same frame, with no intermediate paint. setTimeout(f, 16) is not equivalent — it lands in a task queue with no relationship to the frame boundary, so it produces jitter and dropped frames.
  • Layout thrashing is this ordering violated. Reading a geometric property (offsetHeight, getBoundingClientRect, scrollTop) forces the browser to flush pending style and layout right now to give a correct answer. Alternating writes and reads in a loop forces a full layout per iteration — a hundred elements becomes a hundred layouts. Batching all reads and then all writes turns it into one. This is the single most common cause of janky scroll handlers, and requestAnimationFrame plus batching is the standard fix.
  • requestIdleCallback is SCHED_IDLE from Node 7, for the main thread — and its deadline argument is the browser telling you how much of the frame remains.

React's scheduler sits on top of all of this, as Node 7 described: it slices rendering into units, yields roughly every 5 ms so the browser can take input and paint, and assigns lanes by priority. It uses a MessageChannel rather than setTimeout to schedule its continuations, specifically to avoid the 4 ms clamp from Node 8. Concurrent React is a cooperative scheduler running inside a cooperative scheduler running inside a preemptive one, and every layer of that stack is a node in this document.

Measuring it, and the only metric that matters

Event loop delay is the time between when a callback was due and when it actually ran. Non-zero delay means the loop was busy; large delay means something blocked it. Node exposes it properly through perf_hooks:

const { monitorEventLoopDelay, performance } = require('node:perf_hooks');
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => {
  console.log('p50', h.percentile(50) / 1e6, 'p99', h.percentile(99) / 1e6);
  console.log('ELU', performance.eventLoopUtilization().utilization);
  h.reset();
}, 5000);

Export both of these from every Node service. [USE] The delay histogram tells you whether the loop is being blocked and by how much; event loop utilisation — the fraction of time the loop spent working rather than waiting in epoll_wait — tells you how close to saturated the process is, and is the right signal for autoscaling and for load-shedding decisions, far better than CPU percentage. A p99 delay of 200 ms with 40% CPU is a completely legible diagnosis: something synchronous and slow, not enough work overall.

Where this is in your stack

One request, through every layer built so far. Reading this once, slowly, with the node references, is the point of Part IV:

  1. A packet arrives. NIC writes it to memory by DMA and raises an interrupt (Node 2).
  2. The driver's handler schedules a softirq; the softirq walks the packet up through IP and TCP and appends the payload to a socket's receive buffer (Node 32).
  3. That socket's wait-queue callback fires and pushes its descriptor onto the epoll ready list (Node 19).
  4. Your process, sleeping in epoll_wait with the scheduler having given the core to someone else (Nodes 5, 7), is marked runnable. The scheduler picks it. A context switch restores its registers and page table (Nodes 6, 10).
  5. epoll_wait returns with the ready list. The loop is in its poll phase.
  6. libuv maps the descriptor to a handle and invokes its callback, which issues read (Node 4) and copies bytes from the kernel's socket buffer into a Buffer — memory outside the V8 heap (Node 11).
  7. Node's HTTP parser consumes the bytes. On a complete request, it calls into V8 to invoke your handler — JIT-compiled machine code (Node 0) executing on the main thread.
  8. Your handler awaits a database query. The function suspends; a promise is returned; the query is written to a socket; the loop moves on and serves other connections. The whole architecture pays off exactly here.
  9. The database replies. Steps 1–5 again. The promise resolves, queueing a microtask; the microtask resumes your function's state machine.
  10. You call res.json(...). Node writes to the socket; if the send buffer is full, write returns short and libuv registers for writability (Node 19).
  11. Objects allocated during the request die; V8's scavenger reclaims them in under a millisecond (Node 11).
  12. The loop returns to epoll_wait. If nothing is pending, the process sleeps at zero CPU.

The complete list of things that block the loop, since every one of them is now derivable: any *Sync call; JSON.parse or JSON.stringify on a large object; a synchronous crypto or compression call; a regular expression with catastrophic backtracking (ReDoS — a real denial-of-service vector, and the reason safe-regex and RE2 exist); a large synchronous loop over an array; a deep structuredClone; template rendering of a large page; and — easily missed — a very large number of pending microtasks, since they drain fully before the loop advances. Each blocks every connection in the process, because there is one thread and it is not preemptible (Node 7).

And the fixes, matched to the cause: chunk the work with setImmediate to yield between chunks; move it to a worker thread if it is CPU-bound (Node 15); move it to a separate process or a queue if it is heavy or slow; stream instead of buffering; or push it into the database, where it belongs, if it is really a data operation. Reaching for UV_THREADPOOL_SIZE does nothing for main-thread blocking, and knowing why is the difference between guessing and diagnosing.

Node 21 — the file, the inode, and "everything is a file"

The limitation: a disk is a large array of numbered blocks with no structure. Programs need named, growable, permission-controlled sequences of bytes.

The abstraction, and how radical it was

Unix's definition of a file is deliberately, aggressively minimal: a file is a finite sequence of bytes, and that is all. [EXPLAIN]

No records. No fixed-length lines. No file type known to the system. No structure the operating system understands or enforces. This was not the norm — contemporary systems like OS/360 had record-oriented files with formats declared in the JCL from Node 1, and the system knew about fixed-length blocked records and would enforce them. Unix threw all of it away and said: bytes, and the program that opens the file decides what they mean.

The consequence is compositionality. Because no program can assume structure, every program must handle a plain byte stream, and therefore any program's output can be any other program's input. The Unix toolchain philosophy — small programs composed with pipes — is a direct consequence of this one decision about what a file is.

Separating the name from the file: the inode

The second key decision. A file's identity and its name are separate things.

The file itself is an inode (index node), a fixed-size record on disk holding everything about the file except its name:

  • type (regular file, directory, symbolic link, device, socket, FIFO)
  • permission bits, owner user ID, owner group ID
  • size in bytes
  • timestamps — mtime (contents last modified), ctime (inode last changed, not creation), atime (last accessed)
  • a link count — how many names refer to this inode
  • pointers to the data blocks

A directory is then just a file whose contents are a list of (name → inode number) pairs. Nothing more. Which means:

  • A file can have several names. Two directory entries pointing at the same inode are hard links. Neither is "the original"; they are equally the file.
  • Deleting is really unlinking. The call is unlink, and it removes a directory entry and decrements the link count. The data is freed only when the count reaches zero and no process still has it open. This is why deleting a large log file that a running process still holds open frees no disk space — a classic and confusing production situation, where du shows the space gone and df shows the disk still full. lsof | grep deleted finds it, and the fix is to restart or signal the holder, or to truncate rather than delete.
  • An open file has no name. Once opened, a process holds a reference to the inode; renaming or deleting the path does not affect it. This is why rename() is atomic and why "write to a temporary file, then rename over the target" is the standard safe-write idiom — readers see either the whole old file or the whole new one, never a partial write.
  • Permissions live on the inode, not the name, so all hard links share them.
  • Hard links cannot cross filesystems (inode numbers are per-filesystem) and cannot point at directories (it would create cycles the tree-walking code cannot handle). Symbolic links are the alternative: a tiny file whose contents are a path string, resolved at every use — so they can cross filesystems, can dangle, and add a resolution step to every access.

Running out of inodes while disk space remains is a real failure and a confusing one: df -h shows space free, writes fail with ENOSPC, and df -i shows 100% inode use. Traditional filesystems allocate a fixed inode table at format time, so millions of tiny files — a cache directory, a poorly configured session store, node_modules multiplied across many builds — can exhaust them.

"Everything is a file"

The third decision, and the one with the widest consequences. Unix applies the same interface — open, read, write, close, lseek, ioctl — to things that are not files at all:

  • Devices. /dev/sda is the raw disk. /dev/null discards writes and reads as empty. /dev/zero yields endless zero bytes. /dev/urandom yields cryptographic randomness. /dev/tty is the terminal.
  • Pipes and sockets — Node 22 and Node 31.
  • Kernel state. /proc and /sys are filesystems with no disk behind them at all: reading a file there executes kernel code that generates the content on the spot. This is why every tool from ps to top to a container runtime is, mechanically, a program that reads text files. Node 38.

The payoff is that a tool written for files works on all of it. cat, redirection, grep, and your language's file API operate on devices, kernel state, and network connections with no special support. It is the earliest and one of the best examples of a uniform interface paying for itself over decades. [EXPLAIN]

The VFS: one interface, many implementations

For that uniformity to work with many different filesystems, the kernel needs a layer of indirection, and it has one: the Virtual File System, introduced by Sun in 1985 for NFS and adopted everywhere. The VFS defines a set of operations — look up a name, read, write, create — and every filesystem implements them. ext4, XFS, btrfs, NFS, tmpfs, overlayfs, procfs, and FUSE-based filesystems all plug into the same interface.

So read() is: syscall entry, VFS dispatch on the inode's filesystem type, that filesystem's implementation, the page cache, the block layer, the device driver. The layering is what makes mount possible — attaching any filesystem at any point in the single tree — and mounts are per-namespace, which is the hinge on which containers turn (Node 26).

Where this is in your stack

Every Docker volume mount is this node. -v /host/path:/container/path is a bind mount: the same inodes appearing at a second location in the tree. There is no copying and no synchronisation — it is literally the same files, which is why edits on the host appear instantly inside the container. And it is why mounting over a directory hides what was there: the mount replaces what that path resolves to, so bind-mounting your source directory over /app hides the /app/node_modules the image installed. The standard fix — an anonymous volume at /app/node_modules — is a second mount at a deeper path that shadows the first, and knowing the mechanism makes that trick obvious rather than magical.

Atomic writes in application code. The rename idiom above is the correct way to update a config file, a cache entry, or any file a reader might see mid-write. In Node: fs.writeFile(tmp, data), then fs.rename(tmp, target). It only works if both paths are on the same filesystem — rename across filesystems fails with EXDEV and the library falls back to copy-then-delete, which is not atomic. This is why moving a file from /tmp to a mounted volume in a container often behaves differently from moving within the volume, and why upload handling should write the temporary file into the destination filesystem.

File watching is not part of this abstraction, and that shows. There is no portable "tell me when this changes"; Linux has inotify, macOS has FSEvents, and Windows has ReadDirectoryChangesW. Node's fs.watch maps onto them with real differences in behaviour, which is why chokidar exists and why every bundler depends on it. inotify also has per-user limits — fs.inotify.max_user_watches, historically 8192 — and exceeding them produces ENOSPC from a watcher, which is one of the most misleading error codes in Linux since no space is involved. Anyone who has run a dev server on a large repository has hit it.

node_modules is an inode problem. A large project can have hundreds of thousands of small files. That is slow to create, slow to traverse, slow to copy into a Docker build context, and inode-hungry. pnpm's design is a direct response: one content-addressed global store, with hard links (this node) into each project's node_modules, so the same file exists once on disk with many names. Yarn PnP goes further and eliminates the directory entirely, resolving from a single map file. Both are filesystem-level answers to a filesystem-level problem.

.dockerignore matters more than people think for the same reason: the build context is the entire directory tree sent to the daemon, walked file by file. Excluding node_modules and .git often turns a thirty-second context upload into one second.

Node 22 — file descriptors, pipes, and how redirection actually works

The limitation: open returns a small integer and nothing has said what it refers to.

Three tables, not one

The indirection here is three levels deep, and every confusing thing about descriptors comes from people collapsing it to one. [EXPLAIN]

  1. The per-process descriptor table. An array in the task_struct (Node 5), indexed by the small integer. Entry N is a pointer to an open file description, plus one flag (close-on-exec). Descriptor 3 in your process and descriptor 3 in mine are unrelated.
  2. The system-wide open file table. Each entry — an open file description — represents one act of opening: the current offset, the access mode (read, write, append), the status flags (O_NONBLOCK), and a pointer to the inode.
  3. The inode table. One entry per actual file, as in Node 21.

The middle level is the one that carries the meaning:

  • Calling open() twice on the same path gives two descriptions — two independent offsets. Reading through one does not move the other.
  • dup() and fork() give two descriptors sharing one description — one offset. A parent and child both writing to inherited stdout interleave correctly instead of overwriting each other, because they share the file position. That is not a coincidence; it is the reason for this design.
  • Closing a descriptor decrements a reference count on the description. The description is destroyed when the count reaches zero.

Zero, one, two

By convention — enforced by nothing but universally relied upon — every process starts with:

  • 0: standard input
  • 1: standard output
  • 2: standard error

They are separate so that a program's results and its complaints can go to different places, which is what makes ./build > out.log 2> err.log possible and why error messages still reach your terminal when output is piped.

The rule that makes all of this work: open always returns the lowest-numbered unused descriptor. That specification, which sounds like an implementation detail, is what makes redirection expressible without any dedicated mechanism.

Redirection, derived

ls > out.txt. The shell does this:

pid = fork();                    // Node 14 — child is a copy
if (pid == 0) {
    close(1);                    // descriptor 1 is now free
    open("out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644);
                                 // returns 1 — the lowest free number
    execve("/bin/ls", ...);       // ls replaces the program;
                                 // descriptors survive exec
}

ls writes to descriptor 1 as it always does, knowing nothing. Redirection is implemented entirely by rearranging the child's descriptor table in the interval between fork and exec — the interval Node 14 said existed for exactly this. No special support in ls, no special support in the kernel. [EXPLAIN] (In practice shells use dup2(fd, 1), which atomically makes descriptor 1 a copy of another, rather than the close-then-open race above.)

Pipes

A pipe is a kernel buffer with two descriptors: pipe(fds) fills fds[0] for reading and fds[1] for writing. Bytes written to one end come out the other, in order. The buffer is finite — 64 KB on Linux by default — and that finiteness is the entire mechanism of Unix flow control:

  • Writing to a full pipe blocks until the reader consumes. That is backpressure, built into the primitive: a fast producer is forced to the speed of a slow consumer with no coordination between them. It is the spooling principle from Node 1, made a kernel object.
  • Reading from an empty pipe blocks until data or until all write ends are closed, at which point read returns 0 — end of file. All write ends: if any process still holds one open, the reader waits forever, which is the classic hang when a shell script forgets to close an inherited descriptor.
  • Writing to a pipe with no readers raises SIGPIPE, whose default action is to kill the process. This is why yes | head -5 terminates promptly rather than running forever, and it is a deliberate design: producers die automatically when consumers stop caring.

cmd1 | cmd2 is then: create a pipe; fork twice; in the first child dup2(fds[1], 1) and close both original ends; in the second dup2(fds[0], 0) and close both; exec both. Two unmodified programs, connected, using nothing but the descriptor table.

Where this is in your stack

child_process is this node with a JavaScript surface. The stdio option is literally a specification of the child's descriptor table: 'pipe' creates a pipe and hands you a stream; 'inherit' passes your own descriptor straight through, so the child writes directly to your terminal or log with no relaying through your process; 'ignore' opens /dev/null; and an integer or stream passes a specific descriptor. stdio: ['pipe','pipe','pipe','ipc'] — a fourth entry — is what child_process.fork() uses to add the message channel that makes child.send() work. Choosing 'inherit' for a build subprocess is not just tidier; it removes your process from the data path entirely.

The classic subprocess deadlock. A child produces 10 MB on stdout; the parent waits for the child to exit before reading. The pipe fills at 64 KB, the child blocks writing, the parent blocks waiting, and neither moves. This is why execSync has maxBuffer (1 MB by default) and throws ENOBUFS past it, and why the correct pattern for a chatty child is to consume its output continuously — spawn with stream handling, not exec with a callback. It is a bounded-queue deadlock, exactly the shape from Node 17.

Container logging is a pipe. Docker gives your container's PID 1 a pipe for stdout and stderr, reads from it, and writes to a log driver — a JSON file by default. Consequences that follow directly: if you write to a file inside the container instead of stdout, none of this happens and your logs are invisible to docker logs and to every log shipper; the pipe is why Node treats stdout as asynchronous in a container and synchronous in a terminal (Node 4), so output can be lost on an abrupt exit; and if the log consumer stalls, the pipe fills and your application blocks on console.log, which is a genuine and very confusing production failure. The 12-factor rule "treat logs as event streams and write to stdout" is a statement about this node.

Descriptor limits and leaks, from Node 19, are a descriptor-table problem: every socket, every open file, every pipe, every inotify watch, every epoll instance consumes an entry. EMFILE means the table is full. ls -l /proc/<pid>/fd lists exactly what is in it, with symbolic links naming each target — socket:[12345], pipe:[67890], or a path. Reading that list is how you find which resource is leaking in about a minute.

Close-on-exec, and why it matters for security. The FD_CLOEXEC flag makes a descriptor close automatically on execve. Without it, every descriptor you hold is inherited by every subprocess you spawn — including your database connections, your TLS private key file, and your listening sockets. A subprocess that should have no access to the database can read from a socket that is already authenticated. Modern APIs default to close-on-exec for this reason (open with O_CLOEXEC, socket with SOCK_CLOEXEC, epoll_create1(EPOLL_CLOEXEC)), and libuv sets it. It is worth knowing it exists, because when you deliberately want to pass a descriptor — as cluster does with a listening socket, and as systemd does with socket activation (Node 37) — you must clear it.

Node 23 — the disk underneath, and what fsync is for

The limitation: write() returns as soon as bytes are in the page cache, so nothing yet said has any relationship to data surviving a power cut.

The two devices, and why they behave so differently

A hard disk is spinning magnetic platters with a head on an arm. To read a block, the arm moves to the right track (seek, 4–10 ms) and then the platter rotates until the block passes under the head (rotational latency, averaging half a revolution — 4.2 ms at 7200 rpm). Total for a random read: around 8–12 ms. Once positioned, sequential transfer runs at 100–200 MB/s.

Those two numbers give a ratio of roughly 100 to 1 between sequential and random access, and that ratio is the reason for the entire shape of database design. [EXPLAIN] B-trees exist to keep the number of seeks logarithmic. Write-ahead logs exist to convert random writes into sequential ones. Sequential scans beat index scans past a certain selectivity because a hundred sequential blocks cost less than ten random ones — which is exactly what Postgres's random_page_cost (4.0) versus seq_page_cost (1.0) encodes, and why lowering random_page_cost to about 1.1 on SSD storage is standard and frequently changes plans for the better. The planner is doing arithmetic with this node's physics.

A solid-state disk has no moving parts, so random access costs essentially the same as sequential: around 100 microseconds for SATA, 20–80 for NVMe. A hundred times faster than a disk seek. But flash has three awkward properties that create a whole hidden layer:

  • It is read and written in pages of 4–16 KB, but erased only in blocks of several megabytes.
  • A page cannot be overwritten in place; it must be erased first, and erasure only works at block granularity.
  • Each block tolerates a limited number of erase cycles — thousands to tens of thousands.

So an SSD contains a small computer, the Flash Translation Layer, that maintains a map from logical block addresses to physical pages. A write goes to a fresh page and the map is updated; the old page is marked stale. Background garbage collection later relocates the still-live pages out of a mostly-stale block and erases it. Consequences worth knowing: write amplification, where writing 4 KB causes far more than 4 KB of flash traffic; latency spikes when garbage collection collides with your writes, which is why SSD p99 latency is much worse than its average; wear levelling, spreading writes so no block dies early; and TRIM, by which the filesystem tells the device which blocks are no longer in use so it can garbage-collect them — without it, a full-then-emptied SSD stays slow.

The latency hierarchy, which is worth memorising because it explains most performance intuitions:

  L1 cache                       ~1 ns
  L2 cache                       ~4 ns
  main memory (DRAM)            ~80 ns
  NVMe SSD read                ~20–80 µs      (~1,000× DRAM)
  SATA SSD read                  ~100 µs
  network, same datacentre     ~100–500 µs
  hard disk seek                ~5–10 ms       (~100,000× DRAM)
  network, cross-continent      ~100 ms

The block layer

Between the filesystem and the device sits the block layer, which merges adjacent requests, reorders them, and hands them to the driver. Its I/O scheduler mattered enormously for spinning disks — the elevator algorithm sweeps the head in one direction to avoid pathological back-and-forth seeking. On NVMe it mostly does not, which is why the modern default for such devices is literally none: the device's own queues (thousands of them, deep) do better than the kernel can. cat /sys/block/nvme0n1/queue/scheduler shows the choice.

Readahead is the other important behaviour: on detecting sequential reads, the kernel fetches ahead into the page cache, which is why a sequential scan is fast and why the page cache from Node 13 does most of the work in a well-behaved database.

The durability chain, and the call that closes it

Here is where your bytes actually are, in order, after a write():

  1. Your language's buffer — a Node stream's internal buffer, or libc's stdio buffer. Lost if the process crashes.
  2. The kernel page cache — after the write syscall returns. Survives a process crash, including a SIGKILL or an OOM kill. Lost on power failure or kernel panic.
  3. The device's write cache — after the kernel writes it back. A disk or SSD has its own volatile RAM cache, and it acknowledges writes on arrival there. Lost on power failure, unless the device has a capacitor or battery.
  4. The actual medium — platter or flash. Survives everything.

fsync(fd) forces stages 2 and 3 to complete: it writes back all dirty pages of that file and issues a cache-flush command to the device, returning only when the device says the data is durable. [EXPLAIN] fdatasync is the same but may skip metadata that does not affect reading the data back — cheaper, and what databases usually use. Costs: on a hard disk, a full rotation, so 5–10 ms; on a consumer SSD, tens to hundreds of microseconds; on enterprise hardware with power-loss protection, near zero because the device can honestly acknowledge immediately.

This is the single most important number in database performance. An in-memory row insert is a microsecond. A committed, durable row insert is bounded below by one fsync. That is the whole gap, and every durability setting in every database is a decision about how many fsyncs to do and when.

Three more facts that separate people who have run databases from people who have not:

Devices lie. Some consumer drives acknowledge a flush without performing it, because it benchmarks better. Data written to such a device is not durable no matter what your database does. This is why enterprise drives with power-loss capacitors exist and why cloud block storage is worth its price — the provider has solved this and gives you a written guarantee.

fsync can fail, and what happens then used to be catastrophic. In 2018 the Postgres developers discovered — the incident is known as fsyncgate — that on Linux, when writeback fails, the kernel reports the error to whoever calls fsync next and then marks the pages clean anyway, so a second fsync returns success while the data is gone forever. Postgres had been retrying on fsync failure. The fix, shipped in Postgres 12, is to panic the server on fsync failure and recover from the write-ahead log, because there is no safe way to continue. The general lesson is worth carrying: an I/O error is not a retryable error unless you know exactly what the layer beneath did with the failed data.

Durability is not atomicity. A power cut partway through writing an 8 KB page can leave four kilobytes of new data and four of old — a torn page. Hardware guarantees atomicity only at sector granularity (512 or 4096 bytes). This is why Postgres has full_page_writes on by default: the first modification of a page after each checkpoint writes the entire page image into the write-ahead log, so recovery can reconstruct it. It roughly doubles WAL volume and it is the reason turning it off is tempting and wrong on any storage without atomic-write guarantees.

Where this is in your stack

The write-ahead log is this node's design pattern, and it is worth being able to derive. Modifying a row means changing a page somewhere in a large file — a random write, which on a disk is 10 ms and which cannot be made atomic across several pages. So instead: append a description of the change to a sequential log, fsync that, and only then report the commit as successful. The actual data pages are updated later, lazily, in the background. The random write becomes one sequential append plus one fsync. If the machine dies, replay the log from the last checkpoint. Every durable system does this — Postgres's WAL, MySQL's InnoDB redo log, SQLite's WAL mode, Kafka's log-structured storage, etcd's Raft log, and every LSM-tree database's commit log. [EXPLAIN] Recognising it once means you understand the durability story of all of them.

The knobs, and what they trade:

  • Postgres synchronous_commit. on (default) means every commit waits for a WAL fsync — full durability, and a commit rate bounded by fsync latency. off means commits return without waiting, flushing within wal_writer_delay (200 ms default). You do not risk corruption — only the loss of the last fraction of a second of committed transactions. That is a genuinely reasonable trade for analytics ingestion or event logging and a terrible one for payments. Also relevant: group commit, where concurrent commits share one fsync, which is why throughput scales far better with concurrency than the single-transaction latency suggests, and which commit_delay tunes deliberately.
  • MySQL innodb_flush_log_at_trx_commit: 1 flushes per commit (durable, the default), 2 writes to the page cache per commit and flushes each second (survives a process crash, not a power cut), 0 does neither.
  • Redis appendfsync: always, everysec (the default and the sensible one), or no. And RDB snapshots alone mean losing everything since the last save, which is a fact many people using Redis as a database rather than a cache have discovered at the wrong moment.
  • SQLite PRAGMA journal_mode=WAL and synchronous=NORMAL — the standard pairing, and the reason SQLite is dramatically faster with them than with the defaults.

Diagnosing storage from the outside. iostat -x 1 gives, per device: await (average request latency in milliseconds — the number that matters), %util (misleading on SSDs with parallel queues; a device can be at 100% util and far from saturated), and aqu-sz (queue depth). High await with a deep queue means the device is saturated. In top, the wa column is time processes spent blocked on I/O, and a machine with high wa and low user CPU is storage-bound, not compute-bound. pidstat -d attributes it to processes. [USE] "The database is slow" resolves through these three commands more often than through any query analysis.

Cloud storage adds a layer with its own economics. An AWS EBS gp3 volume has a provisioned IOPS figure and a throughput figure, independently settable; gp2 used a burst-credit system where a small volume accumulates credits while idle and, once they are exhausted, drops to a baseline that can be a fraction of what your application saw in testing. A database that was fast for three weeks and then became permanently slow has usually exhausted burst credits, and no amount of query tuning fixes it. Network-attached storage also has network latency in the durability path — an EBS fsync is a round trip — which is why local NVMe instance storage is dramatically faster and why it is ephemeral, and why a Kubernetes PersistentVolumeClaim's storage class is a database performance decision rather than an infrastructure detail.

Containers and writes. Writing to a container's filesystem goes through the overlay driver (Node 24), which adds copy-up costs. Writing to a volume goes to the host filesystem directly. Never run a database on the container's writable layer — that is the mechanical reason behind the advice, not merely a persistence concern.

Node 24 — filesystems, journaling, and the one a Docker image is made of

The limitation: a block device is a numbered array of blocks; files and directories are not.

What a filesystem has to lay out

Any filesystem divides the device into: a superblock holding global metadata (size, block size, where everything else is, and a clean/dirty flag); allocation structures recording which blocks and inodes are free; the inode table from Node 21; and the data blocks themselves.

The interesting design question is how an inode points at its data. The classic Unix scheme used direct pointers for the first few blocks plus single, double and triple indirect blocks — so a small file needs one lookup and a huge file needs four, with the cost paid only by files large enough to justify it. Modern filesystems use extents instead: a start block and a length, so a contiguous 1 GB file is described by a handful of records rather than 262,144 pointers. That change alone is a large part of why ext4 outperforms ext3 on big files.

Crash consistency: the actual hard problem

Creating a file requires several separate writes: allocate an inode, write the inode, allocate data blocks, write the data, add the directory entry, update the free maps. A crash between any two leaves the filesystem inconsistent — an inode marked in use with no directory entry pointing at it (a leaked file), or a directory entry pointing at an inode that was never initialised (which is worse, since it may contain another file's old data).

The old answer was fsck: on boot after an unclean shutdown, scan the entire filesystem and repair it. On a multi-terabyte filesystem that is hours, during which the machine is down. Unacceptable for a server.

Journaling is the answer, and it is Node 23's write-ahead log applied to filesystem metadata. Before performing a group of related updates, write a description of them to a dedicated journal area and flush it. Then perform the real updates. Then mark the journal entry complete. After a crash, replay any entries that were written but not marked complete — bounded work, seconds rather than hours. [EXPLAIN]

ext4 offers three modes, and the middle one being the default explains a behaviour people find surprising:

  • data=journal — data and metadata go through the journal. Safest, and everything is written twice.
  • data=ordered (the default) — only metadata is journaled, but data blocks are forced to disk before the metadata that references them. So you never see a file whose metadata points at blocks containing another file's old contents. You can still lose recent data.
  • data=writeback — metadata journaled, no ordering. Fastest, and after a crash a file can contain arbitrary stale bytes.

Because ext4 journals metadata rather than data, a crash can leave a file that exists, has the right size, and is full of zeros. That is not a bug; it is the documented consequence of data=ordered with delayed allocation, and it is why applications that care must fsync — and must fsync the directory too, after a rename, or the rename itself may not be durable. The rename idiom from Node 21 is atomic with respect to readers and is not automatically durable with respect to power loss; a correct safe-write is: write temp, fsync temp, rename, fsync the directory.

The filesystems you will meet

  • ext4 (2008) — the Linux default. Journaled, extent-based, dull and reliable. The correct choice unless you have a reason.
  • XFS (SGI, 1993; Linux since 2001) — excellent at large files and high parallelism; the default on Red Hat. Cannot be shrunk.
  • btrfs and ZFS — copy-on-write filesystems (Node 14's pattern at block level) with built-in snapshots, checksums on all data, and volume management. ZFS is the more mature and its licence keeps it out of the Linux kernel tree.
  • tmpfs — a filesystem in RAM, backed by the page cache and swap. This is what /dev/shm and much of /run are, what Docker's --tmpfs and Kubernetes' emptyDir: {medium: Memory} give you, and — importantly — its contents count against your cgroup memory limit (Node 13). A build that writes a few gigabytes into a memory-backed emptyDir will be OOMKilled, and the reason is not obvious from the error.
  • Network filesystems — NFS, SMB, and cloud file services. They break assumptions that local filesystems satisfy: locking is advisory and unreliable, fsync semantics vary, latency is milliseconds, and a server that stops responding puts your process into the D state from Node 5, unkillable. Never put a database on NFS, and be careful about putting anything latency-sensitive there.
  • FUSE — filesystems implemented in user space. s3fs, sshfs, and many container and cloud tools use it. Every operation is a round trip to a user process, so it is slow, and it is why "mount S3 as a filesystem" is always a worse idea than it sounds.

overlayfs, and therefore Docker

A union filesystem presents several directory trees merged into one. overlayfs, in the Linux kernel since 3.18 (2014), is the one Docker uses. It takes some read-only lower directories and one writable upper directory and presents a merged view:

  • Reading a path searches the upper layer first, then each lower layer in order, and returns the first hit.
  • Writing to a file that exists only in a lower layer triggers a copy-up: the entire file is copied into the upper layer, then modified. Copy-on-write at file granularity (Node 14).
  • Deleting a lower-layer file cannot actually delete it, so a whiteout marker is created in the upper layer to hide it.

This is what a Docker image is. [EXPLAIN] Each instruction in a Dockerfile that changes the filesystem produces one layer — a directory of the differences. A running container adds one writable upper layer. Every property of Docker images that you have learned as a rule falls out of this mechanism:

  • Layers are shared. Ten containers from one image share one set of lower directories, so ten containers cost one copy of the image plus ten small upper layers. This is also why the same base image across many services is a genuine and large saving.
  • The writable layer is ephemeral — it is a directory on the host that is deleted when the container is removed. Hence volumes.
  • Deleting a file does not shrink the image. RUN apt-get install ... && rm -rf /var/lib/apt/lists/* in one instruction removes the files before the layer is finalised. Split across two instructions, the first layer still contains them and the second only adds whiteouts — the image is larger, and the deleted secret is still extractable from the layer. This is the single most common way credentials leak from container images, and it is why multi-stage builds and --secret mounts exist.
  • Layer ordering is a caching decision. A layer's cache is invalidated when its instruction or its inputs change, and every layer after it is then rebuilt. So COPY package*.json ./ then RUN npm ci then COPY . . is not a style convention: it puts the slow, rarely-invalidated step above the fast, always-invalidated one. Reversing them means reinstalling dependencies on every source change.
  • Write-heavy workloads are slow on the overlay. The first write to any file pays a full copy-up, which for a large file is a full copy. This is the mechanical reason databases need volumes, and why heavy build work inside a container benefits from a mounted cache.
  • docker commit and image bloat. Because layers are additive, an image's size is the sum of its layers regardless of what the final view contains.

Where this is in your stack

Docker Desktop's bind-mount slowness on macOS and Windows is a filesystem boundary. Linux containers there run inside a virtual machine (Node 29), so a bind mount from the host crosses from the host's filesystem into the VM through a network-style protocol — originally osxfs, then gRPC-FUSE, now VirtioFS, each faster than the last but none free. Every stat crosses that boundary, and a tool that stats a hundred thousand files — which is exactly what a bundler or a test runner does on node_modules — becomes an order of magnitude slower. The standard fix is to keep node_modules inside the container as a named volume rather than bind-mounted from the host, which now has a mechanical explanation rather than being folklore. Running the whole workflow inside WSL2's own filesystem, rather than under /mnt/c, is the same fix on Windows and makes an enormous difference.

Case sensitivity is a filesystem property and it breaks CI. macOS's APFS is case-insensitive by default; ext4 is case-sensitive. import Button from './button' works on a Mac and fails in a Linux container with Cannot find module. This is one of the most common "works on my machine" failures in JavaScript projects and its cause is one line of this node.

Timestamps and reproducible builds. Filesystem mtime values end up in archives and image layers, so identical inputs produce different layer hashes and the cache misses. This is why reproducible-build tooling normalises timestamps and why SOURCE_DATE_EPOCH exists.
