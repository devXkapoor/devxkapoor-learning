The DOM & DOM APIs

The live object tree between your HTML and your pixels — traced as a causal chain from the page that could not change, through selection, events, delegation, geometry, the rendering pipeline, observers, leaks and encapsulation, to exactly what a framework replaced and what it left you.

Read this in order. Each node exists because the node before it left something specifically broken, and the broken thing is named at the end of every node. Nothing here is introduced because it belongs in a category; it is introduced because at that point in the chain you cannot proceed without it.

Depth markers are attached to individual capabilities as they appear. [EXPLAIN] means you should be able to explain it out loud, from first principles, without notes. [USE] means you should be able to use it correctly and debug it when it breaks, without needing the internals cold. [AWARE] means you should know it exists, what it solves, and roughly when someone would reach for it.

Node 0 — The page that cannot change

Before there was a DOM, a web page was a finished thing. A browser asked a server for a document, the server sent back a stream of HTML text, and the browser drew it. That was the entire transaction. If anything about what was on screen needed to be different — a validation error next to a form field, a menu opening, a total updating when you changed a quantity — the only mechanism available was to ask the server for a whole new document and draw that instead.

This is not a hypothetical. Through 1993 and 1994 this was the actual shape of every interactive site. You filled in a form, pressed submit, the browser threw away everything on screen, sent your values to a CGI script, waited for a response over a modem running at 14.4 or 28.8 kilobits per second, and drew a new page. If you had mistyped your email address, you learned about it several seconds later, on a fresh page, often with the rest of your input cleared. The round trip was the unit of interaction, and the round trip was slow.

What made this worse is that the browser genuinely had the page. It had parsed the HTML, worked out where every piece of text went, and drawn it. All of that structure existed inside the browser already. It simply was not exposed to anything. There was no way for a program to say "the text inside that heading should now read something else," because there was no program, and there was nothing to address.

Netscape shipped JavaScript in Netscape Navigator 2.0 in March 1996, and with it the first thin slice of addressability — you could reach document.forms, document.images, document.links, and a handful of other collections. This is retroactively called DOM Level 0, and it was not designed so much as accreted. It was enough to check whether a field was empty before submitting. It was nowhere near enough to build an interface, and crucially, Microsoft and Netscape then invented incompatible extensions of it — Internet Explorer 4 exposed everything through document.all, Netscape Navigator 4 through document.layers — so that any page doing anything real contained two implementations of itself.

What's still broken: there is no single, agreed-upon, complete model of the page that a program can address. You can reach a few named collections that someone thought to expose, in two mutually incompatible dialects, and nothing else.

Node 1 — The page as a tree of live objects

The limitation: a program needs to address any part of the page, not a handful of collections someone chose in advance, and it needs to do so the same way in every browser.

The W3C published DOM Level 1 as a Recommendation in October 1998. Its core idea is the one that everything after it depends on: when the browser parses HTML, it does not just draw it — it builds an object graph in memory that mirrors the structure of the markup, and it exposes that graph to JavaScript. That graph is the Document Object Model. [EXPLAIN]

The word "model" is doing real work there, and it is worth being precise about what the relationship is. The HTML you wrote is a string of text. It is parsed exactly once, and after that it is gone as far as the running page is concerned. What remains is the tree of objects. Every one of those objects is a real JavaScript-reachable object with properties and methods. When you change one, the browser notices and eventually redraws. The DOM is not the HTML, and it is not the pixels — it is a live object graph sitting between them. This single sentence resolves an enormous number of confusions later in the chain, so it is worth holding onto.

The tree is made of nodes, and nodes come in kinds. An element node corresponds to a tag — <p>, <div>, <input>. A text node holds a run of characters. A comment node holds a comment. There is a document node at the very top, which is not an element and has no tag, and which you reach through the global document. Sitting under it is exactly one root element node, <html>, reachable as document.documentElement, with document.head and document.body beneath that. Each node knows its parent, its children in order, and its siblings. [EXPLAIN]

Two things about this tree surprise people, and both matter later. First, the tree the browser builds is not necessarily the tree your markup described. The HTML parser is defined to repair broken markup — it closes tags you left open, it moves a stray <div> out of a <table>, it silently drops a <p> inside a <p>. What you get is the result of that repair. Second, whitespace between tags becomes real text nodes. If you write a <ul> with each <li> on its own line, the <ul> has text nodes between its list items containing newlines and spaces. They are invisible on screen and completely real in the tree.

What you can do at this point: you can describe, accurately, what the browser is holding in memory while a page is open, and why "the DOM" is a different thing from "the HTML file."

What's still broken: you know a tree of objects exists and you have a handle on its root, but reaching a specific node deep inside it means walking down from document by hand, child by child, which is unusable for anything real.

Node 2 — Finding a node

The limitation: you have the root of a tree and no practical way to get hold of the one node you actually care about.

The first answer, in DOM Level 1, was to look things up by identity or by kind. document.getElementById(id) returns the single element whose id attribute matches, or null. It is the oldest and still the fastest lookup in the DOM, because browsers maintain an internal map from id to element rather than searching. document.getElementsByTagName(name) and, added later, getElementsByClassName(name) return every matching element. [USE]

Those two plural methods return an HTMLCollection, and it has a property that catches people out permanently: it is live. It is not a snapshot of the matches at the moment you called the method — it is a standing query. If you hold a collection of every <li> on the page and then append another <li>, the collection you are holding now has one more item in it, without you doing anything. This produces one of the classic infinite loops in web programming: iterating a live collection with an index while appending to the same collection inside the loop, so the collection grows exactly as fast as the index advances. [EXPLAIN]

The real breakthrough was the Selectors API, which browsers began shipping in Safari 3.1 in 2008 and Internet Explorer 8 in 2009, and which the W3C made a Recommendation in February 2013. It exposes querySelector(selector) — the first element matching a CSS selector, or null — and querySelectorAll(selector) — all of them. [EXPLAIN] The significance is not convenience. It is that the same language you already use to describe which elements a style applies to now describes which elements a script operates on. document.querySelector('nav.primary > ul li:last-child a[href^="/docs"]') requires no new vocabulary from anyone who has written CSS. This is the single API that made jQuery's core selling point redundant, roughly a decade after jQuery 1.0 shipped in August 2006.

querySelectorAll returns a NodeList, and the NodeList it returns is static — a snapshot taken at the moment of the call, which will not change when the document does. So the DOM contains both live collections and static ones, returned by methods that look superficially similar, and knowing which is which is not optional. A NodeList from querySelectorAll has forEach, but it is not an array; map and filter are absent, which is why Array.from(...) or [...nodeList] appears constantly in real code. Meanwhile element.children is a live HTMLCollection with no forEach at all. [USE]

One more thing about these methods that is genuinely important: they work from any element, not only from document. container.querySelectorAll('.row') searches only inside container. Every selection method except getElementById is available on elements as well as on the document, and scoping searches to a subtree is both faster and far less fragile than searching the whole page.

What you can do at this point: get a reliable handle on any element on the page, by id, by class, by tag, or by any CSS selector, scoped to any subtree.

What's still broken: selectors describe patterns of elements. They cannot express "the node immediately after this one whatever it is," they cannot reach text nodes or comments at all, and given one node they cannot answer questions about its position among its neighbours.

Node 3 — Walking the tree

The limitation: selection finds elements matching a pattern. It does not let you move relative to a node you already have, and it cannot see the non-element parts of the tree at all.

Every node exposes its relationships directly. parentNode, childNodes, firstChild, lastChild, nextSibling, previousSibling — this is the DOM Level 1 vocabulary, and it walks all nodes, text and comments included. Because whitespace between tags is a text node, this vocabulary is nearly always the wrong one when you actually mean elements. [USE]

So a parallel element-only vocabulary was added: parentElement, children, firstElementChild, lastElementChild, nextElementSibling, previousElementSibling. These skip text and comments entirely. Almost all application code wants these. The reason both sets exist is that the DOM has to describe documents in general, where text nodes are the content and not an accident of formatting. [EXPLAIN] The one asymmetry worth memorising: parentNode and parentElement are the same thing for every element except the root <html>, whose parentNode is the document node and whose parentElement is null, because the document is not an element.

Each node also carries nodeType — a small integer, where 1 is an element, 3 is a text node, 8 is a comment, and 9 is the document itself. Those numbers are historical and arbitrary; they are just the order things were enumerated in the 1998 spec. Modern code rarely tests them directly, preferring instanceof Element or checking tagName, but you will read them in older code and in library internals. [AWARE]

Then there is the method that quietly changed how event handling is written: element.closest(selector), shipped in Chrome 41 in 2015. It walks upward from an element through its ancestors and returns the first one matching the selector, including the element itself. It is the inverse of querySelector, and Node 8 will show why it turned out to be structurally important rather than merely handy. [EXPLAIN] Its companions are matches(selector), which asks "does this element match this selector," and contains(other), which asks "is this node an ancestor of that one."

For the rare case of needing to visit every node of a certain kind in document order, there is TreeWalker and NodeIterator, created via document.createTreeWalker(root, whatToShow, filter). They exist mainly for text processing — a find-and-highlight feature, a text extractor, a spellchecker. Most application code goes an entire career without one. [AWARE]

What you can do at this point: navigate from any node to any related node, in either direction, distinguishing between the element view of the tree and the full-node view.

What's still broken: you can reach any node in the document and you still cannot change a single character of what it says.

Node 4 — Changing what a node says

The limitation: reaching a node is worthless if the node is read-only.

There are three ways to set the content of an element, they behave very differently, and choosing wrongly is how a large fraction of web vulnerabilities happen.

textContent gets or sets the raw text of an element and all its descendants, treating everything as literal characters. Setting it discards every child node and replaces them with a single text node. If the string you assign contains <script>, the element ends up displaying the characters <script> on screen; nothing is parsed and nothing executes. This is the correct default for anything that came from a user, a database, or an API. [EXPLAIN]

innerHTML gets or sets the content as markup. Assigning to it invokes the HTML parser on your string, builds a subtree from the result, and replaces the element's children with it. This is genuinely useful and genuinely dangerous. It was invented by Microsoft for Internet Explorer 4 in 1997, was so obviously convenient that everyone copied it, and was standardised long afterwards. Its danger is direct: el.innerHTML = userInput means any HTML in userInput becomes real nodes in your page, which is the definition of a cross-site scripting vulnerability. It is worth knowing precisely, because interviewers ask it, that innerHTML will not run a <script> tag inserted this way — the HTML spec explicitly disables that — but this provides almost no protection, because <img src=x onerror="..."> works perfectly and there are dozens of equivalents. [EXPLAIN]

innerText is the third, and it is different from textContent in a way that has a real performance consequence. textContent returns what is in the tree, including text inside display: none elements, with the source's whitespace intact. innerText returns what is rendered — approximately what you would get by selecting the element with a mouse and copying. It respects display: none, collapses whitespace the way CSS does, and inserts line breaks where block elements create them. To produce that answer, the browser may have to compute layout, which makes reading innerText potentially expensive in a way reading textContent never is. Node 12 explains why that matters. [EXPLAIN]

Text nodes themselves have nodeValue and data, and can be manipulated with appendData, insertData, splitText. Direct text-node surgery is rare in application code and central in editors. [AWARE]

What you can do at this point: read and replace the visible content of any element, and state correctly which of the three properties is safe for untrusted input and why.

What's still broken: content is only part of what an element is. A checkbox's checkedness, a link's destination, a button's disabledness, an element's classes and inline styling are not content, and none of them are reachable yet.

Node 5 — Attributes, properties, classes and inline style

The limitation: an element's configuration and state live outside its content, and the two are not the same thing.

Here is the distinction that trips up more people than any other in this topic. Attributes are what was written in the HTML. Properties are fields on the JavaScript object. They are two different storage locations that the browser keeps loosely synchronised, and the rules of that synchronisation are not uniform. [EXPLAIN]

getAttribute(name), setAttribute(name, value), removeAttribute(name), and hasAttribute(name) operate on the attribute side. Attribute values are always strings — setAttribute('disabled', false) sets the attribute to the string "false", which is truthy in HTML's boolean-attribute rules, so it disables the element. Property access — el.id, el.href, el.disabled — operates on the object side, and properties have real types: el.disabled is a genuine boolean, el.hidden is a boolean, el.tabIndex is a number.

Most attributes reflect: change one side and the other follows. Some reflect with transformation — the attribute href="/docs" reflects into the property el.href as the fully resolved absolute URL, https://example.com/docs, which is why comparing el.href to a relative path never matches. And some deliberately do not stay in sync at all. The important case is form fields: input.value is the current value, and the value attribute is only the initial value. Once a user types into a field, input.value reflects what they typed and input.getAttribute('value') still returns what the HTML said. The same split exists for checked versus the checked attribute, and it is exactly why defaultValue and defaultChecked exist as properties: to give you a name for the attribute-side value. [EXPLAIN] This is not a quirk to be memorised in isolation — it is the reason React distinguishes controlled from uncontrolled inputs, and it is worth carrying forward to Node 19.

For your own data, data-* attributes and the dataset property are the sanctioned mechanism. <div data-user-id="42" data-role="admin"> becomes el.dataset.userId and el.dataset.role, with the kebab-case-to-camelCase conversion done for you. Everything in dataset is a string. [USE]

Classes have their own API because string manipulation of className was error-prone in exactly the ways you would expect. classList — shipped around 2010–2011 and standardised with HTML5 — gives add, remove, toggle, contains, replace, and accepts multiple arguments. classList.toggle('open', isOpen) with a second boolean argument is the form worth remembering, because it sets rather than flips. [USE]

Inline style is reachable through element.style, which maps to the element's style attribute and nothing else. This is the single most common misunderstanding about styling from JavaScript: element.style.color reads the inline style only. If the colour came from a stylesheet, element.style.color is the empty string. To read the value actually in effect you need getComputedStyle(element), which returns the fully resolved value after every stylesheet, cascade rule, and inheritance has been applied — and which, because it may require layout to be up to date, is not free to call. [EXPLAIN] Property names are camelCased (backgroundColor), except CSS custom properties, which keep their literal names and need style.setProperty('--accent', 'tomato') and getComputedStyle(el).getPropertyValue('--accent').

What you can do at this point: fully configure any existing element — its state, its identity, its data, its classes, its inline style — and explain why the value in a text input disagrees with the HTML that produced it.

What's still broken: everything so far modifies elements that already exist. An interface that grows — a list that gains rows, a dialog that appears, a table rendered from fetched data — needs nodes that were never in the original HTML.

Node 6 — Creating, inserting, moving and removing nodes

The limitation: you can only edit what the server already sent.

document.createElement(tagName) makes a new element node. It exists, it is a real object you can configure, and it is not in the document. It has no parent, occupies no space, and is invisible. This separation — construction and insertion as two distinct steps — is deliberate, and it is what makes it possible to build a subtree completely before the user ever sees a partial version of it. document.createTextNode(text) does the same for text. [EXPLAIN]

Insertion in DOM Level 1 was parent.appendChild(node) and parent.insertBefore(node, referenceNode), with removeChild and replaceChild alongside. These work everywhere and are verbose, and insertBefore requires you to have a reference to the node you want to precede, which frequently means computing nextSibling first. In 2016 — Chrome 54 in October, Firefox 49 in September — browsers shipped a much better set: append, prepend, before, after, replaceWith, and remove. el.remove() needs no reference to the parent. append and its siblings accept multiple arguments and accept plain strings, which are turned into text nodes automatically and safely. [USE]

The property that people consistently do not expect: a node has exactly one parent, so inserting a node that is already in the document moves it rather than copying it. There is no "insert" that duplicates. If you want a copy you ask for one with cloneNode(deep), where deep controls whether descendants come along — and where the copy does not carry the original's event listeners, because listeners are not part of the node's data. [EXPLAIN]

Doing this in a loop raises a real cost. Every insertion into the live document is a change the browser must eventually account for. document.createDocumentFragment() gives you a lightweight, parentless container: append a thousand rows into the fragment, then append the fragment once, and the fragment dissolves, delivering its children in a single operation. [USE] The <template> element serves a related purpose from the HTML side — its contents are parsed but inert, not rendered, not executed, and are cloned into place when needed.

insertAdjacentHTML(position, htmlString) parses a string of markup and inserts it at one of four positions — 'beforebegin', 'afterbegin', 'beforeend', 'afterend' — without destroying and rebuilding the element's existing children the way innerHTML += does. That += pattern is worth calling out as a trap in its own right: it serialises the entire existing subtree to a string, concatenates, reparses the whole thing, and throws away every existing node — which silently destroys any event listeners, any form state, and any node references you were holding. [EXPLAIN]

What you can do at this point: build any structure programmatically and place it anywhere, and construct a list of a thousand rows without a thousand separate document mutations.

What's still broken: all of this is one-directional. Your script decides when things happen. The page still cannot respond to a person — nothing here reacts to a click, a keystroke, a scroll, or a form submission.

Node 7 — Events

The limitation: the page can be changed by a program, and cannot yet be driven by a user.

An event is an object the browser creates when something notable happens and delivers to code that asked to hear about it. This is the point at which the DOM stops being a document API and becomes the foundation of user interfaces. [EXPLAIN]

The original mechanism was DOM Level 0's handler properties and inline attributes: <button onclick="doThing()"> and el.onclick = fn. Both work and both have a fatal structural limit — there is one slot. Assigning el.onclick a second time silently replaces the first handler. Two independent pieces of code cannot both listen to the same event on the same element, which is untenable the moment a page contains more than one author's work. Inline onclick attributes have the additional problem of being strings evaluated as code in the global scope, which is precisely what a Content Security Policy exists to forbid. [AWARE]

DOM Level 2 Events, a W3C Recommendation in November 2000, replaced this with addEventListener(type, handler, options) and removeEventListener. Any number of listeners can coexist on one element for one event type. [EXPLAIN] The handler receives an event object whose shape depends on the kind of event — a MouseEvent carries clientX, clientY, button, and the modifier-key flags; a KeyboardEvent carries key, code, repeat; an InputEvent carries data. Every event carries type, target, currentTarget, and timeStamp.

removeEventListener has a requirement that is a genuinely common source of leaks: it must be given the same function reference that was added. Passing an inline arrow function to addEventListener and then another inline arrow function to removeEventListener removes nothing, because they are two different function objects. Named references, or the signal option from Node 15, are the two ways out. [EXPLAIN]

The third argument grew over time from a bare boolean into an options object: once: true removes the listener automatically after it fires; passive: true promises the handler will not call preventDefault; capture: true is the subject of Node 8; and signal takes an AbortSignal, added to addEventListener in Chrome 90 in April 2021, which is now the cleanest teardown mechanism available. [USE]

passive deserves its own explanation, because it is one of the rare API flags whose entire purpose is a performance guarantee. A touchstart or wheel handler is allowed to cancel scrolling. That means the browser, on receiving the input, must wait for your handler to finish before it knows whether it may scroll — so a slow handler stalls scrolling itself. Declaring passive: true tells the browser in advance that you will not cancel, so it scrolls immediately and runs your handler independently. This mattered enough that Chrome 56, in January 2017, made touchstart and touchmove listeners on document passive by default, changing existing behaviour on the live web. [EXPLAIN]

You can also create and dispatch your own: new CustomEvent('cart:updated', { detail: {...}, bubbles: true }) followed by el.dispatchEvent(event). This is the native mechanism for one part of a page telling another that something happened, without either holding a reference to the other. [USE]

What you can do at this point: make any element respond to any user action, with as many independent listeners as needed, and clean them up correctly.

What's still broken: a listener is attached to one specific element. A table with five hundred rows means five hundred listeners, and rows added after the listeners were attached have none at all.

Node 8 — Propagation, delegation and the path an event takes

The limitation: one listener per element does not scale, and cannot cover elements that do not exist yet.

An event does not fire at one element. It travels a path, and it travels it in three phases. The browser first computes the chain from the document down to the deepest element the event concerns. Then, in the capture phase, it walks down that chain from the root, offering the event to each ancestor in turn. At the deepest point it is the target phase. Then, in the bubble phase, it walks back up to the root, offering the event to each ancestor again. [EXPLAIN]

By default addEventListener registers for the bubble phase. Passing capture: true registers for the downward pass instead. Both directions exist because Netscape and Microsoft implemented opposite models in the browser wars, and DOM Level 2 resolved the argument by specifying both and letting the developer choose.

This gives you the single most important pattern in DOM event handling: event delegation. Instead of a listener per row, put one listener on the table. Every click inside it bubbles up and arrives there. Ask the event which element it originated from, decide whether you care, and act. [EXPLAIN]

table.addEventListener('click', (e) => {
  const btn = e.target.closest('button.delete');
  if (!btn || !table.contains(btn)) return;
  removeRow(btn.closest('tr'));
});

That is where closest() from Node 3 earns its place. e.target is the deepest element the user actually hit — which may be an icon or text span inside the button, not the button itself — so matching on e.target alone is fragile, and closest walks up until it finds the thing you meant. One listener now handles every row, including every row added at any point in the future, because the listener was never attached to the rows in the first place.

Two properties on the event carry the distinction the pattern depends on. e.target is where the event originated and does not change as the event travels. e.currentTarget is the element whose listener is currently running, and changes at each step of the path. Inside a delegated handler, currentTarget is the table and target is whatever was clicked. e.currentTarget is also this in a non-arrow handler. [EXPLAIN]

Two methods control the journey, and they do different things that are constantly confused. stopPropagation() stops the event travelling further along the path — ancestors will not hear it. stopImmediatePropagation() additionally prevents other listeners on the same element from running. preventDefault() does not affect the journey at all; it cancels the browser's own built-in response, which is Node 9. [EXPLAIN] Calling stopPropagation as a reflex is a real and common bug, because it breaks every delegated listener above it — including analytics, dropdown-close handlers, and framework internals — for reasons that are invisible at the call site.

Not everything bubbles. focus and blur do not; focusin and focusout are their bubbling equivalents and exist precisely for delegation. load, error, and scroll on an element do not bubble either. Whether an event bubbles is on the event itself as e.bubbles. [USE]

What you can do at this point: handle events for an entire dynamic region with a single listener, correctly identify what was interacted with, and explain the full three-phase path an event takes.

What's still broken: stopping an event from travelling does nothing about what the browser itself does in response. A form still submits and reloads the page, a link still navigates away, and everything your script just did is discarded.

Node 9 — Default actions, forms and input

The limitation: the browser has built-in reactions to certain events, and propagation control does not touch them.

For a set of events, the browser has a native behaviour that runs after listeners unless it is cancelled. A click on an <a href> navigates. A submit on a form serialises the fields and issues a request. A keydown of Tab moves focus. A contextmenu opens the context menu. preventDefault() cancels that native behaviour, and only that. [EXPLAIN] An event with cancelable: false cannot be cancelled at all — scroll is the notable one, which is why scroll cannot be prevented from a scroll listener and must be prevented at its source, on wheel or touchmove, or with CSS.

This is where the whole single-page-application model begins. Cancel the form's default submission, read the values yourself, send them with fetch, and update the DOM with the response. The page never reloads. Everything Node 0 described as broken is fixed at exactly this line of code.

Forms have a rich and frequently underused API. FormData — new FormData(formElement) — collects every named control's current value, handles file inputs and multi-select correctly, and can be passed straight to fetch as a body. [USE] The constraint validation API exposes the browser's own validation: input.validity is a ValidityState object with flags like valueMissing, typeMismatch, patternMismatch, tooShort, rangeOverflow; input.checkValidity() tests silently; input.reportValidity() tests and shows the browser's message; and input.setCustomValidity(message) makes your own rule participate in native validation rather than sitting beside it. [USE]

The input events are worth separating precisely, because using the wrong one produces a subtly wrong interface. input fires on every change to the value, as it happens. change fires when the value is committed — on blur for text fields, immediately for checkboxes, radios, and selects. keydown and keyup fire for physical keys and tell you nothing reliable about the resulting text, because a key press may produce no character, an IME may produce a character from several key presses, and a paste produces text with no key press at all. The rule that follows from this: if you care about the value, listen to input; if you care about the key, listen to keydown. keypress is deprecated and should not appear in new code. [EXPLAIN]

Keyboard events carry e.key, the character or named key produced ("a", "Enter", "ArrowLeft"), and e.code, the physical key position regardless of layout ("KeyA"). Shortcuts generally want key; games and layout-independent bindings want code. e.keyCode is deprecated and inconsistent. [USE]

Beyond forms, the same default-action machinery underlies the clipboard events (copy, cut, paste, with e.clipboardData), the drag-and-drop events (dragstart through drop, where dragover must have its default prevented or drop never fires — a genuinely notorious gotcha), and pointer events (pointerdown, pointermove, pointerup), which unify mouse, touch, and stylus into one model and are what new code should use in place of separate mouse and touch handling. [USE]

What you can do at this point: intercept and replace every native browser behaviour, build a form that submits without reloading, and choose the correct event for text, keys, and commitment.

What's still broken: form controls are a fixed vocabulary — text, checkbox, radio, select, file. Anything richer, where a user selects a span of text across elements and applies formatting to it, is outside what any of this addresses.

Node 10 — Selection, ranges and editable content

The limitation: the user's own position in the document — where the caret is, what is highlighted — is state you cannot see or set with anything covered so far.

A Range is a pair of boundary points in the tree — a start node with an offset, and an end node with an offset — describing a contiguous stretch of content that may cross element boundaries. It is the DOM's model of "from here to there," and it does not care that "here" is halfway through a text node inside a <strong> and "there" is inside a different paragraph. Ranges can be created programmatically with document.createRange(), and they can be extracted, deleted, surrounded, or cloned. [AWARE]

A Selection, reached with window.getSelection(), is what the user has highlighted, expressed as one or more ranges. selection.toString() gives the highlighted text; selection.getRangeAt(0) gives the range; selection.removeAllRanges() and addRange() set it. The selectionchange event fires as it changes. [AWARE]

The contenteditable attribute turns any element into an editable region, at which point the browser gives you caret handling, selection, and — through the long-deprecated document.execCommand — a set of built-in formatting operations. This is how every rich-text editor on the web is built, and it is also famously the least consistent corner of the platform: what markup each browser produces for the same operation has historically differed enough that serious editors (ProseMirror, Slate, Lexical) maintain their own document model and treat contenteditable purely as an input surface, reconciling what the browser did back into their model on every change. [AWARE] You should know this exists and know why editors are built the way they are; you should not build one from scratch.

What you can do at this point: read and manipulate what the user has selected, and explain why rich-text editing on the web is hard.

What's still broken: an editor needs a formatting toolbar that appears next to the selection. Nothing so far can answer where anything is on screen.

Node 11 — Geometry and scrolling

The limitation: the DOM as described is a tree with no coordinates. You cannot position anything relative to anything.

element.getBoundingClientRect() returns the element's rectangle — top, right, bottom, left, width, height, x, y — in viewport coordinates, meaning relative to the visible window, not the document. It accounts for transforms and is the single geometry method worth knowing cold. Because it is viewport-relative, it changes as the user scrolls, and converting to document coordinates means adding window.scrollX and window.scrollY. [EXPLAIN]

The older offset* / client* / scroll* properties are integers and answer narrower questions. offsetWidth/offsetHeight include padding, border, and scrollbar. clientWidth/clientHeight include padding but exclude border and scrollbar. scrollWidth/scrollHeight are the full size of the content including what is scrolled out of view. offsetTop/offsetLeft are relative to offsetParent, the nearest positioned ancestor — which makes them awkward and layout-dependent. scrollTop/scrollLeft are how far an element is scrolled, and they are writable, which is how you scroll something programmatically. [USE]

The reliable summary a developer actually uses: scrollHeight - scrollTop - clientHeight is how far from the bottom a scrolling element is, which is the entire basis of infinite scroll and "scrolled to bottom" detection.

For moving the viewport there is window.scrollTo({ top, behavior: 'smooth' }), window.scrollBy, and element.scrollIntoView({ behavior, block, inline }). scrollIntoView is the one to reach for, because it does the arithmetic for you and handles nested scroll containers. [USE]

Two numbers worth explaining rather than memorising. window.devicePixelRatio is how many physical screen pixels one CSS pixel occupies — 1 on an old monitor, 2 or 3 on a modern phone or a Retina display — and it exists because CSS pixels are a unit of apparent size, not of hardware. And visualViewport, a separate object, describes the actually visible region on mobile when the on-screen keyboard or pinch-zoom is in play, which the ordinary window dimensions do not reflect. [AWARE]

What you can do at this point: position a floating element next to any other element, implement infinite scroll, and know precisely which box each measurement includes.

What's still broken: every one of these reads is expensive in a way nothing so far has explained, and mixing them with the writes from Nodes 4 through 6 can make a perfectly correct interface unusably slow.

Node 12 — What a mutation actually costs

The limitation: you now write to the DOM and read geometry from it, and you have no model of what either costs.

When something changes, the browser runs a pipeline. It recalculates style — which CSS rules now apply to which elements. It performs layout (also called reflow) — computing the position and size of every affected box. It paints — filling in pixels for each layer. And it composites — assembling the layers into the final frame. Each stage is more expensive than the one after it in terms of how much it can invalidate, and layout is the one that most often becomes a problem. [EXPLAIN]

Crucially, the browser does not run this pipeline on every DOM write. It batches. You can append a hundred nodes and change fifty styles inside one function, and the browser will queue all of it and do the work once, before the next frame is painted. This is why naive "DOM writes are slow" advice is misleading — the writes themselves are cheap; the pipeline is what costs, and it normally runs once.

Unless you force it. Reading certain properties requires an answer the browser cannot give from stale data. If you have pending changes queued and you then ask for getBoundingClientRect(), offsetHeight, scrollTop, getComputedStyle(...), or innerText, the browser must run layout right now to answer truthfully. This is a forced synchronous layout. One is fine. The problem is the loop:

// Pathological: forces a full layout on every iteration.
for (const el of items) {
  el.style.height = el.offsetHeight * 2 + 'px';  // read, then write, then read...
}

Each write invalidates layout; each read forces it to be recomputed. A hundred items means a hundred full layouts instead of one. This is layout thrashing, and the fix is to separate the phases — read everything first, then write everything — which turns N layouts into one. [EXPLAIN] This is the single highest-value performance concept in the whole topic and it is asked about in interviews constantly.

The frame budget is where the numbers come from. A display refreshing at 60Hz gives roughly 16.7 milliseconds per frame — one second divided by sixty. Everything for that frame, including your JavaScript, style, layout, paint, and composite, has to fit inside it or a frame is dropped and the interface visibly stutters. [EXPLAIN]

requestAnimationFrame(callback) — available since Chrome 10 and Firefox 4 in 2011 — schedules a callback to run just before the next paint. It is the correct place for visual updates, because it aligns your work with the browser's own rhythm rather than fighting it, and it stops entirely when the tab is hidden, which setInterval does not. [USE] Its counterpart, requestIdleCallback (Chrome 47), schedules non-urgent work for whatever time is left over.

Which CSS properties you animate matters for the same reason. Animating left or width changes layout on every frame. Animating transform and opacity can usually be handled entirely by the compositor, skipping layout and paint altogether, which is why every performance guide says to prefer them. [EXPLAIN]

What you can do at this point: explain why an interface stutters, identify layout thrashing in a code review, and structure DOM work so the pipeline runs once.

What's still broken: you know when you change the DOM. You do not know when the browser or the user changes something you care about — an element scrolling into view, a container resizing, another script mutating your subtree — and the only tool so far is to poll on an interval, which is exactly the frame-budget disaster just described.

Node 13 — Observers

The limitation: detecting changes you did not cause requires polling, and polling in a scroll or resize handler runs on the main thread at exactly the moments the main thread is busiest.

The DOM's answer is a family of observers: objects you construct with a callback, point at a target, and leave running. They deliver batched, asynchronous notifications, and — this is the point — the work of detecting the condition happens inside the browser rather than in your code on every scroll event. [EXPLAIN]

IntersectionObserver (Chrome 51, May 2016) tells you when an element enters or leaves a viewport or another element, at thresholds you specify. It replaces the entire genre of scroll handlers calling getBoundingClientRect on every element to decide what is visible. Lazy-loading images, infinite scroll, "which section is the reader in" navigation highlighting, and impression tracking are all one-liners with it and all layout-thrashing disasters without it. rootMargin lets you fire early — loading an image 200 pixels before it becomes visible. [EXPLAIN]

ResizeObserver (Chrome 64, January 2018) tells you when a specific element changes size, for any reason — window resize, a sibling growing, content changing, a CSS change. Before it existed there was no way to know an element had resized unless the window did, which meant component-level responsive behaviour was genuinely impossible. [USE] Its callback runs at a defined point in the frame lifecycle, and a callback that resizes the element it observes can loop, which the browser detects and reports as a "ResizeObserver loop limit exceeded" error.

MutationObserver (Chrome 18, 2012) tells you when the DOM tree itself changes — children added or removed, attributes changed, text modified — under a subtree you specify. It replaced Mutation Events, a DOM Level 2 feature deprecated in 2011 because they fired synchronously on every single change and could make a page an order of magnitude slower. MutationObserver delivers a batch of records asynchronously, after the current task finishes. In application code it is a last resort, used mostly when you must react to a third-party script's changes; in extensions and tooling it is everywhere. [USE]

PerformanceObserver delivers timing entries — including the Largest Contentful Paint, Cumulative Layout Shift, and Interaction to Next Paint measurements that make up Core Web Vitals. [AWARE]

All four share a shape: new XObserver(callback), then .observe(target, options), and — importantly — .disconnect(), which Node 15 will insist on.

What you can do at this point: react to visibility, size, and structural change without polling, and explain why a scroll listener that measures elements is the wrong tool.

What's still broken: every technique so far assumes your code runs at a moment when the nodes it needs already exist. Nothing has said when that is, and getting it wrong makes correct code fail with null.

Node 14 — When your script runs

The limitation: document.querySelector('#thing') returning null is the most common beginner failure in the entire topic, and it is a timing problem, not a selector problem.

The HTML parser works through the document top to bottom, building the tree as it goes. When it reaches a classic <script> tag, it stops — parsing halts, the script is fetched if external, then executed, and only then does parsing resume. This is called parser-blocking, and it is why a script in <head> runs before the <body> exists, and therefore why every element it looks for is null. [EXPLAIN] The reason for this behaviour, rather than it being an oversight, is document.write: a script was historically allowed to inject markup at its own position in the stream, so the parser could not safely run ahead.

There are three modern positions, and they should be understood as a set. A script at the end of <body> runs after everything above it is parsed — the old reliable fix. <script defer> downloads in parallel with parsing and executes after parsing completes, with multiple deferred scripts running in document order. <script async> downloads in parallel and executes the moment it arrives, at an unpredictable time and in unpredictable order relative to other scripts. <script type="module"> is deferred by default. For anything touching the DOM, defer or a module is the right answer; async suits only independent scripts like analytics. [EXPLAIN]

Two events mark the milestones and the distinction is asked about frequently. DOMContentLoaded fires when the HTML has been fully parsed and all deferred scripts have run — the tree is complete. load fires later, when every subresource, including images and stylesheets and iframes, has finished. Waiting for load to initialise an interface is a common and unnecessary delay, sometimes of seconds. document.readyState reports the same progression as 'loading', 'interactive', 'complete', and checking it matters because a listener added for DOMContentLoaded after it has already fired will never run. [EXPLAIN]

What you can do at this point: guarantee your code runs at a point where the nodes it needs exist, and choose script loading strategy deliberately rather than by superstition.

What's still broken: everything that has been attached, observed, and created now stays attached forever. In a page that navigates without reloading, that accumulates.

Node 15 — Detachment, leaks and teardown

The limitation: in a single-page application the document outlives every view rendered into it, and nothing so far has removed anything.

JavaScript reclaims an object when nothing can reach it any more. A DOM node removed from the document is not automatically reclaimed if something still holds a reference — and several things routinely do. A node removed from the tree but still referenced is a detached node, and a growing set of detached nodes is the classic memory profile of a leaking SPA. [EXPLAIN]

The reference chains that cause it are worth knowing by name. An event listener on document or window whose handler closes over a component's nodes keeps that entire subtree alive after the component is gone, because the listener is reachable from a global object. An observer that was never disconnect()ed keeps its targets alive the same way. An interval from setInterval that was never cleared keeps its callback, and everything the callback closes over, alive indefinitely — and unlike requestAnimationFrame, it keeps running in a hidden tab. And an array or map of nodes kept as a cache holds every one of them.

Cleanup is therefore not optional bookkeeping, it is a correctness requirement: remove listeners, disconnect observers, clear timers, and drop node references. The modern mechanism that makes this tractable is AbortController. Create one controller per component, pass { signal: controller.signal } to every addEventListener call, and one controller.abort() removes all of them at once, with no need to keep function references around. [EXPLAIN]

const ac = new AbortController();
window.addEventListener('resize', onResize, { signal: ac.signal });
el.addEventListener('click', onClick, { signal: ac.signal });
// teardown, all of it:
ac.abort();

This is exactly what a React useEffect cleanup function or a framework's onDestroy hook is for, and recognising that is what makes those hooks make sense rather than being ritual. Chrome DevTools' Memory → Heap snapshot with the "Detached" filter is how you find these in practice. [USE]

What you can do at this point: build interfaces that create and destroy views repeatedly without growing, and explain what a framework's cleanup hook is actually cleaning up.

What's still broken: even with perfect teardown, everything shares one namespace. Ids collide, a stylesheet from anywhere can restyle anything, and a component genuinely cannot be dropped into an unknown page and be sure of how it will look.

Node 16 — Encapsulation: shadow DOM and custom elements

The limitation: the document is one flat global scope for ids and for CSS, and a reusable component has no way to defend itself.

Shadow DOM attaches a second, separate tree to an element: el.attachShadow({ mode: 'open' }) returns a shadow root, and nodes placed inside it render in the element's place while being invisible to ordinary selectors from outside. document.querySelectorAll('.title') does not reach into a shadow tree. Styles defined inside a shadow root do not leak out, and page styles do not leak in — with deliberate exceptions for inherited properties like color and font-family, and for CSS custom properties, which pass through and are therefore the sanctioned theming mechanism. [EXPLAIN] The mode option, 'open' or 'closed', controls whether el.shadowRoot is accessible from outside; 'closed' is not a security boundary and is rarely worth it.

<slot> elements inside a shadow tree mark where the element's own children — its light DOM — should appear. This is the mechanism behind the difference between the tree you wrote and the tree that renders, and element.assignedSlot and slot.assignedNodes() navigate between them.

Custom Elements complete the picture: customElements.define('user-card', class extends HTMLElement { ... }) registers a new tag that the parser and every DOM API treat as a first-class element. The class gets lifecycle callbacks — connectedCallback when it is inserted into the document, disconnectedCallback when removed (the natural home for the teardown from Node 15), attributeChangedCallback when an observed attribute changes, and adoptedCallback when moved between documents. [USE] Custom Elements v1 and Shadow DOM v1 shipped in Chrome 54 in 2016, Safari 10.1 in 2017, and Firefox 63 in 2018, with the earlier v0 designs abandoned.

Together these are Web Components, and an honest assessment matters more than a feature list. They are genuinely the right tool for a design system consumed by teams using different frameworks, and for widgets embedded into pages you do not control. They are used far less than their promise suggested, because most product teams already have a framework whose component model is more ergonomic, and because shadow boundaries complicate global styling, form participation, and server rendering. Know what they solve and be honest about the trade-off. [AWARE]

Shadow boundaries also change event behaviour in a way worth naming: an event crossing out of a shadow tree is retargeted, so e.target becomes the host element rather than the internal node, preserving encapsulation. e.composedPath() gives the full path when you need it. [AWARE]

What you can do at this point: build a component that cannot be broken by the page it lands in, and explain why teams do or do not choose that trade-off.

What's still broken: a <div> styled to look and behave like a button is, to a screen reader or a keyboard user, still a <div>. Encapsulation guaranteed the visual result and guaranteed nothing about whether the thing is usable.

Node 17 — The accessibility tree, focus and semantics as DOM state

The limitation: what an element looks like and what an element is have come apart, and only the appearance was ever specified.

Alongside the DOM, the browser maintains an accessibility tree — a parallel structure, derived from the DOM, exposing each node's role, name, value, and state to assistive technology through the operating system. A screen reader does not read your CSS. It reads that tree. [EXPLAIN] Native elements populate it correctly for free: <button> has the button role, is focusable, is activated by Enter and Space, and takes its name from its text content. A <div onclick> has none of that.

Focus is DOM state you can read and write. document.activeElement is the currently focused element. el.focus() and el.blur() move it. Only certain elements are focusable by default — links with href, form controls, buttons, and anything with tabindex. tabindex="0" puts an element in the natural tab order; tabindex="-1" makes it focusable programmatically but skipped by Tab, which is what you use for a dialog container you want to move focus into; and positive tabindex values are essentially always a mistake, because they override document order globally and produce a tab sequence nobody can predict. [EXPLAIN]

ARIA attributes are how you describe a non-native widget to the accessibility tree: role="tablist", aria-expanded="true", aria-selected, aria-label, aria-describedby, aria-live. They are ordinary DOM attributes, set with setAttribute like anything else, and keeping them synchronised with your visual state is a normal part of DOM manipulation rather than a separate discipline. The most-quoted rule of ARIA is the honest one: no ARIA is better than bad ARIA — an incorrect role actively misleads, where a plain <div> merely says nothing. And the first rule of ARIA is to not need it: use the native element. [EXPLAIN]

Two behaviours to know for anything modal. Focus must move into a dialog when it opens and return to the trigger when it closes, and it must be trapped inside while open — otherwise a keyboard user tabs into the page behind. The inert attribute (Chrome 102 in 2022, Safari 15.5, Firefox 112 in 2023) makes an entire subtree unfocusable and invisible to assistive tech, which is the native answer to that problem. <dialog> with showModal() does the focus handling, the inerting, and the Escape key for you, and is the correct default. [USE]

What you can do at this point: build a custom widget that is genuinely operable by keyboard and screen reader, and explain what a screen reader is actually reading.

What's still broken: all of this assumed the markup came from you. The moment a string arrives from a user, an API, or a CMS and is turned into nodes, every guarantee in the chain is only as good as what that string contained.

Node 18 — Parsing, serialising and injection

The limitation: innerHTML from Node 4 is a parser you can point at arbitrary input, and Node 6's insertion methods will happily place whatever it produces into your live tree.

Cross-site scripting is the vulnerability class where attacker-controlled text becomes executing code in another user's page. The DOM-based variant needs no server involvement at all: a value read from location.hash or a query parameter, passed to innerHTML, is enough. Because the injected code runs in your origin, it can read cookies not marked HttpOnly, read localStorage, issue authenticated requests as the user, and rewrite the page. This is not a theoretical rank on a list — it is the most common serious front-end bug there is. [EXPLAIN]

The defences, in the order you should reach for them. Use textContent for anything that is text, which ends the problem outright because nothing is parsed. Build nodes with createElement and set properties, so structure comes from your code and only values come from input. If HTML genuinely must be accepted — a comment system, a CMS field — sanitise it with a maintained library such as DOMPurify, which parses the string, walks the result, and strips anything not on an allowlist. Never sanitise with a regular expression; the space of encodings and parser quirks is far larger than it looks. [EXPLAIN]

Two platform-level defences sit behind those. A Content Security Policy header restricts what a page may execute, and a policy without 'unsafe-inline' neutralises whole categories of injection even when a bug exists. Trusted Types (Chrome 83, 2020, still Chromium-only) goes further: it makes assigning a plain string to innerHTML throw, so the dangerous sinks can only be fed values that passed through a policy function you wrote. [AWARE]

The related parsing tools are worth knowing because they let you handle markup without putting it in the document. new DOMParser().parseFromString(str, 'text/html') produces a complete, inert Document you can inspect and query with everything from Nodes 2 and 3 before deciding what, if anything, to adopt into the live page with document.importNode or adoptNode. XMLSerializer and outerHTML go the other direction, turning nodes back into a string — and note that the string you get is the serialisation of the repaired tree, not the markup you originally wrote. [USE]

What you can do at this point: handle untrusted markup safely, explain DOM-based XSS with a concrete example, and inspect markup without exposing the page to it.

What's still broken: nothing in this chain is wrong, and doing all of it by hand for an application of any size means manually keeping a tree of nodes in agreement with a set of application state, in every direction, forever.

Node 19 — What frameworks took, and what they did not

The limitation: the DOM is an imperative API over a mutable tree, and application state is data. Keeping them synchronised by hand is where the bugs live.

Every DOM operation in this chain answers "how do I change this." An application wants to answer "given this state, what should be on screen." Bridging those by hand means that for every possible state change you must write the specific sequence of mutations that transforms the current DOM into the correct one — and the number of transitions grows far faster than the number of states. Miss one and the screen disagrees with the data. [EXPLAIN]

React, released in May 2013, and every framework in its lineage make the same trade: you write a function from state to a description of the desired tree, and the framework computes and applies the mutations. That is the whole of what a "virtual DOM" is — a plain-object description, cheap to build and discard, diffed against the previous description to derive a minimal set of real DOM operations. Other frameworks reach the same goal differently — Svelte compiles the mutations at build time, and Solid and Vue's reactivity track dependencies at the value level to update precisely the nodes affected — but the trade is identical: you stop writing mutations and start writing a description. [EXPLAIN]

What frameworks do not take away is most of this chain, and this is the practically important point. Event delegation, propagation, and preventDefault are still exactly Nodes 7 through 9 — React's synthetic event system is a delegation layer, and its handlers receive an object with the same target, currentTarget, stopPropagation, and preventDefault. The attribute-versus-property split from Node 5 is precisely why React has className rather than class, and why controlled inputs exist at all. useEffect's cleanup function is Node 15's teardown, unchanged. useRef exists specifically because measurement (Node 11), focus (Node 17), and third-party integration need a real node. Layout thrashing (Node 12) is not prevented by any framework. Accessibility is not provided by any framework. And a key prop is the diffing algorithm asking you for the identity information that Node 6's node-has-one-parent move semantics make necessary.

The honest summary: frameworks replace Node 6 — the manual construction and mutation of nodes — and leave every other node in this chain in force. Which is why "I know React" and "I know the DOM" are different claims, and why the second one is what makes the first one debuggable. [EXPLAIN]

Where the chain gets misread

"The DOM is the HTML." (Node 1) It is not. The HTML is a string, parsed once. The DOM is the live object tree that results — after the parser has repaired malformed markup, and including every change made since. Viewing source shows the HTML; the Elements panel shows the DOM, and they routinely differ.

"querySelectorAll returns an array." (Node 2) It returns a static NodeList, which has forEach but not map or filter. getElementsByClassName returns a live HTMLCollection, which has neither and which changes underneath you as the document changes. The two look interchangeable and are not.

"children and childNodes are the same." (Node 3) childNodes includes text and comment nodes, so any whitespace in your markup appears in it. children is elements only. Nearly every bug of the form "why is firstChild not my element" is this.

"innerHTML is safe because scripts don't run." (Node 4) <script> inserted via innerHTML is indeed not executed, and this stops almost nothing — <img src=x onerror=...>, <svg onload=...>, and <iframe srcdoc=...> all work. Treat innerHTML with untrusted input as executing that input.

"Setting element.style.color and reading it back gives me the colour." (Node 5) It gives you the inline style only. If the colour came from a stylesheet, you get an empty string. getComputedStyle gives the value in effect.

"The value attribute holds the input's value." (Node 5) It holds the initial value. After a user types, input.value and input.getAttribute('value') disagree permanently. This is the origin of controlled versus uncontrolled inputs in React.

"innerHTML += appends." (Node 6) It serialises everything already there, concatenates, and reparses the whole subtree from scratch — destroying every existing node, and with them every event listener, every form state, and every reference you were holding.

"stopPropagation prevents the default behaviour." (Node 8) It stops the event travelling to other elements. The browser's own behaviour — navigating, submitting, focusing — is cancelled only by preventDefault. They are independent, and calling stopPropagation reflexively breaks unrelated delegated listeners elsewhere on the page.

"e.target is the element I attached the listener to." (Node 8) e.target is the deepest element the event originated on, which in a delegated handler is whatever was clicked — often an icon inside the button. e.currentTarget is the element whose listener is running.

"DOM writes are slow, so batch them." (Node 12) The writes are cheap and already batched by the browser. What is expensive is forcing layout, which happens when you read geometry with changes pending. The rule is not "fewer writes," it is "do not interleave reads and writes."

"load is when the page is ready." (Node 14) load waits for every image and subresource, often seconds later. DOMContentLoaded is when the tree is complete, which is what interface code actually needs. And a listener registered after either has fired never runs — check document.readyState.

"Removing an element frees its memory." (Node 15) Only if nothing still references it. A listener on window, an un-disconnected observer, an uncleared interval, or a cached array keeps the whole detached subtree alive.

"React means I don't need the DOM." (Node 19) React replaces manual node construction and nothing else. Events, propagation, geometry, focus, accessibility, layout thrashing, and teardown are all still yours, and they are what you will be debugging.

The chain in one paragraph

Before the DOM, a page was a finished document and every change meant a full server round trip, so the browser's own parsed structure was invisible to code; DOM Level 1 exposed it in 1998 as a live tree of node objects, which had to be reachable, so selection arrived — getElementById, live HTMLCollections, and eventually querySelector and the static NodeList — and, because selectors describe patterns rather than relationships, traversal alongside it; reaching a node is useless without changing it, so textContent, innerHTML, and innerText gave content, and the attribute-versus-property split gave state, classes, and style, at which point you could still only edit what the server sent, so createElement, the insertion methods, and DocumentFragment let you build; that was all one-directional, so addEventListener let the page respond, and because a listener per element scales badly and cannot cover future nodes, the three-phase capture-target-bubble path made delegation possible via closest and e.target; propagation control does not touch the browser's own behaviour, so preventDefault and the form and input APIs took that over — which was still a fixed vocabulary, so ranges, selection, and contenteditable covered the rest; positioning anything relative to anything needed coordinates, so getBoundingClientRect and the scroll and box metrics arrived, and reading them turned out to force layout, which made the style-layout-paint-composite pipeline, the 16.7 millisecond frame budget, and layout thrashing the central performance concern; polling for changes you did not cause was the same disaster, so IntersectionObserver, ResizeObserver, and MutationObserver moved that detection into the browser; all of it assumes your script runs when the nodes exist, which is parser blocking, defer, and DOMContentLoaded; everything attached stays attached, which is detached nodes, leaks, and AbortController; everything shares one global namespace, which is shadow DOM and custom elements; visual correctness says nothing about operability, which is the accessibility tree, focus, and ARIA; every guarantee assumes the markup was yours, which is XSS, sanitisation, and DOMParser; and doing the whole of it by hand at application scale is what React and its successors replaced — the node-building layer only, leaving every other link in this chain exactly where it was.
