Node 34 — dynamic linking, libc, and why Alpine sometimes breaks things

The limitation: static linking copies every library into every program, so one security fix means rebuilding everything, and a hundred programs carry a hundred copies of the same code.

Deferring the link to run time

Dynamic linking leaves references unresolved in the executable and records instead which libraries are needed. At run time, a program called the dynamic linker — /lib64/ld-linux-x86-64.so.2 on Linux, itself named in the executable's PT_INTERP segment — maps the required shared objects into the address space and performs relocation before the program's first instruction runs.

The benefits: one copy of libc in memory shared by every process, since its code pages are mapped from one set of physical frames (Node 10, Node 14); a security fix in a library takes effect for every program on the next start; and executables are far smaller.

The costs, all real: startup does work that used to be done at build time; the deployment environment must supply compatible libraries; and version mismatches become a run-time failure class rather than a build-time one.

The machinery: PLT and GOT

Worth knowing because it explains both lazy binding and a security mitigation you have configured without knowing.

A call to a library function does not jump to the function. It jumps to a stub in the Procedure Linkage Table, which reads an address from the Global Offset Table and jumps there. Initially each GOT entry points back into the linker, so the first call to a function triggers resolution — the linker finds the real address, writes it into the GOT, and jumps. Every subsequent call goes straight through. That is lazy binding: symbols are resolved on first use, so a program that never calls a function never pays to resolve it.

Because the GOT is written at run time it is a natural attack target — overwrite an entry and redirect a call. The mitigation is RELRO: resolve everything eagerly at startup and mark the GOT read-only. LD_BIND_NOW=1 or linking with -z now enables full RELRO, trading slightly slower startup for a closed attack surface, and it is standard on hardened builds.

Finding libraries, and the variables involved

The search order at run time: DT_RPATH in the binary (deprecated), then LD_LIBRARY_PATH from the environment, then DT_RUNPATH, then the cache built by ldconfig from /etc/ld.so.conf, then the default directories.

ldd <binary> lists what it needs and where each was found; not found lines are exactly the cause of error while loading shared libraries: libfoo.so.1: cannot open shared object file. [USE]

LD_PRELOAD is the interesting one: a list of libraries loaded before all others, so their symbols win. This lets you replace any library function in any program without recompiling it. Legitimate uses are common — swapping in jemalloc (Node 12) with a single environment variable, injecting tracing or fault injection, or making a program use a different DNS resolver. It is also a classic persistence technique for attackers, which is why it is ignored for setuid binaries.

Versioning, and the error you will meet

A shared library has a soname like libssl.so.3, where the number is an ABI version. Binaries record the soname, so incompatible versions can coexist. glibc goes further with symbol versioning, keeping multiple implementations of a function under versioned names (memcpy@GLIBC_2.2.5) so that old binaries keep old behaviour.

The practical consequence is an asymmetry worth internalising: glibc is backward compatible but not forward compatible. A binary built against glibc 2.31 runs on a system with 2.36. A binary built against 2.36 fails on 2.31 with version 'GLIBC_2.34' not found. So build on the oldest system you must support, which is why release pipelines pin an old base image, and why building in a modern container and running on an older host fails in this specific way.

musl versus glibc: what Alpine actually changes

Alpine Linux uses musl rather than glibc — a different, smaller, MIT-licensed C library. The image is small (about 5 MB base) and that is genuinely valuable. The differences are also genuine and worth knowing before choosing:

  • Binaries are not interchangeable. Anything compiled against glibc will not run, which is why prebuilt native modules often fail on Alpine and fall back to compiling from source — turning a fast install into a slow one, and requiring a toolchain in the image.
  • DNS resolution differs. musl has no NSS, so it ignores /etc/nsswitch.conf, and it queries A and AAAA records in parallel over the same socket. Some resolvers and middleboxes handle that badly, producing intermittent resolution failures that are very hard to reproduce. It also historically did not honour search domains the same way, which matters inside Kubernetes (Node 32).
  • musl's allocator is slower under multi-threaded allocation-heavy load. This is measurable in Node workloads, and it was significant enough that the Node project stopped treating Alpine builds as fully tier-1 supported. Benchmarks vary, and the honest statement is: test your own workload rather than assume either way.
  • Default thread stack size is much smaller (128 KB versus glibc's 8 MB), which can produce stack overflows in code that is fine elsewhere.

The practical recommendation for Node images, stated plainly: node:20-slim (Debian-based, glibc, around 75 MB) is the safer default; node:20-alpine is worth it when image size genuinely matters and you have tested your dependency tree on it. A distroless image (Google's gcr.io/distroless/nodejs20) is another option — glibc, no shell, no package manager, minimal attack surface — with the trade that you cannot exec into it and must debug with ephemeral containers (Node 28).

Static linking's return

Go statically links by default and produces a binary depending on nothing but the kernel's syscall ABI (Node 4). Hence FROM scratch images of a few megabytes containing exactly one file. Rust with the musl target does the same. Node cannot — it is a large C++ program with a dynamic-linking-dependent addon system — though single-executable applications (Node 20+) bundle your JavaScript into the binary, which is a related but different idea.

Where this is in your stack

Node's module system is dynamic linking, one level up, and the parallel continues from Node 33. require() at run time resolves a name to a file, loads it, executes it, caches it. That is: symbol lookup, mapping, initialisation, and a load cache — the dynamic linker's job. The module cache (require.cache) is why a module executes once no matter how many times it is required, which is exactly why a shared object's initialisation runs once. Dynamic import() is lazy loading, and the bundler's code-split chunks are shared objects fetched on demand. And node_modules's nested resolution is the reason two versions of a package can coexist in one program — something the ELF dynamic linker cannot easily do, and a genuine advantage of npm's design that people rarely credit.

The multi-stage build for a Node service, with every line explained by this part:

FROM node:20-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                    # native addons compiled here (Node 33),
                              # against this image's glibc
COPY . .
RUN npm run build

FROM node:20-slim             # same base ⇒ same libc ⇒ addons still load
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev         # no compiler, no dev deps in the final image
COPY --from=build /app/dist ./dist
USER node                     # Node 25
CMD ["node", "dist/server.js"]  # exec form ⇒ node is PID 1 ⇒ signals work (Node 30)

Copying node_modules from the host into an image is broken for two independent reasons from this part: the native addons were compiled for your host's architecture (Node 33) and against your host's libc (this node). Both fail at run time with errors that do not obviously say so — invalid ELF header for the first, cannot open shared object file or a symbol version error for the second. .dockerignore containing node_modules is not a size optimisation; it is a correctness requirement.
