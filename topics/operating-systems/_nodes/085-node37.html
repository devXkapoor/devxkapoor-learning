Node 37 — init, systemd, and what a "service" is

The limitation: PID 1 is running and the machine has exactly one process. Something must start every service, in the right order, and keep it running.

What PID 1 has to do

Four jobs, and every one of them recurs in your orchestration tooling:

  1. Start services, respecting dependencies — the network before anything that binds a port, the database before the application.
  2. Supervise them — notice when one dies and decide whether to restart it, with a backoff so a crash loop does not consume the machine.
  3. Reap orphans (Node 5). PID 1 inherits every process whose parent died and must collect their exit statuses or the PID space leaks.
  4. Shut down cleanly — signal everything, in dependency order, with a deadline (Node 30).

SysV init, and why it was replaced

The traditional design: /etc/inittab named a runlevel (a number: 3 for multi-user text, 5 for graphical, 0 halt, 6 reboot), and each runlevel had a directory of shell scripts run in filename order — S10network, S20ssh, S99myapp. Each script accepted start, stop, restart and status.

Its problems were structural rather than cosmetic:

  • Strictly sequential. Ordering was expressed by numbering, so nothing could start in parallel even when independent. Boot took as long as the sum of every service.
  • No real dependency model. Numbers encode order, not requirement. If a service needed the network, the best you could do was pick a higher number and hope.
  • No supervision. Once a script forked a daemon and exited, init had no relationship with it. A crashed service stayed dead. Every project therefore invented its own supervisor — daemontools, runit, supervisord, monit, and in the Node world forever and pm2.
  • Tracking processes was guesswork. A "daemonised" process double-forks to detach from its parent, so init loses track of it entirely. Scripts wrote PID files, which go stale, which is why service foo status so often lied.

systemd

Written by Lennart Poettering and Kay Sievers at Red Hat, first released in 2010 and adopted by essentially every major distribution between 2012 and 2015 — over sustained and often bitter objection, on the grounds that it was doing far more than an init system should. Whatever one's view of that argument, it is what runs on the servers you deploy to, and its design decisions are worth understanding because they solve the four problems above directly.

Units, declared not scripted. A unit file is configuration rather than code. Types include .service (a process), .socket, .timer (a cron replacement), .mount, .target (a grouping, replacing runlevels), and .path.

Real dependencies, and ordering separated from requirement. Requires= states that another unit must be active; After= states ordering. These are independent, which is the key improvement — you can require without ordering and order without requiring — and it means everything not explicitly ordered can start in parallel. Boot times fell substantially.

Supervision by cgroup. systemd puts each service in its own cgroup (Node 27), so it knows every process belonging to that service regardless of forking or daemonising. No PID files, no guessing, and systemctl stop can reliably kill the whole tree. This also means resource limits are available to any service: MemoryMax=, CPUQuota=, TasksMax=.

Socket activation. systemd can create the listening socket itself and pass the descriptor to the service when a connection arrives (Nodes 22, 31). Two consequences: services can start on demand, and dependency ordering becomes less important, because a client connecting to a not-yet-started service simply waits in the accept queue (Node 32) rather than being refused.

Journald. Logs are captured from the service's stdout and stderr — which are pipes systemd created (Node 22) — and stored as structured, indexed records with metadata. journalctl -u myapp -f, journalctl -p err --since "1 hour ago", and journalctl -k for the kernel ring buffer.

A real unit file

[Unit]
Description=My Node API
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=simple                       # the main process is the one we exec
User=nodeapp                      # Node 25 — never root
WorkingDirectory=/srv/api
Environment=NODE_ENV=production
EnvironmentFile=/etc/api.env      # secrets as a file, not inline (Node 35)
ExecStart=/usr/bin/node /srv/api/dist/server.js
Restart=on-failure                # supervision
RestartSec=5
TimeoutStopSec=30                 # then SIGKILL (Node 30)
KillSignal=SIGTERM
MemoryMax=1G                      # Node 27 — cgroup limit, no container needed
CPUQuota=200%
NoNewPrivileges=true              # Node 35
ProtectSystem=strict              # read-only /usr, /boot, /etc
PrivateTmp=true                   # its own /tmp — a mount namespace (Node 26)

[Install]
WantedBy=multi-user.target

Note what the last few lines are: systemd applies namespaces and cgroups to ordinary services. PrivateTmp is a mount namespace. ProtectSystem is a read-only bind mount. MemoryMax is memory.max. These are the container mechanisms from Part VI, available without any container at all — which is a genuinely useful thing to know when someone insists containers are the only way to isolate a service.

Where this is in your stack

The genuine differences are that Kubernetes schedules across machines, and that it is declarative with a reconciliation loop — you state a desired state and a controller continuously works to make reality match, rather than issuing imperative start and stop commands. But the per-machine mechanisms are identical, because on each node the kubelet is ultimately writing cgroup files and calling clone().

PM2 and its container-era irrelevance. PM2 gives you supervision, clustering (Node 5), log rotation and restarts — a userspace init system for Node. On a bare virtual machine it is reasonable, though systemd does the same job with better process tracking. Inside a container it is usually wrong: it adds a process, obscures the exit code (so Kubernetes cannot see that your app crashed, because PM2 is still alive and healthy), duplicates restart logic the orchestrator already has, and breaks signal propagation exactly as Node 30 described. One process per container, restart handled by the orchestrator, is the correct shape.

CrashLoopBackOff, decoded. It is supervision plus backoff, and it means the container's main process is exiting. The diagnosis follows from the exit code, which you can now read entirely from Node 30: 137 is SIGKILL (usually OOM — check lastState.terminated.reason for OOMKilled); 143 is SIGTERM; 139 is a segmentation fault in a native module; 1 is your application throwing; 127 is "command not found", meaning your entrypoint path is wrong or a library is missing (Node 34). kubectl logs --previous retrieves the dead container's output, which is the step people forget.

Docker's restart policies are a small init system — no, on-failure[:max], always, unless-stopped — and Docker Compose's depends_on is After=. Note that depends_on only waits for the container to start, not to be ready, which is why condition: service_healthy and a healthcheck exist, and why so many compose setups have a wait-for-it script. That is exactly the ordering-versus-readiness distinction systemd solved with socket activation.

What you can do at this point: state the four jobs of PID 1, explain what was structurally wrong with SysV init, write and read a systemd unit file including its isolation directives, explain why systemd tracks processes by cgroup, map Kubernetes concepts to their systemd counterparts, explain why PM2 inside a container is usually a mistake, and diagnose a CrashLoopBackOff from its exit code alone.

What's still broken: the system is now complete — it boots, runs services, isolates them, schedules them, and shuts them down. What is missing is any way to see inside it while it runs. Every number in every dashboard you have ever looked at comes from somewhere specific, and Part IX is where.
