Node 21 — the file, the inode, and "everything is a file"

The limitation: a disk is a large array of numbered blocks with no structure. Programs need named, growable, permission-controlled sequences of bytes.

The abstraction, and how radical it was

Unix's definition of a file is deliberately, aggressively minimal: a file is a finite sequence of bytes, and that is all. [EXPLAIN]

No records. No fixed-length lines. No file type known to the system. No structure the operating system understands or enforces. This was not the norm — contemporary systems like OS/360 had record-oriented files with formats declared in the JCL from Node 1, and the system knew about fixed-length blocked records and would enforce them. Unix threw all of it away and said: bytes, and the program that opens the file decides what they mean.

The consequence is compositionality. Because no program can assume structure, every program must handle a plain byte stream, and therefore any program's output can be any other program's input. The Unix toolchain philosophy — small programs composed with pipes — is a direct consequence of this one decision about what a file is.

Separating the name from the file: the inode

The second key decision. A file's identity and its name are separate things.

The file itself is an inode (index node), a fixed-size record on disk holding everything about the file except its name:

  • type (regular file, directory, symbolic link, device, socket, FIFO)
  • permission bits, owner user ID, owner group ID
  • size in bytes
  • timestamps — mtime (contents last modified), ctime (inode last changed, not creation), atime (last accessed)
  • a link count — how many names refer to this inode
  • pointers to the data blocks

A directory is then just a file whose contents are a list of (name → inode number) pairs. Nothing more. Which means:

  • A file can have several names. Two directory entries pointing at the same inode are hard links. Neither is "the original"; they are equally the file.
  • Deleting is really unlinking. The call is unlink, and it removes a directory entry and decrements the link count. The data is freed only when the count reaches zero and no process still has it open. This is why deleting a large log file that a running process still holds open frees no disk space — a classic and confusing production situation, where du shows the space gone and df shows the disk still full. lsof | grep deleted finds it, and the fix is to restart or signal the holder, or to truncate rather than delete.
  • An open file has no name. Once opened, a process holds a reference to the inode; renaming or deleting the path does not affect it. This is why rename() is atomic and why "write to a temporary file, then rename over the target" is the standard safe-write idiom — readers see either the whole old file or the whole new one, never a partial write.
  • Permissions live on the inode, not the name, so all hard links share them.
  • Hard links cannot cross filesystems (inode numbers are per-filesystem) and cannot point at directories (it would create cycles the tree-walking code cannot handle). Symbolic links are the alternative: a tiny file whose contents are a path string, resolved at every use — so they can cross filesystems, can dangle, and add a resolution step to every access.

Running out of inodes while disk space remains is a real failure and a confusing one: df -h shows space free, writes fail with ENOSPC, and df -i shows 100% inode use. Traditional filesystems allocate a fixed inode table at format time, so millions of tiny files — a cache directory, a poorly configured session store, node_modules multiplied across many builds — can exhaust them.

"Everything is a file"

The third decision, and the one with the widest consequences. Unix applies the same interface — open, read, write, close, lseek, ioctl — to things that are not files at all:

  • Devices. /dev/sda is the raw disk. /dev/null discards writes and reads as empty. /dev/zero yields endless zero bytes. /dev/urandom yields cryptographic randomness. /dev/tty is the terminal.
  • Pipes and sockets — Node 22 and Node 31.
  • Kernel state. /proc and /sys are filesystems with no disk behind them at all: reading a file there executes kernel code that generates the content on the spot. This is why every tool from ps to top to a container runtime is, mechanically, a program that reads text files. Node 38.

The payoff is that a tool written for files works on all of it. cat, redirection, grep, and your language's file API operate on devices, kernel state, and network connections with no special support. It is the earliest and one of the best examples of a uniform interface paying for itself over decades. [EXPLAIN]

The VFS: one interface, many implementations

For that uniformity to work with many different filesystems, the kernel needs a layer of indirection, and it has one: the Virtual File System, introduced by Sun in 1985 for NFS and adopted everywhere. The VFS defines a set of operations — look up a name, read, write, create — and every filesystem implements them. ext4, XFS, btrfs, NFS, tmpfs, overlayfs, procfs, and FUSE-based filesystems all plug into the same interface.

So read() is: syscall entry, VFS dispatch on the inode's filesystem type, that filesystem's implementation, the page cache, the block layer, the device driver. The layering is what makes mount possible — attaching any filesystem at any point in the single tree — and mounts are per-namespace, which is the hinge on which containers turn (Node 26).

Where this is in your stack

Every Docker volume mount is this node. -v /host/path:/container/path is a bind mount: the same inodes appearing at a second location in the tree. There is no copying and no synchronisation — it is literally the same files, which is why edits on the host appear instantly inside the container. And it is why mounting over a directory hides what was there: the mount replaces what that path resolves to, so bind-mounting your source directory over /app hides the /app/node_modules the image installed. The standard fix — an anonymous volume at /app/node_modules — is a second mount at a deeper path that shadows the first, and knowing the mechanism makes that trick obvious rather than magical.

Atomic writes in application code. The rename idiom above is the correct way to update a config file, a cache entry, or any file a reader might see mid-write. In Node: fs.writeFile(tmp, data), then fs.rename(tmp, target). It only works if both paths are on the same filesystem — rename across filesystems fails with EXDEV and the library falls back to copy-then-delete, which is not atomic. This is why moving a file from /tmp to a mounted volume in a container often behaves differently from moving within the volume, and why upload handling should write the temporary file into the destination filesystem.

File watching is not part of this abstraction, and that shows. There is no portable "tell me when this changes"; Linux has inotify, macOS has FSEvents, and Windows has ReadDirectoryChangesW. Node's fs.watch maps onto them with real differences in behaviour, which is why chokidar exists and why every bundler depends on it. inotify also has per-user limits — fs.inotify.max_user_watches, historically 8192 — and exceeding them produces ENOSPC from a watcher, which is one of the most misleading error codes in Linux since no space is involved. Anyone who has run a dev server on a large repository has hit it.

node_modules is an inode problem. A large project can have hundreds of thousands of small files. That is slow to create, slow to traverse, slow to copy into a Docker build context, and inode-hungry. pnpm's design is a direct response: one content-addressed global store, with hard links (this node) into each project's node_modules, so the same file exists once on disk with many names. Yarn PnP goes further and eliminates the directory entirely, resolving from a single map file. Both are filesystem-level answers to a filesystem-level problem.

.dockerignore matters more than people think for the same reason: the build context is the entire directory tree sent to the daemon, walked file by file. Excluding node_modules and .git often turns a thirty-second context upload into one second.
