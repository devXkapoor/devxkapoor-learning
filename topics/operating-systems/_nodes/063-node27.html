Node 27 — cgroups: accounting for and limiting resources

The limitation: a namespaced process cannot see the rest of the machine and can still consume all of it.

The mechanism

Control groups — cgroups — were written at Google by Paul Menage and Rohit Seth in 2006 (originally "process containers") and merged into Linux 2.6.24 in 2008. A cgroup is a set of processes plus a set of resource controllers applied to it, arranged in a hierarchy that appears as a filesystem, so configuring resource limits is writing text into files — which is why every container runtime's resource management is a handful of file writes.

cgroups v2, the unified hierarchy, is now the default on all current distributions and is what Kubernetes uses from 1.25 onward. It lives at /sys/fs/cgroup and a container's own view of it is at /sys/fs/cgroup inside the container thanks to the cgroup namespace.

The controllers that matter

cpu. Two independent things, and confusing them is the most consequential misunderstanding in Kubernetes resource configuration.

  • cpu.weight — a relative share, 1 to 10000, default 100. It is CFS's task weight from Node 7 applied to a group. It only has an effect when the processor is contended. A cgroup with weight 100 competing with one of weight 200 gets a third of the contended time, and gets everything when nothing else wants it.
  • cpu.max — a hard quota, written as "quota period", e.g. 50000 100000 meaning at most 50 ms of processor time per 100 ms period. When the quota is exhausted, every task in the group is stopped until the period ends, even if the machine is completely idle. That is throttling.

The arithmetic is worth doing once, because it explains a whole class of latency problem. A container with cpu.max = 100000 100000 (one core's worth) running a Node process that also has four threadpool threads: if five threads run simultaneously, they consume the 100 ms quota in 20 ms of wall clock, and then the entire container sleeps for 80 ms. Average utilisation reads as 100% of one core — apparently fine — while every request that arrived during those 80 ms took an extra 80 ms. Latency spikes at moderate average CPU, with no corresponding CPU graph, is the signature of throttling, and the evidence is in /sys/fs/cgroup/cpu.stat: nr_throttled and throttled_usec climbing. [EXPLAIN] It also raises nonvoluntary_ctxt_switches from Node 6.

The practical consequence, which is contested but well argued: for latency-sensitive services, set CPU requests and no CPU limit. Requests give you a guaranteed share under contention; limits only add throttling. The counter-argument is that without limits a misbehaving container degrades its neighbours, and both positions are defensible — but the decision should be made knowingly rather than by copying a template.

memory. Three thresholds, and knowing all three is more useful than knowing the one Kubernetes exposes.

  • memory.max — the hard limit. Exceeding it triggers reclaim, and if reclaim cannot free enough, the cgroup OOM killer fires SIGKILL (Node 13). This is what Kubernetes sets from limits.memory, and it is why you get exit code 137 and OOMKilled.
  • memory.high — a soft limit. Above it the kernel throttles the group's allocations and reclaims aggressively, making it slow rather than dead. This is very often the behaviour you actually want for a service with a spiky working set, and Kubernetes does not expose it directly, which is a genuine gap.
  • memory.min and memory.low — reclaim protection. Memory below memory.min is never reclaimed from this group.

memory.current is the group's usage and memory.stat breaks it down — crucially into anon (heap and stack) and file (page cache). Node 13's point returns here concretely: page cache from your container's file writes counts towards memory.max, so a service that logs to a file can be OOMKilled with a flat heap. Reading memory.stat is how you prove that is what happened.

io. io.max sets per-device read and write limits in bytes per second and operations per second; io.weight is proportional sharing. Note that these work properly for direct block I/O and are much weaker for buffered writes, since those are performed later by kernel writeback threads and attributing them is hard — one reason "why is my disk-noisy neighbour still affecting me" has no clean answer.

pids. pids.max caps the number of tasks. This is the defence against a fork bomb, and it is a real one: without it, one container can exhaust the machine's PID space and nothing anywhere can start a process. Docker's --pids-limit and Kubernetes' pod PID limits set it.

PSI — Pressure Stall Information (Linux 4.20, 2018) — is worth knowing because it is a genuinely better signal than utilisation. /sys/fs/cgroup/cpu.pressure, memory.pressure and io.pressure report the fraction of time tasks were stalled waiting for that resource. Utilisation says how busy something is; pressure says how much your work is being delayed by it, which is the thing you actually care about. It is what modern autoscaling and out-of-memory daemons like Facebook's oomd use. [AWARE]

Where this is in your stack

Kubernetes resource fields map onto cgroup files exactly, and the mapping is worth memorising because it makes the semantics obvious.

resources:
  requests:            # scheduling + relative share
    cpu: "500m"        # → cpu.weight, scaled from the millicores
    memory: "256Mi"    # → used for scheduling; also memory.min-ish protection
  limits:              # hard ceilings
    cpu: "1000m"       # → cpu.max = "100000 100000"  (throttling!)
    memory: "512Mi"    # → memory.max                  (OOMKill!)

Two different enforcement mechanisms with two different failure modes: exceeding a CPU limit makes you slow; exceeding a memory limit makes you dead. [EXPLAIN] That asymmetry is because CPU is compressible — you can give a process less of it and it still runs — and memory is not: there is nothing to give back once the bytes are written. This is the single most useful sentence about Kubernetes resource management.

QoS classes follow from the fields, and they determine who dies first when a node runs out of memory. Guaranteed (requests equal limits for every resource) gets the most protective oom_score_adj; Burstable (requests set, limits higher or absent) is in the middle, scored by how far above its request it has grown; BestEffort (nothing set) gets oom_score_adj = 1000, making it the first thing the kernel kills. Setting requests is therefore not merely a scheduling hint — it is a survival decision.

Sizing a Node process against a cgroup, derived from Parts III and this node. Container limit 1 GB. RSS will include the V8 heap, external buffers, the binary and libraries (50–100 MB), code space, thread stacks, and allocator fragmentation (Node 12). So set --max-old-space-size=640 or thereabouts, so V8 hits its own limit — throwing a catchable heap-limit error with a stack trace, and optionally a snapshot via --heapsnapshot-near-heap-limit — before the kernel delivers an uncatchable SIGKILL. Add MALLOC_ARENA_MAX=2 if RSS is unexplained. On the CPU side, use os.availableParallelism() rather than os.cpus().length for pool sizing, because Node 26 established that /proc/cpuinfo is not namespaced.

The systemd connection. systemd (Node 37) organises every service into a cgroup, so MemoryMax=, CPUQuota=, and TasksMax= in a unit file are this node applied outside containers entirely. systemd-cgtop shows resource use by cgroup, which is often more informative than top, and systemctl status shows the cgroup tree of a service. Running a Node service under systemd with a MemoryMax gives you container-style limits with no container.

What you can do at this point: explain cgroups as a filesystem interface, distinguish weight from quota and explain throttling with the arithmetic, name the three memory thresholds and explain why Kubernetes only exposing the hard one is a limitation, explain why exceeding CPU limits differs from exceeding memory limits, map Kubernetes resource fields to cgroup files, derive QoS classes and their OOM ordering, and size a Node process against a container limit from first principles.

What's still broken: nothing. Every ingredient of a container now exists — a filesystem view, a process view, a network view, an identity mapping, a resource budget, a syscall filter, and a layered image. Node 28 assembles them, and there is no new concept in it.
