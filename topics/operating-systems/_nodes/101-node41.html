Node 41 — kernel architectures, and the argument that shaped Linux

The limitation: everything has been described as "the kernel" as though there were one obvious way to arrange it. There is not.

The monolithic kernel

All operating system services — scheduler, memory manager, filesystems, network stack, device drivers — run in kernel mode, in one address space, calling each other as ordinary functions.

Fast, because a filesystem calling the block layer is a function call, not a boundary crossing (Node 40). Fragile, because a bug anywhere is a bug everywhere: a defect in a Wi-Fi driver can corrupt the page cache, and there is no isolation between components because they share an address space (Node 15's trade, at kernel scale). And large — Linux is over 30 million lines, of which the majority is drivers.

Linux mitigates the size problem with loadable kernel modules: drivers compiled separately and loaded on demand (lsmod, modprobe). They still run in kernel mode with full privilege, so this is a packaging improvement, not an isolation one — a fact worth being clear about, since people often assume otherwise.

The microkernel

Keep only the irreducible minimum in kernel mode — address spaces, threads, scheduling, and inter-process communication — and run everything else as ordinary user-mode processes. The filesystem is a server. The network stack is a server. Drivers are servers. They communicate by message passing.

Robust: a crashed driver is a crashed process, restartable without touching the rest, and it cannot corrupt anything it was not given access to. Verifiable: seL4, a microkernel of about 10,000 lines, has a machine-checked mathematical proof of functional correctness — something inconceivable for a monolithic kernel. And slower, historically decisively so: an operation that was a function call becomes several IPC round trips, each with a context switch and a boundary crossing.

Mach, from Carnegie Mellon in the 1980s, was the influential attempt and was notably slow. Later designs (L4, from Jochen Liedtke in 1993) reduced IPC cost by an order of magnitude and made the argument much closer.

The 1992 argument, which is worth knowing accurately

In January 1992, on the comp.os.minix newsgroup, Andrew Tanenbaum — professor at Vrije Universiteit Amsterdam and author of Minix, a microkernel teaching system — posted "LINUX is obsolete". His argument: microkernels were the settled direction of operating systems research, and Linux's monolithic design was a step backwards; also that tying it to x86 was short-sighted.

Linus Torvalds, then 22, replied at length and with some heat. His argument: Linux was portable in practice, it worked, it was free, and theoretical elegance that ships nothing loses to practical code that runs. The exchange ran for weeks and is one of the best-documented arguments in computing.

The honest assessment thirty years later is that both were right about different things. Tanenbaum was right that monolithic kernels have serious reliability and security properties, and the entire subsequent history of kernel vulnerabilities bears him out. Torvalds was right that Linux would win, and it did, comprehensively — every cloud server, every Android phone, most embedded systems. Microkernel ideas did not lose either; they moved. Every mechanism in Part VI is a microkernel-flavoured retrofit onto a monolithic kernel: user-space filesystems via FUSE, user-space drivers via VFIO and DPDK, gVisor implementing the syscall interface in a user process (Node 4), and eBPF running verified code in the kernel rather than trusted code (Node 39). And seL4 runs in aviation and defence systems where the proof is worth the cost.

The systems you actually use

  • Linux — monolithic with modules. The stable interface is the syscall boundary (Node 4); internal APIs change freely, which is why out-of-tree drivers break on every kernel upgrade and why NVIDIA's driver situation is what it is.
  • Windows NT — designed by Dave Cutler from 1989 as a hybrid: a microkernel-influenced structure with an "executive" of subsystems, but with most of it running in kernel mode for performance. Graphics moved into the kernel in NT 4.0 (1996) for speed, at a real cost in stability — the archetypal instance of this node's trade. The stable interface is ntdll.dll, not the syscall numbers.
  • macOS / iOS (XNU) — literally "X is Not Unix", a hybrid combining the Mach microkernel with a BSD layer, both in kernel mode. Mach provides IPC and memory objects; BSD provides the POSIX interface. Modern macOS pushes drivers into user space with DriverKit, which is a microkernel move made thirty years later.
  • Android — the Linux kernel with a substantially different user space: Bionic instead of glibc, the ART runtime, and Binder, a fast IPC mechanism that is essentially a microkernel-style message-passing layer. Android's security model uses SELinux and one Linux user ID per application — Node 25's mechanism as an app sandbox.
  • Unikernels — the opposite extreme: compile the application and the operating system functions it needs into a single binary with no user/kernel split at all, running directly on a hypervisor. No syscall cost, no context switches, tiny attack surface, and no ability to run anything else or to debug it conventionally.

Where this is in your stack

The monolithic trade is why a kernel bug is a container escape (Node 28). One kernel, shared by every container, with 30 million lines of attack surface — and a container's processes call directly into it. That is the entire argument for gVisor, Kata and Firecracker, and each is a different point on this node's spectrum: gVisor is a microkernel-style syscall server in user space, Kata and Firecracker restore a hardware boundary.

The same trade recurs in architecture, and naming it makes the discussion better. A monolith is one address space with function calls between modules: fast, simple to deploy, and a memory leak or a crash in any module affects all of them. Microservices are separate processes communicating by messages: independently deployable and restartable, a failure contained to one service, and every internal call becomes a network round trip — 200 microseconds instead of 20 nanoseconds, four orders of magnitude, exactly the microkernel's IPC penalty. The arguments made for and against microservices are, term for term, the arguments Tanenbaum and Torvalds made in 1992, and the resolution is likely to be the same: mostly monolithic, with boundaries where isolation genuinely earns its cost.

The browser is the clearest working example of the resolution. Chrome moved from one process to process-per-site (Node 3), accepting a large memory cost and constant IPC to gain the hardware isolation boundary — because the threat model demanded it. It is a monolith that became a microkernel where it mattered, which is the honest general answer.

What you can do at this point: explain the monolithic and microkernel designs and their trade-offs, describe the 1992 debate accurately and assess it fairly, place Linux, NT, XNU, Android and unikernels on the spectrum, explain why a container escape is a consequence of monolithic design, and map the architecture argument onto monolith versus microservices with the actual latency figures.

What's still broken: the chain is complete but its history has been delivered in pieces, one date at a time. Seeing it in order — who did what, when, and in response to whom — makes the whole thing considerably easier to hold.
