Node 43 — one click, all the way down and back

The limitation: none. This node exists because the mechanisms have been built one at a time, and the thing worth having is all of them at once, in order, for one real event.

A user clicks a button in a React application. It calls an API on a Node service in a Kubernetes cluster, which queries Postgres, and the result renders. Every step below is a mechanism from this document, with its node named. Nothing is skipped and nothing is approximated.

A — the click becomes an event (browser machine)

  1. A finger closes a physical contact in a mouse or a touch digitiser. Voltage on a wire (Node 0).
  2. The USB or I²C controller raises an interrupt (Node 2). The processor finishes its current instruction — quite possibly JIT-compiled JavaScript from the page you are on — saves rip, and enters the kernel's handler through the IDT.
  3. The handler is short: it acknowledges the device and schedules a softirq. The kernel's input subsystem turns the report into an event on /dev/input/eventN (Node 21 — it is a file).
  4. The display server (Wayland, X11, or the platform equivalent) reads that descriptor. It was blocked in epoll_wait and is now runnable; the scheduler picks it, and a context switch restores its registers and page table (Nodes 6, 7, 10).
  5. It determines which window is under the pointer and sends the event to that client over a Unix domain socket (Node 31).
  6. The browser's UI process receives it, decides which renderer process owns that area, and forwards it over an IPC channel — a real process boundary, because of Site Isolation (Node 3).
  7. The renderer process wakes. Its event loop takes the message as a task, hit-tests the layout tree to find the target element, constructs a MouseEvent, and dispatches it through capture, target and bubble phases (Node 20).
  8. React's synthetic event system, listening at the root, routes it to your onClick. Your handler runs — machine code TurboFan generated from your JavaScript at some earlier point (Node 0).

B — the request leaves

  1. Your handler calls fetch(). Objects are allocated by a pointer bump in V8's new space (Node 11).
  2. The URL's hostname must be resolved. If it is not cached, this is a DNS query — itself a UDP sendto and a wait (Node 32).
  3. socket(), then connect(): syscalls (Node 4), each a trap into kernel mode with arguments in registers.
  4. The kernel sends a SYN. One round trip for the TCP handshake, then one or two more for TLS (Node 32). If the browser already has a warm connection to this origin, all of this is skipped — which is the entire value of connection reuse.
  5. The request bytes are copied into the socket's send buffer and the network card DMAs them out (Node 2).
  6. The renderer's JavaScript continues immediately; fetch returned a promise. The tab is not blocked (Node 20).

C — arrival at the server machine

  1. Packets cross the internet, are rewritten by NAT at several points, and reach the cluster's load balancer, which is itself a machine doing all of this.
  2. On the destination node, the network card DMAs the packet into a ring buffer in host memory and raises an MSI-X interrupt on a specific core (Node 2).
  3. The driver's top half schedules a NET_RX softirq and returns. Whatever was running resumes, unaware.
  4. The softirq walks the packet up: Ethernet, then netfilter — where kube-proxy's rules rewrite the destination from the Service IP to a specific pod IP (Nodes 26, 32) — then IP, then TCP. Sequence numbers are checked, an acknowledgement is scheduled, and the payload is appended to a socket's receive buffer.
  5. That socket's wait-queue callback fires and pushes its descriptor onto an epoll ready list (Node 19).
  6. Your Node process — one process in one container, which is a set of namespaces and a cgroup (Nodes 5, 26, 27, 28) — has been sleeping in epoll_wait, consuming zero processor time (Node 18). It is marked runnable.
  7. The scheduler picks it, subject to its cgroup's cpu.weight and, if a limit is set, whether its quota remains (Nodes 7, 27). A context switch loads its registers and its page table root into cr3 (Nodes 6, 10).

D — your code runs

  1. epoll_wait returns. libuv is in its poll phase (Node 20).
  2. libuv maps the descriptor to a handle and calls its callback, which issues read() (Node 4). The kernel copies bytes from the socket buffer into a Buffer — memory outside V8's heap (Node 11), which is why it will not appear in heapUsed.
  3. Node's HTTP parser consumes the bytes. On a complete request it calls into V8, which invokes your route handler.
  4. Your handler runs synchronously. During this time no other request in this process can be served — the event loop is cooperative and cannot be preempted (Nodes 7, 20). The kernel can preempt the thread, which protects the rest of the machine but does nothing for the other connections in this process.
  5. You await a database query. The function suspends; its continuation is captured; a promise is returned; and the loop moves on to other connections. This is where the whole architecture pays for itself (Node 18).

E — the database

  1. The query goes out over a pooled connection — pooled because Postgres runs one process per connection and processes are expensive (Nodes 5, 6, 14). If the pool is exhausted, your request waits here, invisibly, in a bounded queue (Node 18).
  2. On the database machine: interrupt, softirq, epoll or a blocking read, and a backend process wakes.
  3. The planner chooses a plan using cost constants that encode disk physics — random_page_cost against seq_page_cost (Node 23).
  4. Execution reads pages from shared_buffers, a shared memory mapping (Nodes 11, 31). A miss falls through to the kernel's page cache (Node 13); a miss there is a real disk read — a major fault or a pread, tens of microseconds on NVMe, and during it the backend is in D state (Nodes 5, 23).
  5. Shared structures are protected by lightweight locks, which are futexes: an atomic compare-and-swap in user space, entering the kernel only under contention (Nodes 16, 17).
  6. If this is a write, a WAL record is appended and — at commit, with synchronous_commit=on — fsynced, forcing the page cache and the device's own write cache to the medium. That single call is the largest cost in the transaction (Node 23).
  7. Result rows are written to the socket and the path from step 16 repeats in the other direction.

F — the response, and back to the browser

  1. Your process wakes in epoll_wait again. The driver's promise resolves, queueing a microtask, which resumes your async function's state machine (Node 20).
  2. You call res.json(...). JSON.stringify runs synchronously — on a large object this blocks every other connection in the process, and it is one of the commonest hidden stalls in Node services.
  3. Node writes to the socket. If the send buffer is full, write returns short and libuv registers for writability; Node surfaces this as write() returning false and a later 'drain' — backpressure (Node 19).
  4. Objects allocated during the request are now unreachable. V8's scavenger reclaims them in under a millisecond, because they died young (Node 11).
  5. Packets traverse back. In the browser, interrupt, softirq, TCP reassembly, socket buffer, the network process, IPC to the renderer, and a task queued on its event loop.
  6. Your await fetch() resolves as a microtask. setState is called.

G — the pixels

  1. React schedules a render. Its own scheduler assigns a lane by priority and yields to the browser roughly every 5 ms, checking shouldYield() between units — a cooperative scheduler inside a cooperative scheduler inside a preemptive one (Nodes 7, 20).
  2. Reconciliation produces a minimal set of DOM mutations.
  3. At the next frame boundary the browser runs the rendering steps: requestAnimationFrame callbacks, style recalculation, layout, compositing, paint (Node 20). If any code read a geometric property between writes, layout ran extra times.
  4. Painted tiles are uploaded to the GPU. The compositor issues draw calls; the GPU process rasterises; the result is written into a framebuffer.
  5. The display controller DMAs the framebuffer out over HDMI or DisplayPort, sixty times a second, whether or not anything changed.
  6. Photons. The user sees the button's new state.

Forty-five steps, six machines' worth of kernels, and roughly eight boundary crossings between user and kernel mode on each side. Every one is a mechanism in this document, and a slow request is one of them being slow. That is the payoff of the whole chain: "the API is slow" is not a diagnosis, and this list is the set of places the time can be.

The second lifecycle: how the code got there

The same tracing applied to a deployment, more briefly, because it is the other half of "the complete lifecycle" and it is made of the same parts.

  1. You write a file. The editor writes to the page cache; the bytes reach disk when the kernel decides, or when the editor fsyncs (Nodes 13, 23).
  2. git commit writes content-addressed objects — copy-on-write and structural sharing, which is why branching is free (Node 14).
  3. git push is TCP over TLS to a remote (Node 32), authenticated by an SSH key or a token.
  4. A CI runner picks up the job. It is a resident monitor: a process polling a queue, running steps, reporting, and repeating (Node 1). The job runs in a container on a machine somewhere (Node 28).
  5. The build. npm ci creates a hundred thousand small files (Node 21's inode cost), compiling any native addons against this image's libc (Nodes 33, 34). A bundler links your modules, resolving symbols and eliminating dead code (Node 33). TypeScript type-checks, which is a separate tool doing a separate thing.
  6. The image is built. Each instruction produces an overlayfs layer, content-addressed, cached by input (Node 24). A multi-stage build discards the toolchain.
  7. Push to a registry — HTTPS, layer by layer, skipping digests the registry already has.
  8. The orchestrator reconciles. A new ReplicaSet is created; the scheduler places pods on nodes by their requests (Node 27).
  9. The kubelet starts a container. Pull layers; assemble the overlay; create the cgroup and write its limits; clone() with namespace flags; wire a veth pair; pivot_root; mount /proc, /sys, /dev; set the UID; drop capabilities; install the seccomp filter; execve the entrypoint (Nodes 4, 14, 22, 25, 26, 27, 28, 35).
  10. Your process starts. The dynamic linker maps libc and every .node addon and relocates them (Node 34). Pages fault in on demand, which is most of the cold-start cost (Node 13). V8 restores its heap from a snapshot via mmap (Node 10). Your modules are resolved, loaded and cached — dynamic linking again, one level up.
  11. It listens. socket, bind, listen with a backlog, and then epoll_wait (Nodes 19, 32).
  12. The readiness probe passes, the endpoints controller adds the pod to the Service, and kube-proxy on every node programs netfilter rules so traffic can reach it (Node 32).
  13. The old pod is removed. Endpoint removal and SIGTERM happen concurrently, so the old process must keep serving briefly after the signal or the rollout drops requests (Node 30). At terminationGracePeriodSeconds it is SIGKILLed regardless.

What you can do at this point: narrate a request end to end without gaps, name the mechanism behind every step, and — the actual skill — given a symptom, enumerate the specific places in these two lists where the time or the failure could be, rather than guessing.
