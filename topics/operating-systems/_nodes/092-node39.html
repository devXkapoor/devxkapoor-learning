Node 39 — tracing: ptrace, perf, and eBPF

The limitation: /proc shows state, not behaviour. It cannot say which function burned the processor or which syscall was slow.

ptrace: one process controlling another

ptrace() lets one process attach to another and control its execution: stop it, read and write its registers and memory, single-step it, and intercept every system call entry and exit. It is the mechanism behind every debugger — gdb, lldb, and strace from Node 4.

A breakpoint, mechanically, is this: the debugger writes the one-byte instruction 0xCC (int3) over the first byte of the target instruction, saving the original. When the process reaches it, the processor raises an exception (Node 2), which becomes SIGTRAP, which suspends the process and notifies the debugger. To continue, the debugger restores the original byte, single-steps one instruction, re-inserts the breakpoint, and resumes. A debugger is a program that edits your machine code while it runs, which is only possible because of Node 0's stored-program property.

The cost is severe: strace stops the traced process twice per system call, so a syscall-heavy program can slow by an order of magnitude. That makes ptrace excellent for correctness debugging and unusable for production performance work.

It is also a security-sensitive capability — attaching to a process means reading all its memory, including its keys — so it is gated by CAP_SYS_PTRACE (Node 25) and by /proc/sys/kernel/yama/ptrace_scope, which by default permits attaching only to descendants. This is why strace on someone else's process needs sudo, and why docker run --cap-add=SYS_PTRACE is required to debug inside a container.

perf: sampling instead of intercepting

The alternative to observing every event is to sample. perf uses the processor's performance monitoring unit — hardware counters that can be programmed to raise an interrupt every N events. Set it to interrupt every ten million cycles, record the instruction pointer and call stack at each interrupt, and after a few seconds you have a statistical picture of where time went, at an overhead of one to two percent.

The counters are hardware and go far beyond cycles: instructions retired, cache misses at each level, branch mispredictions, TLB misses (Node 10). perf stat on a workload tells you not just that it is slow but why — a low instructions-per-cycle figure with high cache misses is a memory-layout problem, not an algorithmic one.

perf stat -d ./workload            # counters: IPC, cache misses, branch misses
perf record -F 99 -g -p <pid> -- sleep 30
perf report                        # or fold into a flame graph

A flame graph (Brendan Gregg, 2011) aggregates those sampled stacks: width is the proportion of samples in which a function was on the stack, and the vertical axis is stack depth. Width means time; the ordering left to right is alphabetical and carries no meaning — a point people get wrong constantly. A wide plateau at the top is a function burning CPU in itself; a wide tower is a deep call path.

eBPF: programs that run in the kernel

The modern answer, and the most significant change in Linux observability in twenty years. eBPF lets you load a small program into the kernel, attached to a kernel function, a tracepoint, a syscall, a network hook, or a user-space function, which runs on every occurrence and writes results into a map that user space reads.

Node 3 said user code must never run privileged, so the resolution matters: the kernel runs a verifier over the bytecode before accepting it, statically proving that it terminates (no unbounded loops), that every memory access is in bounds, and that it calls only permitted helpers. It is then JIT-compiled to native code. A proof obligation substituting for a hardware boundary.

The consequence is aggregation in the kernel. Rather than copying every event to user space and analysing it there — strace's fatal cost — an eBPF program can, say, compute a latency histogram of every disk I/O in the kernel and hand you the finished histogram. Overhead falls to the point where it is acceptable in production.

The tools built on it, worth knowing by name: bpftrace (a small scripting language for one-off questions), the BCC collection (execsnoop, opensnoop, biolatency, tcplife, runqlat, profile), bpftop, and at the platform level Cilium for container networking and policy, Pixie and Parca for continuous profiling, and Falco for runtime security.

# every process executed anywhere on the machine, as it happens
execsnoop-bpfcc

# a histogram of block-device latency (Node 23)
biolatency-bpfcc 10 1

# how long tasks wait in the run queue before running (Node 7)
runqlat-bpfcc

# one-off: count syscalls by name for one process
bpftrace -e 'tracepoint:raw_syscalls:sys_enter /pid == 1234/ { @[probe] = count(); }'

runqlat deserves a note: it measures scheduler wait time, which is precisely the CPU-contention signal that utilisation cannot show you. A container being throttled (Node 27) shows up there directly.

Where this is in your stack

Profiling a Node process has three layers and you must pick the right one. [EXPLAIN] This is the single most useful practical content of this node.

  • JavaScript-level. node --prof then --prof-process, or the Chrome DevTools CPU profiler via node --inspect, or 0x, or a continuous profiler. These use V8's own sampling profiler and give you your function names. This is where you start, and it answers "which of my functions is hot".
  • Native-level. perf record on the Node process. By default the JIT-compiled frames appear as unresolved addresses, because the machine code was generated at run time and no symbol table describes it (Node 0, Node 33). node --perf-basic-prof makes V8 write a map file of address ranges to JavaScript function names, which perf then reads. This is what you need when the time is in V8, in libuv, in a native addon, or in the kernel — things the JavaScript profiler cannot see at all.
  • Kernel-level. eBPF tools, for when the answer is "waiting on the disk", "waiting in the run queue", or "spending its time in futex".

The diagnostic sequence that follows: if event-loop delay is high (Node 20) and CPU is high, use the JavaScript profiler. If CPU is high but no JavaScript function accounts for it, use perf — the answer is usually garbage collection, JSON serialisation, TLS, or an addon. If CPU is low and latency is high, the process is waiting, and the eBPF tools tell you for what.

Heap profiling is a separate axis. node --inspect plus DevTools' heap snapshots, or v8.writeHeapSnapshot(), or --heapsnapshot-near-heap-limit to capture one automatically as the process approaches its limit (Node 12). Comparing two snapshots taken minutes apart and sorting by retained size is the standard leak hunt. And Node 11's warning applies: a buffer leak does not appear in a heap snapshot, because those bytes are outside V8's heap — that one shows as rising RSS with a flat heap, and you find it with perf or by auditing addon usage.

Continuous profiling in production is now normal. Because sampling costs one to two percent, running a profiler permanently across a fleet is affordable, and it changes the economics of performance work: instead of trying to reproduce a problem, you look at what the process was doing when it happened. Pyroscope, Parca, Datadog's and Google's profilers all do this, and the underlying mechanism is this node.

Kubernetes debugging tools are these mechanisms with permissions attached. kubectl debug creates an ephemeral container in the target pod's namespaces (Node 26), which is how you get tooling into a distroless image. Profiling inside a container generally needs SYS_PTRACE or SYS_ADMIN, and eBPF needs privileged access or CAP_BPF — which is why observability agents are among the few workloads that legitimately run privileged, and why they are also a serious supply-chain risk.

What you can do at this point: explain how a debugger sets a breakpoint and why strace is too slow for production, explain sampling profilers and what hardware counters tell you, read a flame graph correctly, explain eBPF's verifier as the resolution of Node 3's rule, choose the right profiling layer for a Node symptom, and explain why a buffer leak is invisible in a heap snapshot.

What's still broken: one number has been referenced repeatedly without being confronted — the cost of crossing between user mode and the kernel. It has grown, for reasons that are not about software design, and the response to it is reshaping how I/O is done.
