JavaScript

The runtime and semantics underneath every backend, frontend, and AI thing you build — from the event loop to why this does what it does.

Read this top to bottom, in order. Each node exists because the node before it left something specifically broken. Every node ends by naming what is still broken, and that broken thing is the entire reason the next node exists. If you read it this way, you should be able to derive most of JavaScript rather than memorize it — and when you later forget a detail, you'll know which link in the chain it hangs off.

Depth markers appear inline. [EXPLAIN] means you must be able to explain it out loud, from first principles, under interview pressure, with no notes. [USE] means you must use it correctly and debug it when it breaks, without needing the internals cold. [AWARE] means know it exists, know what problem it solves, know roughly when to reach for it.

Node 0 — the problem before JavaScript exists

Imagine the web as it actually was in 1994. A web page is a text document. It arrives from a server, the browser draws it, and that is the end of the story. If you want to know whether the email address someone typed contains an @, you send the whole form to the server, the server writes a new page saying "invalid email," and sends that page back. Every single interaction — every click that changes anything, every check, every menu that opens — is a full round trip to a machine potentially on another continent, on a modem, at a few kilobytes per second. A form with four validation errors takes four round trips to discover them, one at a time.

The obvious fix is to let some code run inside the browser, on the reader's own machine, so trivial questions get trivial answers. But that requirement is unusual and it shapes everything the language became. The code arrives as plain text from a stranger's server. It must start running essentially instantly — there is no install step, no compile step the user waits through, no "please wait while we build." It must never be able to read the user's files or crash their machine, because it came from an untrusted source. It must not be allowed to freeze the browser's ability to draw the page. And it must never, ever break old pages when the language gets a new feature, because nobody can go back and edit the billions of pages already published.

Brendan Eich wrote the first version of this language at Netscape in ten days in May 1995. Ten days is not enough time to design a language carefully, and it shows — the rough edges you will meet later (typeof null returning "object", == doing surprising conversions, var behaving oddly) are almost all decisions from that period that could never be undone afterwards. The name "JavaScript" was a marketing decision to ride the popularity of Java, a completely unrelated language. This matters practically: interviewers still ask "what's the difference between Java and JavaScript" and the honest answer is "nothing except the name was borrowed."

The pressure that shaped the language is worth holding onto, because it explains the whole rest of the chain. Backward compatibility is close to absolute — the language grows by adding, almost never by removing. That is why JavaScript has three ways to declare a variable, two ways to write a function, two module systems, and both a class keyword and the prototype machinery underneath it. Nothing was ever deleted. Everything was layered.

What's still broken: we have a reason for a language to exist, but no language. The smallest thing any language must do is hold a piece of data and let you name it.

Node 1 — values, types, and the coercion tax

The limitation: you cannot compute anything until you can hold a value and know what kind of thing it is.

JavaScript has exactly seven primitive types [EXPLAIN] and everything else is an object. The primitives are number, string, boolean, undefined, null, symbol, and bigint. That is the entire list, and being able to recite it cold is worth more than it looks, because most confusion in the language traces back to not knowing which side of the primitive/object line something falls on. A primitive is a bare value — it has no parts, it cannot be changed in place, and when you assign it somewhere else you get an independent copy.

number is where the first real surprise lives. JavaScript has one numeric type for ordinary arithmetic, and it is a 64-bit floating point number — the IEEE 754 double that most languages call double. There is no separate integer type. This means 0.1 + 0.2 produces 0.30000000000000004, not because JavaScript is broken but because 0.1 cannot be represented exactly in binary any more than one-third can be written exactly in decimal. It also means integers are exact only up to 2^53 - 1 (9,007,199,254,740,991, exposed as Number.MAX_SAFE_INTEGER) — beyond that, consecutive integers start colliding onto the same floating point value. That number is why bigint [USE] was added in 2020: database IDs, timestamps in nanoseconds, and currency in the smallest unit routinely exceed it. number also carries three strange values you must recognise: Infinity, -Infinity, and NaN ("not a number"), which is what you get from arithmetic that has no meaningful answer, like 0/0 or Number("hello").

string is a sequence of UTF-16 code units [EXPLAIN], and that phrase does real work. Characters outside the basic set — emoji, many CJK characters, mathematical symbols — take two code units, so "👋".length is 2, not 1. Strings are immutable: s[0] = "x" silently does nothing. Template literals with backticks let you interpolate (`hi ${name}`) and span lines [USE].

undefined and null both mean "no value," which is a design wart with a real distinction underneath [EXPLAIN]. undefined is what the language gives you when nothing was supplied — an unassigned variable, a missing function argument, a property that isn't there, a function with no return. null is what a programmer assigns to say "deliberately empty." The practical rule: undefined is absence by accident, null is absence on purpose. And typeof null returns "object", which is simply a bug from 1995 that can never be fixed without breaking existing pages.

symbol [AWARE] creates values guaranteed unique, used as property keys that can't collide with anyone else's. boolean is true/false and needs no explanation, but what converts to them does.

Which brings us to the tax. Because the language was designed so that a novice writing a form validator never sees a type error, JavaScript converts types automatically rather than complaining — this is coercion [EXPLAIN], and it is the single most-probed corner of the language in interviews. Eight values are falsy — they become false in a boolean position — and they are false, 0, -0, 0n, "", null, undefined, and NaN. Everything else is truthy, including "0", "false", [], and {}. The empty array being truthy while [] == false is true is not a contradiction once you know the rules, but it is exactly the kind of thing that gets asked.

The == operator applies those conversion rules before comparing; === does not and requires both type and value to match [EXPLAIN]. Use === always, with one idiomatic exception: x == null is a compact, well-understood check for "is this null or undefined," which is why you'll see it in real code. The famous oddities — NaN !== NaN (use Number.isNaN), null == undefined being true while null === undefined is false, typeof NaN being "number" — all fall out of rules you can state rather than trivia you must memorise.

What you can do at this point: hold single values, know their type, compare them safely, and predict what a conversion will do.

What's still broken: real data is not single values. A user is a name and an email and a signup date, held together as one thing.

Node 2 — objects, and the reference model

The limitation: single values can't represent anything real. You need to group them, and to group groups.

An object [EXPLAIN] in JavaScript is, at bottom, a bag of key-value pairs where keys are strings (or symbols) and values are anything. { name: "Devansh", city: "Noida" } is a complete object. You reach in with dot notation user.name when you know the key at authoring time, and bracket notation user["name"] when the key is itself a value in a variable — that is the only real distinction between the two syntaxes [USE]. Non-string keys get converted to strings, which is why obj[1] and obj["1"] are the same property.

Arrays are objects too [EXPLAIN]. [10, 20, 30] is an object whose keys happen to be "0", "1", "2" plus a length property, with a pile of useful methods attached. This is why typeof [] returns "object" and why you need Array.isArray() to check for one. Functions are objects as well — they can hold properties like anything else. Dates, regular expressions, Map, Set, and errors are all objects. The primitive/object line from Node 1 divides the entire language, and objects are the whole other half.

Now the consequence that generates more real bugs than any other single thing in the language. Objects are handled by reference; primitives by value [EXPLAIN]. When you write const b = a where a is a number, b gets a copy and the two are independent forever. When a is an object, b gets a reference to the same object — a pointer to one shared thing — and b.name = "x" changes what a.name reads. Passing an object into a function is the same story: the function receives a reference, and mutations it makes are visible to the caller. This is why const is weaker than people assume: const user = {} prevents reassigning user to a different object, and does absolutely nothing to prevent user.name = "changed" [EXPLAIN]. const freezes the binding, not the value.

Equality follows the same rule, which trips everyone: {a: 1} === {a: 1} is false, because they are two distinct objects that happen to look alike. === on objects asks "same object?", never "same contents?". There is no built-in deep-equality operator; you compare contents by writing a function, using a library, or (crudely, and only for simple data) comparing JSON.stringify output.

Because references are shared, copying becomes a thing you have to think about [USE]. {...original} and Object.assign({}, original) make a shallow copy — a new outer object whose nested objects are still the same shared nested objects. For a genuinely independent copy you need structuredClone(original) [USE], a built-in that handles nesting, Map, Set, Date, and circular references. Object.freeze(obj) makes an object's own properties unwritable, and it too is shallow.

You'll use a handful of object utilities constantly [USE]: Object.keys, Object.values, and Object.entries turn an object into arrays you can loop over; Object.assign merges; in and Object.hasOwn(obj, key) test for a property's presence, which is different from testing whether its value is truthy. Optional chaining user?.address?.city [USE] returns undefined instead of throwing when something in the middle is missing, and nullish coalescing x ?? "default" [USE] supplies a fallback only when x is null or undefined — crucially not when it's 0 or "", which is exactly where the older || gets it wrong.

What you can do at this point: model real data — nested, grouped, with arrays of records — and reason correctly about what happens when you pass it around.

What's still broken: data sits there. Nothing does anything to it, repeatedly, on demand.

Node 3 — functions as values

The limitation: you need to name a chunk of behaviour and run it many times with different inputs — and, it will turn out, hand that behaviour to other code.

A function packages a piece of work. function add(a, b) { return a + b; } declares one; add(2, 3) runs it. Parameters are the names in the declaration, arguments are the values at the call site. A function with no explicit return returns undefined. Nothing here is unusual yet.

The unusual part, and the one that makes JavaScript what it is, is that functions are values [EXPLAIN]. A function is an object. You can store one in a variable, put one in an array, pass one as an argument, and return one from another function. This is what "first-class functions" means, and it is not a fancy edge feature — it is the mechanism the entire rest of the language is built on. arr.map(fn) works because fn is a value you can hand over. Event handlers work because you hand the browser a function to call later. Every callback, every promise .then, every React hook, every Express middleware is this one property being used.

A function that takes or returns a function is called a higher-order function [EXPLAIN]. That is the entire definition.

There are two syntaxes and the difference matters [EXPLAIN]. A function declaration or expression creates a function with its own this and its own arguments object, and declarations are hoisted (usable before the line they appear on — see Node 4). An arrow function (a, b) => a + b is shorter, implicitly returns the expression when written without braces, and — the load-bearing part — does not have its own this; it uses the this of the surrounding code. That single difference is why arrows fixed an entire class of bug, and it becomes concrete in Node 5. A trap worth memorising now: to arrow-return an object literal you must wrap it in parentheses, () => ({a: 1}), otherwise the braces are read as a function body.

Modern parameter handling removes a lot of old boilerplate [USE]. Default parameters function greet(name = "there") fill in when an argument is undefined. Rest parameters function sum(...nums) collect all remaining arguments into a real array — which replaces the old array-like arguments object that arrow functions don't even have. And the spread operator at a call site, add(...pair), does the reverse, expanding an array into individual arguments. Rest and spread are the same three dots doing opposite jobs depending on which side of the equals sign or call they appear on [EXPLAIN].

What you can do at this point: package behaviour, parameterise it, and pass it around as data.

What's still broken: you have no idea which names a function can actually see when it runs — especially if it runs later, somewhere else, long after the code around it finished.

Node 4 — scope, hoisting, and closures

The limitation: if functions are values that get passed elsewhere and called later, "what does this name refer to right now?" stops being obvious.

Scope is the region of code where a name is visible [EXPLAIN]. JavaScript has three: global scope, function scope, and — since 2015 — block scope, meaning anything between { }. Scopes nest, and lookup goes outward: an inner function can see the names of every function enclosing it, but not the reverse. This is lexical scoping [EXPLAIN], and the word "lexical" means it is determined by where the code is written, not by where or how it is called. That distinction will matter enormously at Node 5, because this is the one thing in the language that breaks it.

The three declaration keywords are a fossil record of the language's history [EXPLAIN]. var is the original: function-scoped (a var inside an if block leaks to the whole function), redeclarable without error, and hoisted — the declaration is conceptually moved to the top of its function and initialised to undefined, so reading it before its line gives undefined rather than an error. let and const, added in 2015, are block-scoped and cannot be redeclared in the same scope. They are also hoisted, but into a temporal dead zone [EXPLAIN] — the name exists but touching it before its declaration line throws a ReferenceError. That is deliberately louder than var's silent undefined, because silence was the bug. The rule in real code: const by default, let when you genuinely reassign, var never — but you must be able to explain var because legacy code and interviewers are both full of it.

Now the payoff. A closure [EXPLAIN] is what you get when a function keeps access to the variables of the scope it was created in, even after that outer scope has finished running. This isn't an add-on feature — it is the direct consequence of lexical scoping plus first-class functions. If a function can be returned and called later, and it was written inside a scope, then the language has no choice but to keep that scope's variables alive as long as the function is reachable.

function makeCounter() {
  let count = 0;
  return () => ++count;
}
const next = makeCounter();
next(); // 1
next(); // 2

makeCounter has returned and its stack frame is gone, but count is still alive because the returned arrow still refers to it. Two calls to makeCounter() produce two independent count variables. Every practical use of closures is this: private state (nothing outside can touch count), function factories, memoisation caches, the module pattern from before modules existed, and — critically — every callback that "remembers" something from where it was defined. When a React useState value seems stale inside a callback, that is a closure over an old value, and knowing this node is what lets you diagnose it instead of guessing.

The classic interview version is the loop [EXPLAIN]: for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)) prints 3, 3, 3, because var created one variable shared by all three closures and by the time they run it is 3. Change var to let and it prints 0, 1, 2, because let creates a fresh binding per iteration. If you can explain that difference in terms of scope and closures rather than reciting it, you understand this node.

What you can do at this point: predict exactly which value any name will have at any point in your program, including inside callbacks that run much later.

What's still broken: this — a name that appears inside functions, is used constantly, and follows none of the lexical rules just described.

Node 5 — this, and how a function is called

The limitation: lexical scope explains every name in the language except one, and that one is everywhere in real code.

this is a name whose value is decided at call time, by how the function was called [EXPLAIN] — not by where it was written. This is the single sentence that dissolves most confusion about it. Four call patterns give four answers, and you should be able to state them in order.

Called as a plain function, fn(), this is undefined in strict mode (and modules and classes are always strict) or the global object in old sloppy mode. Called as a method, obj.fn(), this is obj — the thing to the left of the dot at the moment of the call. Called with new, new Fn(), this is the freshly created object. And called via fn.call(x), fn.apply(x), or a function produced by fn.bind(x), this is whatever x you supplied [USE]. call and apply differ only in how the remaining arguments are passed — individually versus as an array. bind doesn't call the function; it returns a new one permanently tied to that this.

The bug this generates is so common it has a name: losing this. const f = user.greet; f(); — f is now a plain function call, the dot is gone, and this is no longer user. The same thing happens the instant you pass a method as a callback: setTimeout(user.greet, 100) or button.addEventListener("click", this.handleClick) both strip the object away. Historically people fixed this with const self = this captured in a closure, or with .bind(this) in a constructor.

Arrow functions are the modern fix [EXPLAIN], and now you can see exactly why. An arrow has no this of its own, so this inside it resolves lexically — outward through enclosing scopes, exactly like any other variable. That makes this finally obey the Node 4 rules. So: use arrows for callbacks written inside a method, so they inherit the method's this. Do not use an arrow as an object's own method ({ greet: () => this.name } inherits from the surrounding module, not the object) and never as a constructor — arrows cannot be called with new.

What you can do at this point: read any code containing this and say with confidence what it refers to, and fix a "cannot read property of undefined" from a detached method.

What's still broken: you can make one object with behaviour attached. You cannot make ten thousand of them without duplicating the behaviour ten thousand times.

Node 6 — prototypes, and classes on top of them

The limitation: if every user object carries its own copy of every method, you are storing the same functions once per record.

Every object in JavaScript has a hidden internal link to another object, called its prototype [EXPLAIN]. When you read a property and the object doesn't have it, the engine follows that link and looks there, then follows that object's link, and so on until it finds the property or reaches null. This is the prototype chain, and it is the language's entire mechanism for sharing behaviour. Put the methods on one shared prototype object, and a million instances can use them while storing only their own data.

This is why [1,2,3].map(...) works: the array itself holds only the elements, map lives on Array.prototype, and the lookup walks up to find it. Same for "abc".toUpperCase() — with the extra wrinkle that primitives get temporarily wrapped in an object so the lookup can happen at all [AWARE]. The chain also explains why hasOwnProperty exists and why for...in sees inherited properties while Object.keys doesn't.

The name is genuinely confusing and worth pinning down [EXPLAIN]: obj.__proto__ (properly Object.getPrototypeOf(obj)) is the link this object follows. Fn.prototype is a different thing — it is the object that will become the prototype of instances made with new Fn(). One is an object's parent; the other is a constructor function's template. Object.create(parent) makes a new object with parent as its prototype directly, which is the clearest way to see the machinery with nothing on top of it.

new is not magic once you know this [EXPLAIN]. new Fn(args) does four things: creates an empty object, sets its prototype to Fn.prototype, calls Fn with this bound to that object, and returns it (unless the function explicitly returns a different object). Being able to recite those four steps is a standard interview checkpoint.

Classes, added in 2015, are syntax over exactly this [EXPLAIN] — a cleaner way to write the same prototype arrangement, not a new object system. class User { greet() {} } puts greet on User.prototype. extends sets up a prototype chain between the two prototypes. super calls the parent's version. constructor is the function that runs at new. static members live on the class itself rather than instances. Modern additions include #private fields [USE], which are genuinely inaccessible from outside — unlike the old underscore-prefix convention, which was only ever a request. instanceof asks whether a constructor's prototype appears anywhere in an object's chain, which is why it can be fooled and why Array.isArray exists for arrays.

Worth saying plainly: this is prototypal inheritance, and it differs from class-based inheritance in languages like Java in a way interviewers like to probe. There are no classes underneath — only objects linking to other objects. In practice, most modern JavaScript avoids deep inheritance hierarchies entirely in favour of composition, but you will meet the chain constantly when debugging, and class syntax is everywhere.

What you can do at this point: model entities with shared behaviour, read any class-based codebase, and explain what's actually happening underneath.

What's still broken: you can model one thing well. Real programs work on lots of things at once, and looping over them by hand is verbose and error-prone.

Node 7 — collections, iteration, and destructuring

The limitation: almost all real work is "take a list of things, transform it, narrow it, and combine it into an answer" — and a hand-written index loop expresses that badly.

Arrays [EXPLAIN] are ordered, index-from-zero, and their methods split into three groups you should keep straight because the split is where bugs come from. Mutating methods change the array in place and mostly return something other than a new array: push, pop, shift, unshift, splice, sort, reverse, fill. Non-mutating methods return a new array and leave the original alone: map, filter, slice, concat, and the newer toSorted, toReversed, with. sort mutating and comparing as strings by default (so [10, 9].sort() gives [10, 9]) is a perennial gotcha — pass a comparator, sort((a, b) => a - b) [USE].

The three that matter most are map, filter, and reduce [EXPLAIN]. map transforms each element into a new one and always returns an array of the same length. filter keeps elements where the predicate is truthy and returns a shorter or equal array. reduce collapses a whole array into one value by carrying an accumulator through it — it's the general case, and map and filter can both be written with it. Alongside them: find and findIndex for the first match, some and every for boolean questions, includes and indexOf for membership, flat and flatMap for nesting, and forEach for side effects only — forEach returns undefined and cannot be broken out of, which is precisely when you should use a for...of loop instead.

There are four loop forms and choosing wrong is a tell [USE]. Classic for when you need the index or unusual stepping. for...of for values of any iterable — arrays, strings, Map, Set — and it supports break and continue and works with await. for...in for an object's enumerable string keys, including inherited ones, which is why you rarely want it on arrays. And while for "until a condition changes."

Map and Set [USE] exist because plain objects are poor collections. A Map allows keys of any type including objects, preserves insertion order, has a real .size, and doesn't inherit stray keys from Object.prototype; use it when keys are dynamic or non-string. A Set holds unique values, making [...new Set(arr)] the standard deduplication idiom. WeakMap and WeakSet [AWARE] hold keys weakly so entries vanish when nothing else references the key — the tool for attaching metadata to objects without leaking memory, which reconnects at Node 15.

Underneath all of this sits the iteration protocol [EXPLAIN]: an object is iterable if it has a Symbol.iterator method returning an object with a next() that yields {value, done}. for...of, spread, Array.from, and destructuring all speak this protocol, which is why they work uniformly across arrays, strings, Map, Set, and anything you make iterable yourself. It is also what Node 12's generators plug into.

Finally, destructuring [EXPLAIN] is how values come out of these structures cleanly. const {name, email} = user pulls properties by name, with renaming ({name: n}), defaults ({role = "user"}), and nesting all supported. const [first, second, ...rest] = arr pulls by position. It works in function parameters, which is how you get named-argument-style APIs: function createUser({name, email, role = "user"}). Combined with spread, {...defaults, ...overrides} becomes the standard merge, later keys winning. You will read these in every modern codebase, and in React they are unavoidable.

What you can do at this point: express real data transformations concisely and idiomatically — which is most of what a working JavaScript developer actually types.

What's still broken: all of this assumes nothing goes wrong. Things go wrong constantly.

Node 8 — errors and failure

The limitation: transformations assume valid input and available resources. Real input is malformed and real resources are missing.

An error in JavaScript is thrown with throw and caught with try/catch/finally [EXPLAIN]. When something throws, execution stops immediately and unwinds outward through the call stack looking for the nearest enclosing catch; if none exists, the program crashes — in Node the process exits, in a browser the error surfaces in the console and that turn of work stops. finally runs regardless of whether the block succeeded or threw, which makes it the place to release things.

You can throw any value, but you should throw Error objects [USE], because they carry a message, a name, and a stack recording where the throw happened. The built-in subclasses are worth recognising by sight since they tell you what kind of mistake you made: TypeError (used a value in a way its type doesn't support — the "cannot read properties of undefined" family), ReferenceError (a name that doesn't exist, including the temporal dead zone from Node 4), SyntaxError (the code didn't parse — including JSON.parse on bad input), and RangeError (a legal type, illegal value, like infinite recursion blowing the stack). Custom errors [USE] are made by extending Error, and they are the mechanism that lets a caller distinguish "the user sent bad data" from "the database is down" — which in an API is the difference between returning 400 and 500. Error also has a cause option for wrapping a lower-level error without discarding it.

The judgement call, which is a genuine interview topic: catch only what you can handle [EXPLAIN]. A catch that swallows an error and continues turns a loud failure into a silent wrong answer, which is strictly worse. Either handle it meaningfully, or enrich it and rethrow, or let it propagate to a place that can. This is the same principle that produces centralised error middleware in an Express or Fastify app.

What you can do at this point: fail loudly, deliberately, and with enough information to debug — and distinguish between kinds of failure.

What's still broken: every technique so far assumes each line finishes before the next begins. But the whole reason for Node 0 was talking to a server, and that takes time you cannot stand still for.

Node 9 — one thread, and the event loop

The limitation: fetching data over a network takes hundreds of milliseconds. If the language waits for it, everything stops.

Here is the constraint that defines JavaScript's second half. JavaScript runs your code on a single thread [EXPLAIN] — one sequence of instructions, one thing happening at a time, no two lines of your code ever running simultaneously. This was a deliberate simplification: multiple threads sharing memory produce a category of bug (race conditions, deadlocks) that is genuinely hard, and a language meant to be written by everyone couldn't afford it. It also fell out of the browser's needs — the same thread draws the page, so if your code is running, the page is frozen.

A single thread plus a slow network sounds like a contradiction, and resolving it is the key idea. The trick is that the slow work does not happen on that thread. When you call something like setTimeout or fetch, you are not asking JavaScript to wait; you are handing the job to the surrounding environment — the browser, or Node — which has other threads and operating-system facilities available. That environment goes off and does the work, and your thread continues to the next line immediately. When the work finishes, the environment doesn't interrupt you. It places a callback — a function you supplied earlier, exactly as Node 3 made possible — into a queue.

The event loop [EXPLAIN] is the piece that connects those. It is a simple, endless cycle: run the current piece of work until it finishes completely; when the call stack is empty, take the next callback off the queue and run it; repeat. The rule that "the current work runs to completion before anything queued can start" is called run-to-completion, and it has a direct consequence you should be able to state: any long synchronous loop blocks everything — no clicks handled, no rendering, no timers firing, no incoming requests served, until it ends. A tight while loop for five seconds freezes a browser tab and stalls a Node server for every user at once. This is the reason "don't block the event loop" is repeated so often in backend interviews.

It also explains setTimeout(fn, 0) [EXPLAIN], which does not mean "run now." It means "put this in the queue; it will run after the current work finishes and after anything already queued." A timeout's delay is a minimum, not a guarantee.

The historical way to use this was to pass callbacks directly, and it works fine for one level. It falls apart when one asynchronous step depends on the result of the previous one, because each nests inside the last — the shape people call callback hell [EXPLAIN]. The nesting is ugly, but the real defects are structural: there is no way to return a value out of the pyramid, try/catch from Node 8 doesn't work (the callback runs later, on a fresh stack, long after the try block exited), so every level must handle errors manually via the (err, result) convention, and it's easy to call a callback twice or never.

What you can do at this point: explain why JavaScript can be single-threaded and still handle thousands of concurrent connections — the most valuable thing in this entire node for a backend interview.

What's still broken: asynchronous results are not values. They can't be returned, composed, or wrapped in try/catch.

Node 10 — Promises

The limitation: callbacks make "a result that will exist later" invisible to the language. It needs to be a thing you can hold.

A Promise [EXPLAIN] is an object representing a value that isn't available yet. That reframing is the whole innovation: the eventual result becomes a first-class value you can store in a variable, return from a function, pass around, and put in an array. A promise is in exactly one of three states — pending, fulfilled (with a value), or rejected (with a reason) — and once it leaves pending it is settled and can never change again. That immutability is what makes it safe to hand around.

You consume one with .then(onFulfilled), .catch(onRejected), and .finally(onSettled) [USE]. The mechanical fact that makes it powerful: .then returns a new promise, and if your handler returns a promise, the chain waits for it and unwraps it [EXPLAIN]. That's what turns the nested pyramid into a flat chain — each .then returning the next step's promise instead of nesting inside it. And because a rejection propagates down the chain until it meets a .catch, a single .catch at the end handles failures from every step above it. That is try/catch restored for asynchronous code, which was exactly what Node 9 broke.

You create promises with new Promise((resolve, reject) => {...}) [USE], but you should mainly be doing this to wrap an older callback-based API — most things you touch already return promises. Promise.resolve(v) and Promise.reject(e) make already-settled ones.

The combinators are where real concurrency lives, and knowing which is which is a genuine interview differentiator [EXPLAIN]. Promise.all([...]) waits for all to fulfil and gives you an array of results, but rejects immediately if any one rejects — use it when you need everything and partial success is useless. Promise.allSettled([...]) waits for all and gives you a status-tagged result for each, never rejecting — use it when you want the successes even if some fail. Promise.race([...]) settles as soon as the first one settles either way — the standard way to add a timeout. Promise.any([...]) gives the first fulfilment, ignoring rejections unless all fail.

This is also where concurrency and parallelism separate cleanly [EXPLAIN]. Promise.all gives you concurrency: several operations in flight at once, still on one thread, because the waiting happens outside your thread. It is not parallelism — your JavaScript still runs one line at a time. Genuine parallel execution needs separate workers (Node 17).

Two failure modes to know: an unhandled rejection [USE] is a promise that rejects with no .catch anywhere — in modern Node this crashes the process by default, and in browsers it logs loudly. And a promise's executor function runs immediately when you construct it, not when you call .then, which surprises people who expect it to be lazy.

What you can do at this point: compose asynchronous work, run it concurrently, and handle its failures in one place.

What's still broken: chains are flat but still not readable. Conditionals, loops, and shared intermediate values across steps remain awkward, and the code looks nothing like the sequential logic in your head.

Node 11 — async/await, and the microtask queue

The limitation: promise chains express sequence with method calls. Your brain expresses sequence with lines.

async/await [EXPLAIN] is syntax over promises — no new capability, a completely different reading experience. Marking a function async makes it always return a promise (a plain value gets wrapped, a thrown error becomes a rejection). Inside it, await promise pauses that function until the promise settles, then evaluates to its fulfilled value, or throws its rejection reason.

The two consequences are what make it worth having. Sequential asynchronous code reads top to bottom, so const user = await getUser(id); const orders = await getOrders(user.id); looks like ordinary code. And because a rejected await throws, ordinary try/catch from Node 8 works again — one error mechanism for the whole language instead of two.

The thing to be crisp about, because it's the most common mistake: await does not block the thread [EXPLAIN]. It suspends the one async function and returns control to the event loop, which is free to run everything else. It is not the blocking while loop from Node 9. But it does serialise the awaits within that function, which produces the most common real performance bug in modern JavaScript: awaiting inside a loop turns work that could have taken as long as the slowest item into work that takes as long as all of them combined. The fix is to start them all and await together — await Promise.all(items.map(fetchOne)) [USE]. Knowing when sequencing is required (the second call needs the first's result) versus accidental is a real skill.

A few practicals [USE]: top-level await works in ES modules but not in CommonJS or plain scripts (Node 13). for await (const x of asyncIterable) iterates asynchronous sequences (Node 12). An async callback passed to forEach does not make forEach wait — the callbacks all start and forEach returns immediately, which silently breaks sequencing; use for...of with await, or Promise.all with map. And an await inside a try whose promise you started earlier can still produce an unhandled rejection if it rejects before you get to the await.

Now the mechanism that ties this node back to Node 9. There are two queues, not one [EXPLAIN]. The macrotask queue holds things like timers, I/O completions, and (in browsers) events. The microtask queue holds promise callbacks and queueMicrotask. The rule is: after each macrotask, the event loop drains the entire microtask queue — including microtasks added while draining — before taking another macrotask. So promise callbacks always run before a setTimeout(fn, 0) queued at the same moment. This is the mechanism behind the "predict the output order" question that appears in a large fraction of JavaScript interviews, and once you have this rule plus run-to-completion, you can derive the answer instead of memorising it. A related consequence: an infinite chain of microtasks starves the macrotask queue and hangs the program, even with nothing blocking.

Node adds its own ordering details on top — process.nextTick running before other microtasks, and named phases for timers, I/O and setImmediate [AWARE] — which belong to the nodejs-runtime topic rather than here.

What you can do at this point: write asynchronous code that reads sequentially, choose deliberately between sequential and concurrent, and predict execution order exactly.

What's still broken: everything so far produces one value, eventually. Some things produce many values over time, or more values than fit in memory at once.

Node 12 — generators, iterators you write, and async iteration

The limitation: a function runs to completion and returns once. A stream of results — pages of an API, lines of a huge file — doesn't fit that shape.

A generator [USE] is a function declared function* that can pause itself. yield produces a value and suspends; calling .next() on the returned generator object resumes it from exactly where it stopped, with all its local state intact. This gives you a function that produces a sequence lazily, computing each value only when asked. An infinite sequence becomes expressible, because nothing is computed until requested.

Generators return objects that satisfy the iterator protocol from Node 7, which means they slot straight into for...of, spread, and destructuring with no extra work. That is the cleanest way to make your own data structure iterable: define *[Symbol.iterator]() on it. yield* delegates to another iterable, which makes recursive traversal of trees remarkably short.

Async generators [USE], async function* consumed with for await (const x of ...), are the same idea where each value arrives asynchronously. This is the natural shape for paginated APIs — yield each page's items, let the consumer loop, and fetch the next page only when they reach it — and for consuming Node streams and streaming LLM responses, which is where you will actually meet it given your work on qbank.

Honest scoping: you will read generators more often than you write them, and in application code they're uncommon. But async iteration is genuinely useful for streaming, and the pause/resume idea is worth having because it's what powers a lot of library internals [AWARE].

What you can do at this point: produce and consume sequences that arrive over time or don't fit in memory.

What's still broken: everything so far lives in one file. Real programs are thousands of functions, and putting them all in one scope is untenable.

Node 13 — modules

The limitation: you need many files, without every name in every file colliding in one global namespace.

The original model was <script> tags, and everything a script declared at the top level went into one shared global object [EXPLAIN]. Two libraries both defining $ broke each other silently. Load order was implicit and fragile — a script using something another script defined had to come after it, enforced by nothing. There was no way to state a dependency and no way to keep anything private.

The first workaround used Node 4's closures: wrap a file's contents in an immediately-invoked function expression (IIFE) so its variables are function-scoped rather than global, and deliberately assign only the public parts outward. That was the module pattern [AWARE], and it worked, but dependencies were still implicit.

Node.js, arriving in 2009 and needing real modules for server code, brought CommonJS [USE]: require("./thing") and module.exports. Loading is synchronous — require reads and evaluates the file right then and returns its exports — which is fine on a server with a local disk and impossible in a browser over a network. require also caches, so a module's body executes only once no matter how many files require it, making module-level state effectively a singleton.

The standard answer came in 2015: ES Modules (ESM) [EXPLAIN], import/export, now the official language module system in both browsers and Node. The differences from CommonJS are not cosmetic. ESM is statically analysable — imports and exports are declarations resolved before the code runs, not function calls you can put inside an if. That's what enables tree-shaking, where a bundler proves an exported function is never imported anywhere and drops it from the output. Loading is asynchronous, so it works over a network. ESM bindings are live: you get a view of the exporting module's variable, not a copy of its value at import time. Modules are always in strict mode, have their own top-level scope (so a top-level const is not global), and support top-level await.

Practically you need to know both, because the ecosystem still straddles them [USE]. Named exports (export const x, many per file) versus a single export default. import("./m") as a function for dynamic, on-demand loading — which is what code-splitting and lazy-loading a route are built on. In Node, .mjs/.cjs extensions and "type": "module" in package.json decide which system a file uses; ESM can import CommonJS but not cleanly the reverse; and __dirname and require don't exist in ESM. The ERR_REQUIRE_ESM error and "cannot use import statement outside a module" are both this boundary biting, and recognising them instantly saves real time.

Since browsers historically couldn't load thousands of module files efficiently, bundlers [AWARE] — Webpack, Rollup, esbuild, Vite — arose to combine, transform, and minify modules into a few files. Modern browsers do support ESM natively, but bundlers remain standard for tree-shaking, code splitting, and handling non-JavaScript assets.

What you can do at this point: structure a real codebase across many files with explicit, private-by-default dependencies.

What's still broken: structured code that has no idea how to handle dates, parse a payload, format a number for a user, or match a pattern in text.

Node 14 — the standard library for real data

The limitation: every real program serialises, parses, formats, and matches. Getting these wrong produces bugs that survive to production.

JSON [EXPLAIN] is the data interchange format, and it is a subset of JavaScript object syntax, which is the source of most surprises. JSON.stringify converts a value to a string; JSON.parse converts back and throws a SyntaxError on bad input, which means every parse of untrusted data belongs in a try/catch from Node 8. What JSON cannot represent matters: undefined and functions are dropped from objects and become null in arrays; Date objects silently become ISO strings and do not come back as dates; Map, Set, BigInt, and NaN/Infinity don't survive at all; circular references throw. stringify takes a replacer and an indent argument (JSON.stringify(x, null, 2) for readable output), and parse takes a reviver — the standard place to turn date strings back into Date objects.

Dates are the weakest part of the standard library [USE]. Date months are zero-indexed (December is 11), a Date is really a millisecond count since 1 Jan 1970 UTC, and parsing non-ISO strings is implementation-dependent. Timezones are where the real damage happens: a date rendered in the user's local zone and stored in the server's is a classic production bug. The practical guidance is to store UTC ISO strings, convert at the display boundary only, and reach for a library rather than hand-rolling. The Temporal API [AWARE] is the standardised replacement designed to fix all of this and is now shipping in browsers — worth knowing it exists, and worth saying so in an interview.

Intl [AWARE] is the built-in internationalisation layer that formats numbers, currency, dates, relative times ("3 days ago"), and plurals correctly per locale. Most people hand-roll these badly; knowing Intl.NumberFormat and Intl.DateTimeFormat exist is cheap and looks good.

Regular expressions [USE] are a full topic of their own in your catalog, so here just the JavaScript-specific surface: literals /pattern/flags versus new RegExp(str) for dynamic patterns, the flags g (all matches), i (case-insensitive), m (multiline anchors), s (dot matches newline), u (Unicode); test for a boolean, match/matchAll for extraction, replace/replaceAll with a function replacer; capture groups and named groups (?<year>\d{4}). The one real trap: a regex with the g flag carries mutable lastIndex state between test calls, so reusing a global regex gives alternating results.

Strings and numbers round it out [USE]: split, join, trim, padStart, slice versus substring, startsWith/includes, and localeCompare for sorting text correctly. On numbers, parseInt versus Number (parseInt("12px") is 12, Number("12px") is NaN), toFixed returning a string and rounding in ways that surprise, and the direct consequence of Node 1: never store money in floating point — use integer minor units or a decimal library.

What you can do at this point: handle the data formats and text manipulation that make up the bulk of day-to-day application code.

What's still broken: all of this allocates memory, and nothing has explained when it goes away — or why a long-running server slowly dies.

Node 15 — memory and garbage collection

The limitation: closures (Node 4) and references (Node 2) both keep things alive. In a program that runs for weeks, that becomes a question you have to answer.

JavaScript is garbage collected [EXPLAIN]: you never free memory explicitly. The engine periodically determines which values are still reachable — traceable from a set of roots like the global object and the current call stack — and reclaims everything else. Reachability, not reference counting, is the rule, which is why two objects pointing at each other but at nothing else are both collectable. Modern engines use generational collection, on the observation that most objects die young [AWARE].

The reason to care is that reachability can be accidental, and a memory leak in JavaScript is simply something staying reachable that you thought was finished [EXPLAIN]. The recurring causes are worth having in your head as a checklist: an event listener registered and never removed keeps its handler alive, and the handler's closure keeps everything it captured alive; a setInterval never cleared does the same forever; a module-level Map or array used as a cache that only ever grows; a detached DOM node still referenced by a JavaScript variable, keeping the whole subtree alive; and closures capturing far more than they need. Each of these traces directly back to an earlier node, which is the point — leaks are not a separate subject, they're the consequence of the reference and closure semantics you already learned.

WeakMap and WeakSet from Node 7 are the deliberate escape hatch [USE]: they hold their keys weakly, so an entry disappears when the key becomes otherwise unreachable. That makes them the correct tool for attaching data to objects you don't own the lifetime of. WeakRef and FinalizationRegistry [AWARE] exist for rarer cases and are easy to misuse.

Two practical additions: the call stack has a limit, so unbounded recursion throws RangeError: Maximum call stack size exceeded — JavaScript does not reliably do tail-call optimisation despite it being in the spec. And browser DevTools' heap snapshots and allocation timelines are the actual tool for finding a leak [AWARE]; naming that tool in an interview is worth more than reciting the leak list.

What you can do at this point: reason about why a long-running Node process's memory grows, and know the shape of the fix.

What's still broken: you can use the language's objects. You cannot yet change how objects themselves behave.

Node 16 — metaprogramming

The limitation: frameworks do things — reactive state, ORM models, dependency injection — that ordinary object syntax can't express. You should know how, because you use those frameworks.

Properties are not just key-value pairs; each has a descriptor [AWARE] — value, writable, enumerable, configurable, or alternatively a get/set pair. Object.defineProperty sets these explicitly. enumerable: false is why some properties don't appear in Object.keys or for...in.

Getters and setters [USE] let a property look like data while running a function: get fullName() { return this.first + " " + this.last; } is accessed as obj.fullName with no parentheses. Useful for computed values and validation on assignment; a hazard when they hide expensive work behind innocuous-looking property access.

Symbols [AWARE] from Node 1 come into their own here. Well-known symbols let you hook into language behaviour: Symbol.iterator (Node 7) makes an object iterable, Symbol.asyncIterator does it for for await, Symbol.toPrimitive controls coercion (Node 1), Symbol.toStringTag changes what Object.prototype.toString reports.

Proxy and Reflect [AWARE] are the deep end. A Proxy wraps an object and intercepts fundamental operations — property get, set, delete, has — letting you run code on every access. This is exactly how Vue's reactivity, several ORMs, and mocking libraries work. You will very rarely write one, but knowing the mechanism means framework "magic" stops being magic, and that's a good thing to be able to say out loud.

What you can do at this point: read framework internals without treating them as unknowable, and recognise which mechanism a piece of magic is using.

What's still broken: everything so far treats JavaScript as one fixed language in one fixed place. It is neither.

Node 17 — the language as a moving target, and where it runs

The limitation: the code you write is not exactly the code that runs, and "JavaScript" behaves differently depending on where it executes.

The language is standardised as ECMAScript, governed by a committee called TC39 [AWARE]. Proposals move through stages 0 to 4; stage 4 means shipping. Since 2015 there has been an annual release — ES2015 (also called ES6, and by far the biggest, giving us let/const, arrows, classes, promises, modules, destructuring, template literals, Map/Set, symbols, generators) and a steady yearly trickle since: async/await in ES2017, optional chaining and nullish coalescing in ES2020, Object.hasOwn and top-level await in ES2022. When someone says "ES6 features" in an interview they nearly always mean that 2015 batch.

Because backward compatibility is near-absolute (Node 0), new syntax can't change old behaviour — so "use strict" [USE] exists as an opt-in stricter mode: assigning to an undeclared variable throws instead of creating a global, this is undefined in plain function calls (Node 5), and various silent failures become errors. Modules and class bodies are strict automatically, so in modern code you get it without asking.

Your code often isn't what runs. Transpilers like Babel and TypeScript's compiler rewrite modern syntax into older syntax so it runs in older engines; polyfills add missing functions (an old engine has no Array.prototype.flat, so you supply one) — syntax needs transpiling, missing library functions need polyfilling, and knowing which is which is a real distinction [EXPLAIN]. Browser support targets are usually expressed via browserslist, and source maps map the running code back to what you wrote for debugging.

Engines [AWARE] run the language: V8 (Chrome, Node, Deno, Edge), SpiderMonkey (Firefox), JavaScriptCore (Safari, Bun). They parse to bytecode, interpret it, and use a JIT compiler to optimise hot code at runtime, deoptimising when assumptions break — which is the honest answer to "why is JavaScript fast enough" and also why micro-benchmarks mislead.

Most importantly, the language is small and the runtime supplies the rest [EXPLAIN]. setTimeout, fetch, console, the DOM, localStorage — none of these are in the ECMAScript spec. Browsers provide DOM APIs, window, storage, and workers, sandboxed by the same-origin policy. Node provides filesystem, network, process, Buffer, and its own module system. Deno and Bun are newer runtimes with different defaults. This is why code that works in Node crashes in a browser and vice versa, and why "is setTimeout part of JavaScript?" (no) is a fair question. For genuine parallelism — the thing Node 9 ruled out — you use Web Workers in the browser or worker_threads in Node [AWARE]: separate threads with separate memory that communicate by passing messages.

What you can do at this point: explain why a feature works in one place and not another, and speak accurately about the language's versioning and tooling.

What's still broken: the language tells you nothing about your data's shape until the moment it goes wrong, at runtime, in production.

Node 18 — what JavaScript cannot tell you

The limitation: dynamic typing (Node 1) is why user.emial is a silent undefined that surfaces three functions later as "cannot read properties of undefined."

This is the honest endpoint of the chain. JavaScript checks nothing until it executes. A typo in a property name is legal. A function expecting a number happily receives a string and returns "12" instead of 12 via coercion. Refactoring is risky because nothing tells you which of two hundred call sites you broke. Editors can only guess at autocomplete because they don't know what a variable holds.

The ecosystem's answers, in increasing order of commitment: JSDoc comments [AWARE], which let editors infer types from annotations in plain JavaScript; runtime validation with a library like Zod, which checks data at the boundaries where it actually arrives untrusted — from an HTTP request, a database, or an LLM response — and is a separate need that types alone don't cover, because types vanish at runtime; and TypeScript [AWARE], a superset that adds a compile-time type system, catches these errors before the code runs, and erases entirely to plain JavaScript at build time.

That last one is the next topic in your catalog for exactly this reason, and the framing that matters: TypeScript is not a different language. It is JavaScript plus a checker. Every node in this chain remains true underneath it — closures, this, prototypes, the event loop, microtasks, modules. People who learn TypeScript without this chain end up writing type annotations over a runtime they cannot explain, which is precisely the gap that shows under interview pressure.

What you can do at this point: state clearly what dynamic typing costs and what the ecosystem does about it — and move into typescript knowing what it's fixing.

Where the chain gets misread

  • "JavaScript is single-threaded, so it can't do things concurrently." (Node 9) Your code runs on one thread; the I/O doesn't. The runtime does slow work elsewhere and queues callbacks. That's how one Node process serves thousands of simultaneous connections.
  • "await blocks the thread." (Node 11) It suspends one async function and hands control back to the event loop. Everything else keeps running. The blocking thing is a synchronous loop, not an await.
  • "const makes a value immutable." (Node 2) It prevents reassigning the binding. const arr = []; arr.push(1) is completely legal. Immutability needs Object.freeze — and even that is shallow.
  • "{...obj} gives me a copy so I'm safe." (Node 2) It's a shallow copy. Nested objects are still shared, so mutating copy.address.city changes the original. Use structuredClone for deep.
  • "Classes mean JavaScript has real class-based inheritance." (Node 6) class is syntax over prototypes. There are only objects linking to other objects underneath.
  • "Arrow functions are just shorter functions." (Nodes 3, 5) They also have no own this, no arguments, and can't be used with new. That's why they fix callbacks and break as object methods.
  • "Hoisting means let and const aren't hoisted." (Node 4) They are hoisted — into the temporal dead zone, where access throws instead of quietly giving undefined. The difference is the error, not the hoisting.
  • "setTimeout(fn, 0) runs immediately." (Nodes 9, 11) It runs after the current work completes and after the entire microtask queue drains. Any pending promise callback beats it.
  • "== is just a looser ===." (Node 1) It runs a conversion algorithm first. Use ===; the one reasonable exception is x == null to catch both null and undefined.
  • "0.1 + 0.2 !== 0.3 is a JavaScript bug." (Node 1) It's IEEE 754 floating point, identical in Java, Python, and C. The JavaScript-specific part is having no separate integer type.
  • "forEach with an async callback waits for each one." (Node 11) It doesn't. It fires them all and returns immediately. Use for...of with await for sequence, or Promise.all with map for concurrency.
  • "A .catch at the end catches everything." (Node 10) Only what's in that chain. A promise started elsewhere, or one thrown inside a setTimeout callback, escapes entirely.
  • "setTimeout and fetch are part of JavaScript." (Node 17) They're runtime APIs from the browser or Node, not the ECMAScript language.
  • "Memory leaks can't happen with garbage collection." (Node 15) GC frees the unreachable. A listener you never removed or a cache that only grows keeps things reachable forever.

The chain in one paragraph

JavaScript exists because a web page couldn't respond to its own user without a network round trip, and it was built in ten days under a constraint of never breaking what came before — which is why nothing was ever removed and everything was layered on. It starts with seven primitive types and automatic coercion, adds objects that are handled by reference (so copying, equality, and const all behave differently from what people assume), then makes functions into values, which immediately forces the question of what names a function can see — answered by lexical scope and, unavoidably, closures. this is the one name that ignores those rules, resolving by how a function was called, which is exactly why arrow functions exist. Prototypes let many objects share behaviour without duplicating it, and class is syntax over that machinery, not a replacement for it. Collections and the iteration protocol make bulk transformation expressive, errors make failure loud and distinguishable, and then the whole language turns a corner: because it runs on a single thread and can't wait for a network, slow work is handed to the runtime and returns as callbacks through an event loop — which broke returning values and try/catch, which Promises restored by making an eventual result a real value, which async/await then made read like ordinary sequential code, on top of a two-queue ordering rule where microtasks always drain before the next macrotask. Generators handle sequences that arrive over time, modules replace one shared global namespace with explicit private-by-default dependencies, the standard library handles JSON, dates, and text with well-known sharp edges, and garbage collection frees whatever is unreachable — which is why every leak is really a closure or a reference you forgot you were holding. Above all of that sits a language that is versioned annually by TC39, transpiled and polyfilled to reach older engines, and executed by runtimes that supply most of the APIs you actually call. And the one thing it still won't do is tell you the shape of your data before it runs — which is the entire reason TypeScript is the next topic.
