Node 38 — /proc, /sys, and where every metric comes from

The limitation: the system is complete and opaque. Nothing can see inside it.

A filesystem that is not a filesystem

/proc is a procfs mount — a filesystem with no storage behind it. Reading a file there does not read a disk; it calls a kernel function that generates the content at that instant. Writing to one calls a function that changes kernel state.

This is Node 21's "everything is a file" used as the kernel's entire user interface, and the payoff is total: every diagnostic tool on Linux is a program that reads text files. [EXPLAIN] ps, top, free, uptime, vmstat, lsof, your Prometheus node exporter, your APM agent, your container runtime — all of them are parsing /proc. There is no privileged metrics API. Knowing this means you are never dependent on a tool being installed: cat is enough.

The per-process files that matter

Under /proc/<pid>/, and the six worth knowing cold:

  • status — human-readable summary: state (Node 5), thread count, VmRSS and VmSize (Node 10), UID and GID, capabilities (Node 25), signal masks (Node 30), and the two context-switch counters (Node 6).
  • stat — the same in a single machine-readable line: 52 fields including utime and stime in clock ticks, minor and major faults (Node 10), and the start time. This is the file top reads.
  • maps and smaps_rollup — the address space, region by region, with RSS and PSS totals (Node 11).
  • fd/ — one symbolic link per open descriptor, naming its target. ls -l /proc/<pid>/fd is the descriptor-leak diagnosis from Node 19, and it works with no tooling at all.
  • limits — the effective resource limits, which is how you check whether ulimit -n actually applied to a running service rather than to your shell.
  • cmdline and environ — arguments and environment, NUL-separated (Node 35, including the secret-exposure point).
  • task/ — one subdirectory per thread, each with the same files. This is how top -H works and how you attribute CPU to a specific thread in a Node process (Node 15).
  • stack and wchan — the kernel-side stack and the function the process is sleeping in. For a D-state hang, cat /proc/<pid>/stack tells you exactly which kernel operation it is stuck in.

The system-wide ones

  • /proc/stat — cumulative processor time since boot, per core, split into user, nice, system, idle, iowait, irq and softirq. These are counters, not percentages. Every CPU percentage you have ever seen is computed by sampling this twice and dividing the deltas — which is why a tool's first sample is meaningless and why "average CPU since boot" is a different and usually useless number.
  • /proc/meminfo — MemTotal, MemFree, MemAvailable, Buffers, Cached, Dirty, Writeback, SwapTotal. This is what free -m formats, and Node 13's point about reading MemAvailable rather than MemFree lives here.
  • /proc/loadavg — the 1, 5 and 15 minute load averages, plus the running/total task counts. Worth restating from Node 5: Linux load average counts running and uninterruptibly-sleeping tasks, so a machine with a hung disk shows a load of 40 with idle processors. Load average is not a CPU metric on Linux, and treating it as one is a common and consequential misreading.
  • /proc/interrupts — per-IRQ, per-core counts (Node 2). Uneven distribution across cores on a network-heavy machine is diagnosable here.
  • /proc/net/tcp and tcp6 — every socket with its state and queue depths. This is what ss and netstat read (Node 32).
  • /proc/pressure/ — PSI (Node 27), the stall-time metrics.
  • /proc/sys/ — the writable half. Every sysctl is a file here: vm.swappiness, net.core.somaxconn, fs.file-max, vm.overcommit_memory. sysctl -w is a file write, and /etc/sysctl.d/ makes it survive a reboot.

/sys (sysfs) is the newer, more structured counterpart, exposing the device model — block devices, network interfaces, cgroups (Node 27 is entirely /sys/fs/cgroup), CPU frequency scaling, and the I/O scheduler selection from Node 23.

Where this is in your stack

Container metrics are the same files, in the container's namespaces. A Prometheus node exporter reads /proc and /sys; cAdvisor reads /sys/fs/cgroup for per-container CPU, memory and I/O. When you look at a Grafana panel showing container memory, the number came from memory.current in a cgroup file. When you look at CPU throttling, it came from cpu.stat's nr_throttled. There is no other source.

And the namespace gap from Node 26 lands here as a practical problem. /proc/cpuinfo and /proc/meminfo inside a container show the host's values, because those files are not namespaced. So any library or runtime that sizes itself from them is wrong inside a container. This is why the JVM needed UseContainerSupport, why Node added os.availableParallelism(), and why lscpu in a one-core pod reports 64 cores. The correct source is the cgroup files, and tools like lxcfs exist to present a namespace-correct /proc by mounting a FUSE filesystem over it.

Reading these directly is often faster than any tooling. A practical sequence for a misbehaving Node process, using nothing but cat:

PID=$(pgrep -n node)
cat /proc/$PID/status | grep -E 'State|Threads|VmRSS|ctxt'
ls /proc/$PID/fd | wc -l                    # descriptor count vs the limit
grep 'Max open files' /proc/$PID/limits
cat /proc/$PID/stack                        # if it is in D state
cat /sys/fs/cgroup/cpu.stat                 # nr_throttled — Node 27
grep -E '^(anon|file) ' /sys/fs/cgroup/memory.stat

Six commands, and between them they distinguish a blocked event loop, a descriptor leak, CPU throttling, page-cache-driven memory pressure, and a storage hang — the five most common production failures in this document. [USE]

Node's own metrics come from the same place. process.memoryUsage().rss reads /proc/self/statm. process.cpuUsage() uses getrusage. os.loadavg() reads /proc/loadavg. And what Node cannot tell you — its own cgroup limits, its throttling, its accept-queue depth — you read from these files yourself. Exporting nr_throttled and event-loop delay (Node 20) side by side is a genuinely high-value pair of custom metrics for any containerised Node service.

What you can do at this point: explain what procfs is and why every Linux tool is a text parser, name the per-process and system-wide files that matter and what each answers, explain why CPU percentages require two samples, correct the common misreading of Linux load average, explain why container CPU and memory detection is wrong and where the right numbers live, and diagnose the five common failures with cat alone.

What's still broken: /proc gives you state — a snapshot of what is. It cannot tell you what happened: which function consumed the CPU, which syscall was slow, which query caused the disk activity. Observing behaviour rather than state needs a different mechanism.
