Node 28 — the container, assembled

The limitation: none. Everything needed exists. This node contains no new mechanism and exists to put the pieces together, because the assembly is the thing people never see.

A container is a process — an ordinary Linux process, visible in the host's process list with a real PID — started with a particular combination of namespaces, cgroups, a layered root filesystem, a credential mapping, a capability set, and a syscall filter. [EXPLAIN] There is no container object in the kernel. The kernel has no idea containers exist. grep -r container in the Linux source finds nothing relevant, because a container is a userspace convention about how to call clone().

What an image is, precisely

Before the runtime, the artefact. An OCI image is three kinds of thing, all content-addressed by SHA-256 digest:

  • Layers — tar archives of filesystem differences, usually gzip- or zstd-compressed. Each is identified by the digest of its content, which is why an unchanged layer is never re-pulled and why layers are shared across images.
  • A config — a JSON document with the default command, environment, working directory, user, exposed ports, and the ordered list of layer digests.
  • A manifest — a JSON document listing the config and the layers. Its own digest is the image's digest, the sha256:... you see. A manifest list (or image index) maps architectures to manifests, which is how one tag serves both linux/amd64 and linux/arm64 (Node 0).

A tag like node:20-alpine is a mutable pointer to a digest. Digests are immutable and tags are not, which is why production deployments should reference image@sha256:... and why imagePullPolicy: Always exists. Pulling is plain HTTPS against a registry API: fetch the manifest, then fetch each layer the local store does not already have.

What docker run does, step by step

Every step below is a node in this document. That is the point of reading it.

  1. Resolve and pull. The client asks the daemon; the daemon asks the registry for the manifest, selects the right architecture, and downloads missing layers. Each is verified against its digest and unpacked into a directory in the local store.
  2. Prepare the filesystem. Create a writable upper directory and assemble an overlayfs mount with the image's layers as lower directories (Node 24). Also prepare the mount specifications for any volumes and bind mounts (Node 21).
  3. Create the cgroup. Make a directory under /sys/fs/cgroup and write cpu.max, cpu.weight, memory.max, pids.max (Node 27).
  4. Create the process with new namespaces. clone() with CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWCGROUP, plus CLONE_NEWUSER if rootless (Nodes 14, 26). The child is PID 1 in its new PID namespace.
  5. Wire the network. Create a veth pair; move one end into the new network namespace; attach the other to the bridge; assign an address; set routes; install NAT rules for published ports (Nodes 26, 32).
  6. Set the root. Inside the child: mount the overlay, then pivot_root to it, then unmount the old root — so the host's filesystem is no longer reachable at all, which is the difference between pivot_root and the escapable chroot.
  7. Mount the pseudo-filesystems. A fresh /proc (which now reflects the new PID namespace), /sys, a tmpfs on /dev with a minimal device set, /dev/pts, and /dev/shm (Nodes 21, 24).
  8. Set the hostname in the new UTS namespace.
  9. Apply the security posture. Set the UID and GID (Node 25); drop capabilities to the retained set; set no_new_privs; install the seccomp filter (Node 4); apply the AppArmor or SELinux label.
  10. Set the environment and working directory, and set up the standard descriptors — pipes back to the daemon for logging, or a pseudo-terminal for -it (Node 22).
  11. execve() the entrypoint (Node 35). Your process is now running.

Eleven steps, no new mechanism, all of it kernel features from 2002–2016 that existed for years before anyone packaged them together.

The layers of tooling above it

The vocabulary confuses people and the structure is simple:

  • runc — the low-level runtime. Reads an OCI bundle (a directory with a root filesystem and a config.json) and performs the eleven steps. It is essentially the reference implementation of the OCI runtime specification, and you can run it by hand.
  • containerd — the daemon that manages images, storage, networking and lifecycle, and calls runc to actually start things. This is what Kubernetes talks to, through the CRI (Container Runtime Interface).
  • The shim — one small process per container, which is runc's parent. It exists so that containerd can be restarted or upgraded without killing every running container, and so someone stays around to collect the exit status (Node 5's zombie problem).
  • Docker — a developer-facing layer over containerd: the CLI, the build system, compose, and the image-building experience. Kubernetes removed its Docker-specific support in 1.24 (2022) because containerd was underneath all along; images built by Docker are OCI images and continued to work, which is why "Kubernetes is dropping Docker" caused far more alarm than it warranted.
  • Podman — daemonless and rootless by default, using the user namespace from Node 26. No background daemon means containers are children of your shell and integrate with systemd naturally.
  • BuildKit — the modern builder: it constructs a dependency graph of the build, executes independent steps in parallel, supports cache mounts (RUN --mount=type=cache, which makes a persistent npm or apt cache across builds) and secret mounts (--mount=type=secret, which never lands in a layer — the fix for Node 24's credential-leak problem).

Where this is in your stack

Everything you know about Dockerfiles now has a mechanism behind it. Multi-stage builds work because only the final stage's layers become the image, so the compiler and the source never ship. COPY --from=builder /app/dist ./dist copies between overlay trees. .dockerignore shrinks the tree walked in step 1's build-time equivalent. Ordering instructions from least to most volatile is layer-cache management (Node 24). A distroless or FROM scratch image works because a statically linked binary needs only the kernel's stable syscall ABI (Node 4) — and it has no shell, so docker exec sh fails and you need kubectl debug's ephemeral containers, which join the target's namespaces with setns (Node 26).

Debugging a container from the host is namespace entry. nsenter -t <host-pid> -n -p -m puts a shell into a container's network, PID and mount namespaces without the container needing any tooling of its own — invaluable for a distroless image. docker inspect --format '{{.State.Pid}}' gets the host PID. ctr and crictl talk to containerd directly when the higher layers are the problem.

The security properties, stated honestly. A container's isolation rests entirely on kernel correctness, because there is one kernel and every container calls into it directly. A kernel privilege-escalation bug reachable from a container is a host compromise. That is a real and different risk profile from a virtual machine, and it is why untrusted multi-tenant workloads use gVisor (Node 4), Kata Containers, or Firecracker microVMs (Node 29) rather than plain containers. The mitigations that matter, in rough order of value: do not run as root; drop all capabilities; keep seccomp enabled; use a read-only root filesystem; and use a user namespace.

What you can do at this point: state exactly what a container is, describe an OCI image's three parts and why digests matter, walk the eleven steps of docker run naming the mechanism behind each, place runc/containerd/shim/Docker/Podman/BuildKit correctly, debug a container by entering its namespaces, and state its security properties honestly.

What's still broken: one kernel, shared. Every container on a machine trusts the same code, and a bug in it is a bug for all of them. Some workloads cannot accept that, and the answer predates containers by forty years.
