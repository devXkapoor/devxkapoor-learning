Node 31 — inter-process communication

The limitation: a signal carries one integer, and isolated processes need to exchange data.

Every mechanism below trades the same three things: how fast it is, whether the parties must be related, and whether it works across machines. Knowing the trade is more useful than memorising the list.

The mechanisms

Pipes (Node 22) — a kernel buffer, unidirectional, between related processes. Built-in backpressure. A named pipe or FIFO (mkfifo) is the same object given a filesystem name, so unrelated processes can use it. Both copy data through the kernel: one copy in, one copy out.

Unix domain sockets — the same API as network sockets (socket, bind, listen, accept) with a filesystem path instead of an address, and no networking underneath. Bidirectional, supporting both stream and datagram semantics, and typically two to three times faster than a TCP connection over loopback because the entire protocol stack is skipped. Two abilities make them special:

  • They can pass file descriptors. SCM_RIGHTS in a control message transfers an open descriptor to another process, where it lands as a new number in that process's table referring to the same open file description (Node 22). This is how Node's cluster module hands a listening socket to workers, and how systemd socket activation works.
  • They can pass verified credentials. SO_PEERCRED tells you the connecting process's real UID, GID and PID, checked by the kernel and unforgeable. This is how the Docker daemon authorises access via /var/run/docker.sock — which is also why mounting that socket into a container is equivalent to giving it root on the host, since anything that can talk to the daemon can start a privileged container.

Shared memory — the fastest possible, because there is no copy at all: the same physical frames appear in two address spaces (Node 10). POSIX shm_open plus mmap, or the older System V shmget, or simply mmap of a file with MAP_SHARED. The cost is that it provides no synchronisation whatsoever — you are back in Node 16's territory and must supply your own atomics or locks, and a shared-memory bug is a data race across a process boundary. Postgres's shared_buffers is a shared mapping, and its internal LWLocks are the synchronisation over it.

Message queues — kernel-held queues of discrete messages with priorities. POSIX (mq_open) or System V (msgget). Preserve message boundaries, which streams do not. Rarely used in modern application code, largely because user-space brokers are more capable.

Semaphores and futexes (Node 17) — synchronisation rather than data transfer, but shared between processes when placed in shared memory.

Network sockets — Node 32, and the only one that crosses machines.

The trade, stated as a decision

Copies through the kernel cost about the same as a system call plus a memory copy — fine for kilobytes, wasteful for megabytes. Shared memory costs nothing per byte and everything in complexity. Unix sockets are the right default for local IPC because they are as fast as anything that copies, use the same API as networking so code ports trivially, and carry descriptors and credentials. Reach for shared memory only when profiling proves the copy is the bottleneck, which is much rarer than people assume.

Where this is in your stack

Node's cluster IPC channel is a Unix socket pair. child.send(obj) serialises to JSON (or, since Node 8, the richer V8 serialisation for some types), writes to the socket, and the parent's 'message' event fires from an ordinary event-loop read. So messaging between cluster workers costs serialisation plus two copies plus two syscalls per message — cheap for coordination and completely wrong for a shared cache. The listening socket, by contrast, is passed once as a descriptor using SCM_RIGHTS, which is why every worker can accept on the same port without any of them binding it.

worker_threads is not IPC at all, and the contrast is instructive. Workers are threads in one process (Node 15), so their postMessage is an in-memory structured clone with no kernel involvement — no syscall, no socket, just a copy on the heap. transferList avoids even the copy. And SharedArrayBuffer is shared memory, with Atomics as the synchronisation, which is precisely this node's shared-memory row with all of its hazards.

nginx to your Node app over a Unix socket. proxy_pass http://unix:/run/app.sock; instead of http://127.0.0.1:3000 avoids the entire TCP stack: no three-way handshake, no ephemeral port allocation, no TIME_WAIT accumulation (Node 32), and lower latency. It also means the service is unreachable from the network by construction, with filesystem permissions as the access control. The same applies to Postgres — psql on the same host connects over /var/run/postgresql/.s.PGSQL.5432 by default, and switching an application from host=localhost to host=/var/run/postgresql is a real, free latency reduction for a high-query-rate service. It is also why pg_hba.conf distinguishes local from host lines, with peer authentication on the former using SO_PEERCRED.

/var/run/docker.sock, restated because it matters. The Docker daemon listens on a Unix socket and authorises by peer credentials. Mounting it into a container — common for CI runners and for tools that inspect containers — hands that container the ability to create privileged containers, mount the host filesystem, and read every secret on the machine. It is a full host compromise waiting to happen, and the alternatives are a rootless daemon, a socket proxy that whitelists specific API calls, or building images with a daemonless tool such as Kaniko or BuildKit's rootless mode.

Redis as an IPC broker across processes and machines. Once you have several Node processes — cluster workers, replicas in Kubernetes, serverless instances — nothing in this node works between them, because they may not share a machine. That is the mechanical reason Redis ends up in so many architectures: it is the shared mutable state that separate address spaces (Node 5) cannot have. Rate limiter counters, session stores, cache, pub/sub for websocket fan-out, and BullMQ's queues are all one problem — state that must be visible to processes with separate address spaces — solved by putting it in a process that everyone can reach over a socket. Recognising that unifies half of a typical backend architecture.

What you can do at this point: list the IPC mechanisms with their trade-offs and choose correctly, explain descriptor passing and why cluster needs it, explain peer credentials and why the Docker socket is dangerous, explain why worker_threads messaging is not IPC, and explain Redis's role in an architecture as a consequence of address-space isolation.

What's still broken: all of this is local. The moment two processes are on different machines, everything changes — packets are lost, reordered, duplicated and delayed, there is no shared kernel to arbitrate, and the connection abstraction that hides all of it is the most elaborate thing in the operating system.
