CORS

The browser's cross-origin rule, derived: why cookies made reads dangerous, what the same-origin policy actually blocks, and how a server grants permission it cannot enforce.

Read this in order. Each node exists because the one before it left something specifically broken, and the broken thing is named at the bottom of every node. If you follow the chain you should be able to derive the CORS protocol rather than memorise its header names.

Depth markers appear inline. [EXPLAIN] means you should be able to explain it out loud, from first principles, with no notes. [USE] means you must be able to use it correctly and debug it when it breaks, without needing the internals cold. [AWARE] means know it exists, know what problem it solves, and know roughly when to reach for it.

Node 0 — the web before any restriction, and why that could not survive

When Netscape shipped JavaScript in Navigator 2.0 in 1995, it added something genuinely new to the web: a document could now run a program. Before that a page was inert — text, images, links, forms. After that a page could read its own contents, modify them, and talk to the network.

The problem arrives immediately, and it arrives because of a design decision made earlier, for a different reason, that nobody thought of as a security decision at the time: cookies are ambient. When your browser holds a cookie for bank.example, it attaches that cookie to every request it makes to bank.example, regardless of which page caused the request. The cookie is a property of the browser's relationship with the server, not a property of the page doing the asking. The same is true of HTTP Basic auth credentials, of TLS client certificates, and — much later — of anything the browser sends automatically on your behalf.

Now put those two facts together. You are logged into your bank in one tab. In another tab you open totally-normal-blog.example. That blog's page runs JavaScript. If JavaScript were allowed to make a request to https://bank.example/accounts and read the response, then the blog's script would issue that request, the browser would helpfully attach your bank session cookie, the bank would see a perfectly valid authenticated request and return your account list, and the blog would read it and post it to its own server. You would not click anything. You would not see anything. The bank did nothing wrong — from its side the request was indistinguishable from you clicking a link.

This is the whole problem. It is not that reading data across sites is inherently evil; it is that the browser silently supplies the user's identity, so a cross-site read is a read as the user, performed by a party the user never authorised. The attacker does not need to steal your password. They just need your browser to make a request while your browser is being you.

The same reasoning applies to reading, not just data but the page itself. If the blog could open a hidden frame containing your bank's dashboard and read the text out of that frame, that is the same attack with a different mechanism. And if it could read the DOM, it could read the CSRF token, the account numbers, everything.

So the browser needs a rule. The rule cannot be "ask the user", because users cannot evaluate this and there would be thousands of prompts. It cannot be "the site opts out", because there was already a decade of sites written by people who had never heard of the problem. It has to be a default deny, applied by the browser, that costs existing sites nothing.

What's still broken: we have named the danger — the browser attaching the user's identity to requests that a foreign page caused — but there is no rule yet that separates "my own site's data" from "somebody else's site's data". We need a definition of whose data this is.

Node 1 — the same-origin policy, and what an origin actually is

The limitation: to deny cross-site reads you first need a machine-checkable definition of "same site", and it has to be one that cannot be talked around.

The answer Netscape landed on in 1995, and which every browser has used since, is the origin [EXPLAIN]. An origin is a tuple of exactly three things: the scheme (http, https, file, and so on), the host (the full hostname, e.g. api.example.com), and the port (80, 443, 3000, …).

Two URLs are same-origin if and only if all three match. That is the entire definition, and its bluntness is the point — it is a string comparison, so it cannot be argued with, misparsed, or socially engineered.

Worked examples, because this is where most people's model is quietly wrong. Starting from https://app.example.com/dashboard:

  • https://app.example.com/settings — same origin; path is not part of an origin.
  • https://app.example.com/x?y=1#z — same origin; query and fragment are not either.
  • http://app.example.com/dashboard — different; the scheme differs.
  • https://api.example.com/dashboard — different; subdomains are different hosts.
  • https://example.com/dashboard — different, for the same reason in the other direction.
  • https://app.example.com:8443/ — different; the port differs.
  • https://app.example.com:443/ — same origin; 443 is the default port for https, so it is filled in before comparison.

That last case is worth pausing on. The port is compared after the default is filled in, so https://example.com and https://example.com:443 are the same origin, and http://example.com and http://example.com:80 are the same origin. Mixing the two schemes is not, even on the same host and even though it feels like "the same site" — this is why moving a local dev server from http://localhost:3000 to https://localhost:3000 breaks things.

localhost:3000 and localhost:5173 are different origins. This is the single most common first encounter with the whole topic: your Vite dev server on 5173 and your Fastify API on 3000 are, as far as the browser is concerned, two unrelated parties.

The same-origin policy [EXPLAIN] — usually written SOP — is then the rule: code running in one origin may not read data belonging to another origin. It is not one mechanism. It is a principle applied separately, and slightly differently, at every place where reading could happen: XMLHttpRequest and fetch responses, the contents of an iframe document, the pixels of a canvas that has had a foreign image drawn into it, the pages in the window.opener relationship, entries in localStorage, cookies (which have their own older and messier rules), and IndexedDB.

Storage is worth naming explicitly because it is the same rule wearing different clothes: localStorage on https://a.example is a different store from localStorage on https://b.example. There is no shared area. Two origins on the same physical machine, in the same browser profile, in adjacent tabs, cannot see each other's storage at all. [USE]

One historical escape hatch existed for the subdomain case: document.domain [AWARE]. Two pages on app.example.com and www.example.com could each assign document.domain = "example.com" and thereby agree to be treated as same-origin. It was always a bad mechanism — setting it opts you into being scriptable by any subdomain, including one an attacker takes over — and browsers have removed it. Chrome disabled it by default in Chrome 115, July 2023. Do not learn it as a technique; learn it as a thing you may find in old code, with the note that it no longer works.

What you can do at this point: look at any two URLs and say instantly whether they are the same origin, and predict which browser operations will be blocked between them.

What's still broken: if the rule were really "nothing crosses origins", the web would not function at all — every page loads images, scripts, and fonts from other origins constantly, and every HTML form has been able to POST to another site since 1993. So the policy is clearly not blocking everything. We need to know exactly what it blocks and what it does not, because that boundary is where every remaining vulnerability lives.

Node 2 — the asymmetry: sending is allowed, reading is not

The limitation: the SOP as stated sounds absolute, but the web visibly does cross origins all day. The rule must be narrower than "no interaction".

Here is the shape of the actual rule, and it is the single most important idea in this topic: the same-origin policy restricts reading responses, not sending requests. [EXPLAIN]

A page on evil.example may, with no permission from anyone, load <img src="https://bank.example/logo.png"> — which issues a real GET, with your cookies, and paints the result; the script cannot read the pixels, but the request happened. It may load <script src="https://bank.example/data.js"> — a real GET, with your cookies, whose response is executed as code in evil.example's own context. The same goes for <link rel="stylesheet">, <video> and <iframe>. And it may build and submit a <form action="https://bank.example/transfer" method="POST"> — a real POST, with your cookies, with a body it controls; the page cannot read the response, but the transfer happened.

Sit with the form case, because it is the historical hinge on which the entire CORS design turns. Since forms existed, any page has been able to POST arbitrary form-encoded data to any other origin, carrying the user's cookies. Servers have therefore always had to be built on the assumption that a cross-origin POST can arrive. It is not a new risk; it is the baseline the web was built on.

This is exactly what CSRF — cross-site request forgery [EXPLAIN] — is: an attack that needs only the send, never the read. evil.example auto-submits a hidden form to the bank's transfer endpoint. Your cookie rides along. The bank performs the transfer. The attacker never sees the response and does not care. Remember this; at Node 12 we come back and show why CORS does not fix it, which is one of the most commonly failed interview questions in this whole area.

So the boundary the browser draws is: you may cause effects across origins; you may not observe results across origins. Effects were grandfathered in because removing them would have broken the entire web. Observation was never possible before JavaScript, so it could be denied from day one at no cost.

There is one more consequence worth extracting now. Because the request genuinely is sent in many cases, "the browser blocked it" is often false. The browser usually lets the request go, gets the response, and then refuses to hand it to your JavaScript. The server ran your query. The row was inserted. You just cannot see the answer. That fact explains almost every confusing CORS debugging session, and it is why the preflight has to exist.

What you can do at this point: explain why an img tag can hit any server but fetch cannot read from one, without saying "because CORS".

What's still broken: XMLHttpRequest arrives and gives JavaScript a general-purpose way to make requests and read responses. Under the SOP it can only ever read from its own origin — which makes public APIs, CDNs serving JSON, and any deliberate cross-origin cooperation impossible. There is no way for a server to say yes.

Node 3 — XHR hits the wall, and the decade of workarounds

The limitation: the SOP is a blanket deny with no consent mechanism. A server that genuinely wants to share data with another origin has no way to express that.

XMLHttpRequest was shipped by Microsoft in Internet Explorer 5, in 1999, as an ActiveX object called XMLHTTP, built for Outlook Web Access. Mozilla reimplemented it as a native object in 2002, Safari and Opera followed, and after Gmail (2004) and Google Maps (2005) made the pattern famous — and Jesse James Garrett named it "Ajax" in February 2005 — it became the standard way to build web applications.

XHR was subject to the SOP from the start: it could only request URLs on its own origin. So for roughly a decade, everyone who needed cross-origin data used a workaround, and it is worth knowing all four, because two of them are still in production code you will meet and each one teaches you something about the eventual design.

JSONP [AWARE] — "JSON with padding", a term coined by Bob Ippolito in 2005 — exploits Node 2's asymmetry directly. A script element may load cross-origin and the response is executed. So instead of returning {"name":"Ada"}, the server returns myCallback({"name":"Ada"}), and the page defines myCallback beforehand. The data arrives as code. It works, it needs no browser support at all, and it is genuinely dangerous: you are executing whatever that server sends, with full access to your page. It is GET-only, has no useful error handling, and if the provider is ever compromised, so are you. You will still find it in older jQuery code as $.ajax({dataType: "jsonp"}). Understand it as a historical exploit of a loophole, not as a technique to use.

A server-side proxy [USE] — your own backend fetches the third-party URL and re-serves it under your origin, so the browser only ever sees a same-origin request. This one is not a hack at all; it is still the right answer in many cases, and it comes back at Node 14 as a deliberate architecture.

document.domain — covered at Node 1, subdomain-only, now dead.

Flash's crossdomain.xml [AWARE] — Adobe Flash could make cross-origin requests if the target server published an XML policy file at its root listing which origins were allowed. Silverlight had clientaccesspolicy.xml. This is historically important because it is the first appearance of the idea that eventually became CORS — the target server declares who may read it — and also the first appearance of its classic misconfiguration, a policy file allowing access from any domain, which let any site on the internet read the server's data as the user.

So by around 2005 the correct shape of the answer was visible. What was missing was to move it out of a browser plugin and into HTTP itself, using headers rather than a magic file, and to make it default-deny so no existing server accidentally opted in.

What's still broken: there is no standard, in-protocol way for a server to say "this specific other origin is allowed to read my responses" — and any mechanism that fixes that must not silently expose the millions of servers already deployed that have never heard of it.

Node 4 — CORS: the server grants read permission, the browser enforces it

The limitation: we need consent, expressed by the party whose data it is, in a way that is invisible to servers that never opt in.

Cross-Origin Resource Sharing [EXPLAIN] is that consent mechanism. Work began at the W3C in the mid-2000s under the ungainly name "Cross-Site XMLHttpRequest", it was renamed CORS in 2009, reached W3C Recommendation on 16 January 2014, and the specification has since been absorbed into the WHATWG Fetch Standard, which is where it lives today. If you go looking for the authoritative text, it is the "CORS protocol" section of the Fetch spec, not the old W3C document.

The design is two headers and one idea.

The idea: the browser asks, the server answers, and the browser enforces the answer. The server is not a bystander and not a policeman — it is the grantor. It cannot force the browser to allow anything; it can only publish a permission that the browser then honours.

The request half. When a page makes a cross-origin request with fetch or XHR, the browser adds a header the page cannot set, forge, or remove: Origin: https://app.example.com. Note carefully: it is the origin, not the full URL. No path, no query. The browser deliberately withholds the rest, because which page you were on is nobody else's business. Origin is one of the forbidden header names, so JavaScript cannot assign it, precisely so the server can trust it. A non-browser client can send whatever it likes; hold that thought for Node 12.

The response half. If the server is willing, it answers with Access-Control-Allow-Origin: https://app.example.com. The browser compares that value against the requesting origin. Match — the response is handed to your JavaScript. No match, or header absent — the browser discards the response and rejects the promise. Your code sees a TypeError, and never sees the body, the status, or the headers.

The header takes one of exactly two useful forms [EXPLAIN]. Either a single specific origin, spelled exactly — scheme, host, and port when non-default, no trailing slash; https://app.example.com is right, https://app.example.com/ is wrong and will not match, app.example.com is wrong, and a comma-separated list of two origins is wrong because the header is defined as a single origin — or *, the wildcard, meaning "any origin may read this", which is correct for genuinely public resources and has a hard limitation with credentials that we get to at Node 7.

Because the header holds one origin and you usually need to allow several, the standard server implementation is: read the incoming Origin header, check it against your own allowlist, and if it is on the list, echo it back. That is a reflection, and doing it without the allowlist check is a serious vulnerability — Node 9.

Three things follow from "the browser enforces", and all three are load-bearing. First, CORS is not a security feature of your server; it protects one user's data in one user's browser from one foreign page's script, and does nothing about anyone using curl. Second, a CORS failure is not a network failure — the request very often reached the server and was processed. Third, only browsers implement it, so your Node script, your mobile app, Postman, and your test suite have no same-origin policy and never see a CORS error. This is why "it works in Postman" is never evidence of anything.

What you can do at this point: make a cross-origin GET work by setting one response header, and explain who is checking it and why.

What's still broken: we have said the browser sends Origin and checks Access-Control-Allow-Origin. But at Node 2 we established that a cross-origin POST from a form has always been possible without permission. If CORS now requires permission for a fetch POST, we have two different rules for the same underlying HTTP request — and worse, if the browser sends a DELETE to a server written in 2003 and only checks the response header afterwards, the deletion has already happened. Something has to distinguish requests that were always possible from requests that were not.

Node 5 — "simple requests": the safelist, and why its shape is historical

The limitation: CORS must not require permission for anything that was already possible before CORS existed, or it would break the web; and it must require permission before sending for anything that was not.

The specification's answer is to define a class of request that is deemed harmless because it was always achievable anyway. The Fetch spec's term is a request that does not require a preflight; everyone else calls it a simple request [EXPLAIN]. A request is simple only if all of the following hold.

One — the method is one of exactly three: GET, HEAD, POST. These are the methods an HTML form or an image tag could already produce. PUT, PATCH, DELETE are not on the list, and there is no way to make them simple.

Two — the only headers your code sets are on the CORS-safelisted request-header list. That list is Accept, Accept-Language, Content-Language, Content-Type (with the restriction below), and Range (added later, with restrictions, for media). Anything else you set yourself takes you off the safelist. In particular Authorization is never safelisted, and neither is any custom header — X-Requested-With, X-API-Key, X-Tenant-Id, all of them disqualify. Headers the browser sets automatically — User-Agent, Referer, Host, Cookie, Origin — do not count against you; the rule is about headers the author sets. For completeness, the client-hint headers DPR, Downlink, Save-Data, Viewport-Width and Width were also historically on the safelist.

Three — if Content-Type is present, its value is one of exactly three: application/x-www-form-urlencoded, multipart/form-data, or text/plain. And that trio is the tell. Those are precisely the three encodings an HTML form can produce. The safelist is not a judgement about which content types are safe in the abstract; it is a list of what an attacker could already do in 1995. Nothing new is being permitted.

The immediate practical consequence, and the reason nearly every real API triggers the machinery in Node 6: Content-Type: application/json is not on the list. A form cannot produce it. So the ordinary, boring act of posting JSON with fetch is not a simple request, and never can be. [EXPLAIN] If you take one fact from this node, take that one.

Four — no ReadableStream is used as the request body, and five — if an XMLHttpRequest is involved, no listener is registered on its upload object, since registering one exposes upload progress, which is information the other origin has not agreed to share.

For a simple request, the browser sends it immediately, exactly as it would have anyway, and applies the Access-Control-Allow-Origin check only to the response. So the effect on the server happens whether or not permission is granted. That is acceptable here — and only here — because that same effect was already reachable via a form.

What you can do at this point: look at a fetch call and say, without running it, whether it will produce one HTTP request or two.

What's still broken: everything outside the safelist — a DELETE, a JSON body, an Authorization header — is a request the old web could not produce, aimed at a server that may well predate CORS and may act on it before anyone checks a header. Checking permission after sending is useless for those. We need to ask first.

Node 6 — the preflight

The limitation: for any request that a pre-CORS web could not have made, the effect must not occur unless permission already exists. Permission therefore has to be obtained before the real request is sent.

The preflight [EXPLAIN] is the browser making a separate, throwaway request to ask permission, automatically, before the one your code asked for. You never write it. You cannot see it in your own code. It appears in the network tab as an extra row and it confuses everyone the first time.

It looks like this. Your code runs:

await fetch("https://api.example.com/orders/42", {
  method: "DELETE",
  headers: { "Authorization": "Bearer eyJ..." }
});

The browser first sends:

OPTIONS /orders/42 HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization

Three things to notice. The method is OPTIONS, chosen because it was already defined in HTTP/1.1 (RFC 2616, 1999) as the "describe what you allow" method. There is no body — the preflight never carries your payload. And by default there are no cookies on it, even if the real request will carry them; the preflight is anonymous, which matters because it means your auth middleware must not reject it.

Access-Control-Request-Method announces the method the real request will use. Access-Control-Request-Headers lists, lowercased and comma-separated, the non-safelisted headers the real request will set.

The server must answer with a success status — 2xx, with 204 No Content the conventional choice and 200 fine — and these headers:

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 86400

Access-Control-Allow-Methods [USE] names which methods are permitted. Unlike Allow-Origin, this one is a comma-separated list, and it does accept * for non-credentialed requests.

Access-Control-Allow-Headers [USE] names which non-safelisted request headers are permitted. Also a list. It supports * for non-credentialed requests, but with a trap worth memorising: * does not cover Authorization. The Fetch spec special-cases it; if your client sends Authorization you must name it explicitly. This one has cost a lot of people an afternoon.

Access-Control-Max-Age [USE] says how many seconds the browser may cache this permission, keyed by origin, URL and method, so that repeated calls do not each pay for a round trip. The value you set is not the value you get: Chrome caps it at 7200 seconds (two hours) — it was 600 before Chrome 76 in 2019 — and Firefox caps it at 86400 (twenty-four hours). Sending a year does not buy you a year; it buys you the browser's cap. Setting it to -1 disables caching.

If the response fails any check — non-2xx status, missing Allow-Origin, a method not listed, a header not listed — the browser never sends the real request. Your promise rejects. Nothing happened on the server beyond the OPTIONS. That is precisely the protection this whole node exists to provide: the DELETE did not occur.

Three failure modes are worth pre-loading, because you will hit all of them. Your framework may return 404 or 405 for OPTIONS — very common when a route is registered for POST only, or when auth middleware runs before the CORS handler and rejects the credential-less preflight with a 401; a 401 on a preflight is not an auth problem, it is an ordering problem. A redirect on the preflight fails outright, because browsers do not follow redirects during a preflight, so an API that redirects /orders to /orders/ will break and the fix is to stop redirecting rather than to configure CORS harder. And adding one header changes everything: a GET with no custom headers is simple, but adding X-Trace-Id silently doubles your request count and introduces a new way to fail.

What you can do at this point: read a network tab showing an OPTIONS followed by nothing, and know exactly which of the four checks failed.

What's still broken: everything so far is anonymous. The preflight carries no cookies, and — a fact that surprises people — neither does the real cross-origin request, by default. Which means none of this yet works for the case you actually care about: a logged-in user's frontend calling their own API on a different origin.

Node 7 — credentials

The limitation: cross-origin requests do not carry cookies by default, so an authenticated session cannot cross origins at all. But turning cookies back on re-creates the Node 0 attack, so it cannot be a one-sided decision.

"Credentials" in CORS means, specifically, cookies, HTTP authentication entries, and TLS client certificates [EXPLAIN] — the things the browser attaches on its own. An Authorization: Bearer header that you set in JavaScript is not a credential in this sense; it is just a header, and it is governed by Access-Control-Allow-Headers at Node 6. That distinction is subtle and is asked about often.

By default, a cross-origin fetch sends no cookies and ignores any Set-Cookie in the response. Both sides must opt in.

The client opts in. With fetch, credentials takes three values [USE]: "omit" (never), "same-origin" (the default — cookies on same-origin requests only), and "include" (send them cross-origin too). With XMLHttpRequest the equivalent is xhr.withCredentials = true. Axios calls it withCredentials: true.

The server opts in, with a second header alongside the first: Access-Control-Allow-Credentials: true. Lowercase true is the only accepted value. And now the rule that catches everyone [EXPLAIN]:

When Access-Control-Allow-Credentials: true, Access-Control-Allow-Origin may not be *. It must name a single explicit origin.

The reason is not arbitrary. * means "any origin may read this". Combined with credentials it would mean "any origin may read this as the logged-in user" — which is exactly the Node 0 attack, re-implemented as a feature and shipped by a server author who thought * meant "convenient". So the spec forbids the combination, and browsers reject it with a specific error: "The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'." The same wildcard ban applies to Access-Control-Allow-Headers, Allow-Methods, and Expose-Headers on credentialed requests — under credentials, * is treated as the literal string, not as a wildcard.

Consequently, any real app with cookie sessions must reflect the origin from an allowlist, which drags in the caching problem at Node 9.

For credentialed requests the preflight matters more, not less: the browser checks Access-Control-Allow-Credentials on both the preflight response and the actual response, and both must be right.

There is a second, entirely separate gate that people forget, and it is not CORS at all: the cookie itself must be willing to travel. In 2026 that means it needs SameSite=None; Secure to be sent on a cross-site request. Getting the CORS headers perfect while your session cookie is SameSite=Lax produces a request with correct CORS and no cookie, and a 401 you will chase for an hour. That is Node 13, and the two mechanisms are genuinely independent — you must satisfy both.

What you can do at this point: make a cookie-authenticated SPA on one origin talk to an API on another, and name the four things that all have to be true for it to work.

What's still broken: the response now arrives, with the right body. But your code asks for a pagination header, or a rate-limit header, or the Location of a created resource — and gets null, even though the header is plainly visible in DevTools.

Node 8 — reading response headers, and why most of them are invisible

The limitation: granting read access to the body did not grant read access to the response's metadata, and headers can leak just as much as bodies.

When a response has passed the CORS check, your JavaScript still cannot read most of its headers. Only the CORS-safelisted response headers [EXPLAIN] are exposed by default: Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified, and Pragma.

Seven headers, chosen because they describe the representation rather than the application. Everything else — X-Total-Count, X-RateLimit-Remaining, Location, ETag, Authorization, Set-Cookie, your own X-Request-Id — returns null and does not appear when you iterate the headers. The header is on the wire. The browser has it. It is simply not handing it to you.

The server fixes this by naming them: Access-Control-Expose-Headers: X-Total-Count, X-RateLimit-Remaining, ETag, Location. The wildcard is allowed here for non-credentialed requests, and — per the rule from Node 7 — means the literal asterisk for credentialed ones, so on a credentialed API you must enumerate. [USE]

Set-Cookie is the exception with no override: it can never be exposed to script, cross-origin or not, because HttpOnly cookies exist precisely to be unreadable. The cookie is still set — the browser stores it — you just cannot see it.

The design principle is the same one from Node 2, applied one level in: default deny, opt in explicitly. A header the server author never thought about cannot leak, because it was never exposed.

The practical rule for API design [USE]: if your frontend needs to read pagination totals, rate-limit budgets, request IDs for support, or the Location of a newly created resource, you must list them in Access-Control-Expose-Headers, and it is the thing most often forgotten when an API is first exposed cross-origin. The alternative is to put that data in the response body, which is often the better design anyway.

There is a specialised cousin worth knowing exists: Timing-Allow-Origin [AWARE], which controls whether detailed timing data for a cross-origin resource shows up in the Resource Timing API. Without it you get zeros for the fine-grained phases, because timing is itself a side channel.

What you can do at this point: explain why a header you can see in DevTools is null in your code, and fix it in one line on the server.

What's still broken: the "reflect the origin from an allowlist" pattern that Node 7 forced on us produces responses whose correct headers depend on who asked — and the entire HTTP caching layer, from your CDN to the browser's own cache, was built on the assumption that a URL maps to one response.

Node 9 — caching, Vary: Origin, and reflecting safely

The limitation: the response now varies by a request header, but nothing has told the caches that.

Picture a CDN in front of your API. A user on https://app.example.com makes a request; your server reflects that origin and returns it in Access-Control-Allow-Origin. The CDN caches the whole response, headers included, keyed by URL. A minute later a user on https://admin.example.com — also on your allowlist — requests the same URL. The CDN serves the cached copy, complete with the other origin's header. The admin's browser sees a mismatch and blocks it. You now have an error that appears for some users, at some times, and vanishes when you reload or bypass the cache. It is one of the genuinely nasty bugs in this area.

The fix is one header, and it must accompany every reflected origin [EXPLAIN]: Vary: Origin.

Vary is a general HTTP mechanism, not a CORS one: it tells every cache that the response depends on the named request header, so the cache key must include it. With Vary: Origin the CDN keeps a separate entry per origin and the bug disappears. If you also vary the response on Access-Control-Request-Method or Access-Control-Request-Headers — as a preflight response does — those belong in Vary too.

You do not need it when you return a constant Access-Control-Allow-Origin: *, because then the response genuinely does not vary. Most CORS middleware adds Vary: Origin automatically when reflecting; check yours, and check that a hand-rolled implementation does.

The second hazard of reflection is a security one, and it is the most common CORS vulnerability in real audits [EXPLAIN]. This code is a hole:

// WRONG — reflects anything
res.setHeader("Access-Control-Allow-Origin", req.headers.origin);
res.setHeader("Access-Control-Allow-Credentials", "true");

It says "whoever you are, you may read this as the logged-in user". It is the wildcard plus credentials, laundered through a header, defeating the exact rule Node 7 imposed. evil.example sends its own origin, gets it back, and reads everything.

Near-misses fail the same way. origin.endsWith("example.com") also matches evil-example.com and notexample.com. origin.includes("example.com") matches https://example.com.evil.net. A regex written without anchors matches anywhere in the string. The correct check is exact membership of an explicit list of full origin strings, or a carefully anchored pattern where a wildcard subdomain is genuinely required. [USE]

Two special values deserve their own note. Origin: null [EXPLAIN] is sent by sandboxed iframes, by documents opened from file://, and after certain redirects. It is not a safe identity — anyone can obtain it by putting your page in a sandboxed iframe — so allowing null is effectively "allow attackers", and it should never be in an allowlist. And on the trust side: Origin is unforgeable by browser JavaScript, which is the only place the SOP applies; it is trivially forgeable by any other client, so never use it for authorisation.

What you can do at this point: review a CORS implementation and find the reflection bug and the missing Vary in under a minute.

What's still broken: you now know how it should be built. What you do not yet have is any ability to work out what went wrong when it is built badly — and CORS failures are deliberately, structurally uninformative.

Node 10 — the failure mode, and how to debug it

The limitation: for security reasons the browser tells your JavaScript almost nothing about a blocked response, so the normal debugging reflex — inspect the error — yields nothing.

Here is what your code actually sees when a CORS check fails: a TypeError, with the message "Failed to fetch" in Chrome or "NetworkError when attempting to fetch resource" in Firefox. No status. No response object. Nothing else.

That is the same error you get for DNS failure, connection refused, TLS failure, and an offline network. [EXPLAIN] The blocked response is deliberately indistinguishable from no response, because distinguishing them would itself leak information: if a script could tell "blocked by CORS" from "host does not exist", it could probe your internal network by timing and error type. The vagueness is the feature.

So the real information lives in exactly two places, and neither is your JavaScript.

The browser console. Browsers print a detailed message there that is intentionally not available to script. Learn to read the four variants. "No 'Access-Control-Allow-Origin' header is present on the requested resource" means the server did not opt in at all, or did not opt in for this route, or an error handler returned a response that bypassed your CORS middleware — watch for that last one, because a 500 thrown before the middleware ran often lacks the headers, which turns a server bug into a CORS message. "Response to preflight request doesn't pass access control check" means the OPTIONS failed, so inspect that row rather than the real one. "Method DELETE is not allowed by Access-Control-Allow-Methods" and "Request header field x-api-key is not allowed by Access-Control-Allow-Headers" mean the preflight succeeded but did not grant enough; these are the friendliest messages CORS produces, so take them literally. And the wildcard-with-credentials message is Node 7's rule.

The network tab. Look for the OPTIONS row. Its presence tells you the request was not simple; its absence tells you it was. Check the response headers on it. Crucially, remember Node 2: you will often see the real request there with a 200 and a full body, and still get an error in your code. That is not a contradiction; it is the whole architecture. The browser fetched it and refused to share it.

Some debugging discipline saves real time [USE]. Run curl -i -H "Origin: https://app.example.com" https://api.example.com/orders to see exactly what the server sends, since curl enforces nothing and this isolates "server not sending the header" from "browser not accepting it". Simulate the preflight directly with curl -i -X OPTIONS plus the two request headers; if that returns 404 or 401 you have found your bug without touching the browser. Remember that "it works in Postman" means nothing, because Postman has no origin and no same-origin policy. Watch out for preflight caching hiding your fix — after changing server config, a cached preflight can keep serving the old answer for up to two hours in Chrome, so use a hard reload, disable cache in DevTools, or test in a fresh profile. And do not reach for a browser flag or extension that disables CORS: it makes the symptom vanish on your machine while the product stays broken for everyone else, and it makes your browser genuinely unsafe to browse with.

There is one more failure shape worth naming: mode: "no-cors" [EXPLAIN]. If you set it on a fetch, the request is sent, no preflight occurs, and you get back an opaque response — type opaque, status 0, no headers, unreadable body. It is not a workaround; it is the browser saying "I will let you fire and forget". It exists for cases like populating a cache with an image, or a beacon-style POST where you do not care about the answer. If you found it on Stack Overflow as a fix for a CORS error, it is not one — you have swapped an error for silence.

What you can do at this point: take a CORS error and reach the actual cause in a couple of minutes, without changing anything at random.

What's still broken: knowing what the headers should say is not the same as knowing where in your stack to say it — and in a real deployment there are three or four places that could each add them, sometimes all at once.

Node 11 — where CORS is actually configured

The limitation: the headers must be attached to every response the browser will check, including error responses and preflights, and in a typical deployment several layers are capable of doing that.

In Express, the cors package [USE]:

import cors from "cors";
app.use(cors({
  origin: ["https://app.example.com", "https://admin.example.com"],
  credentials: true,
  methods: ["GET", "POST", "PUT", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
  exposedHeaders: ["X-Total-Count"],
  maxAge: 86400,
}));

Two things to get right. Mount it before your routes and before your auth middleware, or the preflight — which carries no cookies — reaches auth first and gets a 401. And app.use(cors()) with no options means Access-Control-Allow-Origin: * with no credentials, which is fine for a public API and wrong for an authenticated one.

In Fastify, @fastify/cors [USE] — relevant to you directly, since qbank is Fastify:

await app.register(import("@fastify/cors"), {
  origin: (origin, cb) => {
    const allowed = ["https://app.example.com"];
    if (!origin || allowed.includes(origin)) return cb(null, true);
    cb(new Error("Not allowed"), false);
  },
  credentials: true,
});

The plugin hooks into onRequest and handles OPTIONS for you. Register it before routes. Note the !origin case: same-origin requests and non-browser clients send no Origin at all, and rejecting them breaks your own server-side calls.

Nginx [USE] can add them at the proxy layer with add_header, and there is a classic trap: add_header directives in a location block are replaced, not inherited, by any add_header in a nested block, and by default they only apply to 2xx and 3xx responses unless you append always. Preflights also need explicit handling:

location /api/ {
  if ($request_method = OPTIONS) {
    add_header Access-Control-Allow-Origin "https://app.example.com" always;
    add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;
    add_header Access-Control-Max-Age 86400 always;
    return 204;
  }
  add_header Access-Control-Allow-Origin "https://app.example.com" always;
  add_header Vary Origin always;
  proxy_pass http://backend;
}

Managed platforms each have their own layer: API Gateway on AWS has CORS configuration per route and your Lambda can add headers, Vercel and Netlify have headers config in their project files, and Cloudflare Workers can add them at the edge.

Which brings the failure this node exists to warn about: duplicate headers [EXPLAIN]. If both nginx and Express add Access-Control-Allow-Origin, the response contains it twice, and the browser rejects that outright with "contains multiple values ... but only one is allowed". Two correct configurations combine into a broken one. The rule is to decide on exactly one layer that owns CORS and remove it everywhere else, and when debugging, always check the raw response with curl -i rather than trusting either config file.

What you can do at this point: configure CORS correctly on Express, Fastify or a proxy, and diagnose the duplicate-header failure.

What's still broken: you can now make it work — and that is exactly the moment people start believing it is doing more for them than it is.

Node 12 — what CORS is not

The limitation: CORS looks like a security control and is filed mentally as one, so it gets trusted for jobs it cannot do.

CORS is not authorization. [EXPLAIN] It says which origins may read a response in a browser. It says nothing about which users may access a resource. If your endpoint returns another user's data to anyone who asks, no CORS configuration helps; curl will fetch it happily. Every endpoint still needs its own authentication and authorization. This is the single most important sentence in the topic.

CORS does not prevent CSRF. [EXPLAIN] Go back to Node 2. CSRF needs only the send, and simple requests are sent without any permission at all. An attacker's page can POST a form-encoded body to your endpoint right now, with the user's cookies, and never look at the response. Your CORS config was never consulted for the effect — only for the read that the attacker does not want. CSRF is defended by CSRF tokens, by SameSite cookies (Node 13), and by checking Origin server-side on state-changing requests. That last one is genuinely useful and is often confused with CORS: it is you, on the server, refusing to act — not the browser refusing to share.

There is one narrow sense in which CORS helps: a JSON-body request requires a preflight, and an attacker's page cannot make the browser skip it, so an API that only accepts application/json and rejects form encodings gets meaningful incidental protection. That is a real technique, but it is a consequence of the preflight rule, not a security feature you configured, and it fails the moment an endpoint also accepts form data.

CORS does not protect your server from anything. It is a client-side policy, enforced by browsers, for the benefit of users. Your rate limiting, input validation, and auth are what protect the server.

CORS does not apply to server-to-server traffic, to mobile apps, to curl, to your test suite, or to a scraper. Only to browsers, and within browsers only to JavaScript-initiated reads.

CORS is not SSRF protection. [AWARE] If your backend fetches a URL supplied by a user, CORS is nowhere in that picture — the backend is not a browser.

A permissive CORS policy is not automatically a vulnerability, and a restrictive one is not automatically security. Access-Control-Allow-Origin: * on a public, unauthenticated, non-secret endpoint is correct and intended. The same header on an endpoint returning user data with credentials is a serious hole. Severity comes from what the endpoint returns and whether credentials are involved, not from the header alone.

What you can do at this point: answer "does CORS protect against CSRF?" correctly and explain why, which is a standard interview filter.

What's still broken: the browser's other cross-origin mechanism — cookies — was still doing the 1994 thing of attaching itself to every request to a host regardless of who asked. Until that changed, CSRF stayed easy and every cross-origin session was a liability.

Node 13 — cookies grow their own defence: SameSite

The limitation: CORS governs reading. The ambient-credential problem from Node 0 is about sending. Fixing it requires a change to cookies themselves.

The SameSite cookie attribute [EXPLAIN] lets a server say when its cookie may ride along on a cross-site request. Three values.

  • Strict — never sent on any cross-site request, including a plain top-level link from another site. Maximally safe; the visible cost is that a user following a link from an email to your site arrives logged out, which is why it is usually reserved for the most sensitive cookies.
  • Lax — sent on top-level navigations that use a safe method (clicking a link that does a GET), but not on cross-site subresource requests, and not on cross-site POSTs. This kills the classic form-POST CSRF while keeping links working.
  • None — the old behaviour, sent on everything. It is only accepted together with Secure, so it requires HTTPS.

The pivotal change: Chrome 80, February 2020, made Lax the default when no SameSite is specified. Firefox and Safari followed with their own variations. So a cookie set today with no attribute behaves as Lax, and a very large amount of drive-by CSRF stopped working across the whole web.

The interaction with everything above is what you need to hold [EXPLAIN]. "Same-site" and "same-origin" are different comparisons. Same-origin is scheme plus host plus port. Same-site is looser: it compares the registrable domain — the domain one level below a public suffix, per the Public Suffix List — so app.example.com and api.example.com are different origins but the same site. That difference is the thing to remember, and it means that https://app.example.com calling https://api.example.com is cross-origin, so CORS applies, but same-site, so a Lax cookie is still sent — whereas https://app.vercel.app calling https://api.fly.dev is both, so you need CORS and SameSite=None; Secure.

That is the resolution of the confusion Node 7 flagged: two independent gates. CORS decides whether your script may read the response; SameSite decides whether the cookie is attached at all. Both must pass, and they fail with different symptoms — a CORS failure is an error in the console, a SameSite failure is a successful request that comes back 401.

Sitting behind all of this is the ongoing removal of third-party cookies [AWARE]: Safari's ITP blocked them from 2020, Firefox partitions them via Total Cookie Protection, and Chrome's plans have shifted repeatedly. The direction of travel is that cross-site cookies become unreliable regardless of your configuration, which pushes real applications toward the architectures in the next node, or toward tokens in headers rather than cookies.

What you can do at this point: diagnose the "CORS is perfect but I get 401" bug in one step, and explain the difference between same-origin and same-site.

What's still broken: at this point the honest observation is that a great deal of this complexity — preflights, credential rules, SameSite=None, cookie partitioning — exists only because the frontend and the API are on different origins. That is often a deployment accident rather than a requirement.

Node 14 — designing so the problem does not arise

The limitation: every mechanism so far is overhead you pay for a split that you chose, often without deciding to.

Same-origin deployment [USE] is the simplest answer: serve the frontend and the API from one origin, with the API under a path prefix like /api, routed by a reverse proxy or by the framework itself. Next.js route handlers, a Fastify server serving both static files and routes, nginx routing /api to the backend and everything else to static assets. There is then no cross-origin request, no CORS config, no preflight round trip, no SameSite=None, and session cookies can be Lax and HttpOnly with no special handling. A great many teams pay for CORS complexity permanently to avoid one afternoon of proxy configuration.

The development-time proxy [USE] applies the same idea while you work. Vite's server.proxy and Create React App's proxy field make the dev server forward /api to your backend, so the browser sees only localhost:5173. This is the correct fix for "CORS errors in local development", far better than opening up your API to * in dev and then discovering in staging that the real config was never written.

The backend-for-frontend [AWARE] generalises it: a small server owned by the frontend team, same-origin with the app, which talks to everything else server-side. Cross-origin problems vanish because the browser only ever talks to one origin — and it brings a genuine security benefit, since tokens for downstream services live on the server rather than in the browser.

A public API on its own origin with Access-Control-Allow-Origin: * is the opposite choice, and it is right when the consumers are arbitrary third parties and there are no credentials. Stripe, GitHub and every CDN do this deliberately.

The judgement [USE]: cross-origin is worth it when the API is genuinely consumed by many independent frontends, when the frontend is a static site on a CDN and the API is elsewhere, when teams and deploy cycles are separate, or when you are shipping a public API. It is not worth it when you have one frontend and one backend and they were split because that is how the tutorial did it.

What you can do at this point: decide, at design time, whether a project will have a CORS story at all, and justify it.

What's still broken: everything so far has been about fetch and XHR. But images, fonts, canvases, modules and media all cross origins constantly, and each of them has its own version of this rule that shows up as a completely different-looking bug.

Node 15 — CORS outside fetch

The limitation: the crossorigin attribute and its consequences appear in element-land, where the errors do not mention CORS at all.

The crossorigin attribute [USE] exists on img, script, link, video and audio. It changes the fetch from a no-CORS fetch into a CORS one, which means the browser will send Origin and will require Access-Control-Allow-Origin. Its values are anonymous (send no credentials — this is what a bare crossorigin means) and use-credentials (send cookies; the server must then answer with a specific origin and Allow-Credentials: true). Adding it makes the request stricter, so if the server does not cooperate, the resource that used to load now fails.

Canvas tainting [EXPLAIN] is the classic. Draw a cross-origin image into a canvas and the canvas becomes "tainted"; calling getImageData() or toDataURL() then throws a SecurityError. The reason is Node 2 again — an image may be displayed without permission, but reading its pixels would let a page read, say, a private photo from a service the user is logged into, or a CAPTCHA. Setting crossOrigin = "anonymous" and having the host send Access-Control-Allow-Origin un-taints it. This surfaces in chart libraries, image editors, screenshot tools and WebGL texture loading.

Fonts [USE] are the one case where CORS is required rather than optional: Firefox has always demanded Access-Control-Allow-Origin for cross-origin @font-face files, and it is why every font CDN sends the wildcard. A font that silently falls back to a system face, with a console message about CORS, is this.

ES modules [USE] — a script element with type="module" is always fetched in CORS mode, so a cross-origin module without the header simply does not load. A classic script src is not, which is why the JSONP loophole still exists for classic scripts.

Error detail in scripts [USE] — window.onerror reports "Script error." with no file, line, or message for errors thrown by a cross-origin script. That is a deliberate information restriction, and it is why error monitoring like Sentry needs crossorigin="anonymous" on the script tag plus Access-Control-Allow-Origin on the CDN. Without both, every production error report is a useless "Script error.".

Subresource Integrity [AWARE] — an integrity attribute on a cross-origin resource requires CORS, because the browser must be allowed to read the bytes in order to hash them. And media and range requests [AWARE] — Range is on the safelist with restrictions, which is why video seeking against a cross-origin source has its own class of failures.

What you can do at this point: recognise CORS in disguise — a tainted canvas, an invisible font, a "Script error." — and fix it at the element and the server together.

What's still broken: everything to this point is about one page reading one resource. Then in January 2018 a class of CPU vulnerability made it clear that merely having foreign data in the same process is dangerous, which the origin model had no answer for.

Node 16 — the newer cross-origin policies, and the transports that opt out

The limitation: Spectre showed that a page could read memory it was never handed, so keeping an attacker's data out of your JavaScript was no longer enough — it had to be kept out of your process.

Spectre, disclosed January 2018, allowed a program to infer the contents of memory it had no right to read, by timing. In a browser, a page and a cross-origin resource in the same process meant the page could potentially read that resource anyway, whatever the SOP said. Browsers responded by disabling high-resolution timers and SharedArrayBuffer, and then by building a way for a page to declare itself isolated so those features could be returned. Three headers came out of that, and you need to recognise them, not deploy them from memory. [AWARE]

Cross-Origin-Resource-Policy is set by a resource, saying who may embed it at all: same-origin, same-site, or cross-origin. Unlike CORS it applies to no-CORS loads too, so it can stop your image from being hotlinked into another site's process.

Cross-Origin-Opener-Policy with the value same-origin severs the window.opener relationship with cross-origin documents, so a page you open, or that opened you, cannot get a handle on your window.

Cross-Origin-Embedder-Policy with the value require-corp says this document will only load cross-origin subresources that explicitly permit it. Setting the opener and embedder policies together makes a document cross-origin isolated, which re-enables SharedArrayBuffer and high-resolution performance.now(). This is the requirement people hit when running FFmpeg.wasm or SQLite-wasm in the browser, and it is usually the first time a frontend developer meets these headers.

Private Network Access [AWARE] is an evolving Chrome mechanism — the naming has shifted toward "Local Network Access" — that adds a preflight when a public website requests a resource on a private IP range or localhost, with Access-Control-Request-Private-Network and Access-Control-Allow-Private-Network. It exists because a public page attacking a router or a dev server on the user's own machine is a real attack class. If a local device integration suddenly stops working after a Chrome update, this is a candidate.

Finally, the transports that sit outside all of this, because they are asked about and the answer is counterintuitive.

WebSockets [EXPLAIN] are not subject to CORS. The handshake is an HTTP upgrade, the browser does send an Origin header, and there the browser's involvement ends — there is no allow header for WebSockets and no preflight. The consequence is important: the server must check Origin itself and reject unknown ones, otherwise any website on the internet can open an authenticated socket to your server using the user's cookies. This is called cross-site WebSocket hijacking, and it is a genuine and frequently-found vulnerability precisely because people assume CORS covers it.

Server-Sent Events [USE] use EventSource, which is a normal HTTP request and is subject to CORS in the ordinary way — with the quirk that EventSource has no way to set headers, so you cannot send an Authorization header on it, and cross-origin authentication has to go through cookies (with withCredentials: true) or a query parameter. Relevant to you directly, since SSE is how LLM responses stream.

navigator.sendBeacon [AWARE] sends in no-cors mode where it can, which is why analytics beacons work where a fetch would have been blocked.

What you can do at this point: place CORS correctly among the browser's other cross-origin controls, and explain why a WebSocket server needs its own origin check.

What's still broken: nothing in the chain — this is the current edge of the mechanism. What remains is applying it, which is the project.

Where the chain gets misread

  • "CORS blocks the request." (Node 2, Node 10.) Usually it does not. For simple requests the request is sent, the server processes it, and the response is withheld from your script. Only a failed preflight actually prevents the real request.
  • "CORS protects my server." (Node 12.) It protects a user's data in a user's browser. Your server is exactly as exposed as it was; curl ignores all of it.
  • "CORS prevents CSRF." (Node 12.) It does not. CSRF needs only the send, and simple requests are sent without permission. SameSite, CSRF tokens, and server-side Origin checks are the defences.
  • "Access-Control-Allow-Origin: * is the safe default." (Node 7.) It is correct for public unauthenticated resources and forbidden with credentials. On an authenticated API it is either blocked by the browser or, if you reflect instead, a real vulnerability.
  • "Subdomains are the same origin." (Node 1, Node 13.) Different origins — but the same site, which is why a Lax cookie still crosses between them while CORS still applies.
  • "I fixed it by setting mode: 'no-cors'." (Node 10.) You did not. You got an opaque response with status 0 and no readable body. You replaced an error with silence.
  • "The Origin header proves who is calling." (Node 9.) Only within a browser, where the SOP applies. Any other client sets it to anything. Never authorise on it — though checking it server-side to refuse state changes is still useful defence in depth.
  • "Authorization is a credential, so I need Allow-Credentials." (Node 7.) No — a header you set in JavaScript is governed by Access-Control-Allow-Headers. Allow-Credentials is about cookies, HTTP auth and client certs that the browser attaches itself.
  • "Access-Control-Allow-Headers: * covers everything." (Node 6.) It does not cover Authorization, which must be named explicitly, and it means the literal asterisk on credentialed requests.
  • "My CORS is configured but the header is missing on errors." (Node 11.) Very common: a 500 or a 404 produced before or outside your CORS middleware carries no CORS headers, so a server bug presents as a CORS error. Check the status in the network tab first.
  • "The preflight sends my cookies and auth." (Node 6.) It does not. It is anonymous by design, which is why auth middleware placed before CORS middleware returns 401 on OPTIONS and breaks everything.
  • "It works in Postman, so the server is fine." (Node 4.) Postman has no origin and no same-origin policy. The test proves nothing about the browser path.
  • "CORS applies to WebSockets." (Node 16.) It does not. The server must check Origin itself or accept cross-site socket hijacking.
  • "Access-Control-Max-Age: 31536000 caches the preflight for a year." (Node 6.) Chrome caps at two hours, Firefox at twenty-four.

The chain in one paragraph

Because cookies are attached by the browser to every request to a host regardless of which page caused it, any page that could read a response from another site could read it as you — so browsers adopted the same-origin policy, a blunt comparison of scheme, host and port, denying cross-origin reads while grandfathering in cross-origin sends, since images, scripts and forms had always crossed freely; that asymmetry is why CSRF exists and why, when XMLHttpRequest arrived, deliberate cross-origin cooperation had no expression at all and was faked for a decade with JSONP, proxies and Flash policy files; CORS standardised the consent instead, with the browser sending an unforgeable Origin and the server answering Access-Control-Allow-Origin, but because a request outside the old safelist — anything but GET, HEAD or POST, any author-set header beyond a handful, any body type a form could not produce, and therefore every JSON API call — could have effects the pre-CORS web could not, permission for those has to be obtained first, via an anonymous OPTIONS preflight carrying the requested method and headers and answered with Allow-Methods, Allow-Headers and a capped Max-Age; cookies still do not cross unless the client asks with credentials: "include" and the server answers Allow-Credentials: true, which bans the wildcard and forces per-origin reflection, which in turn forces Vary: Origin so caches do not serve one origin's grant to another and forces exact allowlist matching so reflection does not become "allow everybody"; response headers stay invisible beyond seven safelisted ones until Expose-Headers names them; failures are deliberately opaque to script — a bare TypeError — so debugging lives in the console, the OPTIONS row, and curl -i with a forged Origin; the headers are attached by exactly one layer or they duplicate and break; and none of it is authorization, none of it stops CSRF, none of it constrains non-browser clients, which is why cookies grew SameSite (default Lax since Chrome 80 in 2020) as the send-side defence, why the cheapest architecture is often to have no cross-origin split at all, and why the same consent idea reappears wearing other clothes in canvas tainting, font loading, "Script error.", the post-Spectre isolation headers, and the WebSocket handshake, where there is no CORS at all and the server must check Origin itself.
