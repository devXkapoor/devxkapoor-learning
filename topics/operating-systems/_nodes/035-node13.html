Node 13 — demand paging, the page cache, swap, and the OOM killer

The limitation: physical frames are finite, and nothing has said what happens when they run out.

Nothing is loaded until it is touched

Start with what the page fault made possible. When a program is executed, the kernel does not read it into memory. It sets up page table entries marked not-present, recording where on disk each page lives, and jumps to the entry point. The first instruction immediately faults; the kernel reads that one page; execution proceeds. Pages arrive as they are needed, and pages of a hundred-megabyte binary that are never executed are never read.

That is demand paging, and its consequences are worth stating: a program starts in milliseconds regardless of size, memory holds only what is actually used, and a process can have far more mapped than the machine has. It is also why the very first request to a freshly started server is slower than the ones after it — the code paths it exercises are being faulted in — which is a real and measurable effect in serverless cold starts, in JVM and .NET warm-up, and in the first request to a newly rolled-out Kubernetes pod.

The page cache: free memory is wasted memory

Once pages of a file are in memory, throwing them away when the process closes the file would be foolish. So the kernel keeps them, in the page cache, and uses all otherwise-unused memory for it.

This is the single most misread thing on a Linux dashboard. Every ordinary file read and write goes through the page cache. [EXPLAIN] A read checks the cache first and only touches the disk on a miss. A write copies your bytes into a cache page, marks it dirty, and returns immediately — no disk has moved. Kernel threads write dirty pages back later, governed by vm.dirty_ratio, vm.dirty_background_ratio and vm.dirty_expire_centisecs. Node 23 covers what that means for durability, which is a great deal.

So on a healthy server, free -m shows very little "free" memory and a large "buff/cache" figure, and that is correct and desirable. Free memory is doing nothing; cached memory is saving disk reads and is instantly reclaimable. The column to read is available, which is free plus reclaimable cache — the honest answer to "how much could a new process get". Anyone reporting a memory problem because free is small is reading the wrong column, and it is worth being able to say so precisely.

Choosing what to evict

When frames are needed and none are free, something must go. The theoretically optimal policy is to evict the page that will be used furthest in the future, which requires knowing the future, so it exists only as a benchmark. The practical approximation is least recently used, and true LRU is also too expensive — it would mean updating a timestamp on every single memory access.

So hardware and kernel cooperate cheaply. The processor sets the accessed bit in a page table entry on any access (Node 10). The kernel periodically clears those bits and, on the next pass, sees which were set again. That is the clock or second-chance algorithm. Linux refines it into two lists, active and inactive: a page must be referenced while on the inactive list to be promoted to active, which stops a single large sequential file read from evicting the entire useful working set — a failure mode with the excellent name cache pollution, and the reason a nightly backup used to make a database slow for an hour afterwards.

The concept underneath is Peter Denning's working set (1968): the set of pages a process has touched in the recent past, which is a good predictor of what it will touch next. If the sum of all processes' working sets exceeds physical memory, the machine enters thrashing — every process constantly faults in a page by evicting a page another process is about to need, and the machine spends all its time moving pages and none doing work. Thrashing does not degrade gracefully; it collapses. A thrashing machine shows near-zero user CPU, huge major faults, and enormous disk activity, and it is often easier to reboot than to log into.

Swap: extending memory onto disk

File-backed pages can always be evicted, because the file is their home. Anonymous pages — heap, stack, anonymous mmap — have nowhere to go unless a dedicated area exists. That is swap. With it, total memory is RAM plus swap; without it, anonymous memory can never be evicted at all.

vm.swappiness (0–200, default 60) biases the kernel between reclaiming file pages and swapping anonymous ones. Low values favour keeping anonymous memory resident. Note that swappiness=0 does not disable swap; it makes the kernel avoid it until it is nearly desperate.

The reason swap has a bad reputation is latency. A page from RAM is 80 nanoseconds; from an SSD, around 100 microseconds — a thousand times slower; from a spinning disk, ten thousand times. A process whose active data is swapped out is not slow, it is unusable. Hence Kubernetes historically refused to run at all with swap enabled: swap makes memory limits unenforceable and makes latency unpredictable, and the scheduler's model assumes memory is memory. Support for swap on nodes has been reintroduced gradually (beta from 1.28, with further work through 1.30+), but the default position for a latency-sensitive service remains: no swap, and size the memory correctly.

Overcommit, and the killer

Linux, by default, grants more address space than it has memory to back. It has to, in practice: fork plus copy-on-write (Node 14) means a doubling of address space that will almost never be realised, programs routinely reserve large sparse regions they never touch, and V8 is one of them. vm.overcommit_memory controls the policy — 0 is a heuristic (the default), 1 always says yes, 2 refuses beyond a computed limit.

The consequence is that the machine can promise more than it can deliver, and the debt comes due at a page fault: a process touches a page it was legitimately given, and there is no frame. There is nothing sensible to return — the faulting instruction cannot be failed, because mov has no error path.

So the kernel picks a process and kills it. The OOM killer scores every process, roughly by memory footprint, adjusted by oom_score_adj (−1000 to +1000, where −1000 makes a process exempt), and sends the highest scorer SIGKILL. Not SIGTERM. SIGKILL cannot be caught, blocked, or handled (Node 30), so the process gets no chance to flush anything, close anything, finish an in-flight request, or log a word about it. It simply ceases.

The evidence is in the kernel log — dmesg -T | grep -i "killed process", or journalctl -k — and it is the first place to look when a process vanishes with no application log entry explaining why. [USE]

Where this is in your stack

Exit code 137, decoded. A process killed by a signal reports, by shell convention, 128 + signal number. SIGKILL is 9. So 137 means killed by SIGKILL, and in a container that almost always means the cgroup's memory limit was hit and the cgroup OOM killer fired. (143 is 128 + 15, SIGTERM — a normal shutdown. 139 is 128 + 11, SIGSEGV — Node 3.) Kubernetes reports it as OOMKilled in the container's lastState.terminated.reason. [EXPLAIN] You can derive all of these rather than memorising them, which is exactly the point of this document.

The cgroup memory limit is a separate, per-container OOM domain, which is why a container is killed on a machine with plenty of free memory: it exhausted its budget, not the machine's. Node 27 covers the mechanism; the operational points are that memory.max is a hard wall enforced by killing, while memory.high is a soft limit that throttles reclaim instead — meaning a container over memory.high gets slow rather than dead, which is often the behaviour you actually want, and which Kubernetes does not expose directly.

A container's page cache counts against its memory limit, and this kills containers that have no memory leak at all. [EXPLAIN] This one is genuinely non-obvious and causes real incidents. If your containerised service writes heavily to a file — logs, a temp file, an upload buffer, a SQLite database — those dirty and clean page-cache pages are charged to the container's cgroup. The kernel will reclaim cache before killing, so it usually works out, but under memory pressure combined with heavy write throughput a container can be OOM-killed while its actual anonymous usage is far below the limit. Symptoms: OOMKilled with a flat heap graph and a healthy process.memoryUsage(). Remedies: log to stdout and let the runtime handle it rather than writing files, put genuinely large scratch data on a volume mounted with different semantics, and read memory.stat in the container to see the split between anon and file.

Why a Node process gets no graceful shutdown on OOM. Because it is SIGKILL. Your process.on('SIGTERM') handler, your connection draining, your "finish in-flight requests" logic — none of it runs. This is the strongest argument for sizing memory generously and for setting a heap cap (Node 12) so that V8 hits its limit first: a V8 heap-limit failure throws a JavaScript FATAL ERROR: Reached heap limit with a stack trace and can trigger a heap snapshot via --heapsnapshot-near-heap-limit, which is diagnosable. A kernel OOM kill produces one line in the host's kernel log and nothing else. Choosing which limit you hit first is a real design decision.

Postgres is built on the page cache and its configuration only makes sense in that light. Postgres deliberately keeps shared_buffers modest — the conventional 25% of RAM — rather than claiming everything, because it expects the operating system's page cache to hold the rest. A page can therefore exist twice, once in shared buffers and once in the page cache: double buffering, wasteful in principle and accepted in practice because the kernel's cache is good and its readahead is good. effective_cache_size is not an allocation at all; it is a hint to the query planner about how much total caching it can assume, and setting it too low makes the planner avoid index scans it should be choosing. And this is why running Postgres in a container with a tight memory limit performs badly in a way that adding shared_buffers does not fix: you have taken away the page cache it was designed to rely on.

Cold starts are demand paging. A serverless function's first invocation faults in the runtime, the dependency tree, and the JIT-compiled code, page by page from storage. That is a large part of why a cold start is hundreds of milliseconds while a warm one is single digits, why bundle size affects cold start more than it affects steady-state performance, and why techniques that pre-warm — snapshots, AWS Lambda SnapStart, V8 startup snapshots, Node's --snapshot-blob — attack it by having the pages already laid out rather than by making the code faster.

What you can do at this point: read free -m correctly and explain why low free memory is healthy, explain demand paging and cold starts, describe eviction and thrashing, derive exit codes 137/143/139 from signal numbers, explain why an OOM kill gives no graceful shutdown, explain why a container with no leak can still be OOMKilled by its own log writes, and explain why Postgres wants the page cache.
