Node 35 — execve, and how a command becomes a process tree

The limitation: a complete, loadable executable exists on disk and nothing has said what running it does.

What execve does

execve(path, argv, envp) replaces the program running in the current process. It does not create a process. The PID stays the same, the parent stays the same, open file descriptors stay open, credentials stay as they are — but the address space is destroyed and rebuilt.

In order:

  1. Permission check — is the file executable by this process? Is it setuid, and if so whose identity does the new program take (Node 25)?
  2. Read the header. If it starts with #!, this is a script: read the interpreter path from that first line, and re-run execve on the interpreter with the script's path as an argument. This is the shebang, and it is handled by the kernel rather than the shell. Two details bite: the interpreter path must be absolute, which is why #!/usr/bin/env node is used — env is at a known location and finds node on PATH; and only one argument is portably allowed after the interpreter.
  3. Tear down the old address space. Every mapping from Node 11 is discarded. This is why fork-then-exec copies essentially nothing (Node 14) — the copy-on-write pages are dropped before any are written.
  4. Map the new program's segments from its ELF program headers (Node 33), demand-paged so almost nothing is read yet (Node 13).
  5. Build a new stack containing argv, envp, and the auxiliary vector — kernel-supplied values like the page size, the vDSO address (Node 8), and the ASLR seed.
  6. Close descriptors marked close-on-exec (Node 22); everything else survives, which is what makes redirection work.
  7. Reset signal handlers to default — the handler code no longer exists. The signal mask, however, is inherited, which is a genuine trap: a process that blocked a signal and then execs passes that block to the new program, and there are real bugs where a service never receives SIGTERM because something up the chain blocked it.
  8. Jump to the interpreter named in PT_INTERP — the dynamic linker (Node 34) — which maps the shared libraries, performs relocations, runs initialisers, and finally jumps to the program's entry point.
  9. The C runtime sets up its own state and calls main.

execve only returns on failure. If it succeeds there is nothing to return to, because the code that called it no longer exists.

The environment

envp is a plain array of KEY=VALUE strings copied onto the new stack. That is all an environment variable is: per-process memory, inherited by copy at exec, with no kernel involvement after that. [EXPLAIN] Everything about their behaviour follows:

  • A child cannot modify its parent's environment. There is no channel to do so.
  • Changing a variable after a process starts does not affect it — hence restarting a service after editing its configuration.
  • process.env.FOO = 'x' in Node modifies your copy and affects only children spawned afterwards.
  • They are visible. /proc/<pid>/environ exposes them to anyone who can read that file, and ps eww shows them. This is why secrets in environment variables are a compromise rather than a best practice — they leak into crash dumps, error reporting payloads, subprocess environments, and CI logs. The 12-factor recommendation is about configuration; for secrets, mounted files with restrictive permissions (Kubernetes secret volumes, and the reason _FILE-suffixed variables are a common convention) are meaningfully better.
  • PATH is searched by the shell or by execvp, not by execve — the bare syscall requires a full path. This is why child_process.spawn('node') can fail with ENOENT in an environment with a minimal PATH, and why ENOENT from spawn means "the program was not found", not "your file argument was not found", which misleads people every time.

What the shell does with one command line

Typing ls -l | grep .js > out.txt produces, in order: tokenising and expansion (globs, variables, command substitution, all done by the shell — which is why rm *.txt is expanded before rm ever sees it, and why a filename containing a space breaks unquoted scripts); creating a pipe; forking twice; wiring descriptors with dup2 in each child (Node 22); execve in each; and waitpid in the parent to collect statuses.

Also worth knowing: a shell puts each pipeline in its own process group, and the terminal has a foreground group. Ctrl-C sends SIGINT to every process in the foreground group, which is why it interrupts a whole pipeline. Backgrounding with & means the group is not the foreground one, and a background process that reads from the terminal receives SIGTTIN and stops.

Where this is in your stack

npm start is a process tree, and knowing its shape explains a family of bugs. A typical chain is: your shell → npm (a Node process) → sh -c "node server.js" → node server.js. Four processes, three fork/exec pairs. The consequences:

  • Signals do not reach the bottom. SIGTERM to npm is not automatically forwarded through the shell to your server. In a container this is Node 30's PID 1 problem compounded — which is why the correct production entrypoint is CMD ["node", "server.js"], not CMD ["npm", "start"]. Running npm in production containers costs you signal handling, a process, memory, and startup time, for no benefit.
  • Exit codes are relayed, sometimes badly, and npm adds its own error output on a non-zero exit which obscures the real one.
  • node_modules/.bin is prepended to PATH by npm before running a script — which is the entire mechanism by which "test": "jest" finds jest, and it is PATH plus symbolic links (Node 21) plus a shebang, nothing more.

exec in a shell script is this system call exposed. An entrypoint script that ends with exec node server.js replaces the shell with Node, so Node becomes PID 1 and receives signals directly. Without exec, the shell stays as PID 1 with Node as its child, and shutdown breaks. This single word is the difference between a container that shuts down gracefully and one that does not, and it is the standard fix for entrypoint scripts that need to do setup before starting the app.

spawn versus exec in Node. child_process.spawn is fork+execve directly, streaming output. child_process.exec runs the command through a shell and buffers the output — so it supports pipes and globs, and it is a command injection vulnerability if any part of the string comes from user input, because the shell will interpret ;, &&, backticks and $(). Use spawn with an argument array, where each argument is passed as a separate argv entry and no shell is involved. Also recall Node 22: exec's maxBuffer deadlock on chatty children.

The setuid check in step 1 explains a Docker security control. allowPrivilegeEscalation: false in a Kubernetes security context sets the no_new_privs bit, which makes the kernel ignore setuid bits at execve. So even if a setuid-root binary exists in the image, executing it grants nothing. It is a one-line, near-zero-cost mitigation for a whole class of container escape, and it operates precisely at step 1 of this node.
